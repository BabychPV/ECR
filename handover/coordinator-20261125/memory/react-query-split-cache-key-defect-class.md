2026-09-23: на `/admin/notifications` знайшов живою перевіркою (не з коду) —
після створення каналу в `ChannelsPanel` таблиця правил `RulesMatrixPanel` і
далі показувала «каналів немає», доки не F5. Корінь: обидва компоненти
незалежно викликають `listNotificationChannels()`, але `ChannelsPanel` тримав
ключ `['notification-channels']`, а `RulesMatrixPanel` — свій локальний
`['notifications', 'channels']`. Мутація каналу інвалідувала лише перший.
Виправлено ([[dev-integration-direct-push-not-pr]] коміт `0a4b9100`): єдина
експортована константа ключа в `api.ts`, обидва компоненти імпортують її.

**Why:** у цій кодовій базі кожен "самодостатній" панельний компонент навмисно
робить власні запити (документована причина в `RulesMatrixPanel.tsx`: пропів
немає, щоб не знати про порядок двох адрес сервера). Цей же патерн — джерело
дефекту: самодостатність не гарантує узгодженого ключа кешу, якщо його не
винести в спільне місце одразу.

**How to apply:**
- Під час рев'ю/огляду екрана з кількома панелями, що читають одні дані
  (типовий приклад — довідник/каталог, спільний для 2+ віджетів одного
  екрана) — грепати `queryKey` для всіх панелей екрана й звіряти дослівно,
  а не покладатися на те, що дані "однакові на вигляд".
- Жива перевірка (створити сутність в одній панелі → подивитись, чи бачить
  її інша БЕЗ перезавантаження) дешевша й надійніша за пошук у коді: саме
  так це і знайшлося.
- Коли додаєш ключ кешу для даних, які вже читає інший компонент —
  спершу перевірити, чи нема вже експортованої константи (`grep
  queryKey.*<endpoint-name>` по `features/`), а не заводити свою.

Пов'язане: [[walk-ndjson-append-only]] (інший приклад «стан виглядає застарілим,
а причина в кеші/логуванні, не в даних»).
