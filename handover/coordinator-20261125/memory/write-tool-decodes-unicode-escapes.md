Аргументи інструментів `Edit` і `Write` проходять через JSON-декодування.
Послідовність `\uXXXX`, написана в `new_string`/`content`, потрапляє у файл
**декодованим символом**, а не шістьма літерами.

Для `\u0000` це означає сирий байт 0x00 у файлі. 2026-09-18 це вкусило
**тричі поспіль в одній задачі**, де правка саме й полягала в тому, щоб
прибрати NUL із джерела:

1. коментар, що пояснює escape, сам отримав сирий NUL;
2. повторна спроба через `Write` — те саме;
3. текст коміт-меседжа — git відмовив: `a NUL byte in commit log message
   not allowed`, exit 128.

**Why:** помилка не видно очима — у виводі `Read` і в diff сирий NUL
малюється як пробіл або порожнеча. Тобто правка «виглядає правильною» і
мовчки вносить рівно той дефект, який мала прибрати.

**How to apply:**
- писати `\\uXXXX`, коли у файлі потрібна сама послідовність `\uXXXX`;
- після будь-якої правки, що торкається escape-послідовностей, робити
  побайтну перевірку, а не покладатися на вигляд:
  `$b=[IO.File]::ReadAllBytes($p); @($b | ? { $_ -eq 0 }).Count`;
- для точкових правок недрукованих байтів надійніше
  `ReadAllBytes`/`WriteAllBytes` зі скрипта, ніж текстові інструменти —
  заодно зберігає кодування й закінчення рядків (див.
  [[powershell-corrupts-cyrillic]]).

Суміжне: чому сирий NUL у джерелі взагалі шкідливий — ripgrep вважає такий
файл двійковим і мовчки пропускає при пошуку по каталогу
([[ripgrep-skips-files-with-nul]]).
