2026-09-23: за одну сесію відкрив і змержив ЧОТИРИ окремі PR (#459–#462) із
фіче-гілок у `dev/integration`, кожен через `gh pr merge --squash
--delete-branch`. Це суперечить чинному правилу з `CLAUDE.md`, доданому ще
komітом `8417916b` (2026-09-20, тобто ДО початку цієї роботи, не нова
зміна): «перестань робити багато пулреквестів... створили один [PR у main] і
тільки туди комітимо [у dev/integration]». Дослівно: власна гілка від
свіжого `origin/dev/integration` в ОКРЕМОМУ worktree → `git fetch` →
`git rebase origin/dev/integration` → `git push origin HEAD:dev/integration`
— БЕЗ PR узагалі на цьому кроці. PR існує рівно ОДИН: `dev/integration` →
`main` (зараз #458), мержиться раз на тиждень і лише по семи зелених.

**Why:** «пачка раз на день» (2026-09-17) і «одна підзадача = один PR»
(розділ 4) — старіші правила, явно скасовані записом 2026-09-20. Я
використовував старіший, знайоміший мені патерн (subtask-PR → gh pr merge),
не звірившись із найновішим записом у файлі перед стартом хвилі задач.
Функціонально шкоди не було (код рівно той самий приземлився в
`dev/integration`, усі перевірки пройшли), але процес — не той, і зайві PR
засмічують список та суперечать прямому рішенню людини.

**How to apply:** перед тим, як писати промпт сабагенту про те, як здавати
роботу («відкрий PR у dev/integration»), — перечитати САМЕ ЦЕЙ файл
(`H:\ECR\CLAUDE.md`) целиком, шукаючи НАЙНОВІШИЙ запис про PR/мерж
(дивитися на дату в заголовку `### ✎ YYYY-MM-DD`, не на порядок у файлі —
розділи не завжди хронологічні). Станом на 2026-09-23 чинний процес:
worktree → rebase на `origin/dev/integration` → прямий
`git push origin HEAD:dev/integration`, без PR. Єдиний PR — той, що вже existує
для `dev/integration → main` (не створювати новий).
