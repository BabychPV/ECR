2026-09-22: запустив агента писати `docs/user/user-guide.md` (worktree
`b2-userdocs`). Паралельно запустив агента чистити застряглі worktree.
Чистка визначила `b2-userdocs` як «влитий» (гілка — предок
`origin/dev/integration`) і видалила worktree + гілку. Насправді писар
посібника ще не зробив ЖОДНОГО коміту — тому його HEAD тривіально
«є предком» будь-якої пізнішої вершини (він просто стоїть на своїй базі,
код пішов далі повз нього). Перевірка «чи недавно змінювались файли»
цього не зловила (агент саме розгортав власні дослідницькі сабагенти,
локальних записів файлів не було довгий проміжок). Результат: робота
писаря вбита насправді, без відновлення (git reflog/fsck — чисто, він
нічого не встиг закомітити).

**Why:** `git merge-base --is-ancestor <tip> <target>` каже правду лише
про гілки, що РУХАЛИСЬ. Для гілки без власних комітів (щойно
відгалуджена, ще не писала) вона завжди істинна й нічого не доводить.

**How to apply:**
- У промптах для чистки worktree: «влито» означає (1) `is-ancestor` **І**
  (2) `git log <base>..<tip> --oneline` НЕ порожній (гілка має власні
  коміти) — обидві умови разом, не одна.
- Або простіше й надійніше: перед чисткою запитати список ЖИВИХ
  дочірніх агентів (worktree, які я сам ще не отримав фінальний звіт по
  них) і виключити їх зі сканування взагалі — не покладатися лише на
  git-евристики для worktree, де точно триває активна робота.
- Коли субагент довго мовчить (розвідка/дослідження без локальних
  записів) — це нормально, не привід вважати worktree «покинутим».
- Уперше вдарило по writer-агенту без коду (документація) саме тому, що
  такі задачі довше сидять у фазі «читаю й формулюю» без жодного git-сліду.
