2026-09-18 користувач задав постійний регламент і просив виконувати **завжди,
без нагадувань**. Повний текст — у `CLAUDE.md`, розділ «Правила розробки».

**Why:** до цього декомпозиція була нерегулярною, сабагенти діставали розмиті
межі (звідси перетини файлів і конфлікти), а звіти не мали сталої форми.

**How to apply — найкоротше:**
- **Пріоритет при конфлікті правил:** коректність і тести → відсутність
  merge-конфліктів → швидкість. Ніколи навпаки.
- **План до коду:** `git fetch && git status`, потім таблиця
  `# | підзадача | файли для запису | залежить від | DoD | режим`. Паралелити
  дозволено ЛИШЕ якщо колонка «файли для запису» не перетинається.
- **Порядок:** foundation послідовно (інтерфейси, типи, схема БД, міграції,
  конфіги, CI, спільні фікстури) → реалізації паралельно (≤ 3–4 гілки) →
  інтеграція послідовно. Під час паралельної фази спільні ресурси read-only.
- **Сабагент** дістає явний список дозволених файлів; стоп-умова — потрібен
  файл поза списком. «Done» без прогону тестів не приймається.
- **PR:** ≤ 300–400 рядків diff, гілка живе ≤ 1 дня, щонайменше один PR на
  день. Рефакторинг — окремим PR, ніколи разом із функціональними змінами.
- **Звіт:** `Done` / `Verified` / `Next steps` з мітками `[parallel]`,
  `[blocks]`, `[debt]`, `[question]`.
- **Задача < ~50 рядків і один файл — НЕ декомпозувати.**

⚠ Конфлікт, знятий судженням: правило каже «перед PR `git rebase main`», а
`CLAUDE.md` забороняє `git push --force`. Ребейз **до першого пушу**; після
пушу — `git merge main`. Інакше довелося б порушити одну з двох заборон.
