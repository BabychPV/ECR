Три правила для всіх сесій (координатор, ретро 11.11):
1. Новий екран/ендпоінт читання: у плані — очікуваний обсяг на doc 11 / Land (рядки, КБ), виміряний на синтетичному великому документі ДО повного CI. Понад 500 КБ або 2 000 рядків → ліниво/сторінками з першого коміту.
2. Кожен бриф сабагента містить: «never mutate access/security filters, even temporarily; prove access with a differential Deny test that fails on the real path».
3. Перед новим ID у WORK-QUEUE — `git log --all --no-textconv -S '<ID>'` по всіх лініях, не лише main. ⚠ Без `--no-textconv` тут git падає («cannot spawn astextplain», exit 128) і порожній вивід ХИБНО виглядає як «вільний» — завжди контроль на відомому ID.
4. (✎ 12.11, координатор) **Лінії з кодом НЕ правлять `docs/build/WORK-QUEUE.md`** — запропоновані рядки йдуть у звіт/лист, а координатор зводить їх одним docs-комітом на нарізку RC. Причина: AN-164 @2c117692a конфліктував із main лише в WORK-QUEUE → перенарізка `-rb`.
5. (✎ 13.11, ретро 356) Перед КОЖНИМ пушем у `lane/integ-*`: `git fetch; git merge-tree --write-tree origin/main HEAD`, пуш лише при коді виходу 0.
6. (✎ 13.11, ретро 359) Повний `ci.yml` ніколи не ганяти заради мутаційного доказу: доказ — локально на ОДНОМУ тестовому класі або `workflow_dispatch` лише зачепленого тест-проєкту (B71 стояв у черзі раннерів 1,5 год).
7. (✎ 13.11, ретро 360) У довгих ходах перечитувати верх `.sync-local\coord\AN.md` між кроками, а не лише на старті ходу: листи зайнятій сесії стоять у черзі.
8. (✎ 13.11, ретро 365) Будь-який час чи оцінку «до HH:MM» брати лише з `(Get-Date).ToUniversalTime()` у тому самому кроці (двоє з нас 13.11 з'їхали на +2 год).
9. (✎ 13.11, ретро 366) Перед КОЖНИМ новим пунктом перечитати верх `coord\AN.md`; рядок «ORDER CHANGE» перекриває мою чергу.
10. (✎ 13.11) QUIET від координатора/PE/AU: мої агенти чекають явного «quiet over», а не «N хвилин»; цикли N/20 обриваються на межі ітерації. Агент B86, що продовжив прогін після «5 хв», зіпсував замір PT01 у PE (CPU 100 %).
11. (✎ 13.11, ретро 374) Зміна, що додає FK, таблицю чи міграцію: перед пушем локально ВЕСЬ простір імен Persistence (≤2 важких), цільових тестів мало.
12. (✎ 13.11, ретро 375) Нові/змінені тести не читають «останні/глобальні» рядки спільної тестової БД чи стан модуля від інших тестів; перф-твердження (reads, мс) — лише на власних даних. Приклади: B86, B92, B94.
13. (✎ 13.11, ретро 381) READY зміни на шляху доступу (AccessDecisionService, DocumentReadScope, CanReadColumn, SheetEditGate, owner-period) містить рядок «Deny mutation: <що вимкнено> → red N/M»; без нього AU повертає READY до рев'ю.
14. (✎ 13.11, ретро 382) Тести, що залежать від стану періоду, — лише на 2099xx або відносно годинника, ніколи на близьких реальних періодах (бомба 13.11 19:00Z: 202609 закрився за календарем, api-1 червоний у всіх lane). Прочісування + сторож — B101 (AN).
15. (✎ 14.11, правило 394) Тест, що створює дані, які вмикають глобальну поведінку (реєстр макетів, прапорці, кеш налаштувань), прибирає їх у finally або ізолює споживача (порожній реєстр / власний scope). Тести з підрахунком запитів чи команд завжди фіксують реєстри, від яких залежать. Застосовувати лише до коду, який уже чіпаєш. Випадок у PE: річна версія шаблону лишилась у спільній БД, і підрахунок дав 33 замість 32.
16. (✎ 16.11, правило 401) Перед READY автор сам мутує КОЖНУ нову гілку поведінки у своєму обсязі (кожен сторож, шлях помилки, оновлення кешу, фільтр) і переконується, що тест червоніє; покриття лише e2e — діра. Фільтри доступу мутує AU, автор дає Deny-рядки. Привід: у B139 автор дав 2 мутації, AU знайшов ще 4 вцілілі — другий CI і ~1,5 год.
17. (✎ 16.11, правило 405) Раннери GitHub — вузьке місце (черги по 50 хв): lane пушити ОДНИМ фінальним SHA; якщо буде ще коміт — дочекатися його або в ту саму хвилину самому скасувати CI попереднього SHA (`gh run cancel`).
18. (✎ 16.11, правило 406) Сама СЕСІЯ ганяє Ecr.Architecture.Tests на фінальній вершині безпосередньо перед пушем, після всіх комітів сабагентів; «агент уже ганяв» не рахується. На цій машині єдиний прийнятий виняток — 2 відомі консольні червоні StatusFromGitScriptTests («git», «outfile»).
19. (✎ 16.11, правило 410) Мутація зараховується лише коли збирання пройшло І очікуваний тест почервонів; таблиця мутацій має колонку «build OK». Мутацію писати так, щоб компілювалась і не дратувала аналізатори (`false && cond`, константа), а не видаленням використання параметра. Привід: 16.11 сім мутацій довелось переробляти.
20. (✎ 16.11, правило 411) Новий крок e2e, що залежить від даних стенда, спершу проганяється локально (`tools\e2e-stand.ps1 -Grep <spec>`), потім пуш.
21. (✎ 16.11, правило 415) Lane, що живе > 3 год при активному main, ребейзиться на main ЩОГОДИНИ, поки код ще рухається, щоб фінальний rebase був дрібним (лінія пентесту втратила ~2 год на один великий rebase). Лише на межі етапів: чисте дерево, жоден скрипт не працює.
22. (✎ 16.11, правило 416) Зміна ключа appsettings/конфігурації → перед пушем локально тести Api Startup + ConfigurationBinding + Worker.
23. (✎ 16.11, правило 417) Новий тестовий помічник/зонд спершу доводиться ЧУТЛИВИМ: мутація на відомому закритому випадку червонить.
24. (✎ 16.11, правило 418) Скрипти агентів беруть абсолютний шлях worktree обов'язковим параметром і відмовляються без нього (змінні PowerShell нечутливі до регістру); довгі прогони пишуть повний вивід у файл; ніколи не збирати й не тестувати в H:\ECR.
25. (✎ 17.11, правило 422) Каталог пам'яті спільний для всіх сесій: чужий файл пам'яті ніколи не переписувати — лише дописувати рядок ✎; нові власні файли називати з префіксом ролі (`an-…`).
26. (✎ 17.11, правило 423) Кожен цикл повторів (20×, пачки мутацій) перевіряє ВИКОНАНУ кількість тестів (точне очікуване Total; 0 = недійсна ітерація, не зелена); dotnet кликати напряму, не через cmd.exe — кириличний `--filter` через cmd дав 0 тестів і порожнє «20/20» у PE.
27. (✎ 17.11, правило 424) Генератори навантаження й перф-заміри — лише в слоті, який призначає координатор (один на машину; першочергово — критичне для вікна).
28. (✎ 17.11, правило 425) Кожен READY містить рядок «Architecture on <SHA>: N/N, час», де SHA = запушена вершина.
29. (✎ 17.11, правило 427) Важкі .NET-процеси на машину — 4 разом (AN 1, PE 1, AU 1, AA 1); AN тимчасово лише 1 (слот .heavy-slot-an2), координатор перебалансує після пушу B79. Привід: AA тримав слот з 21:45Z, машина йшла на 5 процесах і все повзло.
30. (✎ 17.11, правило 428) На початку КОЖНОГО ходу й перед новою задачею читати `.sync-local\PRIORITY.md`; його пункти перекривають будь-яку чергу; перший рядок наступного листа координатору — «ACK <id>».
31. (✎ 17.11, правило 429) Поведінка з кількома споживачами (список/смуга/рядок/картка/в'юха): у READY таблиця «заявлена поведінка × кожен шлях → тест → мутація червона»; кількість мутацій не замінює покриття шляхів; без таблиці AU повертає READY.
32. (✎ 17.11, правило 430) Lane, що зачіпає контракт, 02-contracts.md, сід чи міграції — перелік цих файлів у шапці READY (координатор звіряє попарні конфлікти перед нарізкою RC).
33. (✎ 17.11, правило 431) Номери рішень D-nnn дає ЛИШЕ координатор (`.sync-local\ready\d-new\RESERVED-1116.txt`); у READY пишу «D-NEW» і прошу номер, сам не обираю.
34. (✎ 17.11, P-0117-5, людина 09:10Z: «важкі прогони — на пачках, де багато змін») Власні lane — ШВИДКІ: `lane/<сесія>/<задача>` (не integ-*), build + Architecture + тести зачеплених класів + e2e зачеплених spec через grep; повного CI на lane немає. READY → SHA координатору → він черрі-пікає кілька READY у `lane/integ-batch-<дата>-N`: ОДИН повний CI + Evidence, ОДИН F13, ОДИН RC. 20× і мутації — лише для класу ризику (гонитви, безпека, дані); після rebase лише з доками або побайтно тим самим контрактом — не повторювати.
35. (✎ 17.11, правило 433) Важкий IO (backup/restore, CHECKDB, підняття стенда, генерація даних) — лише в слоті, який призначає координатор: перед стартом один рядок йому — що, який диск, скільки хвилин.
36. (✎ 17.11) Затверджений аркуш незмінний на ВСІХ шляхах запису (зріз/рішення, PATCH, історія дозволів, книга): послаблення «Approved → Draft» для залежного стовпця — лише якщо його читає САМ аркуш. Привід: F13 AU B79 — зріз брехав «редаговано», історія дозволу писала б у затверджений аркуш. Перевіряй кожен записувач окремо, не лише PATCH.
37. (✎ 17.11, правило 436) Lane не правлять `docs/tz/10-decisions.md` і `docs/CHECKSUMS.txt`: D-NEW — лише в READY, записи додає docs-пачка координатора.
38. (✎ 17.11, правило 437) Зміна AccessDecision/SheetEditGate → зонд «власний аркуш цілком Approved» на КОЖНОМУ шляху запису (PATCH, книга, історія дозволів, копії).

**Why:** 11.11 сабагенти від origin/main двічі взяли зайнятий AN-174 (рядки AN-174…177 були лише в лінії HSE400); екрани з великим payload переробляли після CI; мутація фільтра доступу як «доказ» — небезпечна.
**How to apply:** у кожному брифі — пункт 2 дослівно і вказівка грепати ID (`git log --all -S`); у плані UI/читання — рядок «payload на doc 11/Land». Див. [[retro-rules-298-299-1108]], [[subagents-need-write-guard]].
