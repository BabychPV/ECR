Паралельні сесії тут беруть задачі самі, тож ту саму ваду можуть правити двоє
одночасно. 2026-09-18: я взявся за межу глибини обчислювача виразів і лише
згодом побачив `H:/ECR-wt/i-stackdepth [fix/evaluator-stack-depth]` — інша сесія
робила те саме. Окремо: PR, який цю ваду **знайшов** (#308,
`feat/client-formula-budget`), змержили в `main` **посеред** моєї роботи, і
описи в ньому («НЕ закрито тут», «Окремий PR») миттєво застаріли.

**Why:** дубльована робота — це не лише витрачений час, а й два PR, що
конфліктують за ті самі файли й номери розділів документації (у мене — за
`02b` §6.6). А чужий щойно змержений опис стану, який суперечить моєму фіксу,
лишає в репозиторії брехню — рівно те, проти чого застерігає
[[claude-md-entries-go-stale]].

**How to apply:** на старті задачі — `git worktree list` (чи не веде її хтось
уже) і `gh run list --limit 10` / `git log --oneline 29fbb49..origin/main` (чи
не змержили щось дотичне). Перед пушем — `git fetch` і `git merge origin/main`,
навіть якщо на старті гілка була свіжа. Якщо колізія є — напиши тій сесії через
SendMessage, а не мовчи: 2026-09-18 це спрацювало, інша сесія зупинилась і
віддала задачу. Пор. [[worktree-branch-switches]].

⚠ `gh run list --branch <гілка>` одразу після пушу може бути **порожній** — GitHub
створює прогін із затримкою в кілька хвилин. Порожній список ≠ «CI не
налаштований»; перевір `on:` у `.github/workflows/ci.yml` перш ніж робити такий
висновок, і просто перепитай пізніше.
