### 1.3 Додаткова знахідка: коментар у lane помилковий

Remarks клону каже: «Предикат (`MatchJson`) — плаский об'єкт "код колонки → значення", ідентифікаторів не містить».

### 1.4 Що буде на документі клону (V2) [ВИВІД з коду]

Нехай V1 — джерело, V2 — клон, методологія M з опублікованою версією MV (правила/вимоги на Id колонок V1):

1. Правило з не-порожнім предикатом `{"<id V1>":"X"}`: у документі V2 ключа `<id V1>` немає → правило не збігається ніколи.
   Рядки «не покриті», `MatchRowsAsync` повертає порожньо → **прогін не рахує нічого, без помилки**; матриця покриття
   показує «не покрито». Це «мовчки порожні результати».
2. Правило-«вся таблиця» `{}` + обов'язковий вхід на колонку V1 (Block): правило збігається, `ValueOf(<id V1>)` завжди `null`
   → `ECR-CALC-0437` на КОЖНОМУ рядку, збереження блокується назавжди (`PatchCellsHandler.cs:1428-1451`, фінальний
   throw `:1615-1630`). Код колонки у повідомленні деградує до числа (`:1435-1437`). Це гірший випадок: не «порожньо», а
   «не можна зберегти».
3. Вимоги (Warning) — аналогічно тихо шумлять попередженнями; у зрізі зірочка «обов'язкова» не з'являється
   (`GetTableSliceHandler.cs:550-563` повертає Id V1, яких немає в зрізі V2).
4. `CalculatedCellOverlay` для не-`{}` предиката прив'язки — результат не накладається (комірка порожня).
5. Зворотне: V1 уживає ті самі правила й працює, бо Id збігаються. Тобто дефект виникає лише на документах клону.
6. `WhereUsedStore` шукає правила за Id → для колонок V2 «де використовується» порожньо (приховує зв'язок). [КОД]

Висновок: D1 справжній. Тяжкість залежить від вмісту Land: чи є взагалі в методологій, прив'язаних до таблиць
редагованих шаблонів, правила з ключами / обов'язкові входи — [НЕВІДОМО] (запит до бази Land, див. «Відкриті питання»).

### 1.5 Важлива структурна обставина (впливає на варіанти)

Версія методології обирається ЧАСОМ, а версія шаблону — проєктом. Обидві версії шаблону (V1 і V2) одночасно живі: проєкти
переносяться між ними окремо (`MigrateDocumentVersionHandler`). Отже ключі правил **не можуть бути Id однієї версії**, доки
існує хоч один документ на іншій. Будь-яке рішення «перезаписати Id на V2» ламає V1.

AF-імпорт методологій (`tools/Ecr.MethodologyImport`, `ImportMethodologyPackageHandler`, `MethodologyPackagePlanner`)
правил/вимог/MatchJson НЕ створює: у моделі гілка `Rules` пропускається (`MethodologyModelBuilder.cs:51`), у handler/planner
`MethodologyRule`/`RequiredInput` не згадується. Правила й вимоги заводяться лише вручну через
`SaveMethodologyRuleHandler` (право `Calculation.EditRule`), `SaveMethodologyRequiredInputHandler`
(`Calculation.ManageRequiredInputs`) і копіюються `MethodologyDraftStore.CopyChildrenAsync` (клон ЧЕРНЕТКИ методології
переносить `MatchJson` і `ColumnDefId` як є, `MethodologyDraftStore.cs:337-364`). [КОД]
Тобто «AF-пакет з MatchJson» як канал — відсутній; зміна формату ключів AF-імпорту не зачіпає.

## 2. Варіанти

### A. Клон шаблону створює ЧЕРНЕТКУ нової версії кожної прив'язаної методології з перемапленими Id

Що міняється: клон шаблону (`TemplateVersionStore.SaveCloneAsync`) викликає `MethodologyDraftStore` (копія версії
`CopyChildrenAsync` + ремап `MatchJson`-ключів і `RequiredInput.ColumnDefId` через `map` source→clone), нова чернетка
методології. Нових сутностей немає. Міграція БД: ні. Контракт: ймовірно ні (відповідь клону могла б повертати список створених
чернеток — опційно).

Вплив:
- **Публікація.** Чернетку мусить опублікувати друга особа (`ECR-CALC-0409 authorCannotPublish`, `Calculation.Publish`) з
  `EffectiveFrom`. **Проблема з §1.5:** опублікована версія стає чинною для ВСІХ документів з періодами ≥ `EffectiveFrom`,
  у тому числі документів V1 — для них ключі V2 не збігаються. Правильно це працює лише якщо `EffectiveFrom` ≥ дати,
  після якої НЕ лишилось жодного проєкту на V1 (або якщо V1 не експлуатується). Для проміжку співіснування версій A ламає V1.
  Для періодів до `EffectiveFrom` V2-документи лишаються на старій версії з ключами V1 (тобто D1 для історичних періодів V2 лишається).
- **Імпорт AF:** не зачіпає (§1.5).
- **migrate-version:** потрібна перевірка «чинні версії методологій цільової версії мають ключі лише з її колонок»; без неї
  порядок «спершу публікація методологій, потім перенос» нічим не примушується.
- **Діфф версій:** `DiffTemplateVersionsHandler` методологій не бачить [НЕ ПЕРЕВІРЕНО повністю]; чернетки лишаться непомітними
  для рев'юера шаблону.
- **Безпека:** право створення — `Template.Edit`/клон; чернетка методології створюється неявно користувачем без
  `Calculation.EditFormula`/`EditRule` — обхід розмежування прав (хто може клонувати шаблон, той породжує вміст методології).
  `Calculation.EditRule`/`ManageRequiredInputs` мали б перевірятись на клоні — уточнити політику. DocumentVisibility не зачіпається
  (дані документів не змінюються).
- **Ризики:** N методологій × N чернеток на кожен клон; кожен клон вимагає ручної публікації другою особою; повторний клон V3 —
  знову; чернетка вже існуючої не-опублікованої версії (колізія `UQ`/одна чернетка?) — [НЕВІДОМО]; ремап тут невіддільний від
  дати чинності (§вище).
- **Обсяг (оцінка):** 3–5 комітів, ~400–700 рядків із тестами; lane один (шаблони + методології), без токена міграцій.
- **Зворотна сумісність:** існуючі дані не чіпає.

### B. Правила й обов'язкові входи — у binding шаблону, за КОДАМИ колонок (резолв у рантаймі)

Що міняється: зберігання правил/вимог переноситься з версії методології на `CalculationBinding` (або таблицю біля нього)
з ключами-кодами колонок; рантайм (`PatchCellsHandler`, `MethodologyResolver`, `RuleCoverageHandler`, зріз, кеш
`MethodologyRequiredColumnsCache`, `WhereUsedStore`) резолвить код → Id по зрізу версії. Клон тоді копіює правила разом із binding
без ремапу.
- **Міграція: так** (нові таблиці/поля + перенос наявних правил з Id → коди; для правила Id→код потрібна таблиця, а в правила її
  немає — виводити з прив'язок методології, неоднозначно, якщо методологія прив'язана до кількох таблиць) → токен міграцій.
- **Контракт: так** (`MethodologyRequiredInputDto.ColumnDefId`, DTO правил, `openapi.snapshot.json`, `schema.d.ts`, адмін-екрани
  правил/вимог).
- **Публікація:** правила переходять із версії методології (чотири очі, `Calculation.Publish`, ФВ-13.9 матриця покриття на
  публікації, `MethodologyRuleChecks`) на binding шаблону — **втрата контролю чотирьох очей над правилами** та прив'язка їх до
  `EditRule` ≠ режим редагування шаблону; `PublishMethodologyHandler` перестає бачити правила. Потрібне продуктове рішення.
- **Імпорт AF:** не зачіпає. **migrate-version:** природно працює (коди). **Діфф:** правила стали б частиною структури шаблону
  → з'явились би в діффі (плюс). **Безпека:** змінюється власник контролю (див. публікація).
- **Ризики:** найбільший обсяг; зламає історичну повторювану логіку «версія методології = правила, що були чинні на дату»
  (правила стали б залежати від шаблону, а не від дати) — перерахунки старих періодів змінять поведінку.
- **Обсяг (оцінка):** 10+ комітів, ~1500–2500 рядків; кілька lane; міграція даних. Для RC12 нереально.
- **Зворотна сумісність:** потрібна міграція даних і перехідний період для старих клієнтів контракту.

### C1. Лишити Id у сховищі, **перекладати чужі Id на локальні при читанні** (за шляхом аркуш/таблиця/колонка)

Додано третім варіантом, бо він єдиний, що узгоджується з §1.5 (V1 і V2 живуть одночасно, одна версія методології на обидві).
Що міняється: один допоміжний «локалізатор ключів» (store-метод: для набору Id → `(sheetCode, tableCode, columnCode)` через
`ColumnDef→TableDef→SheetDef`, далі пошук колонки з тими ж кодами в таблиці екземпляра) і його застосування в споживачах:
`PatchCellsHandler.ResolveApplicableAsync` (+`MatchJsonColumnIds`), `MethodologyResolver.MatchRowsWithRulesAsync`,
`RuleCoverageHandler`, `GetTableSliceHandler.RequiredColumnIdsOfVersionAsync` (+ ключ кешу `MethodologyRequiredColumnsCache`
доповнити `tableDefId`/версією шаблону), `CalculatedCellOverlay` (для binding-предиката), `WhereUsedStore` (пошук за вихідним
Id «сімейства»). Ідентичність за кодами — та сама, що вже використовують гранти клону й `VersionMigrationPlanner`
(«відповідність — за кодами»).
- **Міграція: ні.** **Контракт: ні** (DTO ті самі; можливо поле `ColumnCode` уже є — `MethodologyAuthoringHandlers.cs:475-487`).
- **Публікація/імпорт AF/діфф/безпека:** правила й вимоги лишаються у версії методології (чотири очі збережено); нічого нового
  в правах (`Calculation.EditRule` / `ManageRequiredInputs` як були). Імпорт AF не зачіпається.
- **migrate-version:** працює без додаткового кроку, але перевірку «колонка з правила не існує в цілі» (видалена/перейменована)
  усе одно треба — інакше те саме тихе мовчання, лише для зникнулих кодів.
- **Ризики:** гаряче читання (зріз — «найгарячіше читання системи»; кеш за версією методології стане залежним від таблиці);
  неоднозначність, якщо коди аркушів/таблиць перейменовано між версіями (тоді ключ не резолвиться → потрібна явна відмова/попередження, а не мовчання);
  переклад треба застосувати в усіх споживачах — пропуск одного дає новий тихий дефект (потрібен архітектурний сторож «вхід у
  MatchJson/RequiredInput лише через локалізатор»).
- **Обсяг (оцінка):** 6–8 комітів, ~700–1100 рядків із тестами; 1–2 lane; без міграції.
- **Зворотна сумісність:** повна — наявні дані не змінюються, для V1 перекладач тотожний.

### C2. Зберігати код ПОРУЧ з Id (`ColumnCode` у `MethodologyRequiredInput`; ключі `MatchJson` у формі коду)

Як B, але правила лишаються у версії методології. Потребує міграції (нова колонка/переписування ключів + перенос), зміни контракту

неоднозначність «в якій таблиці» (правило не знає таблицю) не зникає. Не бачу переваг над C1; **не рекомендую**.

## 4. RC11: попередження/відмова (точні місця)

Мета: не мовчки порожні результати, коли binding веде до методології з ключами/вимогами на колонки НЕ цієї версії.
Спільний предикат (одна функція в Application, поряд із `MethodologyRuleChecks`): для версії шаблону T —
активні прив'язки на таблицях T → методологія → усі ОПУБЛІКОВАНІ версії (`EffectiveFrom is not null`; не лише чинна сьогодні, бо
історичні періоди V2-документів беруть старіші версії) → ключі `MatchJson` правил і `RequiredInput.ColumnDefId`, яких немає серед
колонок T (`!IsDeleted`); те саме для `binding.MatchJson`. Результат: перелік `(методологія, версія, правило/вимога, Id)`.

1. **migrate-version — ВІДМОВА.** `MigrateDocumentVersionHandler.PlanAsync` (`MigrateDocumentVersionHandler.cs:268-323`), поряд із
   `refusals.Add("grantsNotMapped")` (`:302-305`) додати причину `methodologyKeysNotMapped` + count у DTO; `CanApply=false`;
   `ThrowIfRefused` (`:383-430`) — окрема гілка `messageKey` на кшталт `err.ECR-SCHM-0422.migrateMethodologyKeysNotMapped`
   (новий messageKey і рядок каталогу — за правилом «завести код помилки»: 4 файли + сторожі, `ErrorCodes.cs`/`ExceptionHandlingMiddleware.cs`).
   Запит у `IDocumentVersionMigrationStore` (за зразком `CountDenyGrantsAsync`, `DocumentVersionMigrationStore.cs:124`) або в
   `IMethodologyStore`. Це відмова, бо наслідок — тихе зникнення розрахунку або блокування збереження (§1.4 п.2), а перенос проєкту
   нерозв'язний назад без втрат. Сухий прогін показує причину; відмова діє й на dry-run як `CanApply=false`.
2. **Публікація шаблону — ВІДМОВА (діагностика), не попередження.** `PublishTemplateVersionHandler.cs` після виклику
   `CheckStructure(version, boundColumnIds)` (`:160-164`): додати діагностики (`ExpressionDiagnostic` + `MessageKey`) у той самий
   перелік. Попередження тут НЕМАЄ: усі `ExpressionDiagnostic` блокують публікацію (`:166-179`), окремого warning-каналу в

## 6. Відкриті питання

1. Скільки в Land (та в усіх шаблонах, які реально клонуватимуть) методологій з правилами не-`{}`, обов'язковими входами

   `grantsNotMapped`) — підтвердити.
