# Цикл керуючого вузла (PK1)

⚠ `gh` може не бути в `PATH` — тоді `& "C:\Program Files\GitHub CLI\gh.exe"`.

---

## 0. Роль

```bash
cat .sync-local/NODE      # має бути PK1
git checkout main && git pull --quiet
```

Не `PK1` — зупинись.

---

## 1. Прочитати, що зробив виконавець

```bash
git fetch origin sync
git show origin/sync:PK2-LOG.md
```

Читай **із кінця**: нові записи дописуються вниз. Дивись на те, чого не було
минулого разу.

| Тип запису | Твоя дія |
|---|---|
| `STATUS` — подав PR | крок 2: рев'ю |
| `ASK` — питання | крок 3: відповідь |
| `DELTA` — вирішив сам | прочитати; заперечення — `ANSWER`, згода — нічого |
| `ANOMALY` | зупинка, це до людини |

Нічого нового і відкритих PR немає — крок 4.

---

## 2. Рев'ю PR

### 2.1 Спершу машина, код не читай

```bash
gh pr checks <N>
```

Хоч один не `pass` → запис `VERDICT` у свій лог: «CI червоний, джоб `<ім'я>`;
на рев'ю подають зелене». Диф **не читай**: це помилка процесу, не коду, і
читати означало б робити роботу виконавця.

⛔ Виняток, який зобов'язує перевірити: **чи це не мій дефект**. Якщо джоб
упав через конвеєр, сторож або настанову — виправляю я, і ітерація виконавцеві
не рахується. Ознака: `server`/`build` зелені, а червоне лише в тому, що я
додав нещодавно.

### 2.2 Зелено — читай диф

```bash
gh pr diff <N>
```

Дивись **тільки на те, чого CI не ловить**:

- **змістовність асертів** — чи впаде тест, якщо зламати рядок, який він стереже;
- **транзакційність і конкурентність** — що буде при двох одночасних прогонах;
- **видимість відмови** — чи помилка тиха;
- **продуктивність на реальних обсягах**, не на трьох рядках фікстури;
- **відповідність бізнес-правилу з ТЗ**, а не буквальному тексту настанови.
  Настанову писав я і міг помилитися; ТЗ — джерело.

### 2.3 Вердикт — записом у свій лог

Класифікація: **КРИТИЧНО** (блокує) · **ВАЖЛИВО** (блокує) · **NITPICK**
(не блокує ніколи).

```bash
gh pr merge <N> --squash --delete-branch      # приймаю
```

Далі — `VERDICT` у `PK1-LOG.md`: прийнято, і що лишилося як NITPICK.

Повертаю — `VERDICT` із переліком: що саме, де, чому. Без цього виконавець
шукатиме навпомацки.

⛔ Не мерж із незеленим CI. Не уживай `--admin`: це обхід власного бар'єра.

---

## 3. Відповіді на `ASK`

Відповідай, коли питання справді блокує. Якщо виконавець міг вирішити сам —
відповідь одна: «застосуй свій дефолт, запиши `DELTA`».

```
## <дата> · PK1 · ANSWER-00N
Відповідь на ASK-00M

**Рішення:** ...
**Підстава:** docs/tz/<файл>#<розділ>
```

⛔ Відповіді немає в ТЗ **і** немає підстав вирішити самому → це до людини.
Не вигадуй бізнес-правило: вигадане правило дорожче за день простою, бо його
виявлять на звірці з регулятором.

---

## 4. Нові настанови

Одна настанова — один запис `DIR`. Три обов'язкові частини:

```
## <дата> · PK1 · DIR-00N
<заголовок>

**Що потрібно:** що має ВМІТИ система, не як це зробити
**Файли:** конкретний перелік
**Готово, коли:** CI job `build`/`test`/`honesty-guard` -> success, і <перевірний факт>
**Якщо неоднозначно:** <дефолт, щоб виконавець не простоював>
```

⚠ Не більше **трьох** відкритих настанов одночасно. Більше — і виконавець
працює за пріоритетом, якого не існує.

⛔ «Готово, коли» має перевірятися **машиною**. Критерій, який не виражається
через CI або читабельний факт, означає одне з двох: він зайвий, або в конвеєрі
бракує перевірки.

## 5. Запис у свій лог

```bash
git checkout sync && git pull --rebase origin sync
# дописати в КІНЕЦЬ PK1-LOG.md
git add PK1-LOG.md
git commit -m "[PK1][DIR] коротко"
git push origin sync
git checkout main
```

⛔ `PK2-LOG.md` не чіпай — ніколи, ні для порядку, ні щоб «поправити формат».

---

## 6. Ознака, що процес крутиться на місці

Три цикли поспіль без жодного змерженого PR.

Причина майже завжди одна з двох, і обидві мої:
- «готово, коли» не перевіряється машиною;
- настанова описує **як робити** замість **що має вийти**.
