## Ключові рішення одним абзацом

**Структура — це дані:** додати колонку в звіт — це `INSERT` у `cfg.ColumnDef`,
а не `ALTER TABLE`; жодного DDL під час роботи. **Ідентичність явна:** рядок —
`RowKey`, поле — `ColumnDef.Code`, а не позиція в `;`-рядку, як зараз.
**Опубліковане структурно незмінне**, змінюється лише презентаційний шар.
**БД не рахує** — розрахунки в сервісі, методології теж дані. **PI AF —
виключно джерело читання**, запису туди немає. **SSRS лишається** звітною
системою на нових структурах через `rpt.*`. **Нічого не затирається** — обсяг
керується рівнями зберігання, а не строками. **Standard — базовий режим SQL**,
Enterprise вмикається автоматично.

Повний перелік із обґрунтуваннями — [`tz/10-decisions.md`](tz/10-decisions.md).

## Перенесення на ПК-2

**Копіювати всю теку `docs/` цілком.** Пакет `build/` не самодостатній: він
посилається на `tz/` (вимоги й рішення) і на `reference/backend/` (фронтенд-
специфікація, фізична модель). Перенести лише `build/` — залишити виконавця з
битими посиланнями.

Нічого, крім `docs/`, переносити не треба: коду, проєкту й git-історії там
немає навмисно — усе, що потрібно, лежить усередині markdown.

### Перевірка після копіювання

Файлів `.md` має бути **84**, плюс `CHECKSUMS.txt`. Перевірка цілісності —
з теки `docs/`:

```bash
sha256sum -c CHECKSUMS.txt
```

У PowerShell, якщо `sha256sum` недоступний:

```bash
Get-Content CHECKSUMS.txt | ForEach-Object { $h,$f = $_ -split '\s+',2; $a=(Get-FileHash $f -Algorithm SHA256).Hash.ToLower(); if ($a -ne $h) { "ЗМІНЕНО: $f" } } ; "перевірку завершено"
```

Мовчазний вивід означає, що всі 84 файли збіглися побайтово.

### Перші кроки там

1. Відкрити [`build/00-START-HERE.md`](build/00-START-HERE.md) — усе інше
   читається за порядком звідти.
2. Виконати ЕТАП 0 із [`build/07-checkpoints.md`](build/07-checkpoints.md):
   створити файли, зібрати, переконатися, що тести **знайдені й падають**.
3. Зупинитися і показати звіт.

Що має бути на ПК-2, крім документів: .NET 10 SDK, Node 22, Docker, SQL Server
2019 (є — `D-101`), інтернет для nuget і npm, а також `.xlsm`, VBA і дампи
`dbo.AF_*` для звірки. Повний перелік — [`build/04-environment.md`](build/04-environment.md).

## Межа відповідальності виконавця

Ці документи не бездоганні. Їх писали люди і AI; шість проходів перевірки
знайшли й виправили десятки розбіжностей — суперечності між вимогами,
вигадані типи, застарілі числа, — але **частина неточностей лишилася**.
Стверджувати протилежне було б неправдою: кожен наступний прохід досі щось
знаходив.

Тому право вирішувати дрібне **делеговане тому, хто реалізує**. Це швидше і
надійніше за здогадку про намір автора, і чесніше за вдавання, що документи
повні.

**Виконавець вирішує сам** і просто записує рішення: розбіжність прози з
контрактом (правий контракт), відсутній `using`, друкарська помилка в шляху,
локальні деталі реалізації, значення у фікстурі, що детерміновано випливає
з правил.

**Виконавець зупиняється і питає**, якщо рішення торкається числа, контракту,
схеми БД, правил доступу, retention, або якщо дві вимоги суперечать по суті.
Такі речі — домовленості із замовником, а не деталі реалізації.

Перевірка одним питанням: **«чи зміниться від мого рішення число у звіті,
форма API або запис у базі?»** Якщо так — це не рішення виконавця.

Механіка — [`build/08-workflow.md`](build/08-workflow.md) §7; журнал —
[`build/questions.md`](build/questions.md), тип запису `DECIDED`.
