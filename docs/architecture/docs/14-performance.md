# Продуктивність: бюджет під 100 одночасних користувачів

Цей документ — не «поради з оптимізації», а **бюджет**: скільки чого можна витратити,
щоб система тримала цільове навантаження, і як це перевіряється.

---

## 1. Модель навантаження

Треба домовитися, що означає «100 одночасних клієнтів». Без цього
цифри продуктивності не мають сенсу.

### 1.1 Профіль користувача

| Клас | Частка | Що робить | Запитів/хв на користувача |
|------|-------:|-----------|--------------------------:|
| **Оператор введення** | 70% | відкриває таблицю, вводить дані, зберігає діапазони | 20–40 |
| **Затверджувач** | 15% | переглядає, порівнює, затверджує | 5–10 |
| **Переглядач / звіти** | 10% | фільтрує списки, експортує | 3–8 |
| **Адміністратор** | 5% | конфігуратор, ролі, довідники | 5–15 |

### 1.2 Розрахункове навантаження

```
100 одночасних користувачів
  × ~25 запитів/хв у середньому
  = 2 500 запитів/хв ≈ 42 RPS (середнє)

Піковий коефіцієнт 3× (кінець місяця, дедлайн звітності)
  = ~125 RPS (пік)
```

### 1.3 ⚠ Пік — це не рівномірний потік

**Найважливіше для sizing.** Робота зі звітністю має різкий пік:
останні 3–5 днів періоду і перші дні grace-періоду. У ці дні:

* одночасних користувачів може бути **не 100, а 100 фактично активних**
  (зараз «100» — це радше зареєстровані);
* масові операції (`BulkSave`-аналог, експорт, збір даних із джерел) йдуть пачками;
* усі працюють з **одним і тим самим періодом** — тобто б'ють в одні партиції.

**Дія:** закласти в план навантажувального тесту окремий сценарій
«останній день періоду» з 3× піком і масовими операціями.

| # | Операція | Ціль p95 | Ціль p99 | Чому саме так |
|---|----------|---------:|---------:|---------------|
| 1 | Логін (обидва провайдери) | 500 мс | 1 с | разова операція |
| 2 | Список документів (фільтр, 50 записів) | 300 мс | 600 мс | головний екран |
| 3 | **Відкриття таблиці 500×60** | **1.5 с** | 3 с | найважчий регулярний запит |
| 4 | Наступна «сторінка» рядків (віртуалізація) | 200 мс | 400 мс | скрол має бути плавним |
| 5 | **Збереження діапазону 100 комірок** | **300 мс** | 600 мс | вставка з Excel — типова дія |
| 6 | Збереження однієї комірки | 120 мс | 250 мс | автозбереження на blur |
| 7 | Перерахунок формул таблиці (сервер) | 500 мс | 1 с | |
| 8 | Перерахунок на клієнті (`formulajs`) | 100 мс | 200 мс | має відчуватися миттєвим |
| 9 | Валідація документа (усі аркуші) | 3 с | 6 с | перед `Submit` |
| 10 | Пошук документа за `BusinessKey` | 200 мс | 400 мс | зараз — вивантаження 1000 EF |
| 11 | Експорт документа в `.xlsx` | 10 с | 20 с | фоново, з прогресом |
| 12 | Довідник у листбоксі (300 значень) | 150 мс | 300 мс | кешується |
| 13 | Збір з PI AF (1 док × 12 періодів; зворотна публікація — опційно) | 60 с | 120 с | фоново |

**Бюджет на запит #3 (відкриття таблиці) — розкладка:**

```
  1500 мс усього
   ├─  50 мс  auth + resolve прав (з кешу AccessProfile)
   ├─ 100 мс  метадані шаблону (з кешу — immutable version)
   ├─ 600 мс  вибірка даних із SQL (30 000 комірок)
   ├─ 200 мс  проєкція в DTO + серіалізація
   ├─ 150 мс  мережа
   └─ 400 мс  рендер на клієнті (canvas, лише видимі рядки)
```

> Якщо вибірка з SQL не вкладається в 600 мс на реальному обсязі —
> це сигнал переходити на JSON-гібрид зберігання (ТЗ §5.1).
> **Це і є критерій рішення на Етапі 0.**

## 3. Головні ризики продуктивності і що з ними робити

### 3.1 Обсяг `doc.CellValue`

| Захід | Ефект |
|-------|-------|
| **Архівація закритих років** у `arc.*` | робочі таблиці тримають ~1 рік (~108 млн), а не N років — **головний захід** |
| Партиціонування по `PeriodId` | запит за один місяць читає одну партицію |
| `PAGE`-стиснення | менше I/O, більше даних у buffer pool |
| Кластерний індекс `(TableRowId, ColumnDefId)` | дані одного рядка лежать фізично поруч |
| **Не матеріалізувати порожні комірки** | замість 108 млн — стільки, скільки реально заповнили |

> Останній пункт часто дає найбільший виграш: у реальних звітах заповнено
> далеко не 100% комірок. Читання повертає `DefaultValue` для відсутніх.

### 3.2 N+1 і надлишкові вибірки

| Правило | Реалізація |
|---------|-----------|
| Жодного лінивого завантаження | `UseLazyLoadingProxies` вимкнено; `AsNoTracking()` за замовчуванням для читання |
| Одна таблиця = один запит | вибірка комірок проєкцією в плоский DTO, без `Include` по графу |
| Пагінація завжди | немає ендпоінтів, що повертають «усе» |
| Компільовані запити | для 5–7 гарячих шляхів (`EF.CompileAsyncQuery`) |
| **Архітектурний тест** | заборона `.ToList()` без `Take()` у шарі Application |

### 3.3 Права доступу

Розв'язання прав на кожну комірку — гарантована смерть продуктивності.

```
Вхід → будуємо AccessProfile (мапа resourceKey -> level)
     → кеш у пам'яті, ключ = userId + templateVersionId + securityStamp
     → API віддає клієнту готову мапу прав для документа
     → grid одразу знає, що read-only, а що приховати
```

Інвалідація тривіальна: `securityStamp` змінюється при зміні ролей/пароля.
Опубліковані версії шаблону **структурно незмінні**, тому метадані кешуються
назавжди під ключем `v{id}:r{PresentationRevision}` — презентаційна правка
не інвалідує кеш, а створює новий ключ. Це ще один практичний виграш від
immutable versions.

### 3.4 Формули

| Проблема | Рішення |
|----------|---------|
| Перерахунок усього документа на кожну зміну | граф залежностей + перерахунок **лише зачепленого піддерева** |
| Крос-аркушні rollup-и (`7.0` ← `7.`) | помітити «брудним», перерахувати відкладено (debounce 300 мс) |
| Топологічна сортовка на кожен запит | `FormulaDef.EvaluationOrder` обчислюється **при публікації версії** і зберігається |
| Клієнт і сервер рахують по-різному | сервер — єдине джерело істини; клієнтське значення ніколи не зберігається |

### 3.5 Конкурентність на одному документі

| Ситуація | Рішення |
|----------|---------|
| Двоє редагують один документ | оптимістичне блокування по `RowVersion` на рівні **рядка**, не документа |
| Конфлікт | показати розбіжність, дати обрати; не «перезаписати мовчки» |
| Гарячі рядки (підсумки) | обчислювані комірки не редагуються вручну -> конфліктів немає |
| Масові операції | окрема черга Hangfire, не в HTTP-запиті |

### 3.6 Довгі операції не тримають HTTP

Усе, що довше ~5 с, іде у фон:
експорт/імпорт, збір даних з AF (і опційна зворотна публікація), міграція документа на нову версію,
масове затвердження, архівація року. Клієнт отримує `jobId` і слухає прогрес.

## 4. Кешування — що, де, надовго

| Дані | Де | TTL | Інвалідація |
|------|-----|-----|-------------|
| Метадані опублікованої версії шаблону | пам'ять | **безстроково** | не потрібна: структура immutable; презентаційна правка дає новий ключ `v{id}:r{PresentationRevision}` |
| Метадані `Draft`-версії | пам'ять | 30 с | при збереженні |
| `AccessProfile` користувача | пам'ять | сесія | `securityStamp` |
| Довідники (списки для листбоксів) | пам'ять + ETag на клієнті | 10 хв | після синхронізації |
| Календар періодів проєкту | пам'ять | 5 хв | `PeriodStateJob` |
| Дані документа | **не кешуються** | — | джерело істини — БД |

> При кількох інстансах — **`IDistributedCache` з SQL Server-провайдером**
> для `AccessProfile` і довідників (у складі ASP.NET Core, без нової інфраструктури).
> Для 100 користувачів цього достатньо. Якщо прототип покаже потребу в окремому
> кеш-сервері — **Microsoft Garnet** (MIT, .NET, RESP-сумісний), **не Redis**
> (AGPLv3/SSPL — суперечить політиці проєкту).
> Метадані опублікованих версій лишаються в пам'яті кожного інстансу: вони
> структурно незмінні, тому розсинхрону бути не може.

## 5. Sizing інфраструктури (стартова оцінка)

| Компонент | Рекомендація | Примітка |
|-----------|--------------|----------|
| App-сервери | 2 × (4 vCPU, 16 GB) за балансувальником | горизонтальне масштабування; sticky-сесії не потрібні (стан у cookie + БД) |
| SQL Server | 8+ vCPU, **64 GB RAM**, NVMe | RAM критична: buffer pool має тримати гарячі партиції |
| Файлові групи | `PRIMARY` / `DATA_HOT` / `DATA_ARCHIVE` / `INDEXES` | архів можна винести на повільніший диск |
| tempdb | 8 файлів, на швидкому диску | масові операції і сортування |
| Кеш-сервер | **не потрібен на старті** | `IDistributedCache` на SQL Server; Garnet (MIT) — лише якщо прототип покаже потребу |

⚠ Це **стартова оцінка**, яка уточнюється за результатами Етапу 0.

## 7. Спостережуваність (без неї бюджет неможливо тримати)

| Що | Як |
|----|-----|
| Метрики | OpenTelemetry -> Prometheus / Azure Monitor |
| Ключові лічильники | p50/p95/p99 по кожному ендпоінту з таблиці §2, довжина черг Hangfire, час запитів до SQL, cache hit ratio |
| Трасування | OpenTelemetry, `CorrelationId` наскрізь: HTTP -> Application -> SQL -> зовнішній адаптер |
| Повільні запити | автоматичний лог SQL > 500 мс з планом |
| Health checks | `/health/live`, `/health/ready`, `/health/schema`, `/health/metadata`, `/health/external` |
| Дашборд | «бюджет vs факт» по кожній операції з §2 — щоб регресію було видно одразу |

> **Правило:** будь-яка операція з таблиці §2, яка вийшла за бюджет
> на проді, заводиться як дефект, а не «оптимізуємо колись».

## 8. Антипатерни, за які цей проєкт заплатить одразу

| ❌ Не робити | Чому саме тут |
|-------------|---------------|
| Повертати весь документ одним запитом | 650 000 комірок × 100 користувачів |
| Резолвити права на кожну комірку | 30 000 перевірок на одне відкриття таблиці |
| Перерахунок усіх формул документа на кожен `PATCH` | ~250 формул × кожна зміна × 100 користувачів; треба лише зачеплене піддерево |
| DDL під час роботи (`ALTER TABLE`) | Sch-M lock блокує всіх (див. [10-schema-evolution.md](10-schema-evolution.md)) |
| Синхронний виклик PI AF у HTTP-запиті | зовнішня система тримає наш пул потоків |
| `Database.Migrate()` при старті в PROD | кілька інстансів роблять DDL одночасно |
| Тримати архів у робочих таблицях | деградація з кожним роком |
| Логувати кожну зміну комірки синхронно в БД | аудит має писатися пачками |
