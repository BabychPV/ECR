# Безпечна зміна структури «на льоту»

> Вимога: структура (аркуші, таблиці, колонки, типи, формули, стилі) змінюється
> постійно і має змінюватися **на льоту, універсально і безпечно для консистентності даних**.

Це найважчий технічний аспект системи. Нижче — повна механіка.

---

## 1. Головне рішення: жодного DDL під час роботи

**Фізична схема БД фіксована. Вона не змінюється при зміні шаблону — ніколи.**

```csharp
// ❌ КАТЕГОРИЧНО НІ
await db.Database.ExecuteSqlRawAsync(
    $"ALTER TABLE Doc_{tableCode} ADD [{columnCode}] decimal(18,4) NULL");

// ✅ ТАК: структура — це рядки в cfg.ColumnDef
await _schemaEvolution.ApplyAsync(new AddColumnChange(tableDefId, code, dataType));
```

### Чому динамічний DDL — це пастка

| Проблема | Наслідок |
|----------|----------|
| `ALTER TABLE` бере Sch-M lock | блокує всіх користувачів таблиці на час операції |
| Немає транзакційного відкату у поєднанні з даними | напівзастосована зміна = пошкоджені дані |
| EF Core migrations розсинхронізуються з реальністю | наступний деплой ламає БД |
| DEV / TEST / PROD розповзаються | неможливо відтворити баг |
| Ліміт 1024 колонки в SQL Server | таблиця `9. Utility` має 60+ колонок × 12 місяців — впритул |
| Права на DDL для облікового запису застосунку | недопустимо з погляду ІБ |

**Наслідок вибору:** структура зберігається як метадані (`cfg.*`),
значення — в одній фізичній таблиці `doc.CellValue`.
Додавання колонки = `INSERT` одного рядка. Атомарно, миттєво, відкатно.

## 2. Immutable versions — фундамент консистентності

```
TemplateVersion 1.0 [Published]  ←── Document A (2025)   ← структура заморожена
                                 ←── Document B (2025)
TemplateVersion 1.1 [Published]  ←── Document C (2026)
TemplateVersion 1.2 [Draft]          (документів немає — можна редагувати)
```

**Інваріант №1:** якщо `TemplateVersion.Status = Published`, жоден запис
структури цієї версії не може бути змінений або видалений.

Забезпечується на трьох рівнях:
1. **Domain** — `TemplateVersion.EnsureEditable()` кидає виняток;
2. **Application** — перевірка перед будь-якою командою зміни;
3. **БД** — тригер `INSTEAD OF UPDATE/DELETE` на `cfg.*`, який відхиляє зміну,
   якщо `TemplateVersionId` вказує на опубліковану версію.

Третій рівень — не паранойя: він ловить помилки в коді, ручні правки і
міграції, що пішли не так.

**Інваріант №2:** документ назавжди прив'язаний до версії, на якій створений.
`Document.TemplateVersionId` — `readonly` після створення; змінюється лише
через явну операцію `MigrateDocument`.

## 2a. Уточнення: два шари опублікованої версії ⭐

Повна заморозка опублікованої версії має побічний ефект: щоб виправити
друкарську помилку в підписі колонки, довелося б створювати нову версію і
мігрувати на неї документи. Це суперечить вимозі «працює на льоту».

Тому опублікована версія складається з **двох шарів із різними правилами**:

| Шар | Що входить | Правило |
|-----|-----------|---------|
| **Структурний** | `Code` усіх сутностей, `DataType`, `Precision/Scale`, `IsKey`, `RowKey`, `LookupRegistryDefId`, `FormulaDef.Expression`, `TableRelationDef`, `LayoutKind`, `RowMode`, `ValidationRule` із `Severity = Error`, `IsRequired`, `PeriodAccessRuleDef` | **заморожений** — інваріант №1 без винятків |
| **Презентаційний** | підписи і переклади (`…L10n`), `StyleDef`, `ConditionalFormatDef`, `Ordinal`, ширини, `DisplayFormat`, `DisplayTemplate`, підказки, `IsHidden`, `ValidationRule` із `Severity = Info/Warning` | **патчиться «на льоту»** з аудитом |

**Чому це безпечно.** Жодне поле презентаційного шару не бере участі в:
* ідентифікації даних (`RowKey`, `Code`);
* інтерпретації збережених значень (`DataType`, `Lookup`);
* обчисленнях (`Expression`);
* блокуванні `Submit` (`Error`-правила).

Отже, зміна презентаційного шару **фізично не може зробити збережені дані
невалідними або неоднозначними**.

**Механіка:**

```
cfg.TemplateVersion
  Status               = Published
  PresentationRevision = 17        ← інкремент при кожній презентаційній правці

Ключ кешу метадат:  schema:v{versionId}:r{presentationRevision}
```

* тригер `INSTEAD OF UPDATE` на `cfg.*` **дозволяє** зміни лише перелічених
  презентаційних полів для `Published`-версій і **відхиляє** решту;
* кожна правка — запис у `aud.SchemaChange` із `ChangeClass = Presentation`;
* документи **не мігрують** — вони й далі на тій самій версії, просто інакше виглядають;
* експорт у `.xlsx` бере актуальний презентаційний шар;
* `Diff(v1, v2)` показує презентаційні зміни окремою групою.

**Що це дає адміністратору:** виправити підпис, додати переклад, підсвітити
колонку, додати попередження — за секунди, без версій і міграцій.
Змінити тип колонки або видалити рядок — тільки через нову версію, як і раніше.

## 3. Класифікація змін

Кожна операція над структурою автоматично класифікується
`SchemaEvolutionService.Classify(change)`.

### 🔵 Presentation — дозволені навіть в опублікованій версії

Не зачіпають ідентифікацію, інтерпретацію чи обчислення даних (§2a).
Застосовуються «на льоту», з аудитом і інкрементом `PresentationRevision`.

| Операція | Вплив на існуючі дані |
|----------|----------------------|
| Змінити підпис / заголовок / переклад (`…L10n`) | немає |
| Змінити `Ordinal` (порядок відображення) | немає — порядок не є ідентичністю |
| Змінити ширину, стиль, `DisplayFormat`, `DisplayTemplate`, `IsHidden` | немає |
| Додати / змінити `ConditionalFormatDef` | немає |
| Додати `ValidationRule` із `Severity = Warning/Info` | попередження, не блокує |

### 🟢 Safe — адитивні, лише у `Draft`-версії

| Операція | Вплив на існуючі дані |
|----------|----------------------|
| Додати `SheetDef` | немає |
| Додати `TableDef` | немає |
| Додати `ColumnDef` (nullable, без `Required`) | нові комірки порожні |
| Додати `RowDef` | новий рядок порожній |
| Розширити тип (`Decimal(10,2)` -> `Decimal(18,4)`) | немає |
| Розширити довідник (додати значення) | немає — це взагалі дані, не структура |

### 🟡 Guarded — потребують стратегії і звіту про вплив

| Операція | Ризик | Обов'язкова стратегія |
|----------|-------|----------------------|
| Звузити тип (`String` -> `Decimal`) | значення, які не конвертуються | `OnConversionFailure`: `Fail` / `SetNull` / `KeepAsText` |
| `Decimal(18,4)` -> `Decimal(10,2)` | втрата точності / переповнення | те саме |
| Додати `IsRequired = true` | існуючі порожні комірки стають невалідними | `ApplyTo`: `NewDocumentsOnly` / `All` (документи -> `Draft`) |
| Додати `ValidationRule` із `Severity = Error` | затверджені документи стають невалідними | те саме |
| Змінити `LookupRegistryDefId` | значення поза новим довідником | `OnOrphanValue`: `Keep` / `Clear` / `MapVia(table)` |
| Зробити колонку обчислюваною (`Formula`) | ручні значення будуть перезаписані | `PreserveManualAsSnapshot` (зберегти в історію) |
| Прибрати значення з довідника | комірки посилаються на неіснуюче | soft delete значення (`IsAvailable = 0`) |

### 🔴 Breaking — заборонені у версії з документами

| Операція | Чому |
|----------|------|
| Видалити `ColumnDef` / `RowDef` / `TableDef` / `SheetDef` | втрата даних |
| Змінити `Code` (ідентифікатор) | розрив посилань у формулах, правилах, імпорті |
| Змінити `TableDef.LayoutKind` | повністю інша розкладка періодів |
| Змінити `ext.LegacyColumnMapping.LegacyFieldIndex` | розрив сумісності з PI AF (поле в адаптерній схемі, але наслідок — для round-trip даних) |
| Перенести `ColumnDef` в іншу `TableDef` | порушує інваріант належності комірки |

**Поведінка системи:** операція **відхиляється** (не попередження — відмова),
з повідомленням: *«Ця зміна неможлива у опублікованій версії. Створіть нову версію
через Clone і виконайте зміну там»*.

## 4. Звіт про вплив (Impact Report)

Перед застосуванням будь-якої зміни класу 🟡 або перед публікацією версії:

```
POST /api/versions/{v}/columns/{c}/analyze-impact
{
  "change": { "type": "NarrowType", "from": "String", "to": "Decimal(18,4)" }
}
```

Відповідь:

```json
{
  "changeClass": "Guarded",
  "affectedDocuments": 47,
  "affectedCells": 128430,
  "warnings": [
    { "code": "CONVERSION_FAILURE", "count": 312,
      "message": "312 комірок не конвертуються в Decimal",
      "samples": ["н/д", "-", "2,5 (прибл.)"] },
    { "code": "PRECISION_LOSS", "count": 89 }
  ],
  "requiresStrategy": ["OnConversionFailure"],
  "estimatedDurationMs": 45000
}
```

Користувач бачить це **до** застосування і обирає стратегію.
Без обраної стратегії операція не виконується.

## 5. Soft delete — дані ніколи не залишаються без структури

```sql
cfg.ColumnDef
  IsDeleted           bit        NOT NULL DEFAULT 0
  DeletedAt           datetime2  NULL
  DeletedBySid        nvarchar   NULL
  DeletedInVersionId  int        NULL
```

**Правило:** фізичне `DELETE` дозволене **лише** якщо
`NOT EXISTS (SELECT 1 FROM doc.CellValue WHERE ColumnDefId = @id)`.
Інакше — `IsDeleted = 1`.

**Поведінка «історичної» колонки:**
* у документах, де вона має дані — показується read-only з позначкою «архівна»;
* у нових документах — не показується;
* в експорті — опційно (перемикач «включати архівні поля»);
* у формулах — посилання на неї викликає помилку валідації при публікації версії.

FK з `doc.CellValue.ColumnDefId` -> `cfg.ColumnDef.Id` — `ON DELETE NO ACTION`.
Висячих посилань не буває **за побудовою**, а не за домовленістю.

## 6. Міграція документа на нову версію

Не автоматична. Явна операція з повним контролем.

```
POST /api/documents/{id}/migrate-to/{targetVersionId}?dryRun=true
```

### Алгоритм

```
1. ChangeSet = Diff(document.TemplateVersionId, targetVersionId)

2. Побудувати мапінг за правилом:
     ColumnDef(v1).Code == ColumnDef(v2).Code  →  перенести значення
     Code є тільки в v1                        →  дані «осиротіли»
     Code є тільки в v2                        →  нова порожня комірка

3. DryRun: сформувати звіт
     • комірок перенесено:      128 430
     • нових порожніх:            2 100
     • осиротілих (буде втрачено):  312   ← список із прикладами
     • конфліктів типів:              4
     • формул, що не резолвяться:     0

4. Показати користувачу. Без явного підтвердження — стоп.

5. ЗАСТОСУВАННЯ (одна транзакція):
     BEGIN TRAN
       snapshot ДО  →  doc.DocumentSnapshot (стиснутий JSON + hash)
       перенести значення за мапінгом
       осиротілі значення  →  aud.OrphanedValue (не видаляються, архівуються)
       створити відсутні комірки з DefaultValue
       перерахувати всі формули цільової версії
       прогнати повну валідацію
       IF будь-яка Error-валідація  →  ROLLBACK, повернути звіт
       Document.TemplateVersionId = targetVersionId
       Document.Status = Draft                  ← мігрований документ завжди чернетка
       aud.DocumentEvent += MigratedFromVersion
     COMMIT
```

**Гарантії:**
* атомарність — або весь документ, або жоден рядок;
* оборотність — snapshot «до» дозволяє відкотити навіть після commit;
* нічого не зникає безслідно — осиротілі значення в `aud.OrphanedValue`;
* мігрований документ **завжди повертається в `Draft`** і потребує повторного
  затвердження (бо структура змінилася — попереднє затвердження стосувалося іншої структури).

### Масова міграція

`MigrateProjectDocuments(projectId, targetVersionId)` — фонова задача Hangfire,
документ за документом, з окремою транзакцією на кожен.
Один невдалий документ не зупиняє решту; звіт у кінці.

## 7. Інваріанти цілісності та їх захист

| # | Інваріант | Domain | БД | Фонова перевірка |
|---|-----------|--------|-----|------------------|
| 1 | Опублікована версія **структурно** незмінна (презентаційні поля — виняток, §2a) | ✅ | тригер | ✅ |
| 2 | `CellValue.ColumnDefId` існує | ✅ | FK | ✅ |
| 3 | Колонка комірки належить таблиці її `TableInstance` | ✅ | computed + CHECK | ✅ |
| 4 | `TableInstance.TemplateVersionId` == `Document.TemplateVersionId` | ✅ | FK + денормалізація | ✅ |
| 5 | Тип значення відповідає `ColumnDef.DataType` | ✅ | — | ✅ |
| 6 | Обчислювані комірки == результат формул | ✅ | — | ✅ |
| 7 | `Approved`-документ не має `Error`-валідацій | ✅ | — | ✅ |
| 8 | `RowKey` унікальний у межах `TableInstance`; `(TableRowId, ColumnDefId)` унікальна | ✅ | UQ-індекси | — |
| 9 | Немає циклів у графі формул | ✅ (при `Publish`) | — | ✅ |

### Інваріант 3 — деталь реалізації

Комірка не має «випадково» опинитися в чужій колонці:

```sql
ALTER TABLE doc.CellValue ADD
  TableDefId AS (…)  -- денормалізовано з TableInstance при вставці
CONSTRAINT FK_CellValue_Column
  FOREIGN KEY (TableDefId, ColumnDefId)
  REFERENCES cfg.ColumnDef (TableDefId, Id)   -- складений унікальний ключ
```

Складений FK робить порушення **фізично неможливим**, а не «перевіреним у коді».

## 8. `ConsistencyCheckJob`

Щоночі, по одному проєкту за раз:

```
для кожного інваріанта з таблиці вище:
    виконати перевірочний запит
    розбіжності → aud.ConsistencyIssue (Severity, Entity, Id, Details)

якщо є Critical:
    сповістити SystemAdministrator (email / Teams)
    позначити проєкт прапорцем у UI
```

Запити пишуться як set-based SQL, не як цикли. Приклад для інваріанта 5:

```sql
SELECT TOP 1000 cv.Id, cd.DataType, cv.ValueString
FROM doc.CellValue cv
JOIN cfg.ColumnDef cd ON cd.Id = cv.ColumnDefId
WHERE cd.DataType = 2 /* Decimal */
  AND cv.ValueNumeric IS NULL
  AND cv.ValueString IS NOT NULL
  AND cv.IsEmpty = 0;
```

> **Це страховка від помилок у коді, а не заміна їм.**
> Якщо `ConsistencyCheckJob` щось знаходить — це баг, який треба виправити,
> а не «нормальний шум».

## 9. Кеш метаданих та інвалідація

Метадані шаблонів читаються на кожен запит -> кешуються в пам'яті.
Оскільки опубліковані версії **незмінні**, кеш стає тривіальним:

```csharp
// Ключ включає версію і презентаційну ревізію → інвалідація «сама собою»:
// структурний шар Published-версії не змінюється ніколи, а презентаційна
// правка просто дає новий ключ (старий запис відмирає по пам'яті)
var schema = await _cache.GetOrCreateAsync(
    $"schema:v{templateVersionId}:r{presentationRevision}",
    _ => _repo.LoadFullSchemaAsync(templateVersionId),
    absoluteExpiration: null);
```

Для `Draft`-версій — кеш із коротким TTL або без кешу
(редагує один адміністратор, навантаження мізерне).

**Це ще один аргумент за immutable versions:** вони прибирають цілий клас
проблем із когерентністю кешу між інстансами застосунку.

## 10. Чек-лист для розробника

При реалізації будь-якої операції над структурою:

- [ ] Операція класифікована (`Presentation` / `Safe` / `Guarded` / `Breaking`)?
- [ ] `Presentation` у `Published`-версії — застосовується без нової версії й інкрементує `PresentationRevision`?
- [ ] `Breaking` у `Published`-версії — відхиляється з зрозумілим повідомленням?
- [ ] `Guarded` вимагає явної стратегії?
- [ ] Є `AnalyzeImpact` до застосування?
- [ ] Застосування — в одній транзакції?
- [ ] Видалення — soft, якщо є посилання з даних?
- [ ] Записано в `aud.SchemaChange` (хто, що, звіт про вплив, підтвердження)?
- [ ] Є тест на кожен клас змін?
- [ ] Є тест «застосували -> відкотили -> дані незмінні»?
- [ ] `ConsistencyCheckJob` покриває новий інваріант, якщо він з'явився?
