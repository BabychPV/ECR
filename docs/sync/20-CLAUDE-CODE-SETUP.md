# 20 — Claude Code: що налаштовано і чому саме так

Довідка про механіку. Покрокове встановлення — у `SETUP-PK1.md` / `SETUP-PK2.md`
(лежать поза репозиторієм, у пакеті людини).

---

## Три рівні налаштувань, і вони не дублюють один одного

| Рівень | Файл | Що тримає | Хто править |
|---|---|---|---|
| репозиторій | `.claude/settings.json` | allow-список команд, спільний для обох вузлів | PK1 |
| машина | `~/.claude/settings.json` | `model` і deny на чужу зону | `scripts/install-node.ps1` |
| процес | `.githooks/*` | заборона коміта поза зоною | PK1 |

Логіка розподілу: allow-список у репозиторії потрібен, щоб **headless**-запуск
(`claude -p`) не зависав на першому підтвердженні команди. Deny на машині —
щоб роль вузла не залежала від того, що приїхало з git. Хуки — останній бар'єр,
який діє навіть якщо перші два обійшли.

⛔ Три рівні не про надмірність. Перші два — це те, що Claude Code **не буде**
робити; хук — це те, що git **не дасть** зробити. Різниця виявляється рівно
тоді, коли модель отримує переконливу інструкцію в тілі issue.

## `/cycle`

`.claude/commands/cycle.md` читає `.sync-local/NODE` і відсилає до відповідного
`PROMPT-PK*-CYCLE.md`. Один вхід на обидві ролі: окремі команди рано чи пізно
розійшлися б, і вузол виконував би чужий цикл, не помітивши.

---

## Планувальник

`scripts/sync-node-gh.ps1` під Windows Task Scheduler.

| Вузол | Інтервал | Чому саме так |
|---|---|---|
| PK1 | 25 хв | рев'ю не має бути миттєвим: виконавець мусить брати наступну директиву, а не чекати |
| PK2 | 5 хв | реагує на нову директиву швидко; черга порожня — виходить одразу, майже без витрат |

Скрипт **не запускає** Claude, якщо в черзі нічого немає. Це головний контроль
витрат: без цієї перевірки кожен тик коштував би повного циклу моделі.

Блокування — `.sync-local/<node>.lock`. Попередній прогін іще йде → тик
пропускається. Без цього два прогони працювали б на одному дереві.

---

## Перші прогони — руками

```powershell
.\scripts\sync-node-gh.ps1 -Force
```

Два-три рази, дивлячись у `.sync-local\pk1-*.log`, і лише потім вмикати задачу.
Причина проста: помилка в непідключеній задачі видна одразу, а в підключеній
проявляється як «нічого не відбувається», і шукати її будеш у процесі, а не в
скрипті.
