# Мокап «Permits» — перміти як джерело для аркушів

**Статус: МОКАП до погодження. Коду продукту немає.** Завдання людини 18.10 (через координатора):
універсальний механізм для пермітів і їхніх внутрішніх сутностей (таблиці з різною кількістю
стовпців), без коду, усе у вебі; перміт використовується в аркушах як **джерело**, а не як
довідник. Новий розділ бічної панелі «Permits» стоїть одразу після «Registries».

Мокап — екрани поверх набору гібридного макета ([`../hybrid/`](../hybrid/), [`KIT.md`](../hybrid/KIT.md)):
ті самі токени, світла й темна теми, ті самі компоненти. Дані — детерміновані демо, виведені з
файлів у `docs/source/Permits` (номери пермітів і рядки взято звідти; решта — синтетика).

## 1. Що таке перміт у джерелах

Джерела: `docs/source/Permits/UI` (розширення PI Vision: `sym-Permit-template.html`,
`sym-Permit.js`, `Permits_Template.xlsx` — шаблони AF) і три книги звітності
(`PermitsInfo.Year`, `…Waste.Year`, `…Water.Year`).

| У джерелі (AF / PI Vision) | Суть | У моделі нижче |
|---|---|---|
| `PermitDocument` | заголовок: номер, категорія, розташування (En/Ru), дати видачі / початку / кінця / фактичного кінця, 4 «Total_*», прапорці `Flert_300/301/302`, `TOx` | **шапка перміта**; «Total_*» — обчислювані, не поля; прапорці — група «Reporting forms» |
| `PermitEmissionValue` | викиди: речовина × площадка → т/рік, мг/нм³, г/с (6 стовпців) | таблиця `Emission limits` |
| `PermitWasteValue` | відходи: площадка × місце × код відходу → т/рік | таблиці `Storage places` і `Waste limits` |
| `PermitWaterDischargeValue` / `PermitWaterIntakeValue` | вода: водойма, коди, 5 приток, 4–6 дат, обсяги за якістю, **12 місяців**, річний обсяг (≈ 31–35 стовпців) | широкі таблиці `Discharge volumes`, `Intake volumes` |
| `PermitWaterEmissionValue` | ліміти речовин у стоках: речовина × випуск → концентрація, г/год, т/рік, витрата | таблиця `Limits by substance` |
| `PermitMetaData*` (Area, Location, IssueNumber, NameObject, WastePlace) + довідники речовин (повітря / вода / відходи) | словники | звичайні **реєстри** (Locations, Sites, Substances, WaterBodies, WastePlaces, WasteCodes, IssueNumbers) |
| «Water/Waste (Vessel) Report Constants» (адмін-дерева Group/Item/Balance/Note) | структура рядків звітів | **поза цим механізмом** — це рядки шаблону звіту |

Поведінка екстеншна, яку мокап зберігає: фільтр пікерів «Select Permit first» (вибір площадки/місця
лише з тих, що належать перміту), заборона видалення, поки на запис є посилання, попередження про
діапазон дат, режим «лише читання», річний звіт, імпорт/вигрузка в Excel.

## 2. Модель даних — розширення механізму довідників, не друга сутність

Опора: `ФВ-8` (`docs/tz/02-requirements.md`), `FEATURE-REGISTRY-TABLES.md` (складені ключі §4.1,
**композиція** master-detail §4.8, функції `REGFIND/REGONE/REGFIELD/REGSUM/REGCOUNT` §5.4, правила
довідника §6), `D-13/14/66` (EAV, DDL під час роботи не виконується), `N-1` («нова сутність поруч
із довідником» — не ціль).

```
PermitTypeDef  (Code, назви EN/RU/KZ, категорія, версія, Draft/Published)        ← нове: упаковка й UX
 ├─ шапка            → RegistryDef  AIR_PERMIT        (поля шапки; ключ: Тип+Номер)
 └─ таблиця N        → RegistryDef  AIR_EMISSIONS     (RelationKind = Composition → AIR_PERMIT)
                         └ RegistryFieldDef × довільна кількість (тип, одиниця, IsRequired, група)
                         └ RegistryKeyDef: ключ рядка = PERMIT + позначені стовпці (§4.8: конструктор пропонує сам)
Екземпляр перміта = RegistryEntry шапки;  рядок таблиці = RegistryEntry дочірнього довідника (батько = перміт)
Привʼязка         = PermitSheetBinding (версія шаблону, таблиця аркуша, тип+таблиця перміта, режим, правило вибору, зіставлення стовпців)
```

Чому так: різна кількість стовпців — це просто різна кількість `RegistryFieldDef`; жодного DDL;
унікальність, FK, `Orphaned`, «Де використовується», історія, імпорт, права, експорт — уже є для
довідників і працюють для пермітів без дублювання. **Нове** лише три речі:

1. **`PermitTypeDef`** — пакет «шапка + таблиці», що створюється, версіюється й публікується разом
   (кнопка *Publish* публікує всі повʼязані `RegistryDef` однією дією; користувач не бачить реєстрів).
2. **Життєвий цикл екземпляра** — `Draft → Active → Expired` поверх `ValidFrom/ValidTo` запису
   (півінтервал, `ФВ-8.5`); `Actual end` — звичайне поле; «Renew» створює копію з початком у день
   завершення; два активні перміти одного типу й номера з перетином дат заборонені.
3. **`PermitSheetBinding`** — привʼязка до аркуша (розд. 3).

Підсумки («Total_*» у джерелі) **не зберігаються**: довідник не має обчислюваних полів (`N-3`);
підсумок — `REGSUM` по рядках у момент читання, тож розбіжності з рядками бути не може. Правила
довідника (`§6`) дають перевірки типу «сума місяців = річний обсяг ±1 %» (у джерелах 320.517 проти
320.52 і 0.143 проти 0.14, тож допуск потрібен).

## 3. Перміт як джерело аркуша

Привʼязка належить **версії шаблону** (як і решта налаштувань аркуша). Два режими:

| Режим | Що робить | Приклад |
|---|---|---|
| **Rows from the permit** | таблиця аркуша отримує по рядку на кожен рядок таблиці перміта; ключові стовпці й **ліміт** заблоковані (штриховка), люди вводять лише факт; «% використання» — формула; перевищення — попередження до `Submit` | «Air emissions › Emission sources by substance» ← `Emission limits` |
| **Formulas only** | рядків не додається; комірки читають перміт функціями довідників | `REGSUM('AIR_EMISSIONS', ROW.PERMIT = [Permit], ROW.EMISSION_T_YEAR)` |

**Який перміт чинний.** За замовчуванням — перміт цього типу для об'єкта документа, чинний в
останній день періоду; при двох — пізніший початок. Альтернатива — пікер «Permit» у шапці аркуша
(комірка `Lookup`) для майданчиків із кількома пермітами одного типу. Закриті періоди читають той
перміт, що був чинний тоді (закриття запису, не видалення — `ФВ-8.6`).

Залежності від наявних механізмів: складені ключі й композиція (`RT-10b`, `RT-17a`…), `REG*` у
шаблонах і методологіях (`RT-24` і далі) — **перед стартом реалізації звірити стан кроків у
`docs/build/WORK-QUEUE.md`**; якщо чогось немає, перміти чекають на цей крок, а не дублюють його.

## 4. Бічна панель

Пункт **Permits** — у групі *Configure* одразу після *Registries* (`order 2.5` у мокапі; у
застосунку — окремий пункт навігації після «Довідників»). Усередині три розділи (смуга посилань
угорі сторінок): *Permits* (екземпляри), *Permit types* (конструктор), *Sheet bindings*. Права:
типи й привʼязки — як `TemplateAdministrator`; ведення пермітів — той, хто має запис у реєстри
(див. питання 8).

## 5. Припущення (діють до відповіді замовника)

1. Унікальність екземпляра — **(тип, номер)**: у джерелах номер `KZ06VCZ14825472` стоїть і в
   повітряному, і у відходному перміті.
2. Псевдоперміти джерел (`N/A`, `No Permit – Overlimit location`, `No Permit – Vessels`) —
   перміти-заповнювачі з ознакою «Placeholder» (мокап: `P-0008`), щоб викиди без дозволу теж
   мали рядки в аркуші.
3. Таблиця `Storage places` — окрема таблиця перміта (а не стовпець): так пікер місця фільтрується
   самим пермітом, як «Select Permit first» у PI Vision.
4. Ключі рядків водних таблиць (мокап): водойма + початок підперіоду (+ вид використання для
   водозабору; випуск для лімітів речовин). У джерелах ключа немає — рядки названі хешами AF.
5. Сума місяців проти річного обсягу — попередження з допуском 1 %.
6. Одиниця водних обсягів — `10³ m³` («тыс.м³» у джерелах).
7. Мова: стовпці мають назви EN/RU (KZ — так само, як у решти конструкторів).
8. Імпорт — «все або нічого» (рішення 12.10 для Excel-імпорту); формат — наявна річна книга.

## 6. Питання замовнику (лише факти, яких немає в джерелах)

Усі йдуть через координатора; блокувальних немає — діють дефолти з розд. 5.

| # | Питання | Дефолт до відповіді |
|---|---|---|
| 1 | Що означають прапорці `Flert_300/301/302` і `TOx` («Used in Reports»): до яких звітних форм входить перміт? Чи потрібні вони й далі? | група «Reporting forms» у шапці, чотири Yes/No |
| 2 | Чи псевдоперміти (`N/A`, `No Permit – …`) — постійний бізнес-механізм, і чи є інші такі? | так, перміти-заповнювачі |
| 3 | Чи можуть два перміти одного типу бути чинними одночасно на одному об'єкті? Як обирати, якщо так? | ні, у перетині дат — помилка; для винятків пікер у шапці аркуша |
| 4 | Чи «Total_Sulfur_Placement_t» ще потрібен (у книгах його немає)? Чи всі «Total_*» мають дорівнювати сумі рядків? | так, обчислювані; Sulfur — додати таблицю, якщо замовник підтвердить |
| 5 | Допуск розбіжності сум місяців і річного обсягу та рівень правила | 1 %, попередження |
| 6 | Що однозначно ідентифікує рядок у водних таблицях (водойма, підперіод, випуск, вид використання)? | ключі з розд. 5 п.4 |
| 7 | Одиниця водних обсягів і чи бувають інші | `10³ m³` |
| 8 | Хто веде перміти й хто — типи (ролі, люди) | типи — `TemplateAdministrator`; перміти — власники запису в реєстри |
| 9 | Чи лишається потрібним річний звіт «PermitsInfo.Year» (Excel) як вихід, чи досить імпорту? | імпорт у тому ж форматі; експорт — той самий формат |
| 10 | Чи «Report Constants» (дерева Group/Item/Balance/Note) мають лишитися окремою адмінкою, чи це рядки шаблону звіту? | поза цим механізмом |

## 7. Поза обсягом мокапу й першої версії

Звірка з PI AF і синхронізація (`SourceKind`, `ФВ-8.9`) — окрема тема; повні права на рівні
таблиць перміта; M:N між таблицями (`R-7` — довідник-зв'язка); автоматичний перерахунок аркушів
після зміни перміта (`D-39`: закриті періоди — ніколи, відкриті — явною дією); редактор формул
перевірок — той самий, що в реєстрах.

## 8. Що показує мокап, а що ні

Показує: усі екрани й стани (дані / порожньо / помилка), діалоги й майстри, широку таблицю, шторку
рядка, конструктор, привʼязку з переглядом аркуша, світлу й темну теми. Не показує: справжнє
збереження (дії змінюють демо-дані лише в межах сеансу), пошук по рядках усередині таблиці перміта,
порівняння версій типу, права доступу. Розбіжності з реальними форматами джерел названо в розд. 5–6.
