# Посібник адміністратора ECR Web

Для адміністратора застосунку, тобто того, хто видає права й веде довідники.
Встановлення описано в `docs/build/11-install-guide.md`, експлуатація сервера — в
`docs/admin/operations-runbook.md`.

Кожне твердження тут перевірено по коду. Джерело вказано в дужках. Позначка
**⚠ потрібне рішення замовника** означає, що код цього факту не знає.

## 1. Ролі й права

Каталог прав і вбудовані ролі засіває `src/Ecr.Infrastructure/Persistence/Sql/09-seed.sql`.
Сід виконується на **кожному** старті застосунку (`SeedRunner`, `StartupSequence.cs`) і лише
додає відсутні права, ролі й пари «роль–право». ⚠ Тому зняти право з вбудованої ролі не
вийде — на наступному старті воно повернеться; потрібен інший набір — створіть власну роль.
Виняток: прибрані з каталогу права (`Template.Migrate`, `Calculation.EditScript`,
`Report.MarkSubmitted`) сід видаляє разом із роздачами.

### 1.1. Вбудовані ролі

| Роль | Що має за замовчуванням |
|---|---|
| `SystemAdministrator` | усі безпечні права (`%`) **і десять небезпечних прав керування** (рішення людини 2026-10-11 і 2026-10-12, секція сіду `FP:sysadmin-rights`): `Security.ManageUsers`, `Security.ManageRoles`, `Security.Simulate`, `Integration.Manage`, `System.ManageNotifications`, `System.RunJob`, `Report.ViewCampaign`, `Calculation.Publish`, `Period.Reopen`, `Document.ChangeKey`. **Не** має `Report.EditDefinition` (лише `Approver`, `D-203`) |
| `TemplateAdministrator` | `Template.*`, `Registry.View`, `Calculation.View`, `Document.View`, `System.ViewHealth` |
| `PeriodAdministrator` | `Period.*` (крім небезпечного `Period.Reopen`), `Project.Manage`, `Document.View`, `System.ViewHealth` |
| `DataEntry` | `Document.View/Create/Import/Export/Submit`, `Template.View`, `Registry.View`, `Calculation.View`, `Report.Export` |
| `Approver` | `Document.View/Export/Reopen`, `Registry.View`, `Calculation.View`, `Report.*` без небезпечних (`ViewRegulatory`, `ViewSnapshot`, `BuildSnapshot`, `Export`) і окремим рядком — небезпечне `Report.EditDefinition` (`D-203`) |
| `Viewer` | `Document.View`, `Registry.View`, `Calculation.View`, `Report.ViewRegulatory`, `Report.Export` |
| `Auditor` | `Document.View`, `Registry.View`, `Calculation.View`, `Template.View`, `Integration.View`, `Report.ViewRegulatory`, `Report.ViewSnapshot` (без `Report.Export`), `Security.ViewAudit`, `System.ViewHealth` |
| `ReportViewer` | `Report.ViewRegulatory`, `Report.ViewSnapshot`, `Report.Export` (секція `SEC:RPT` сіду). Без ресурсного гранта Read на проєкт не бачить нічого. Стартова сторінка — «Report snapshots» (без `Document.View` перелік документів недоступний); перелік проєктів для вибору (`GET /api/v1/projects`) віддається і за `Report.ViewRegulatory` (FP-1) |
| `BootstrapAdministrator` | лише `Security.ManageUsers`, `Security.ManageRoles` |

⛔ Шаблонні роздачі сіду фільтруються `WHERE p.IsDangerous = 0` у самому `MERGE`.
Поіменні винятки — окремими `MERGE`: `BootstrapAdministrator` (`Security.ManageUsers`,
`Security.ManageRoles`), `Approver` (`Report.EditDefinition`, `D-203`) і `SystemAdministrator`
(десять прав: вісім адмін-прав керування 2026-10-11 і з 2026-10-12 ще `Period.Reopen`,
`Document.ChangeKey`; секція `FP:sysadmin-rights`). Решту небезпечних
прав (`Report.EditDefinition` для всіх, крім `Approver`)
адміністратор дає, **створюючи роль** із ними (п. 2.3); у журналі безпеки — подія
`DangerousPermissionsGranted`. Призначення групі AD ролі з небезпечними правами
(зокрема `SystemAdministrator`) вимагає підтвердження.

⚠ **BREAKING для адміністраторів (`D-285`, 2026-10-05).** Рівень гранта `Write` САМ
подання аркуша не дає (як і раніше), але тепер його складає право `Document.Submit`:
`Write` + `Document.Submit` = подання і відкликання автором.
Вбудована `DataEntry` і `SystemAdministrator` отримують право на наступному старті
застосунку (сід, секція `SEC:SUBMIT`). **Власні ролі** з `Write`, носії яких мають
подавати, права не отримують — видайте його ролі (`/admin/security`) або підніміть
рівень до `Submit`. Інтерфейс не бачить проєктних прав ролей з областю (`/me` віддає лише
глобальні), тому кнопка «Submit» **активна вже з рівня `Write`**, а рішення приймає сервер:
без права `Document.Submit` у проєкті документа він відповідає `403` з поясненням
(`deny.InsufficientGrantLevel.Submit`: потрібен `Submit` або `Write` + право).

**Повторний сід повертає право.** Пара `DataEntry` + `Document.Submit` засівається через
`MERGE … WHEN NOT MATCHED`, тож якщо адміністратор зняв право з `DataEntry`, наступний
старт поверне його; щоб прибрати назавжди — використовуйте Deny або власну роль.

**Known limitations (D-285).** Роль, **звужена аркушами чи періодами** (`D-214`), права
`Document.Submit` не дає: воно не входить до прав рівня документа (`Narrowable`), тож носій
такої ролі з `Write` на своєму аркуші отримує `403` (`InsufficientGrantLevel`) при поданні.
Щоб він подавав — видайте право окремою роллю без звуження або підніміть рівень до `Submit`.

**Вибір аркуша/таблиці/колонки в гранті (A1-05).** Адміністратор безпеки (`BootstrapAdministrator`)
має лише `Security.ManageUsers/ManageRoles` і не має `Template.View`, тож у «Security → Grants → Add
grant» для виду «Sheet/Table/Column» список шаблонів повертає `403`. Панель називає причину
(`grants.pickerForbidden`: потрібне `Template.View`), а не загальне «Could not load the list». Це
задум (мінімальна роль), не збій. Щоб видати такі гранти — дайте тому, хто їх видає, додатково роль
`TemplateAdministrator` (або будь-яку з `Template.View`: `DataEntry`, `Auditor`). Гранти на проєкт і
довідник цього права не потребують.

**Клон версії шаблону і гранти (A1-04).** Гранти на аркуш/таблицю/колонку прив'язані до Id версії
шаблону. «Clone version» копіює на нову версію за кодами **заборони (Deny) і дозволи рівня ≤ Read**;
дозволи вище Read (напр. колонка `Write`) **не копіюються** — видайте їх на новій версії заново.
Known limitations (не цього циклу): (а) заборона, додана на старій версії **після** клону, на
новій не діє — додайте її й на новій; (б) клон не переносить правила доступу до періоду
(заблоковані періоди на новій версії редагуються — перенастройте); (в) версії, склоновані
**до цього виправлення**, грантів не мають — перевірте заборони на їхніх проєктах.

## 2. Користувачі

### 2.1. Типи облікових записів

| Тип | Вхід | Ендпоінт |
|---|---|---|
| Windows (домен) | Negotiate/Kerberos, без пароля в ECR | `POST /api/v1/login/windows` |
| Локальний | ім'я + пароль, політика паролів ECR | `POST /api/v1/login/local` |

Вхід Windows вимикається ключем `Auth:EnableNegotiate` (дефолт `true`).

### 2.2. Первинне налаштування (bootstrap)

1. На старті застосунок створює запис `bootstrap` (роль `BootstrapAdministrator`, вимога
   змінити пароль при першому вході), лише якщо **одночасно**: запису `bootstrap` ще немає,
   немає активного доменного адміністратора (п. 4) і пароль задано (`BootstrapAdmin.Decide`,
   `EnsureBootstrapAdminHandler`). Наявний запис не змінюється ніколи: повторний пароль його
   не скидає. Без пароля — лише попередження в лозі старту.
2. Пароль береться з файлу `%ProgramData%\ECR\config\bootstrap.secret`. Застосунок
   **читає і видаляє** цей файл на кожному старті, навіть якщо пароль не знадобився. Файл пише `tools/deploy-ecr.ps1 -BootstrapPassword`.
   Запасний шлях — змінна оточення `ECR_Bootstrap__Password`.
3. Увійдіть як `bootstrap` (логін/пароль) і змініть пароль. Створіть роль із
   `Security.ManageUsers`, `Security.ManageRoles` (і потрібними небезпечними правами) —
   `POST /api/v1/roles`. Доменний користувач з'являється в переліку після свого першого входу
   Windows (без ролей) або створюється `POST /api/v1/users`. Призначте йому роль **особисто**
   (`PUT /api/v1/users/{id}/roles`), не через групу.
   ⚠ SID у `POST /users` набирається вручну і перевіряється лише за формою (`S-1-…`). Якщо в ньому
   помилка, Windows-вхід людини отримає `409 ECR-USR-0409` (`windowsSidMismatch`) зі СПРАВЖНІМ SID у
   тексті відмови; у журналі сервера — Warning з номером запису. Виправте SID цього запису
   (`PUT /api/v1/users/{id}/windows-sid`) — це можливо лише до його першого входу.
4. Запис `bootstrap` вимикається (не видаляється; подія `BootstrapAdminDisabled`), щойно
   з'являється **доменний** (Windows) адміністратор, який справді може адмініструвати:
   запис активний, не заблокований, **уже входив через Windows** (SID підтверджено входом),
   і має **особисте**, **безобласне**, **чинне сьогодні** призначення **активної** ролі з
   `Security.ManageUsers` (`DisableBootstrapAdminHandler`, `UserStore.HasActiveDomainAdminAsync`).
   Перевірка йде після `POST /users`, `PUT /users/{id}/roles` і після кожного Windows-входу.
   Тобто запис, створений через `POST /users`, вимикає `bootstrap` лише на своєму першому
   вході — до того помилка в SID, строкове призначення «з понеділка», роль з областю чи
   заблокований запис `bootstrap` не вимикають (S1-01, аудит 5). Роль, видана через групу AD,
   і локальний користувач його не вимикають.

⚠ **Пароль `bootstrap` не відновлюється на наявній базі.** Запис створюється лише раз, а
повторний `-BootstrapPassword` його не скидає (п. 1). Якщо доступ до `bootstrap` втрачено, а
доменного адміністратора ще немає, шляхів два: розгорнути **нову порожню базу**
(`deploy-ecr.ps1 -BootstrapPassword …` на новій БД — запис створиться заново) або, якщо дані
вже є, скинути пароль іншим носієм `Security.ManageUsers` (`POST /users/{id}/reset-password`).
Прямих SQL-правок `sec.[User]` не робіть: хеш — PBKDF2-HMAC-SHA512 (п. 2.4).

Технічний запис `svc-integration` створює сід. Його пароль випадковий і нікому не
відомий, ролей і грантів запис не має. Від його імені пише збір даних з AF.
**Не видаляйте і не вмикайте його для входу.**

| Блокування / розблокування | `POST …/users/{id}/lock`, `…/unlock` |
| Виправлення SID доменного запису, який ще не входив (X5-01) | `PUT …/users/{id}/windows-sid`; кнопка «Виправити SID» у переліку користувачів |
| Зміна власного пароля | `POST /api/v1/auth/change-password` |

⚠ Набір прав наявної ролі не редагується; вбудовані ролі не перейменовуються й не
видаляються (`ECR-SEC-0409`, `roleBuiltIn`). Щоб дати небезпечне право, створіть нову роль
(`POST /roles` або клон і нова роль) з потрібним набором і призначте її. Без ресурсного гранта
роль не відкриває жодного проєкту.

Обмеження:

- **Останній адміністратор** (активний незаблокований носій `Security.ManageUsers`): його не
  можна заблокувати, скинути йому пароль чи зняти/замінити його ролі так, що право зникає
  (`PUT /users/{id}/roles`) — `ECR-SEC-0409` (`lastAdministrator`,
  `UserAdministrationHandlers.cs`). Перевірка іде в тій самій транзакції під замком; bootstrap
  не виняток; групові призначення не рахуються (членство чужих сесій невідоме), а відновлення,
  якщо адміністраторів усе ж не лишилось, — нова порожня БД за рішенням людини. Захищається
  носій права `Security.ManageUsers`, а не роль `SystemAdministrator`. Строкове (обмежене в
  часі) призначення права керування користувачами при захисті останнього адміністратора не
  враховується: у рідкісному разі система відмовить консервативно (409).
- Блокування безстрокове, з обов'язковою причиною; знімається лише `unlock`.
- Не можна заблокувати себе чи скинути собі пароль (`cannotTargetSelf`).
- Після скидання пароля користувач мусить змінити пароль при вході (`ECR-PWD-0428`).
  Доки він цього не зробить, інші запити не пройдуть.

### 2.4. Політика паролів і блокування

Одна політика `Default` (`sec.PasswordPolicy`), лише для локальних записів. Діють
(`PasswordPolicyCheck.cs`): `MinLength` (дефолт 12), стеля 256 символів, заборона містити
ім'я входу (від 3 символів), заборона поширених паролів (вбудований список), новий ≠ чинний.
`RequireUpper`/`RequireDigit`/`RequireSpecial` і `ExpirationDays` у таблиці є, але код їх
**не застосовує** (`P-1`). Відмова — `ECR-PWD-0422` з причиною. Після `MaxFailedAttempts`
(дефолт 5) невдалих входів локальний запис блокується на `LockoutMinutes` (дефолт 15) —
`ECR-AUTH-0423`. Екрана й API для політики немає: змінити її можна лише SQL-оновленням
`sec.PasswordPolicy` (DBA). Хеш — PBKDF2-HMAC-SHA512, 200 000 ітерацій (`D-218`); старіші
хеші перехешовуються при вході.

Обмеження частоти: вхід (`/api/v1/login/*`) — `Security:RateLimit:LoginPermitPerMinute`
(дефолт 60 на IP-адресу); зміна пароля — `Security:RateLimit:ChangePasswordPermitPerMinute`
(дефолт 10 на користувача).

### 2.5. Групи AD

Ролі можна видати доменній групі: `GET`/`POST`/`DELETE
/api/v1/security/group-assignments` (`GroupAssignmentsController.cs`), право
`Security.ManageUsers`. `principal` — SID або `ДОМЕН\Група`; можна задати строк дії
(`validFrom`/`validTo`) і область (проєкти). Роль із небезпечними правами — лише з
`confirmDangerous: true`, інакше `409 ECR-SEC-0409`. Нова група діє для вже залогінених членів
з наступного входу; відкликання — негайно. ⚠ Роль із `Security.ManageUsers`, видана групою,
не вимикає `bootstrap` і не рахується як «останній адміністратор».
Користувач бачить власні групи на `/my-groups`. Цей екран доступний без прав, щоб
людина з порожніми екранами бачила причину.

⚠ **потрібне рішення замовника:** які домен і групи AD відповідають яким ролям.
Дефолту в коді немає.

Перенос на нову версію шаблону існує (ФВ-7.5): `GET`/`POST`
`/api/v1/documents/{id}/migrate-version`. Окремого права немає — потрібне
`Template.Edit` (`Template.Migrate` прибрано з каталогу, сід видаляє його з
наявних баз). Версія шаблону живе на проєкті, тож переноситься весь проєкт
разом. Режими: `Safe` і `Presentation`; `dryRun` дає сухий прогін зі звітом.
Відмови: `ECR-SCHM-0422` (втрата даних чи заборонена зміна), `ECR-DOC-0409`
(подані/затверджені аркуші або архівний проєкт).

Відоме обмеження переносу версії (`POST /documents/{id}/migrate-version`): перенос проєкту на нову версію шаблону блокується (422 `ECR-SCHM-0422`, `migrateGrantsNotMapped`), якщо на аркуші, таблиці чи колонці вихідної версії стоїть заборона (deny), якої немає за кодом у новій версії: адміністратор спершу знімає заборону. Список скопійованих/не змаплених грантів у dry-run не показується (планується). Після переносу версії шаблону з заборонами (deny) перезапустіть застосунок/інстанси, якщо потрібна негайність: кеш профілів процесний, інші інстанси до TTL (60 хв) профіль не скидають. Поточний процес скидає профілі користувачів із прямими ролями, що мають гранти на перенесені ресурси (стеля переліку 100 000); при перевищенні стелі або збої скидання скидається ВЕСЬ кеш профілів процесу (запис у журналі, рівень Warning), а перенос не відхиляється. Якщо скидання не вдалося, кеш переходить у стан fail-closed (dirty): профіль будується щоразу без кешування (ціна — продуктивність), відновлення — лише успішним повним скиданням (`InvalidateAll`) або перезапуском процесу; сигнал збою — лічильник `ecr.access_profile.invalidation_failures`.

**Перенос великого проєкту: маркер «міграція в процесі», відновлення, ручне зняття (рішення 21.10).**
Комірки, оформлення, рядки й індекс пошуку переносяться діапазонами по 5000 рядків `doc.TableRow` (≈ 15 тис. комірок),
кожен — окремим комітом; версію проєкту, шапку, склад аркушів, екземпляри таблиць, гранти й результати валідації
перемикає/видаляє остання транзакція (атомарно). Практично:
- **Маркер.** Поки перенос іде (і після обриву), у `doc.Project.ExternalSettingsJson` стоїть ключ `migratingTo` (цільова
  версія) разом з `planHash` (відбиток мапи), `startedAt`/`startedBy`, орендою `owner`/`leaseUntil` (10 хв, подовжується
  кожним діапазоном) і watermark `wmCellsPeriod`/`wmCellsHi`/`wmIndexHi`. Читання й запис документів проєкту (будь-який
  маршрут `/api/v1/documents/{id}/…`, `/api/v1/projects/{id}/…`) дають `409 ECR-DOC-4091`; сам `migrate-version` і
  `/jobs/{id}` (прогрес) доступні.
- **Обрив** (збій, Cancel, перезапуск процесу): проєкт лишається на СТАРІЙ версії під маркером. Єдиний шлях —
  ПОВТОРИТИ той самий перенос з тією самою мапою (колонки, рядки, Lookup шапки): повтор продовжує з watermark. Інша мапа —
  `422 ECR-SCHM-0422` (`migrateResumeMismatch`); інша ціль — `409 migrationInProgress`. Після збою оренда знімається
  одразу, після аварійного завершення процесу — спливає за ≤ 10 хв (до того повтор дістає 409).
- **Відкат — лише бекапом.** Зафіксовані діапазони не відкочуються (атомарність послаблено свідомо). Перенос від 500 000
  значень стартує тільки з `backupConfirmation` у запиті (шлях і/або час резервної копії; без нього `422
  migrateBackupRequired`); значення потрапляє в журнал безпеки (`DocumentVersionMigrationStarted`,
  `DocumentVersionMigrated`). Діалог переносу в інтерфейсі показує обов'язкове поле «Підтвердження бекапу», коли звіт
  сухого прогону показує від 500 000 значень (шлях, час або ідентифікатор резервної копії); введене значення
  записується в аудит початку й завершення переносу. API-шлях лишається чинним: `POST /api/v1/documents/{id}/migrate-version`
  з `async = true` і полем `backupConfirmation` у запиті apply.
- **Вплив на інших.** Зміна ключової колонки `CellValue` ескалує блокування до рівня таблиці на час діапазону (≈ 1,2 с на
  5000 рядків): PATCH інших проєктів під час переносу великого проєкту можуть чекати до ~1–3 с або дістати `409 lockTimeout`
  (повтор допомагає). 1 млн комірок ≈ 1,5 хв (виміряно на тестовій базі).
- **Ручне зняття маркера** (лише DBA, коли проєкт відновлено з бекапу або перенос визнано недоцільним; перед цим переконатися,
  що задача переносу не виконується): `UPDATE doc.Project SET ExternalSettingsJson = NULLIF(JSON_MODIFY(JSON_MODIFY(
  JSON_MODIFY(JSON_MODIFY(JSON_MODIFY(JSON_MODIFY(JSON_MODIFY(JSON_MODIFY(JSON_MODIFY(ExternalSettingsJson,'$.migratingTo',NULL),
  '$.planHash',NULL),'$.startedAt',NULL),'$.startedBy',NULL),'$.owner',NULL),'$.leaseUntil',NULL),'$.wmCellsPeriod',NULL),
  '$.wmCellsHi',NULL),'$.wmIndexHi',NULL), '{}') WHERE Id = <projectId>;` (інші ключі, напр. `CustomPeriodCount`, лишаються).
  Фільтр читачів оновлюється за ≤ 2 с.
- **Після зняття маркера й після RESTORE — не писати в проєкт.** Після ручного зняття маркера міграції (див. SQL вище) до
  повторної міграції, а також після RESTORE — у проєкт НЕ писати (PATCH комірок, подання, перерахунок, імпорт): інакше
  повторна міграція падає з `PK_CellValue` duplicate (частково перенесені комірки конфліктують з новими записами).

**Зміна довідника поля `Lookup` (ретаргет, `ФВ-8.12`).** Змінити чи прибрати
довідник-ціль наявного поля `Lookup` у визначенні довідника не можна, якщо крізь це поле
читають атрибути правила довідників, формули шаблонів чи версії методик: `422`
`ECR-REG-0422` «The link of field "{fieldCode}" cannot be changed: {total} rule(s),
formula(s) or methodology version(s) read attributes through it: {usedBy}. Change or
disable them first.» Число `{total}` — повне, а перелік `{usedBy}` містить лише тих
споживачів, яких автор має право бачити (правила недоступних йому довідників, формули без
`Template.View`, методики без `Calculation.View` не називаються; у відповіді API — поле
`hiddenCount`, до 20 елементів на сторінку). Тому перелік на екрані може бути коротшим за
число: решту знайде адміністратор із ширшими правами. Ключові поля й поля, у збережених
значеннях яких уже є посилання на записи, не ретаргетяться ніколи
(`relationKindImmutable`, `lookupRetargetInUse`).

**`REGFIELD(@Arg, …)` у методиці: спершу прив'язка, потім золотий тест.** Коли формула
методики читає поле запису, що прийшов аргументом із колонки-довідника
(`REGFIELD(@Stream, 'MW')`), довідник цього запису розрахунок бере з
**прив'язок** методики: з `Lookup`-колонок таблиць, до яких методику активно
прив'язано (`cfg.CalculationBinding`). У тексті формули коду довідника немає. Тому в
методики, яку ще **не прив'язано** до жодної таблиці, золотий тест і симуляція дають
`#REF` для такого виходу, а публікація відмовляє через розбіжність золотого набору
(«виходу не було»). Порядок дій такий: прив'язати методику до таблиці з потрібною
колонкою-довідником, потім проганяти тест і публікувати. Якщо прив'язка неможлива,
можна назвати запис через довідник літералом:
`REGFIELD(REGFIND('STREAM', @StreamCode), 'MW')`. Тоді довідник відомий з тексту
формули. (Рев'ю AN-38, P3-8.)

**Межі обчислення формули (RC5).** Одне обчислення формули обмежене двома незалежними
межами; перевищена будь-яка дає значення `#BUDGET`, яке не ловить `IFERROR`.
**Крок:** 20 000 кроків (вузол дерева = крок; читання комірок діапазону теж коштує
кроки). **Вкладеність:** 96 рівнів — це межа стека, і рахується лише *справжня*
вкладеність: дужки, аргументи функцій, гілки `IF`, правий операнд. **Плаский ланцюг
однотипних операторів** (`a+b+c+…`, `a-b-c`, `a*b`, `&`, `AND`, `OR`) вкладеності не
додає: його можна писати до ~1000 доданків (парсер: 1024 ланки; довжина формули
обмежена окремо), він коштує ~2 кроки на доданок. Формулу з
вкладеністю понад 96 публікація шаблону чи методики відхиляє з поясненням («формула надто
складна: глибина N, дозволено 96 — розбийте на кілька обчислюваних колонок»; шаблон —
`422 ECR-EXPR-0422`, ключ `expr.tooDeep`; методика — пункт `publish.problem.formulaTooDeep`),
редактор виразів показує те саме зауваження. Якщо вже збережена формула впирається в межу
під час експлуатації, правило валідації дає **Warning** `validation.rule.budget` («формула
завелика для одного обчислення: розбийте на кілька обчислюваних колонок»), а не голе `#BUDGET`.

### 3.1. Вигляд таблиць: ширина, порядок, умовне форматування (`ФВ-2.6`, `ФВ-2.7`, `D-234`)

Екран версії шаблону `/admin/templates/{id}/versions/{versionId}`.

**Ширина колонки за замовчуванням** (`ColumnDef.WidthPx`). Задається у формі колонки
чернетки («Default width, px») або в діалозі «Appearance» — він доступний і для
опублікованої версії, бо ширина — презентаційне поле (`ChangeClassifier.cs`). Право —
`Template.Edit`. Ціле число від 40 до 800 px; порожнє — типова ширина 140 px. Поза межами —
`422` `ECR-TMPL-0422` «Column width must be a whole number from 40 to 800 px…»
(`ColumnDef.cs`). Ширина, яку користувач сам задав у сітці, перекриває шаблонну, але не
змінює її (посібник користувача, п. 4.7). В Excel-експорт ширини не переносяться: колонки
підганяються під заголовки (`ExcelExporter.cs`).

**Порядок колонок і рядків.** Перетягування за ручку («Drag to reorder») або кнопки
«Move … up» / «Move … down» (клавіатурна альтернатива: Tab, потім Enter чи пробіл).
Порядок колонок можна міняти з `Template.Edit` і в опублікованій версії; порядок рядків —
лише в чернетці. Обидва йдуть через `PATCH /api/v1/template-versions/{id}/presentation`.

**Умовне форматування.** Кнопка «Conditional formatting» біля таблиці. Правило — одна
колонка, умова (Greater than, Greater than or equal to, Less than, Less than or equal to,
Equal to, Not equal to, Between, Is empty, Is not empty) і стиль: колір заливки, колір
тексту (`#rrggbb`) та/або жирний. Операнди — числа (кома дозволена), до 64 символів.
Правила застосовуються за порядком, діє перше, що збіглося. Перевірити правило можна
полем «Check on a value» до збереження.

- Змінювати правила можна лише в **чернетці** і з `Template.Edit`; опублікована версія
  незмінна (тригер БД). До 500 правил на версію.
- Одночасна правка іншим адміністратором — `409` `ECR-TMPL-0409` (`condFormatChanged`):
  перезавантажте правила й повторіть.
- Правила діють у сітці введення і в Excel-експорті (кнопка експорту завжди вмикає стилі).
- API: `GET`/`PUT /api/v1/template-versions/{id}/conditional-formats` (`PUT` — з `If-Match`).

Формул області `Cell` конструктор не приймає (`D-231`): лише `Column` або `Row`, інакше
`422` `ECR-TMPL-0422` (`formulaScopeInvalid`).

### 3.2. Зв'язки таблиць: `Rollup` і `Check` (`ФВ-2.12`, `D-230`)

Екран «Table relations»: кнопка на сторінці версії шаблону, маршрут
`/admin/templates/{id}/versions/{versionId}/relations`. Перегляд — `Template.View`;
створення, правка, видалення — `Template.Edit`. API:
`GET/PUT/DELETE /api/v1/template-versions/{id}/relations[/{code}]` (`PUT` — створити або
оновити за кодом).

- Опублікована (заморожена) версія: зв'язки не змінюються — банер «Published version:
  relations are frozen», `409` `ECR-TMPL-0409`. Клонуйте версію.
- Чернетка, за якою вже є документи: зміна виду або видалення — `409` `ECR-SCHM-0409`
  (`templateRelationBreaking`); додавання дозволене.
- Код: латиниця, цифри, `_`, до 64 символів, починається з літери; перейменувати не можна.
- «The relation is in force» вимкнено — зв'язок лишається в структурі (переживає
  клонування), але не діє.

**Діють лише два види.** `Rollup` і `Check` виконуються; `Mirror`, `Reference`, `Cascade`,
`Copy` і поле «When the source changes» зберігаються, але ні на що не впливають.

⚠ Формат полів «Row matching» і «Column mapping» нижче — **припущення розробки**
(рішення людини 2026-10-01 «реалізувати зараз»), у ТЗ схеми немає. Якщо замовник
назве свою, зміниться формат цих полів.

**Row matching** (`MatchJson`) — як рядок джерела знаходить рядок приймача:

```json
{"keys":[{"source":"FacilityCode","target":"FacilityCode"}]}
```

Рядки пов'язані, якщо збігаються всі пари ключових колонок (точне порівняння тексту);
порожній ключ не збігається ні з чим. `{}` — без ключів: усі рядки джерела йдуть в
**єдиний** рядок приймача (якщо в приймачі рядків більше одного, `Rollup` нічого не рахує).

⚠ Для `Check` те саме: без `keys` порівняння відбувається лише тоді, коли в приймачі **рівно один
рядок**; інакше «нічого не порівняно» і помилок немає. Невідомі поля (наприклад,
`{"by":"RowKey"}`) ігноруються й дають той самий порожній `keys`. Збереження такого зв'язку
не відхиляється (політика D-230); натомість панель валідації документа показує інформаційне
повідомлення «A Check without keys compares only when the receiving table has exactly one row…»
(не блокує ні збереження, ні подання).

**Rollup** — приймач агрегує джерело. «Column mapping»:

```json
{"sourceColumn":"Emission","targetColumn":"EmissionTotal","aggregate":"sum"}
```

- `aggregate`: `sum`, `avg`, `min`, `max`, `count`.
- `targetColumn` — колонка типу **Formula** у таблиці-приймачі: значення пише система,
  користувач його не править («The cell is computed», `ECR-CELL-4221`). Формула шаблону на
  цій колонці **не потрібна**: приймач активного зв'язку `Rollup` — повноцінне джерело
  значення для перевірки публікації (`ECR-TMPL-4226`, FP-5); фіктивна формула `0` не
  потрібна. Вимкнений зв'язок джерелом не є.
- `sourceColumn` числова (Int, Decimal, Formula, Calculated); для `count` — будь-яка.
- Порожні значення в агрегат не входять (`avg` — середнє непорожніх). Немає значень або
  немає відповідного рядка — порожньо (`count` — 0); порожній результат очищає раніше
  заповнену комірку. Результат округлюється до точності колонки приймача.
- Рахується під час перерахунку документа: фоновий після збереження комірок і синхронний
  при поданні аркуша. Лише в межах того самого документа й періоду; таблиці, якої в
  документі немає, зв'язок пропускає. Бачить результати формул того ж прогону, але
  ланцюги `Rollup` → `Rollup` не підтримуються.

**Check** — звірка без переносу значень. «Column mapping»:

```json
{"left":"Emission","right":"EmissionReported","tolerance":"0.5","toleranceKind":"abs","severity":"Block"}
```

- `left` — колонка джерела, `right` — колонка приймача, обидві числові.
- Відхилення `|left − right|`; допустимо `tolerance` (`abs`) або `tolerance × |right|`
  (`rel`). Типово: допуск 0, `abs`, `Warn`. Рядки з порожньою стороною або без пари не
  звіряються.
- Виконується кнопкою «Validate» в документі й під час подання аркуша. Знахідка — у панелі
  перевірки з кодом правила `REL-<код зв'язку>`, на колонці `right` приймача; збереженню
  комірок не заважає.

| `severity` | Як показано | Подання аркуша |
|---|---|---|
| `Block` | помилка | блокується: `ECR-SUB-4221` «…blocking validation error(s)» |
| `Warn` | попередження | лише після підтвердження користувачем (записується в аудит) |
| `Info` | інформація | не впливає |

⚠ **Відоме обмеження форми:** для виду `Check` поле «Column mapping» у формі вимкнене
(«Not applicable: Check is a cross-table rule…»), а сервер для `Check` його вимагає —
збереження відхиляється `422` `ECR-TMPL-0422` (`relationSpecInvalid`, причина `mapMissing`).
Поки форму не виправлено: заповніть «Column mapping», **доки** вид іще не `Check`, і лише
потім оберіть `Check` (вимкнене поле зберігає текст), або створіть зв'язок через
`PUT …/relations/{code}`.

Інші відмови збереження — `422` `ECR-TMPL-0422` «Relation "{code}": {detail}» з причиною
в `details.reason`: `columnMissing` (колонки немає в таблиці цієї версії),
`columnNotNumeric`, `targetNotFormula`, `aggregateUnknown`, `toleranceInvalid`,
`invalidJson` тощо. Зв'язок, збережений до появи перевірки з некоректним полем, під час
перерахунку мовчки пропускається — перевірте його, відкривши й зберігши ще раз.

### 3.3. Імпорт структури шаблону з Excel: консольна утиліта (`ФВ-2.10`, `ФВ-2.11`, `D-94`)

✎ 2026-10-12, рішення людини (квіз 6, п. 5): імпорт структури **лишається консольною
утилітою**, екрана «Імпорт» у `/admin/templates` не буде. Утиліта — `tools/Ecr.Bootstrap.Excel`
(коміт `d9f7d336`). Вона покриває обидві вимоги ТЗ: `ФВ-2.10` (bootstrap із чинного
`.xlsm`, обов'язковий звіт про відповідність, який підтверджує бізнес) і `ФВ-2.11`
(структура нового шаблону з довільного `.xlsx`). Інтерактивного майстра немає: імпорт
**напівручний**, рішення про нерозпізнане приймає людина за звітом.

**Що робить.** Читає книгу `.xlsx`/`.xlsm` (VBA не виконується і не читається) і з видимих
аркушів будує структуру: аркуш → таблиця → колонки (тип, масштаб, одиниця, формула) →
фіксовані рядки. **Дані комірок не імпортуються** (`D-94`: історичні дані йдуть лише з
дзеркал `dbo.AF_*`, `ФВ-15.4`). Книга спершу проходить ту саму перевірку безпеки пакета
(`XlsxSafetyGate`), що й імпорт даних у застосунку.

**Два режими.**

| Режим | Що робить | Що змінює в системі |
|---|---|---|
| Сухий прогін (типово) | читає книгу, пише звіт (і, за бажанням, план у JSON) | нічого |
| `--apply` | після чистого звіту пише структуру через HTTP API застосунку у **нову версію-чернетку** | створює (за `--template-code`) шаблон і чернетку версії |

Запис іде тими самими `PUT …/sheets|tables|columns|rows|formulas`, що й конструктор у
веб-інтерфейсі, тож діють усі правила застосунку: право, перевірка кодів, аудит, скидання
кешу метаданих. Прямого запису в `cfg.*` немає й не буде. **Публікацію версії (`ФВ-2.9`)
утиліта не робить** — її виконує людина після звірки звіту, правом `Template.Publish`.

**Передумови.**

- Книга, доступна утиліті локально. Для `--apply` — застосунок, доступний за HTTP(S), і
  обліковий запис із правом `Template.Edit` (у вбудованих ролях — `TemplateAdministrator`,
  `SystemAdministrator`). Вхід — локальний користувач або Windows-вхід процесу.
- Пароль **лише через змінну оточення** (`--password-env`); у командний рядок його не
  передають. Прапорців `-ConfirmStand` чи подібних запобіжників утиліта не має: захистом
  слугують сухий прогін за замовчуванням, заборона запису при помилках у звіті та те, що
  результат — чернетка, а не опублікована версія.
- Одиниці з книги мають існувати в каталозі сервера (`/admin/units`); утиліта читає його
  перед записом і відмовляє, якщо коду немає (див. «Помилки»).
- Запуск з клону репозиторію потребує .NET SDK 10: утиліта окремим пакетом у MSI не
  постачається (не доведено — перевірте склад вашого релізу).

**Команди.**

Сухий прогін, звіт поруч із книгою (`книга.import-report.md`) і план у JSON:

```powershell
dotnet run --project tools/Ecr.Bootstrap.Excel -- `
  --workbook C:\work\legacy\form.xlsx `
  --out-report C:\work\legacy\form.report.md `
  --out-plan C:\work\legacy\form.plan.json
```

Запис у нову чернетку наявного шаблону (локальний користувач; пароль — зі змінної):

```powershell
$env:ECR_IMPORT_PASSWORD = Read-Host 'Пароль'
dotnet run --project tools/Ecr.Bootstrap.Excel -- `
  --workbook C:\work\legacy\form.xlsx --apply `
  --api https://ecr.example --version 2.0.0.0 --lang en `
  --template-id 12 `
  --user template.admin --password-env ECR_IMPORT_PASSWORD
```

Створення нового шаблону й вхід від імені Windows-користувача процесу:

```powershell
dotnet run --project tools/Ecr.Bootstrap.Excel -- `
  --workbook C:\work\new\form.xlsx --apply `
  --api https://ecr.example --version 1.0.0.0 `
  --template-code AIR_FORM --template-name "Повітря" --windows
```

(`ecr.example`, імена, коди й шляхи вище — умовні.)

| Параметр | Значення |
|---|---|
| `--workbook` | книга (обов'язковий) |
| `--out-report`, `--out-plan` | куди писати звіт Markdown і план JSON; звіт типово — `<книга>.import-report.md` |
| `--row-mode auto\|fixed\|dynamic` | як визначати рядки таблиці; `auto` — фіксовані, якщо перша колонка містить підпис у кожному рядку, інакше динамічні |
| `--layout PerPeriodInstance\|Static\|MonthsInColumns\|MonthsInRows` | розкладка періодів для всіх таблиць; типово `PerPeriodInstance` (12 колонок-місяців утиліта розпізнає сама → `MonthsInColumns`) |
| `--apply` | запис (взаємовиключний з `--dry-run`, який є типовою поведінкою) |
| `--api`, `--version` | адреса застосунку (абсолютна) і номер нової версії `Major.Minor.Patch.Build` |
| `--template-id` / `--template-code` + `--template-name` | рівно одне з перших двох: наявний шаблон або код нового |
| `--lang` | мова каталогу, якою записуються назви (`ru`, `en`, `kk`); **типово `ru`** — задайте іншу, якщо книга не російськомовна |
| `--user` + `--password-env` / `--windows` | спосіб входу |

**Що утиліта визначає сама, а що лишає людині.**

- Межі таблиць, у порядку довіри: таблиці Excel, іменовані діапазони, і лише за їх
  відсутності — блоки рядків, розділені порожнім рядком (це здогадка, кожна така
  таблиця йде у звіт на звірку).
- Одиниця — із заголовка колонки (`«Викид, т/рік»`, `«Витрата (м³)»`, `«Маса [кг]»`) за
  каталогом; неоднозначні позначення (`год`, `%`, `МВт`) і невідомі коди не вгадуються:
  колонку створено **без одиниці**, місце названо у звіті (`ФВ-16.12`).
- Формули: переказуються лише однозначні (посилання на комірки того самого рядка таблиці,
  функції `SUM`, `AVERAGE`, `MIN`, `MAX`, `COUNT`, `ROUND`, `ABS`, `PRODUCT`, `IF`, `IFERROR`).
  `VLOOKUP`, `DATE`, `TEXT`, посилання на інші рядки чи аркуші — у звіт для ручного
  рішення; колонка створюється як `Decimal` лише для читання, формулу задають у
  конструкторі.
- Типи колонок — за значеннями комірок (`Decimal`, `Date`, `Bool`, `String`; змішані →
  `String` із пунктом у звіті). Випадний список (`DropdownList`) не відновлюється — ручне
  рішення.
- Розбір VBA `MapAttributes` до утиліти не підключено (клас `VbaMapAttributesParser` є,
  але з `Program` не викликається): параметра `--vba` немає.

**Звіт про відповідність** (Markdown): результат прогону; лічильники; розділи «Помилки» (запис
заборонено), «Потребує ручного рішення» (імпорт не вгадує); чек-лист звірки кожної таблиці
(`- [ ]`, адреса діапазону в книзі, звідки взято межі); перелік колонок із типом, одиницею й
формулою; довідка про автоматичні рішення. Приймання — **людиною на файлі замовника**
(`contracts/trace-exempt.md`, `ФВ-2.10`/`ФВ-2.11`): ТЗ вимагає, щоб бізнес підтвердив звіт.

Приклад підсумкового рядка в консолі (числа умовні):

```text
сухий прогін; нічого не записано. Аркушів 3, таблиць 7, колонок 52, рядків 40; помилок 0, ручних рішень 5. Звіт: C:\work\legacy\form.report.md
```

**Коди виходу:** `0` — успіх (сухий прогін без помилок або запис виконано); `1` — у звіті є
помилки, нічого не записано; `2` — неправильні аргументи (повідомлення і довідка в stderr);
`3` — сервер відмовив чи недоступний під час запису.

**Після запису.** Утиліта лише повідомляє `шаблон N, версія-чернетка M`. Далі: відкрити
чернетку на `/admin/templates`, пройти по чек-листу звіту, закрити пункти «ручного
рішення» (одиниці, формули, колонки-місяці, випадні списки), опублікувати. Збій
посеред запису лишає **частково заповнену чернетку** — її id у повідомленні; видаліть її
або допишіть вручну; поведінку повторного `--apply` з тим самим `--version` не перевірено
(не доведено) — краще спершу прибрати чернетку чи взяти новий номер версії.

**Обмеження.**

- Лише структура; даних із книги утиліта не бере (`D-94`).
- Ручні рішення неминучі: «нерозпізнане» — це пункт звіту, а не автоматична здогадка
  (`tz/09` §9.4).
- Екрана й API окремого імпорту немає: утиліта користується звичайними ендпоїнтами
  конструктора шаблонів. Для браузерних клієнтів діє перевірка origin (`CsrfOriginMiddleware`);
  утиліта не браузер і заголовків `Sec-Fetch-Site`/`Origin` не шле, тож її це не зачіпає.
- Назви записуються однією мовою (`--lang`); інші мови додають у конструкторі.
- Автоматичного тесту «книга → чернетка → публікація» на живій системі в CI немає
  (юніт-тести утиліти — `tests/Ecr.Bootstrap.Tests`); `smoke.ps1` структуру шаблону
  утилітою не створює.

Посилання на ТЗ: `docs/tz/02-requirements.md` (`ФВ-2.10`, `ФВ-2.11`, `ФВ-2.9`, `ФВ-16.12`),
`docs/tz/10-decisions.md` (`D-94`), `contracts/trace-exempt.md` (приймання `ФВ-2.10`/`2.11`).

### 5.1. Розклади збору

Розклад належить **сутності джерела**, не з'єднанню: одна сутність — один розклад
(`ext.CollectionSchedule`, унікальний `SourceEntityId`; другий — `409 ECR-JOB-0409`
`collectionScheduleExists`). Право — `Integration.EditSchedule` (типово SysAdm); воно
потрібне навіть для перегляду переліку.

**Де:** `/admin/sources` → шухляда з'єднання → вкладка «Розклад» (перелік розкладів цього
з'єднання з колонкою «Залежить від» і форма для вибраної сутності). Без
`Integration.EditSchedule` вкладка показує відмову 403.

**API** (`CollectionSchedulesController.cs`): `GET /api/v1/collection-schedules?dataSource=<код>`;
`POST` (`sourceEntityId`, `cron`, `isEnabled`, `lookbackDays`, `dependsOnScheduleId`) — 201;
`PUT /{id}` (`cron`, `isEnabled`, `lookbackDays`, `dependsOnScheduleId`, `clearDependency`) і
`DELETE /{id}` — обидва з обов'язковим `If-Match: <rowVersion>`. Без нього — 422
(`collectionScheduleIfMatch`), із застарілим — `409 ECR-JOB-0409` (`collectionScheduleChanged`).

**Формат cron — Quartz, 6–7 полів:** `секунди хвилини години день-місяця місяць день-тижня [рік]`,
рівно одне з полів дня — `?`. Приклади: `0 0 * * * ?` — щогодини о хх:00; `0 30 1 * * ?` —
щодня о 01:30. П'ятипольний Unix-cron недійсний. Довжина ≤ 100 символів. Час — локальний
час ОС сервера застосунку, не пояс проєкту (runbook, п. 4).

**Вікно перекриття** `lookbackDays` — 1…366, типово 7: кожен прогін перечитує
`[зараз − N діб; зараз]`; ідемпотентність за природним ключем не дає подвоїти точки.
Пропущені інтервали до 45 діб збирає наздоганяння. Один прогін обмежено 15 хв: що не
встигли прочитати, піде в наздоганяння.

**Застосування:** правка й вмикання/вимикання діють одразу, без перезапуску (на вузлі, що
прийняв запит; про кілька вузлів — нижче). Якщо планувальник не прийняв розклад, він усе
одно збережений, а відповідь — 422 `collectionScheduleNotApplied` з причиною в `LastError`.
Недійсний cron з API не зберігається (422 `collectionScheduleCron` / `…CronLength`). Рядок
із недійсним cron, що потрапив у базу в обхід API, на старті пропускається з помилкою в лозі
й у `LastError` (на вкладці — «не поставлено»). Розклад для власної форми ECR
(`SourceKind = Local`) заборонено (422 `scheduleForLocalEntity`). У планувальник ставиться
не більше 1000 увімкнених розкладів, решта — з помилкою в лозі. Усі зміни пишуться в журнал
аудиту інтеграції (старий/новий cron, вмикання, вікно, залежність).

⚠ **Кілька вузлів `EcrApi`:** розклади живуть у пам'яті кожного процесу, тож правка,
вимкнення чи видалення розкладу доходить до інших вузлів лише після їх перезапуску (висновок
із коду, `CollectionScheduleApplier`; на стенді не відтворено). Після зміни розкладів
перезапустіть `EcrApi` на решті вузлів.

**Відмови збору:** недоступне джерело чи перевищення 15 хв — прогін `Degraded`, задача
успішна, діапазон іде в наздоганяння. `401`/`403` — задача `Failed` і негайний алерт.
Транзієнтні відмови (`ECR-INT-0503`) повторюються до 3 разів (30 с, 60 с, 120 с). Журнал
прогонів і події покриття — `/admin/sources` (`GET /api/v1/collection-runs`,
`…/coverage-events`).

**Адреса SQL-джерела (PiSqlClient, ODBC):** політика адреси (`DataSourceEndpointPolicy`) приймає
лише ASCII-хост (без `/` і керівних символів); хост з не-ASCII літерами (наприклад, кириличне
NetBIOS-ім'я) завжди дає `422 ECR-REQ-0422` `dataSourceEndpointMalformed`. У полі «Endpoint»
вказуйте IP-адресу або punycode-ім'я (`xn--…`). Зіпсований рядок з'єднання вже наявного джерела
дає недоступне джерело `ECR-INT-0503` `connectionStringBroken` без тексту внутрішньої помилки:
у повідомленні лише код джерела та кореляція, подробиці — в журналі сервера.

### 5.2. Залежності розкладів (ФВ-13.15)

Розклад може залежати від іншого розкладу **того самого з'єднання**: поле «Залежить від
розкладу» у формі, в API — `dependsOnScheduleId` (зняти — `clearDependency: true` або
порожній вибір у формі).

**Перевірки при збереженні** (усі — 422 `ECR-REQ-0422`): розкладу-залежності не існує
(`collectionScheduleDependencyNotFound`); він належить іншому з'єднанню
(`collectionScheduleDependencyOtherSource`); залежність замикає цикл, зокрема сам на себе
(`collectionScheduleDependencyCycle`; ланцюг довший за 50 ланок теж вважається циклом).

**Як працює** (`CollectionSchedule.IsDependencyMet`, `CollectionJob.cs`). Перед **плановим**
запуском (тик cron) збір порівнює час останнього прогону свого розкладу і розкладу-залежності:

- залежність відпрацювала не раніше, ніж цей розклад востаннє, — збір іде;
- інакше запуск **пропускається**: задача в `/admin/jobs` завершується успішно з текстом
  «пропущено, чекає успішного прогону розкладу N», а в журналі подій покриття з'являється
  подія `SkippedDependency` («Очікує залежності», не частіше разу на годину на розклад);
- наступний тик cron перевіряє знову. Пропуск — затримка, не втрата: вікно перекриття й
  наздоганяння доберуть пропущене.

**Не блокує ніколи:** ручний збір кнопкою «Зібрати»; запуск із явним вікном (наздоганяння,
`fromUtc`/`toUtc`); розклад-залежність вимкнений, ще жодного разу не бігав або не бігав
понад **48 годин**; сам цей розклад ще жодного разу не бігав.

**«Успішний прогін» залежності** — будь-який, що завершився без помилки задачі, зокрема
`Degraded` (джерело недоступне чи 15-хвилинний ліміт) і ручний. Прогін `Failed` (відмова
автентифікації `401`/`403`, правило даних, збій сховища, скасування) час останнього прогону
**не** оновлює: залежний розклад чекає, доки залежність не відпрацює, але не довше 48 годин
від її останнього успіху.

**Видалення** розкладу, від якого хтось залежить, дозволене: у залежних залежність
знімається автоматично (без окремого запису в журнал аудиту інтеграції).

**Порада** (висновок із коду, не вимога ТЗ): ставте cron залежного розкладу пізніше за cron
залежності із запасом, не меншим за тривалість її прогону (до 15 хв). Порівнюється **час
старту** прогонів, тож за однакового cron порядок випадковий: залежний може піти зі старими
даними залежності або пропустити тик.

## 12. Q-17: консолідація місячних стовпців (`D-457`)

Для таблиць `MonthsInColumns` Monthly-проєктів кожна введена комірка має ОДНОГО власника: місячний стовпець M{m}
живе в екземплярі періоду (рік, m), введений не-місячний стовпець — в «якорі року» (найменший період календаря
проєкту цього року). Раніше однакові значення лежали копіями в екземплярах усіх місяців. Перенесення зводить
копії до власника, не змінюючи схеми (EF-міграцій немає). Скрипти: `tools/q17/` — `Preview-MonthColumnConsolidation.sql`
(один T-SQL: Preview / Apply / Purge) і `Apply-MonthColumnConsolidation.ps1` (запобіжники й запуск).

Правила вибору значення для комірки (документ, рік, таблиця, RowKey, стовпець):

1. Значення власника, якщо воно непорожнє, лишається. Інші відмінні непорожні копії — **конфлікт** (лише у звіті).
2. Власник порожній — береться «останнє введене» серед копій: максимум `aud.CellChange.ChangedAt` для цієї комірки
   (`Origin` не `Recalculation`, `NewValue` не `NULL`), далі `TableRow.ModifiedAt`, далі період, найближчий до власника,
   далі менший період.
3. Похідні комірки (`IsCalculated = 1`) не переносяться.
4. Склад рядків: об'єднання живих `RowKey` по всіх копіях; якір і кожен наявний екземпляр одержують відсутні рядки
   (дзеркала). Відсутній екземпляр власника створюється з усіма рядками.
5. Власник, заблокований станом (`wf.ApprovalState` = Submitted/Approved для аркуша й періоду, або період `Closed`), —
   лише звіт `lockedTargets`; запис у такого власника — окреме рішення (`-IncludeLockedTargets`, лічильник `writtenToLocked`).
6. Період власника без рядка в `doc.Period` — звіт `noPeriodRow`, локальна копія лишається.
7. Запис: `aud.CellChange` з `Origin = 'Migration'`, `CorrelationId = <runId>`, `PeriodKey` власника. Транзакція — на документ.
   Повторний запуск нічого не змінює (ідемпотентність).

### 12.1. Порядок робіт

Усі кроки — на **копії** бази, поки не збіглися звіти; на живу базу — лише за окремим словом людини.

1. **Бекап.** `BACKUP DATABASE [<база>] TO DISK = N'<шлях>.bak' WITH COPY_ONLY, INIT, COMPRESSION` (шлях має бачити служба
   SQL Server). Скрипт сам перевірить `RESTORE VERIFYONLY`, що в заголовку саме ця база й що бекап не старший за 48 год
   (`-BackupMaxAgeHours`).
2. **Пауза джобів.** Зупиніть фонові задачі, що пишуть комірки або читають їх для розрахунку: `ConsistencyCheck`, перерахунок
   (`FormulaRecalculation`), `SourceEventSync`, збір (`Collection*`), імпорт Excel; користувачі не редагують. Підтвердження —
   прапор `-JobsPaused` (без нього Apply відмовляє).
3. **Preview** (лише читання). Без режиму скрипт друкує лічильники й пише CSV:
   `powershell -File tools\q17\Apply-MonthColumnConsolidation.ps1 -Server localhost -Database <база> -OutDir <каталог>`
   (`-DocumentId`, `-Year` звужують обсяг). Той самий T-SQL можна відкрити в SSMS: за замовчуванням він у режимі Preview.
   Лічильники: `copyPlanned`, `conflicts`, `stillEmpty`, `noPeriodRow`, `lockedTargets`, `mirrorRowsToCreate`,
   `anchorRowsToCreate`, `ownerInstancesToCreate`. Детальні CSV: `*-conflicts.csv` (документ, рік, таблиця, RowKey,
   стовпець, значення по періодах із `ChangedAt`, вибране, причина), `*-noPeriodRow.csv`, `*-lockedTargets.csv`.
4. **Рішення людини** по конфліктах і заблокованих власниках. Конфлікти Apply не чіпає (власник виграє; якщо власник
   порожній — виграє остання введена копія). Заблоковані власники без `-IncludeLockedTargets` не пишуться.
5. **Apply:**
   `powershell -File tools\q17\Apply-MonthColumnConsolidation.ps1 -Server localhost -Database <база> -Apply -JobsPaused -ConfirmBackup <шлях>.bak -OutDir <каталог>`
   Скрипт друкує «ДО» (Preview) → запис → «ПІСЛЯ» (Preview). У «ПІСЛЯ» `copyPlanned`, `mirrorRowsToCreate`,
   `anchorRowsToCreate`, `ownerInstancesToCreate` мають бути 0 (залишок — лише заблоковані цілі, видалені рядки
   власника, `noPeriodRow`). База `EcrLandUi` вимагає ще й `-AllowLive` — це рішення людини, агенти його не вмикають.
6. **Перерахунок.** Скрипт його не запускає. Для кожного зміненого документа (список — `*-run-perDocument.csv`,
   колонка `copiesWritten` > 0) виконайте перерахунок: `POST /api/v1/documents/{id}/recalculate` по періодах (готовий
   інструмент — `tools\land\Invoke-LandRecalc.ps1`, режим плану й `-Execute`). Порівняйте суми методологій «до/після».
7. **Прапор маршрутизації.** ⛔ СПЕРШУ накотіть процедуру вʼюх на базу — ПЕРЕД рестартом нового API, навіть якщо прапор
   лишається вимкненим: `sqlcmd -S <сервер> -E -C -b -I -d <база> -i <каталог розгортання>\Sql\05-rpt-views.sql`

### 12.2. Відкат

Перенесення не має зворотного скрипта: відкат — `RESTORE DATABASE` із бекапу кроку 1
(`RESTORE DATABASE [<база>] FROM DISK = N'<шлях>.bak' WITH REPLACE, RECOVERY` після `ALTER DATABASE ... SET SINGLE_USER WITH ROLLBACK IMMEDIATE`),
далі вимкнути `Collection:MonthColumnRouting`. Дані, введені користувачами ПІСЛЯ бекапу, при відкаті втрачаються, тому
між кроками 1 і 7 користувачів до бази не допускають. Помилка посеред Apply відкочує лише поточний документ; уже
завершені документи лишаються — прогін можна повторити (він ідемпотентний).
