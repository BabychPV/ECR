# Runbook: пошта (SMTP) і сповіщення

✎ 2026-10-01, `D-263` (рішення людини): SMTP і правила сповіщень налаштовує
адміністратор у самому застосунку, а не конфігурацією розгортання. Адресати —
ролі й адреси, іменних осіб у налаштуваннях немає (`D-262`).

⚠ Назва міграції `D256SmtpSettingsAndChannelRoles` і позначки «D-256» у коді
історичні; запис реєстру для SMTP — `D-263` (`docs/tz/10-decisions.md`).

Усе нижче звірено з кодом `dev/integration` (2026-10-02). Подій із шаблонами листів
зараз дві (відкриття періоду і початок пільгового строку); інших нагадувань за
розкладом у коді немає — з'являться, цей документ доповнюється.

## 2. Налаштувати SMTP

Панель «SMTP (outgoing mail)». Таблиця `sys_ecr.SmtpSettings`, один рядок.

| Поле (en) | Що вводити | Перевірка при збереженні |
|---|---|---|
| Server | ім'я хоста або IP, без схеми, шляху й порту | обов'язкове для ввімкнених; ≤ 255; link-local та імена метаданих хмари заборонені, приватні й loopback-адреси дозволені (внутрішній релей). ⚠ Порт у полі «Server» (`host:25`) перевірка не відхиляє, але з ним проба впаде «DNS» — порт лише в полі Port |
| Port | 1–65535, дефолт 587 | |
| Encryption | `STARTTLS` (дефолт) або `None` | ⚠ неявного TLS (порт 465) немає: потрібен сервер зі STARTTLS або без шифрування |
| Sender address | адреса відправника | обов'язкова для ввімкнених (заповнена — перевіряється й для вимкнених); одна адреса ≤ 254 символи: без імені-відображення, лапок, `[ ]` (доменних літералів), пробілів і керівних символів; локальна частина ≤ 64, мітка домену ≤ 63, без кінцевої крапки й дефіса на краю мітки (`SmtpSettings.IsValidAddress`) |
| Sender name | необов'язкове | ≤ 100 |
| Authentication | `None` або `Login and password` | для пароля потрібні логін і пароль |
| Login, Password | облікові дані поштової скриньки | логін ≤ 254 символи; пароль write-only (п. 2.2). ⚠ Пароль без шифрування заборонено: `Authentication: Login and password` з `Encryption: None` дає `422` («Password authentication needs encryption»). Змінили сервер, порт, шифрування чи логін — введіть пароль заново, збережений на нову адресу не переноситься (`422`, підсвічено поле пароля) |
| Use these settings | вмикає налаштування | вимкнені можна зберегти неповними як чернетку |

Порядок:

1. Отримати від служби пошти замовника: сервер, порт, режим (STARTTLS чи без
   шифрування), адресу відправника, спосіб входу. Для `None` сервер має
   приймати пошту від хоста застосунку без логіна (анонімний релей за IP).
   ⚠ Інтегрована (Windows/NTLM) автентифікація більше НЕ підтримується:
   облікові дані облікового запису служби `EcrApi` на SMTP-сервер не
   надсилаються ніколи (ні з адмін-налаштувань, ні з `Smtp:*`). Лишаються
   логін і пароль через STARTTLS або анонімний релей (`Authentication: None`).
2. Заповнити поля, увімкнути «Use these settings», «Save SMTP settings».
   Помилка поля — `422` «The SMTP settings are not valid: check the field "…"»
   з назвою поля (`host`, `port`, `from`, `fromName`, `auth`, `mode`).
3. Перевірити рядок стану над формою:
   - «In use: the settings below.» — діють налаштування з бази;
   - «In use: the process configuration (Smtp:*).» — у базі вимкнено або
     неповно, працює запасний шлях (п. 2.3);
   - «Mail is not configured: events stay queued.» — пошти немає (п. 5).
4. Надіслати пробу (п. 2.4).

### 2.1. Коли зміни починають діяти

Ефективні налаштування кешуються в кожному процесі на **30 с**. Процес, що
прийняв збереження, скидає кеш одразу; інші вузли й процеси підхоплюють зміни
протягом 30 с. Перезапуск не потрібен.

### 2.2. Пароль

- Пароль не повертається жодною відповіддю API і не показується на екрані:
  лише «A password is stored. Leave empty to keep it.» / «No password stored yet.».
- Порожнє поле при збереженні — пароль не змінюється. Прибрати —
  «Remove the stored password». Перемикання на `Authentication: None` теж
  стирає пароль.
- Зберігається зашифрованим Data Protection (purpose `Ecr.Smtp.Password.v1`).
  Без ключів кільця (втрата бекапу `sec.DataProtectionKey` чи видалений старий
  сертифікат, `https-certificate.md` §9, `operations-runbook.md` п. 6.4) пароль не
  розшифрується: проба дає загальне «The channel refused the test message.», у
  журналі доставок — `Failed` з помилкою розшифрування. Введіть пароль наново і
  повторіть пробу. Пароль запасного шляху (`Smtp:SecretName`) від Data Protection
  не залежить.

### 2.3. Запасний шлях: конфігурація процесу `Smtp:*`

Діє, лише поки налаштування в базі вимкнені або неповні (немає сервера чи
відправника), а також коли база недоступна в момент читання. Ключі —
`operations-runbook.md` п. 2.1 (`Smtp:Host`, `Smtp:From`, `Smtp:Port`,
`Smtp:UseStartTls`, `Smtp:User`, `Smtp:SecretName` → секрет `Secrets:<ім'я>`).
Для нового майданчика заповнюйте форму, а не змінні оточення.

### 2.4. Проба

Кнопка «Send test message». Шле лист `ECR test notification` через
**збережені** ефективні налаштування (поки є незбережені зміни, кнопка
неактивна).

Лист іде на **одну введену адресу** з поля «Send a test message to» (воно
обов'язкове: інакше кнопка неактивна). Список, кілька адрес через кому чи
крапку з комою, ім'я-відображення, пробіли й керівні символи — `422`
«The test recipient is not an email address.» (`smtpTestRecipientInvalid`):
проба не є відкритим релеєм від імені організації. Порожня адреса на рівні API —
пошта вашого облікового запису; якщо її немає — `422` `smtpTestRecipientInvalid`. Журнал подій безпеки (`SmtpSettingsTested`)
зберігає лише результат, ознаку «введена / власна» і домен адреси.

Підсумок проби — категорія відмови без тексту сервера:

| Повідомлення починається з | Що перевірити (поле форми / ключ запасного шляху) |
|---|---|
| …the server name could not be resolved (DNS) | Server / `Smtp:Host`, DNS на хості застосунку |
| …could not connect to the server | Server, Port / `Smtp:Port`, брандмауер між хостом і поштовим сервером |
| …TLS/STARTTLS error | Encryption / `Smtp:UseStartTls`, довіра до сертифіката поштового сервера |
| …the server rejected the login | Login, Password / `Smtp:User` + секрет `Smtp:SecretName` |
| …refused to relay for the sender or a recipient | Sender address / `Smtp:From`; дозвіл релею для хоста й облікового запису |
| …did not respond in time | сервер не відповів за 30 с |
| SMTP is not configured: fill in and enable the SMTP settings, or set Smtp:* in the process configuration. | пошти немає взагалі (п. 5) |

Тексти повідомлень називають поле форми, а в дужках — ключ `Smtp:*` на випадок,
коли діє конфігурація процесу. Нерозпізнана відмова — загальне «The channel refused the test
message.»; подробиці — у журналі застосунку.

### 2.5. Межа частоти проб

«Send test message» і «Send test» каналу (будь-якого типу, зокрема Teams) ділять дві межі
(`SmtpTestRateLimitPolicy.cs`, `SmtpTestQuotaMiddleware.cs`): **5 проб за хвилину на
користувача** і **30 за годину на всю систему**. Понад межу — `429` `ECR-REQ-0429` «Too many
test messages in a short time. Wait a moment and try again; the Retry-After header says how
long.» із заголовком `Retry-After`.

- Системна межа витрачається кожною пробою, що пройшла межу користувача й перевірку права
  `System.ManageNotifications`, — зокрема тією, яку далі відхилено як `422` (некоректний
  адресат) чи `404` (немає каналу). Відмови `429` і `403` її не витрачають.
- Квоти живуть у пам'яті кожного процесу: перезапуск їх скидає, а на кількох вузлах межа
  діє на кожному окремо (разом — N × 30 за годину).
- Відомий вектор: носій права може вичерпати системну квоту для всіх (30 прийнятих проб за
  ~6 хв); відновлюється протягом години.
- Ключі: `Security:RateLimit:SmtpTestPermitPerMinute`,
  `Security:RateLimit:SmtpTestSystemPermitPerHour` (`operations-runbook.md` п. 2.1),
  мінімум для обох — 1. Межу не знімати: проба шле справжній лист від адреси організації.

## 3. Канали

SMTP задає, **чим** слати; канал — **кому**. Без каналу й правила подія нікуди
не йде (п. 4).

Поштовий канал («Email (SMTP)»):

- назва до 100 символів, унікальна;
- адресати: явні адреси через кому та/або **ролі-адресати** («Recipient roles»);
  потрібен хоча б один;
- заголовок (title) стає префіксом теми: `<title>: <тема події>`;
- сервер, порт, TLS і відправника в каналі задати не можна (`422`
  `notificationChannelTransportFromConfiguration`): вони беруться з п. 2;
- секрет поштовому каналу не потрібен і не читається.

Ролі-адресати (`sys_ecr.NotificationChannelRole`):

- лист отримують **активні** користувачі ролі з заповненою поштою на момент
  відправки; зміна складу ролі змінює адресатів без правки каналу;
- кожен отримує текст **своєю мовою** (налаштування мови в меню користувача),
  якщо подія має локалізований текст (зараз — «Reporting period opened» і «Reporting period entered its grace window»);
  явні адреси отримують мову каталогу за замовчуванням (`en`);
- адреса, що є і серед явних, і в ролі, отримує один лист;
- перемикач «Alerts» користувача для ролей не потрібен.

⚠ Явні адреси каналу (і всі адресати алертів п. 6) отримують **один лист зі спільним полем
«Кому»** — кожен бачить адреси інших (`SmtpChannelSender.cs`, без `Bcc`). Адресати з ролей —
один лист на кожну мову, теж зі спільним «Кому».

Перемикач «Enabled» каналу: вимкнений канал не отримує нічого й рядків у журналі доставок
не дає. Видалення каналу видаляє і його правила (`removedRules` у журналі безпеки); журнал
доставок лишається.

Канал Teams: секрет каналу — сам URL вебхука (`PUT {id}/secret`), лише `https`
на хост із `Notifications:WebhookAllowedHostSuffixes`
(`operations-runbook.md` п. 2.1).

Проба каналу («Send test») для пошти йде тим самим відправником, що й розсилка:
явні адреси каналу — **усі, без обмеження**, плюс адреси, розкриті з ролей
(активні користувачі з поштою, мова за вподобанням, дублі прибрано) — не більш ніж
**20 з ролей** (`ProbeRecipientLimit`). Тримайте перелік явних адрес коротким: проба шле
на кожну. Межа частоти — п. 2.5. Якщо адрес немає ні
явних, ні з ролей — відповідь «No recipients: the channel has no explicit
addresses, and its roles resolve to no active user with an email address.»
(`notifications.test.smtpNoRecipients`). Транспорт без каналу перевіряє проба з п. 2.4.

## 4. Правила

Матриця «Rules»: рядок — подія, стовпець — канал; у клітинці увімкнення і межа
серйозності «From severity» (`Info` < `Warning` < `Error`): правило пропускає
події не нижчі за межу. «Save rules» замінює матрицю цілком.

| Подія (en) | Звідки береться | Серйозність |
|---|---|---|
| Background job failed | щогодинне зведення збоїв (`NotificationJob`): задачі обслуговування (зокрема `partition-check` `Failed` і рядки `audit-archive` `Failed`/`Degraded`), перерахунок, імпорт, знімки звітів, перенесення зібраного в комірки | `Error` |
| Consistency issues found | нічна перевірка узгодженості | `Error` |
| Partitions running out | нічна перевірка партицій `partition-check` зі статусом `Degraded`: менше 2 меж `pf_ByPeriodKey` попереду, немає функції партиціонування **або збій архівації аудиту** (`auditArchiveFailed`, `operations-runbook.md` п. 7.3) | `Error` |
| Collection from a source failed | збір із джерела, відмова автентифікації джерела, журнал покриття | `Error`; записи журналу покриття — `Warning` (пропуски: період закрито, конфлікт запису, потрібне підтвердження; зміни довідника) або `Info` (автостворений запис довідника, пропуск через залежність розкладу); група подій бере найвищу серйозність. Щоб бачити й попередження покриття, межа клітинки — `Warning` або `Info` |
| Export failed | вивантаження в Excel | `Error` |
| Reporting period opened | перехід періоду `Scheduled → Open` (`PeriodStateJob`) | `Info` |
| Reporting period entered its grace window | перехід періоду `Open → Grace` (`PeriodStateJob`): термін подання минув, лишився пільговий строк | `Info` |

Для нагадування «відкрито новий період — заповніть документ» увімкніть клітинку
«Reporting period opened» × канал із межею `Info`; для «термін минув, лишився пільговий
строк» — «Reporting period entered its grace window». Лист іде один раз на проєкт і
період; текст — ключі `notifications.periodOpened.*` і `notifications.periodGraceStarted.*`
(`.subject`, `.body`; редагуються на `/admin/ui-strings` або в панелі «Message templates»
правом `System.ManageLocalization`, підстановки лише `{project}` (код проєкту) і `{period}`
(ключ і межі періоду)). Адресат у явному переліку без ролі отримує текст мовою каталогу за
замовчуванням (`en`).

Панель «Message templates» (`NotificationTemplatesPanel.tsx`) редагує ті самі ключі для
кожної мови (en/ru/kz) і показує «Who gets it» — виведення з увімкнених правил × каналів ×
ролей, з поясненням, якщо межа вища за `Info` або транспорту немає. Без права
`System.ManageLocalization` — лише повідомлення. Невідомі підстановки (крім `{project}`,
`{period}`) не зберігаються. Порожній переклад — адресат отримує текст мови за
замовчуванням.

Розклад (`operations-runbook.md` п. 4): `NotificationJob` і `PeriodStateJob` —
щогодини о хх:05, `PeriodStateJob` ще й один раз на старті.

### 4.1. Повтори

Та сама подія (той самий ключ) у той самий канал не йде частіше за раз на
**30 хв** після успішної доставки: повтор пишеться в журнал як `Suppressed`.
Невдала спроба вікно не відкриває.

### 4.2. Журнал доставок

Панель «Deliveries» (`itg.NotificationDelivery`): кожна спроба — рядок
`Sent`, `Failed` або `Suppressed` з причиною (до 400 символів, без секретів і
тіла листа). Причина `Failed` — текст відмови транспорту як є (зокрема відповідь поштового
сервера); категоризація проби (п. 2.4) тут не діє. Фільтр за каналом і підсумком є лише в API (`GET …/deliveries?channelId=…&status=…`), на екрані фільтрів немає. Журнал переживає видалення каналу.
Подія без жодного правила рядка не дає.

## 5. Що відбувається без транспорту

«Без транспорту» — немає ні ввімкнених повних налаштувань у базі, ні
`Smtp:Host` + `Smtp:From` у конфігурації. Застосунок працює, пошта не йде:

| Шлях | Що з подією |
|---|---|
| Канали й правила (п. 3–4) | кожна спроба — рядок `Failed` у журналі доставок («транспорт SMTP процесу не налаштовано»). Повторно не надсилається: нагадування про період, відкритий без транспорту, не прийде і після налаштування |
| Черга алертів `itg.NotificationOutbox` (п. 6) | події лишаються `Pending` і накопичуються, спроби не витрачаються; після налаштування підуть найближчим прогоном `NotificationJob` |
| Проба | «SMTP is not configured: fill in and enable the SMTP settings, or set Smtp:* in the process configuration.» |
| Стан | панель SMTP: «Mail is not configured: events stay queued.»; `/health/facts`: `notificationTransport.isConfigured = false` |

## 6. Черга алертів для адміністраторів (`ReceivesAlerts`)

Окремо від каналів: щогодинне зведення збоїв (тема `ECR: збоїв за період — N`)
і негайний алерт про відмову джерела в автентифікації йдуть через чергу
`itg.NotificationOutbox` усім **активним** користувачам із поштою і ввімкненим
перемикачем «Alerts» на `/admin/security` (без пошти перемикач не вмикається).

- Один лист на всіх; текст зведення не перекладається.
- До 200 листів за прогін; після 5 невдалих спроб (≈ 5 год) запис — `Failed`.
- Жодного адресата: спроба зараховується з причиною «Адресатів не визначено…», запис
  лишається `Pending` і стає `Failed` після 5-ї спроби (≈ 5 год); увімкніть комусь «Alerts»
  до того — і лист піде найближчим прогоном. У зведенні прогону — рядок `recipients` /
  `sec.User.ReceivesAlerts`, а прогін `notification` позначається `Degraded`
  (`OutboxDispatcher.cs`, `NotificationOutbox.cs`).
- Ті самі збої йдуть і каналами за правилами п. 4; одне одного не заміняє.

## 7. Типові проблеми

| Симптом | Причина | Дія |
|---|---|---|
| стан «process configuration», хоча форму заповнено | не ввімкнено «Use these settings» або порожні Server / Sender address | увімкнути, заповнити, зберегти |
| проба успішна, а лист не дійшов | проба йде на введену адресу (порожня — на пошту вашого облікового запису) | перевірити адресу, скриньку й спам-фільтр |
