# 01. Контекст і межі

## 1.1 Задача

Побудувати **універсальний інструмент структурованої звітності**: систему, у
якій форма звіту, її правила й розрахунки описуються **як дані**, а не як код.
Перша область застосування — екологічна звітність. Друга і наступні мають
підключатися конфігурацією, а не розробкою.

Це формулювання визначає майже всі архітектурні рішення далі. Якщо мета —
переписати конкретні 24 аркуші, правильна відповідь була б інша й дешевша.

## 1.2 Чинне рішення (AS-IS)

### Excel-контур

| Показник | Значення |
|---|---|
| Аркушів у книзі | 24 (з них 7 legacy — не в потоці збереження) |
| Рядків VBA | ~45 000 у 96 файлах |
| Обчислювальних формул | ~250 |
| `VLOOKUP` | 429 |
| Крос-аркушних залежностей | 7 ребер |
| Excel-функцій власної розробки | 11 |

Дані рядка серіалізуються в **один рядок із роздільником `;`** і лягають в
атрибут `Attribute_XXXX` елемента PI AF. Порядок значень у цьому рядку **і є**
ідентичністю полів.

> **Це головний дефект чинного рішення.** Вставлена колонка зсуває всі значення
> праворуч; історія при цьому не помічає нічого. Помилку видно лише як
> неправильні числа у звіті — місяці потому.

### Бекенд

| Показник | Значення |
|---|---|
| Розрахункових класів `ECW_C**` | 44 |
| Процедур `Report_*` | 127 |
| Звітів RDL (SSRS) | 166 |
| Завдань SQL Agent | ~100 |
| Land-процедур через PI SQL DAS (RTQP) | 63 |
| Повний річний перерахунок | **20 хвилин** |

Логіка розподілена між CLR-збірками, збереженими процедурами, аналізами AF і
VBA. Одне бізнес-правило зазвичай існує у двох-трьох місцях одночасно.

### Наслідки для експлуатації

1. **Зміна форми = зміна коду.** Нова колонка означає правку VBA, зсув
   серіалізації, ручну міграцію історії.
2. **Немає надійного аудиту.** Хто змінив конкретне число і коли — невідомо.
3. **Немає одночасної роботи.** Книга блокується.
4. **Розрахунок неможливо відтворити.** Немає зрізу вхідних даних на момент
   подання.
5. **Правила розсипані.** Розбіжність між двома копіями правила ніщо не ловить.

Детальний розбір — [`../reference/as-is/`](../reference/as-is/01-as-is-overview.md).

## 1.3 Цільове рішення (TO-BE) в шести реченнях

Форма звіту описується як **шаблон**: аркуші, таблиці, колонки, рядки, стилі,
формули, правила валідації. Шаблон **публікується у версію**, після чого його
структура незмінна, а презентаційний шар (підписи, стилі, порядок) лишається
патчабельним. Дані вводяться в **документ** — екземпляр шаблону для проєкту й
періоду — і зберігаються **покоміркою** з явною ідентичністю рядка й колонки.
Формули обчислюються **на сервері**, граф залежностей будується при публікації,
зміна комірки перераховує лише залежне піддерево. Методології розрахунку — теж
дані: версійні, з датою чинності й обов'язковим рев'ю перед публікацією.
Звітність лишається в **SSRS**, читаючи стабільний контракт `rpt.*`.

## 1.4 Межі

### Входить

- Ядро: шаблони, версії, документи, комірки, формули, валідація
- Розрахунковий рушій: методології, константи, одиниці, трейс
- Реєстри (довідники) з темпоральністю і каскадами
- Безпека: два провайдери автентифікації, ролі, ресурсні гранти
- Періоди: стани, offsets, пізні зміни, `Reopen`
- Робочий процес: `Draft → Submitted → Approved` на рівні аркуш × період
- Інтеграція: читання PI AF двома транспортами, ідемпотентний збір
- Звітний контракт `rpt.*` для SSRS
- Експорт/імпорт Excel із diff
- React SPA: сітка введення, 15 областей адміністрування
- Архівація і рівні зберігання

### Не входить

| Що | Чому |
|---|---|
| Веб-переглядач звітів і конструктор звітів | SSRS лишається (D-52) |
| Запис у PI AF будь-якого виду | D-44 |
| Мобільний клієнт | D-61 |
| Інтеграція з SAP | D-61 |
| Офлайн-режим | D-41; закривається маршрутом «експорт → правки → імпорт» |
| Перенесення legacy-аркушів `9c`, `HSE_373/400/401_Air` | D-60 — поза потоком збереження |
| Автоматична еволюція фізичної схеми | D-13 — структура є даними, DDL не потрібен |

## 1.5 Глосарій

| Термін | Значення |
|---|---|
| **Шаблон** (`Template`) | опис форми звіту: аркуші, таблиці, колонки, рядки, формули |
| **Версія шаблону** (`TemplateVersion`) | опублікований незмінний знімок структури |
| **Презентаційний шар** | підписи, стилі, порядок — патчиться після публікації, з `PresentationRevision` |
| **Проєкт** (`Project`) | майданчик/контур звітності: часовий пояс, календар періодів, політика |
| **Період** (`Period`) | звітний інтервал зі станом; ключ `PeriodKey = Year*100 + Sequence` |
| **Документ** (`Document`) | екземпляр шаблону в межах проєкту, унікальний за `BusinessKey`. **Наскрізний по періодах**: період живе на рядках і комірках, а не на документі |
| **`RowKey`** | стабільний ідентифікатор рядка в межах таблиці; не залежить від порядку |
| **Реєстр** (`Registry`) | універсальний довідник: темпоральність, каскади, довільні поля |
| **Методологія** (`Methodology`) | версійний набір формул розрахунку з датою чинності |
| **Зріз** (`ReportSnapshot`) | матеріалізований стан документа для звітності; має статус |
| **Розмірність** (`Dimension`) | клас величини: маса, об'єм, час, витрата |
| **Пізня зміна** (`IsLateEdit`) | зміна після межі періоду або після `Reopen` |

Повний глосарій із відповідністю «термін → клас → таблиця» —
[`../build/03-glossary.md`](../build/03-glossary.md).
