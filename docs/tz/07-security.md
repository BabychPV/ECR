# 07. Безпека, періоди, робочий процес

## 7.1 Автентифікація

Два провайдери → **одна** cookie (D-33):

| Провайдер | Механізм | Кому |
|---|---|---|
| Доменний | Negotiate (Kerberos/NTLM) на `/login/windows` | усім, хто має обліковий запис AD |
| Локальний | логін + пароль на `/login/local` | лише тим, у кого доменного немає |

**Авторизація не знає, як користувач увійшов.** Після входу є `sec.User.Id` — і
далі різниці немає ніде. Це дозволяє мати єдиний аудит і єдину модель прав.

- Локальні користувачі — виняток, не альтернатива (ФВ-6.4).
- **Обсяг першого релізу — саме ці два провайдери** (`D-104`, ФВ-6.4a): базова
  політика паролів діє, **TOTP і самостійне скидання не робимо**. Пароль
  скидає адміністратор. `P-1` і `P-2` відкладені, не закриті.
- Первинний локальний адміністратор — одноразовий пароль, обов'язкова зміна,
  автоматичне вимкнення після появи доменного (`D-97`, ФВ-6.18).

**Доступ до зовнішніх джерел — сервісний обліковий запис** (D-34).
Kerberos-делегування не використовується.

## 7.2 Авторизація

Ролі — **дані**, не код (D-35).

| Складова | Що |
|---|---|
| **Функціональні права** | `Template.Edit`, `Calculation.Publish`, `Integration.Manage`, … |
| **Ресурсні гранти** | доступ до конкретного проєкту / аркуша, з успадкуванням проєкт → аркуш |
| **`IsDeny`** | заборона **виграє завжди**, на будь-якому рівні |

`IsDeny` виграє завжди — це свідома жорсткість. Альтернатива («конкретніший
рівень перемагає») дає ситуації, де людина має доступ і ніхто не може пояснити
чому.

### Одна точка рішення

Усі рішення про доступ проходять через `IAccessDecisionService`, який повертає
**причину**, а не `bool` (D-36, ФВ-6.8):

```csharp
public sealed record EditDecision(
    bool     IsAllowed,
    string   ReasonCode,     // ECR-SEC-xxxx
    string   ReasonMessage,  // локалізоване
    string?  ResourceRef);
```

Причина потрібна не для краси: «чому я не можу зберегти» — найчастіше питання
підтримки в системах такого класу. Порожній `403` перетворює його на розслідування.

Перевірка для зрізу — **пакетна** (ФВ-6.10): одне рішення на зріз (аркуш ×
період), не на кожну з тисяч комірок.

## 7.3 Права на розрахунки

Найнебезпечніша операція — публікація версії методології, бо вона змінює числа.

| Право | Хто | Правило |
|---|---|---|
| `Calculation.EditScript` | автор формул | — |
| `Calculation.Publish` | рев'ювер | **не може бути автором останньої правки** (D-40) |

Заборона діє **системно**, не інструкцією: спроба опублікувати власну останню
правку відхиляється сервером.

Хто саме отримує ці права — `K-2` (2–3 іменовані особи).

## 7.4 Періоди

### Стани

```
Future → Open → Grace → Closed → Archived
                  ↑        │
                  └────────┘  Reopen періоду (адміністратор, з причиною)
```

| Стан | Запис даних | `Submit` | `Reopen` документа |
|---|---|---|---|
| `Future` | ні | ні | — |
| `Open` | так | так | так |
| `Grace` | так, `IsLateEdit = 1` | так | так |
| `Closed` | ні | ні | **ні** |
| `Archived` | ні | ні | ні |

### Offsets

Задаються на чотирьох рівнях із наростанням конкретності (ФВ-1.7):

```
глобально → проєкт → період → роль
```

Роль на останньому місці свідомо: «бухгалтерії дати ще три дні» — типова
реальна потреба, і вона не має вимагати зміни правил проєкту.

### Час

`PeriodStateJob` виконує переходи **за поясом майданчика**
(`Project.TimeZoneId`), не за UTC-опівніччю (D-68). Період, що закривається
«31 числа о 23:59», має закритися о 23:59 **там, де сидять люди**.

Зберігання — UTC у `datetime2(3)` (D-85). Відображення — теж у поясі
майданчика, однаково для всіх: різні пояси у різних користувачів зробили б
неможливим спільне обговорення «коли саме це змінили».

## 7.5 Робочий процес документа

```
Draft ──Submit──→ Submitted ──Approve──→ Approved
  ↑                    │
  │                    └──Reject (з причиною)──┐
  │                                            │
  └──Reopen документа (з причиною, D-67)───────┘
```

Гранулярність — **аркуш × період** (D-38): 24 аркуші рідко готові одночасно, і
чекати найповільніший не має сенсу.

### Поданий документ не редагується

Це принципово (D-67). `Grace` дає час на правки **неподаних** документів — він
**не** дає права змінити подану форму.

Правка поданого документа:

1. `Reopen` документа з **обов'язковою причиною** → `Draft`.
2. Правки; кожна позначається `IsLateEdit = 1` (D-70).
3. Повторний `Submit` → створюється **новий** зріз.
4. Старий зріз лишається `Submitted` **назавжди** — його ніщо не перезаписує.

`Reopen` документа **неможливий, поки період у `Closed`**. Спочатку `Reopen`
періоду (окрема адміністративна дія), потім документа.

Два рівні `Reopen` — не дублювання: період відкриває адміністратор системи,
документ — відповідальний за форму. Різні люди, різні причини, різний аудит.

## 7.6 Аудит

| Журнал | Що фіксує |
|---|---|
| `aud.CellChange` | старе/нове значення, автор, час, джерело зміни |
| `aud.StructureChange` | зміни метаданих і адміністративні дії |
| `aud.AccessDenied` | відмови в доступі з причиною і ресурсом (ФВ-5.24) |

- Автор — **`ChangedByUserId` → `sec.User(Id)`**, не SID (D-37, D-86): у
  локальних користувачів SID немає взагалі.
- Пишеться **пакетно**, не рядок на комірку (ФВ-5.21): batch-PATCH на 500
  комірок — це один запис пачки, а не 500 вставок.
- Джерело зміни розрізняється: UI / імпорт / розрахунок / інтеграція.
- Партиціонується по `ChangedAt`, архівується щомісячно (D-26).
- **Не затирається ніколи** (D-25).

Доступний в інтерфейсі (ФВ-5.22): по комірці — хто, коли, з чого на що; по
документу — стрічка змін із фільтром за автором і датою.

> `sec.User.Sid` (ідентифікатор доменного користувача) і `PrincipalSid`
> (AD-група) лишаються — це **не** авторство, а зіставлення з каталогом.
