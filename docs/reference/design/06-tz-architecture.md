# 1. Мета та межі

## 1.1 Мета

Створити **універсальний інструмент побудови та заповнення структурованої звітності**:
проєкт на рік -> версійний шаблон (аркуші, таблиці, стилістика) -> згенеровані з нього
документи з обраним набором аркушів і таблиць -> заповнення -> валідація -> затвердження.

Перший сценарій застосування — заміна чинного Excel/VBA-рішення ECR
(екологічна звітність). Але **ядро системи не залежить від ECR і не залежить від PI AF**.

## 1.2 Два рівні системи

```
┌──────────────────────────────────────────────────────────────┐
│  ЯДРО (домен-агностичне, не знає про PI AF і про екологію)   │
│  • Проєкти                                                    │
│  • Версійні шаблони: аркуші, таблиці, колонки, стилі          │
│  • Генерація документів із шаблону                            │
│  • Заповнення (grid), формули, валідація                      │
│  • Workflow затвердження                                      │
│  • RBAC, аудит                                                │
│  • Експорт/імпорт .xlsx                                       │
└───────────────────────────┬──────────────────────────────────┘
                            │ підключувані адаптери
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
┌───────────────┐  ┌─────────────────┐  ┌──────────────────┐
│ PI AF         │  │ Розрахункові    │  │ Майбутні         │
│ Connector     │  │ модулі емісій   │  │ джерела/споживачі│
│ (джерело      │  │ (backend,       │  │                  │
│  сирих даних) │  │  перша черга)   │  │                  │
└───────────────┘  └─────────────────┘  └──────────────────┘
```

## 1.3 У межах першої черги

* Проєкти на звітний рік
* **Конфігуратор шаблонів**: аркуші / таблиці / колонки / рядки / **стилістика** /
  формули / правила валідації
* **Версійність шаблонів** (нова версія створюється на основі попередньої)
* **Генерація документів** із шаблону з довільним набором аркушів і таблиць
* Заповнення документів у grid-редакторі з формулами
* Валідація (комірка / рядок / таблиця / документ)
* Робочий процес затвердження (Draft -> Submitted -> Approved)
* Налаштовувана рольова модель доступу; **два провайдери автентифікації**
  (Windows SSO + внутрішні облікові записи)
* Довідники/реєстри як універсальний механізм (від плоского списку до `Permit`)
* Правила доступу до періодів (offsets, grace) як конфігурація
* Експорт/імпорт документів у `.xlsx`
* Архівування закритих років
* **PI AF Connector — інтерфейси збору даних з AF** (довідники, сирі дані, які
  існують тільки там); зібране зберігається **напряму в SQL**
* Міграція існуючих даних з PI AF у SQL

## 1.4 Наступні фази (враховуються в архітектурі, не реалізуються зараз)

* **Розрахункові модулі емісій** — переносяться з PI AF **у backend**.
  Архітектура має передбачити точку розширення: `ICalculationModule`, окрема схема
  `calc` у БД, версійність методик розрахунку. Детальний контекст буде додано окремо.
* Додаткові адаптери джерел даних

## 1.5 Поза межами

* Мобільний клієнт
* Інтеграція з обліковими системами (SAP тощо)
* Збереження PI AF у ролі цільового сховища для введених даних —
  **система обліку тепер SQL** (див. §5.3)

## 2.2 Frontend — React + TypeScript (рішення прийнято)

Один SPA обслуговує **і адміністрування, і роботу звичайних користувачів** —
розділення за ролями через маршрути і policy, а не через окремі застосунки.

**Чому Mantine, а не MUI / Ant Design:**
* MUI безкоштовний, але потрібний `MUI X DataGrid Pro/Premium` — платний;
* Ant Design має власну стилістику, яку важко узгодити з корпоративною;
* Mantine — MIT цілком, ~120 компонентів, вбудовані хуки, гарна темізація,
  не тягне за собою платних рівнів.

**Альтернатива, якщо потрібен повний контроль над виглядом:**
**shadcn/ui + Radix UI + Tailwind CSS** (усе MIT). Компоненти копіюються в проєкт,
не є залежністю. Дорожче на старті, гнучкіше далі.

### ⚠ Grid — окреме рішення, бо тут «безкоштовно» стає проблемою

Потрібна Excel-подібна поведінка: виділення діапазону, копіювання/вставка з Excel,
fill handle, undo/redo, віртуалізація на 500+ рядків × 60 колонок.

| Варіант | Ліцензія | Діапазони / clipboard / fill | Оцінка |
|---------|----------|------------------------------|--------|
| **AG Grid Community** | MIT | ❌ Range selection, Fill handle, multi-cell clipboard — **тільки Enterprise** | не покриває вимогу |
| AG Grid Enterprise | комерційна | ✅ все | ~$1000/розробник/рік |
| **Handsontable** | безкоштовно **лише non-commercial** | ✅ все | комерційна ліцензія обов'язкова |
| **RevoGrid** | MIT (open-core) | ✅ Excel-подібна навігація, copy/paste з Excel, віртуалізація; **активно супроводжується** (реліз 6 днів тому) | **рекомендація** |
| **Glide Data Grid** | MIT | ✅ виділення діапазонів, copy/paste, fill, canvas-рендер; ⚠ **остання публікація ~3 роки тому** | запасний |
| **react-datasheet-grid** | MIT | ✅ базово, легкий | для простих таблиць |
| TanStack Table + TanStack Virtual | MIT | ❌ headless — Excel-поведінку писати самим | найбільше роботи |

**Рекомендація: RevoGrid** (основний) з **Glide Data Grid** як запасним.

Повторна перевірка змінила порядок: Glide Data Grid функціонально підходить,
але **остання версія 6.0.3 опублікована близько трьох років тому** — для системи
з горизонтом 10+ років це ризик. RevoGrid — MIT для ядра, **остання версія
4.21.8 опублікована 6 днів тому**, CD-конвеєр збирає обгортки під React/Angular/Vue,
заявлені Excel-подібна навігація і безшовне copy/paste з Excel.

⚠ RevoGrid — **open-core**: на прототипі підтвердити, що fill handle,
range selection і clipboard — у **MIT-ядрі**, а не в платних Pro-плагінах.

**План зниження ризику:** на Етапі 0 зробити прототип на найбільшій реальній таблиці
(`9. Utility`, 471 рядок × 60 колонок) на **обох** кандидатах і обрати за результатом.
Якщо жоден не влаштує — рахувати вартість AG Grid Enterprise як прийнятну
(це ~1% бюджету проєкту).

### ⚠ Формули на клієнті — ліцензійне застереження

**HyperFormula (рекомендована раніше) має подвійну ліцензію GPLv3 / комерційна.**
GPLv3 для закритого корпоративного застосунку неприйнятна. Тому:

| Варіант | Ліцензія | Підхід |
|---------|----------|--------|
| **Формули тільки на сервері** (NCalc) | MIT | клієнт показує значення, отримані з API; перерахунок — запит з debounce ~300 мс |
| **formulajs** (`@formulajs/formulajs`) | MIT | 500+ Excel-функцій; граф залежностей пишемо самі |
| **fast-formula-parser** | MIT | парсер + обчислювач Excel-формул із підтримкою посилань |

**Рекомендація: серверний рушій як єдине джерело істини + `formulajs` на клієнті
для миттєвого відгуку в межах однієї таблиці.**

Це прибирає найбільший ризик проєкту — розбіжність двох рушіїв формул
(див. §8 «Ризики»): авторитетне значення завжди одне, серверне.
Клієнтське обчислення — лише візуальна підказка, яка при збереженні
замінюється серверним результатом.

> ⚠ Ліцензії перевірити повторно на момент старту розробки — вони змінюються.

## 2.3 Розгортання

| | |
|---|---|
| Хостинг | IIS на Windows Server (обов'язково для Windows Auth + Kerberos) або Kestrel за IIS-reverse-proxy. ⚠ IIS має бути налаштований на **анонімний доступ за замовчуванням** — інакше локальні користувачі не дійдуть до форми входу; Negotiate вмикається лише на endpoint `/login/windows` |

| CI/CD | Azure DevOps (у сесії доступний MCP-конектор `azure-devops`) |
| Середовища | DEV / TEST / PROD, окремі БД і окремі AF-бази |

## 3.3 Ключове архітектурне рішення: metadata-driven

> **Усе, що зараз є кодом VBA і координатами комірок, стає ДАНИМИ в SQL.**

| Зараз | Стане |
|-------|-------|
| `Configuration.bas` словники | таблиці `SheetDef`, `TableDef` |
| `sheet.Cells(i, 22)` | `ColumnDef.Ordinal = 22` |
| `Range("A6:E90").Locked = True` | `ColumnDef.IsReadOnly` / `RowDef.IsReadOnly` |
| Excel Data Validation | `ValidationRule` (тип, параметри, повідомлення) |
| Excel-формула `=SUM(I7:I11)` | `FormulaDef.Expression` |
| `HSE_*.bas` × 19 | **один** generic `DataEntryService` (запис комірок за метаданими) |
| `Protection.bas` номери рядків | `RowDef.RowType = Header` + `PeriodAccessRuleDef(HeaderRows)` |
| `DropdownList` рядки 3–4 (прив'язка списків до комірок) | `ColumnDef.LookupRegistryDefId` |
| `Configuration.bas` мапінг на AF-шаблони | `ext.LegacyTableMapping` (поза ядром) |

Наслідок: **додавання нової таблиці або аркуша — це операція в UI, не реліз коду.**
Це прямо покриває ФВ-2.

## 3.4 Правки універсальності після повторної перевірки ⭐

Повторний прохід по прийнятих рішеннях з критерієм «універсальний інструмент,
що працює на льоту» виявив чотири місця, де ECR-специфіка або зайва жорсткість
просочилися в ядро. Виправлено:

| # | Було | Проблема | Стало |
|---|------|----------|-------|
| 1 | `cfg.TableDef.AfEventFrameTemplate`, `AfElementTemplate`, `AfElementName`; `cfg.ColumnDef.AfAttributeName`, `LegacyFieldIndex`; `RowDef.LegacyAfAttributeName`; усі `Legacy*` | **PI AF- і Excel-специфіка в ядрі** — суперечить правилу «Domain не знає про AF» і архітектурному тесту §4 у [13](13-backend-assignment.md) | винесено в **`ext.LegacyTableMapping` / `ext.LegacyColumnMapping` / `ext.LegacyRowMapping`**, якими володіють адаптер PI AF і bootstrap-імпортер. Ядро про них не знає |
| 2 | `cfg.Template.LocationKind` = `Land`/`Offshore`/`Vessels` | ECR-специфічний enum у ядрі | прибрано; замість — `cfg.Template.Tags` (JSON) і/або посилання на реєстр `Location` |
| 3 | Локалізація як фіксовані колонки `NameEn/NameRu/NameKz` | **додати мову = зміна схеми** — суперечить принципу «структура = дані» | усі локалізовані поля — одна колонка `…L10n nvarchar(max)` з JSON `{"en":…,"ru":…,"kz":…}` + реєстр `sys.Language`. Нова мова — це запис, а не міграція |
| 4 | Опублікована версія повністю заморожена | виправити друкарську помилку в підписі = нова версія + міграція документів — **не «на льоту»** | структурний шар заморожений; **презентаційний шар патчиться** з аудитом (ФВ-2.8, [10](10-schema-evolution.md) §2a) |
| 5 | `doc.Project.Year smallint` | проєкт може бути не календарним роком (фіскальний, довільний діапазон) | `PeriodStart`/`PeriodEnd` — джерело істини; `Year` — необов'язковий підпис |
| 6 | Формули лише в межах документа | перенесення залишків минулого року робилося вручну | `[Period:-1]`, `[PrevProject]…` з `RefMode = Snapshot/Live` (ФВ-3.4) |

**Кандидати на розширення `ColumnDef.DataType` для універсальності** (не для першої
черги, але модель має їх допускати без міграції — тому `DataType` це код, а не enum
із фіксованим набором): `LongText`, `MultiLookup`, `Attachment`, `Json`, `Percent`,
`Duration`.

# 4. Функціональні вимоги

Нумерація відповідає вимогам замовника.

## ФВ-1. Проєкт на рік

**ФВ-1.1** Створення `Project` з полями: назва, **`PeriodStart` / `PeriodEnd`**
(джерело істини — довільний діапазон, не лише календарний рік; `Year` — необов'язковий
підпис), `PeriodKind`, посилання на версію шаблону, теги, статус,
посилання на зовнішні джерела даних (`ext.DataSource`) — **не** AF-сервер у полях
проєкту, бо ядро не знає про AF.

**ФВ-1.2** Проєкт прив'язується до **версії шаблону** (`TemplateVersion`). Зміна шаблону
не змінює вже створені проєкти.

**ФВ-1.3** Клонування проєкту з попереднього року: копіюються довідники, налаштування,
структура; дані — ні. Опційно — перенесення «залишків на початок року».

**ФВ-1.4** Статуси проєкту: `Draft` -> `Active` -> `Closed` -> `Archived`.
У `Closed` заборонено будь-які зміни даних.

**ФВ-1.5 Календар періодів.** Кількість періодів визначається `Project.PeriodKind`
(`Monthly` = 12 / `Quarterly` = 4 / `Yearly` = 1 / `Custom`). Для ECR — 12 місяців.

Стани періоду:

```
 Scheduled ──► Open ──────► Grace ──────► Closed ──┐
 (ще не       (звичайне    (пільговий    (тільки   │
  почався)     введення)    період —      читання) │
                            видно, що               │
                            це «понад                │
                            строк»)                  │
                                                     │
      ▲                                              │
      └──────── Reopen (PeriodAdministrator, ────────┘
                 з обов'язковим коментарем)
```

**ФВ-1.6 Offsets (зсуви) — конфігуруються адміністратором.**

Замість одного `CutoffDay` — набір зсувів, які визначають межі станів
відносно **дати завершення періоду**:

| Параметр | Що означає | Приклад для ECR | Знак |
|----------|------------|-----------------|------|
| `OpenOffsetDays` | коли період відкривається для введення, відносно **початку** періоду | `0` — з першого дня | може бути від'ємним (відкрити наперед) |
| **`GraceOffsetDays`** | **скільки днів після завершення періоду дані ще редагуються** | **`+15`** | ≥ 0 |
| `HardCloseOffsetDays` | коли період закривається остаточно | `+30` | ≥ `GraceOffsetDays` |

Приклад: період «Вересень 2026» (завершується 30.09):

```
01.09 ──────────── 30.09 ─────────── 15.10 ─────────── 30.10 ────►
  │                  │                 │                 │
  Open               │                 │                 Closed
  (звичайне вводення)│                 │
                     └── Grace ────────┘
                     +0 днів      +15 днів (GraceOffsetDays)
```

**ФВ-1.7 Рівні застосування offsets** (від загального до конкретного,
виграє найконкретніший):

| Рівень | Де налаштовується | Призначення |
|--------|-------------------|-------------|
| 1. Глобальний за замовчуванням | системні налаштування | базова політика організації |
| 2. **Проєкт** | `Project.PeriodPolicy` | «для проєкту 2026 grace = 15 днів» |
| 3. **Окремий період** | `Period` override | «за грудень дали 30 днів» |
| 4. **Роль** | `sec.RoleAssignment.ExtraGraceDays` | «контролер має +10 днів понад загальні» |

**ФВ-1.8 Offset на рівні року (проєкту).**
Окремо від місячних періодів: `Project.YearGraceOffsetDays` — скільки днів після
завершення звітного року дані **за минулий рік** ще можна редагувати.

Приклад: проєкт «2026» завершується 31.12.2026, `YearGraceOffsetDays = 45` ->
до 14.02.2027 користувачі можуть виправляти дані 2026 року, після чого проєкт
переходить у `Closed` і потребує явного `Reopen` адміністратором.

> Це прямо покриває сценарій «+15 днів після завершення — ще можемо редагувати
> дані за минулий рік».

**ФВ-1.9 Поведінка у стані `Grace`:**
* введення дозволене, але UI явно позначає: «Редагування понад строк, залишилось N днів»;
* кожна зміна у `Grace` фіксується в аудиті з окремою ознакою `IsLateEdit = 1`;
* опційно (`RequireReasonInGrace`) — обов'язкове зазначення причини зміни;
* опційно (`RequireReapprovalAfterGrace`) — документ повертається в `Draft`
  і потребує повторного затвердження.

**ФВ-1.10 Reopen.** `PeriodAdministrator` може відкрити `Closed`-період:
обов'язковий коментар, обмежений строк відкриття (`ReopenDurationDays`),
автоматичне закриття після його спливу, запис в `aud.DocumentEvent`.

**ФВ-1.11 Валідація періоду при збереженні:** період документа має лежати в
`[Project.PeriodStart, Project.PeriodEnd]` — перенос `ValidateStartYearVsContractYear`.
Для ECR ці межі наповнюються з AF (`CALCULATION_START/ENDDATETIME` через
`ExternalSettingsJson`), але **саме правило — універсальне** і про AF не знає.

**ФВ-1.12** Усі переходи станів виконує фонова задача `PeriodStateJob` (щодня),
а не тригер при відкритті файлу (як зараз у `Protection.ToggleProtection`).
Стан періоду завжди детермінований і однаковий для всіх користувачів.

## ФВ-2. Конфігуратор (аналог аркушів і таблиць)

**ФВ-2.1** Ієрархія: `Template` -> `TemplateVersion` -> `SheetDef` -> `TableDef` -> `ColumnDef` / `RowDef`.

**ФВ-2.2** `SheetDef`: код, локалізована назва (JSON `…L10n`, мови — з реєстру
`sys.Language`; для ECR — EN/RU/KZ), порядок, видимість, група, чи обов'язковий.

**ФВ-2.3** `TableDef`:
* код і локалізована назва;
* **`LayoutKind`**: `PerPeriodInstance` (рекомендований для нових шаблонів) |
  `MonthsInColumns` | `MonthsInRows` | `Static` — два середні лише для сумісності
  з чинним шаблоном (див. `01-as-is-overview.md` §5, `09-template-engine.md` §7);
* `RowMode`: `Fixed` (визначені рядки) | `Dynamic` (користувач додає) | `Mixed`.

> Прив'язка до PI AF (`EventFrameTemplate`, `ElementTemplate`, `ElementName`) і до
> чинного Excel (`TemplateRow`) — **не в ядрі**, а в `ext.LegacyTableMapping`
> (§3.4 п.1, [07](07-data-model.md) §8.1).

**ФВ-2.4** `ColumnDef`: код, локалізований заголовок, `Ordinal`, `DataType`
(`String` | `Int` | `Decimal(p,s)` | `Bool` | `Date` | `Lookup` | `Formula`;
код, не закритий enum — див. §3.4), `IsReadOnly`, `IsRequired`, `IsHidden`,
`Width`, `DisplayFormat`, `LookupRegistryDefId` + `LookupFilter` + `CascadeFromColumnId`,
`IsBusinessKey`, `IsScopeField`, `IsIndexed`, `DefaultValue`.

> `AfAttributeName` і **`LegacyFieldIndex`** (позиція в `;`-рядку) — в
> `ext.LegacyColumnMapping`; критичні для round-trip з AF, але ядро про них не знає.

**ФВ-2.5** `RowDef` (для `RowMode = Fixed`): **`RowKey`** (стабільна ідентичність),
локалізований підпис, `RowType` (`Group` | `Item` | `Balance` | `Note` | `Header`),
`ParentRowDefId`, `Ordinal` (лише порядок), `StyleId`.
`Attribute_0010`-мапінг — в `ext.LegacyRowMapping`.

**ФВ-2.6** Конструктор у UI: drag-and-drop колонок, попередній перегляд таблиці,
імпорт структури **з існуючого `.xlsm`** (див. ФВ-2.10).

**ФВ-2.7 Стилістика.** Шаблон визначає не лише структуру, а й вигляд:

| Рівень | Що налаштовується |
|--------|-------------------|
| `TemplateVersion` | палітра, базовий шрифт, іменовані стилі (`StyleDef`) |
| `SheetDef` | колір вкладки, заголовок, підзаголовок, фіксовані області |
| `TableDef` | стиль заголовка, чергування рядків, рамки, висота рядка |
| `ColumnDef` | ширина, вирівнювання, формат відображення (`#,##0.00`), колір фону/тексту |
| `RowDef` | стиль за типом рядка (GROUP — жирний із заливкою, ITEM — звичайний) |
| Умовне форматування | `ConditionalFormatDef`: вираз -> стиль (аналог 900 conditional formats у чинному шаблоні) |

Стилі описуються **декларативно** (іменовані стилі + посилання на них), а не
дублюються на кожній комірці. Один опис стилів застосовується і в веб-гріді,
і при експорті в `.xlsx`.

**ФВ-2.8 Версійність шаблону:**
* `TemplateVersion` після публікації **структурно незмінна** (колонки, рядки, типи,
  ключі, формули, зв'язки, `Error`-правила);
* **презентаційний шар** опублікованої версії **можна правити «на льоту»**
  без нової версії: підписи, переклади, стилі, ширини, порядок відображення,
  `DisplayTemplate`, `Info`/`Warning`-правила, підказки. Ці зміни фізично не
  можуть зачепити збережені дані, тому вимагати для них нову версію — зайва
  бюрократія, яка суперечить вимозі «працює на льоту». Кожна така правка
  аудитується і збільшує `PresentationRevision` (для інвалідації кешу);
  детально — [10-schema-evolution.md](10-schema-evolution.md) §2a;
* **структурні** зміни можна вносити лише у версію в стані `Draft`, до якої
  не прив'язано документів;
* **`CloneFrom`** — нова версія створюється копіюванням попередньої з усією
  структурою, стилями, формулами і правилами;
* `Diff(v1, v2)` — порівняння двох версій з класифікацією змін за ризиком;
* документ назавжди прив'язаний до тієї версії, на якій створений.

**ФВ-2.9 Публікація версії:** валідація цілісності — усі формули парсяться,
немає циклічних посилань (формули + `TableRelationDef`), усі `RegistryDef`
існують і опубліковані, усі посилання між аркушами резолвяться, немає порожніх
обов'язкових полів конфігурації, `EvaluationOrder` обчислено і збережено.

**ФВ-2.10 Bootstrap-імпорт:** утиліта `Ecr.Bootstrap.Excel`, що читає поточний
`.xlsm` + VBA (`Configuration.bas`, `Sheet_Config.bas`, `Protection.bas`,
`MapAttributes` у 19 модулях) і генерує: `SheetDef`/`TableDef`/`ColumnDef`/`RowDef`,
`StyleDef` (згортання тисяч комбінацій у ~40), `ValidationRule` (з Data Validation),
`PeriodAccessRuleDef` (з `hdrRows` і `Init*`), `TableRelationDef` (з графа формул),
`RegistryDef` + записи (з `DropdownList` і `Configuration` R…BL),
`ext.Legacy*Mapping` (з `MapAttributes` — порядок полів у `;`-рядку).
Без цього ручне заведення ~90 таблиць × ~40 колонок = ~3 600 записів вручну.
**Обов'язково** — звіт про невимпортоване (87 `#REF!`-імен, 16 зовнішніх книг).

**ФВ-2.11 Імпорт структури з довільного `.xlsx`** — створення нового шаблону
з наявного Excel-файлу (розпізнавання заголовків, типів, стилів). Це робить
інструмент придатним не тільки для ECR.

**ФВ-2.12 Зв'язування таблиць** (`TableRelationDef`) — **опційний** механізм:
шаблон може не мати жодного зв'язку, і тоді таблиці незалежні.

| Тип зв'язку | Призначення | Приклад у чинному шаблоні |
|-------------|-------------|---------------------------|
| `MetadataSource` | одна таблиця постачає поля всім іншим | `2. Contract` -> усі 18 звітних аркушів |
| `Lookup` | колонка посилається на рядок іншої таблиці | Permit number -> довідник дозволів |
| `Rollup` | таблиця агрегує іншу | `7.0 Water consolidation` <- `7. Water Report` |
| `Mirror` | значення дзеркалиться | `7a` / `7b` <- `7. Water Report` |
| `ParentChild` | ієрархія рядків між таблицями | GROUP -> ITEM |
| `Constraint` | крос-табличне правило без переносу даних | «сума A == підсумок B» |

`SyncMode` = `Reference` (за замовчуванням — значення живе в одному місці) /
`Copy` (матеріалізація) / `Computed`.

`OnSourceChange` = `Propagate` / `Warn` / `Block` / `Ignore` — що робити із
залежними даними при зміні джерела.

> Це замінює зашиті у VBA `GetContractSheetAttributes` (метадані контракту),
> `modB16AmendmentFlow` (764 рядки — стає `OnSourceChange = Warn`),
> автовиклик `SaveWaterConsolidationForMonth` (стає `Propagate`)
> і `ExpandLinkedSheetGroups`.

**ФВ-2.13 Зв'язки налаштовуються у веб-інтерфейсі, а не в конфігах чи коді.**

Адміністратор має окремий екран **«Зв'язки»** у конструкторі шаблону:

| Елемент UI | Призначення |
|------------|-------------|
| **Схема зв'язків** | візуальний граф: вузли = таблиці, ребра = зв'язки, підписані типом. Клік по ребру -> редагування |
| **Майстер створення зв'язку** | покроково: тип -> джерело (таблиця/колонка) -> ціль -> `SyncMode` -> `OnSourceChange` -> перевірка |
| **Список зв'язків** | таблична форма з фільтрами, для великих шаблонів |
| **Перевірка на льоту** | цикли, недосяжні посилання, несумісні типи колонок — показуються одразу, до збереження |
| **Попередній перегляд впливу** | «цей зв'язок зачепить 90 таблиць і 47 документів» |
| **Тестування виразу** | для `Rollup`/`Constraint` — підстановка тестових значень і показ результату |

Правила екрана:
* створення зв'язку **між несумісними типами колонок відхиляється** (напр. `Lookup`
  з `Decimal`-колонки на `String`-ключ);
* **цикл заборонений** — майстер не дає зберегти, показує ланцюжок;
* зв'язок редагується лише у `Draft`-версії шаблону;
* видалення зв'язку класифікується як зміна структури (§5.5) — зі звітом про вплив.

**ФВ-2.14 Той самий підхід — для решти конфігурації.** У вебі налаштовуються:
структура, стилі, формули, правила валідації, зв'язки, правила складу документа,
довідники, політики періодів, ролі і права, мапінг зовнішніх джерел.

> **Принцип: у файлах конфігурації залишаються тільки рядки підключення
> і технічні параметри інфраструктури. Уся предметна конфігурація — в БД,
> редагується через UI, версіонується і аудитується.**

Детально — [09-template-engine.md](09-template-engine.md) §5.

**ФВ-2.15 Правила доступу до періодів — частина шаблону** ⭐

Чинна кнопка **«Protect sheets»** (`Protection.ToggleProtection`) робить складну
річ: запитує пароль і «день відсічення», блокує всі аркуші, розблоковує колонки
лише одного місяця, потім **повторно блокує рядки-заголовки за жорстко зашитими
номерами для кожного аркуша**, а для `7. Water Report` ще й перевіряє вікно дії
дозволу по кожному рядку окремо.

Усе це стає **конфігурацією шаблону** (`cfg.PeriodAccessRuleDef`), що задається
при створенні шаблону у вебі.

| Поле | Призначення |
|------|-------------|
| `Scope` | `Sheet` / `Table` / `Column` / `Row` |
| `TargetId` | до чого застосовується |
| `RuleKind` | тип правила (нижче) |
| `Parameters` | JSON з параметрами правила |
| `Priority` | порядок застосування; конкретніше правило перекриває загальніше |
| `IsDeny` | явна заборона — виграє над дозволами |

**Типи правил (`RuleKind`):**

| Тип | Що робить | Що замінює у VBA |
|-----|-----------|------------------|
| `AlwaysReadOnly` | завжди тільки читання | жорстко зашиті `Range("A6:E90").Locked = True` у `Sheet_Config.Init*` |
| `HeaderRows` | рядки-заголовки завжди заблоковані | масиви номерів рядків у `Protection.bas` (`hdrRows = Array(3,4,14,15,…)`) |
| `EditablePeriodOnly` | редагується лише період у стані `Open`/`Grace` | основна логіка `ToggleProtection` |
| `RelativeWindow` | вікно «поточний період ± N» | «попередній місяць за cutoff day» |
| `SourceWindow` | вікно береться з довідника (напр. дати дії дозволу) | `ApplyPermitMonthLocks` |
| `Expression` | довільна умова над значеннями рядка | нове — раніше вимагало правки коду |

**Приклад конфігурації для `7. Water Report`:**

```
Rule 1  Scope=Sheet  Target="7. Water Report"  Kind=EditablePeriodOnly
Rule 2  Scope=Row    RowType=Header            Kind=HeaderRows
Rule 3  Scope=Column Target="A..E"             Kind=AlwaysReadOnly
Rule 4  Scope=Row    RowType=Group             Kind=AlwaysReadOnly   ← формульні підсумки
Rule 5  Scope=Row    RowType=Item              Kind=SourceWindow
        Parameters = { source: "Registry:Permit",
                       keyColumn: "PermitId",
                       from: "StartDate", to: "ActualEndDate",
                       onOutOfWindow: "LockAndWarn" }
```

**ФВ-2.16** `onOutOfWindow` визначає поведінку поза вікном:
`Lock` (заблокувати), `LockAndWarn` (заблокувати з попередженням),
`LockAndClear` (заблокувати і очистити — поточна поведінка Excel,
**потребує підтвердження користувача**), `Warn` (лише попередити).

> ⚠ Чинна реалізація **очищає дані** при зміні дозволу. Це має лишитися
> явним, підтверджуваним вибором, а не типовою поведінкою.

**ФВ-2.17** Шаблон містить **типову політику періодів** (`PeriodPolicy`:
`OpenOffsetDays` / `GraceOffsetDays` / `HardCloseOffsetDays`). При створенні
проєкту з шаблону вона підставляється як значення за замовчуванням; проєкт
може її перевизначити.

**ФВ-2.18** У конструкторі шаблону є **попередній перегляд матриці доступу**:
таблиця `період × аркуш` із кольоровим позначенням «редагується / тільки читання
/ приховано» — щоб адміністратор бачив результат правил до публікації версії,
а не з'ясовував його на живих даних.

## ФВ-3. Документи (для ECR — «HSE-файли»)

**ФВ-3.0 Модель зберігання — сутність з іменованими полями, а не рядок.**

Чинне рішення пише весь рядок таблиці в **один текстовий атрибут**, розділений `;`,
без жодного опису того, що означає кожна позиція:

```
Attribute_0010 = "1;7001001;ITEM;094f83a4-…;0151202a-…;;125.5;1;0;0;0;"
```

У новій системі кожен рядок — **сутність із явно ідентифікованими полями**:

| Рівень | Ідентичність | Де описано |
|--------|--------------|------------|
| Таблиця | `TableDef.Code` | `cfg.TableDef` |
| **Рядок** | **`RowKey`** — стабільний бізнес-ключ (`7001001`), **не позиція** | `doc.TableRow` |
| **Поле** | `ColumnDef.Code` + `DataType` | `cfg.ColumnDef` |
| Значення | типізоване: `ValueNumeric` / `ValueString` / `ValueDate` / `ValueBool` / `ValueRegistryEntryId` (FK на довідник) | `doc.CellValue` |

Ключова відмінність — **ідентичність рядка стає стабільною**. Зараз вона
позиційна (`Attribute_0010` = «перший рядок діапазону»), тому вставка рядка
в Excel зсуває всю нумерацію і старі дані починають означати інше.
З `RowKey` перестановка рядків не зачіпає дані.

Порядок відображення (`Ordinal`) відокремлений від ідентичності (`RowKey`) —
це два різні поля.

Наслідки: типізація, посилальна цілісність через FK на довідники,
звичайні SQL-запити замість вивантаження й парсингу, безпечна зміна структури.

**ФВ-3.1** Створення документа: вибір проєкту -> вибір аркушів/таблиць
(аналог `UserSelection.frm`) -> заповнення шапки (`__Header`) -> створення.

**ФВ-3.2** Правила складу документа (`SheetGroupRule`: `RequiresAll` / `RequiresOne` /
`Excludes` / `AlwaysInclude`) задаються в шаблоні і перевіряються при генерації
та при зміні складу. Приклад для ECR: обрано будь-який з `7. Water Report` / `7a` /
`7b` / `7.0` — додаються всі чотири, бо між ними є `Mirror`/`Rollup`-зв'язки
(перенос `ExpandLinkedSheetGroups`, але як дані, а не код).

**ФВ-3.3** Заповнення таблиць у grid-редакторі:
* навігація клавіатурою як в Excel (Tab, Enter, стрілки);
* вставка діапазону з буфера обміну (Ctrl+V з Excel);
* автозаповнення (fill down/right);
* undo/redo;
* заблоковані комірки візуально відрізняються;
* «брудні» (незбережені) комірки підсвічуються.

**ФВ-3.4** **Формули.** Підтримуються на рівні:
* `ColumnDef.Formula` — формула для всієї колонки;
* `RowDef.Formula` — формула для рядка (підсумки `GROUP`);
* `CellOverride` — формула для окремої комірки.

Синтаксис — підмножина Excel. **Точний набір за автоматичним аналізом усіх
формул чинного шаблону — 11 функцій:**

| Функція | Входжень | Коментар |
|---------|---------:|----------|
| `VLOOKUP` | 429 | ⚠ **не формула, а посилання на довідник** — замінюється `ColumnDef.LookupRegistryDefId` і **зникає** |
| `LEFT` | 384 | витяг ID з композита `"7001001 - Name"` |
| `SUM` | 245 | підсумки GROUP-рядків |
| `VALUE` | 230 | текст -> число |
| `IFERROR` | 228 | обгортка навколо VLOOKUP |
| `ROUNDDOWN` | 5 | |
| `TEXT`, `CHAR`, `CONCATENATE`, `TEXTBEFORE`, `TEXTAFTER` | 12 разом | побудова відображуваного тексту |

**Наслідок:** у першій редакції ТЗ фігурувало «~25 функцій». Реально **11**,
з них після заміни `VLOOKUP` на прив'язку до реєстру і `CONCATENATE`/`TEXT`
на `DisplayTemplate` лишається **~7 обчислювальних функцій і ~250 формул**.

Це суттєво знижує ризик «розбіжність рушіїв формул» (§8) порівняно з
початковою оцінкою. Додатково додати за потреби: `IF`, `ROUND`, `AVERAGE`,
`MAX`, `MIN`, `ABS`.

Посилання: `[Sheet].[Table].[Row].[Column]`, діапазони, `[CurrentRow]`, `[Period]`.

**Посилання на інші періоди і документи** — обов'язкові для універсальності:
* `[Period:-1]` — попередній період того самого документа
  (у чинному шаблоні: «Residual waste on site from previous month»);
* `[Period:First]` / `[Period:Last]` — межі року;
* `[PrevProject].[Sheet].[Table].[Row].[Column].[Period:Last]` — **перенесення
  залишків з минулого року** (колонка H «previous year balance» у `7. Water Report`
  зараз заповнюється вручну);
* `[__Header].[Field]` — поля шапки документа через `MetadataSource`-зв'язок.

Крос-документні посилання резолвяться при генерації документа (значення
копіюється як `Snapshot`) або динамічно (`Live`) — задається в `FormulaDef.RefMode`.
За замовчуванням `Snapshot`: затверджений минулий рік не має «пливти».

**Перерахунок:** на клієнті — миттєва підказка (`formulajs`); на сервері — **авторитетний**.
Клієнтське значення ніколи не зберігається; при збереженні замінюється серверним.
Розбіжність показується користувачу як попередження.

**ФВ-3.5** Крос-аркушні формули (як `7.0 Water consolidation` = rollup з `7. Water Report`).
Граф залежностей будується при публікації версії шаблону; циклічні посилання
відхиляються.

**ФВ-3.6** Автозбереження чернетки (кожні N секунд або на blur комірки).

**ФВ-3.7** Одночасна робота: оптимістичне блокування по `RowVersion`; при конфлікті —
показ розбіжностей і вибір користувача. Опційно — presence (хто ще в документі).

**ФВ-3.8** Копіювання документа з попереднього періоду/документа (структура + опційно значення).

**ФВ-3.9** Зміна бізнес-ключа документа (для ECR — `FileNumber`) -> контрольована
операція через `TableRelationDef.OnSourceChange = Warn` на `MetadataSource`-зв'язку
(перенос `modB16AmendmentFlow`): показ, які дані вже існують під старим і новим
ключем, вибір дії (перенести / створити новий документ / скасувати).

## ФВ-4. Експорт та імпорт

**ФВ-4.1 Експорт у `.xlsx`:**
* повний документ (усі аркуші) або вибрані;
* збереження візуального макета (заголовки, об'єднання, формати, кольори);
* два режими: **«з формулами»** (формули записуються як Excel-формули) і
  **«тільки значення»**;
* лист «Метадані»: бізнес-ключ документа, проєкт, версія шаблону
  (+ `PresentationRevision`), статус, хто/коли експортував, контрольна сума.

**ФВ-4.2 Експорт у CSV/JSON** — для інтеграцій.

**ФВ-4.3 Імпорт з `.xlsx`:**
* розпізнавання за контрольною сумою/метаданими -> прив'язка до документа;
* **режим «попередній перегляд»**: показати diff (що зміниться) до застосування;
* повна валідація перед застосуванням; часткове застосування заборонено —
  або все, або нічого (транзакція);
* звіт про помилки з посиланням на конкретну комірку.

**ФВ-4.4 Імпорт legacy `.xlsm`** — одноразова міграція існуючих HSE-файлів.

**ФВ-4.5** Асинхронність: файли > N МБ обробляються фоновою задачею з прогресом.

## ФВ-5. Доступ, валідація, затвердження

### 5.1 Ролі — створюються адміністратором, не зашиті в коді ⭐

**ФВ-5.1** Ролі — це **дані**, а не enum. Адміністратор створює роль, набирає їй
права і призначає користувачам або AD-групам. Додати роль «Аудитор води, тільки
читання» — операція в UI, не реліз коду.

Повний опис моделі — **[11-security-model.md](11-security-model.md)**.

**ФВ-5.2 Два види прав у ролі:**

| Вид | Що дає | Приклад |
|-----|--------|---------|
| **Функціональні** (`Permission`) | дія в системі загалом | `Template.Publish`, `Period.Reopen`, `Security.ManageUsers`, `Dictionary.Sync` |
| **Ресурсні** (`ResourceGrant`) | рівень доступу до конкретного об'єкта структури | «`7. Water Report` -> `Write`», «`9. Utility` -> `Read`», «колонка `Cost` -> `None`» |

Каталог функціональних прав — **системний** (задається розробником, поповнюється
з релізами). Ролі, набори прав і призначення — **користувацькі дані**.

**ФВ-5.3 Рівні доступу до ресурсу** (упорядковані):

| Рівень | Значення |
|--------|----------|
| `None` | ресурс не видно взагалі |
| **`Read`** | видно, редагування заблоковане (**«тільки для читання»**) |
| `Write` | введення і зміна даних |
| `Submit` | + подання на затвердження |
| `Approve` | + затвердження/відхилення |
| `Manage` | + зміна структури цього ресурсу |

**ФВ-5.4 Ресурси, на які видаються права** (ієрархія з успадкуванням):

```
Project
  └─ SheetDef          «аркуш 7. Water Report»
      └─ TableDef      «таблиця Utility_9_05»
          └─ ColumnDef «колонка Cost — приховати від підрядників»
```

Право видане на верхньому рівні успадковується вниз; більш конкретний
грант перекриває успадкований. **Явна заборона (`IsDeny`) виграє завжди.**

**ФВ-5.5 Області дії (scopes).** Призначення ролі обмежується даними:
`Project` × `Area` / `Region` / `Contractor` / `Location` — тобто будь-якими
полями, позначеними `ColumnDef.IsScopeField`.

Приклад: «роль *Затверджувач* для проєкту 2026, регіон Mangistau, підрядник AGS».

**ФВ-5.6 Рядковий фільтр (опційно).** Грант може містити `RowFilterExpression` —
роль бачить лише рядки, що задовольняють умову.
Приклад: `[Row].[PermitId] IN [User].[AllowedPermits]`.

**ФВ-5.7 Режим «тільки читання»** реалізується трьома незалежними способами:
1. роль, у якій усі гранти = `Read`;
2. прапорець `IsReadOnly` на **призначенні** ролі — обмежує ефективний рівень
   до `Read`, не змінюючи саму роль (зручно для тимчасового обмеження);
3. системний стан (закритий період, `Approved`-документ, `Deprecated`-версія
   шаблону) — примусово знижує рівень до `Read` для всіх, крім носіїв
   відповідного функціонального права.

**ФВ-5.8 Вбудовані ролі.** Система постачається з набором готових ролей
(`IsSystem = 1`): `Viewer`, `DataEntry`, `Approver`, `PeriodAdministrator`,
`TemplateAdministrator`, `SystemAdministrator`. Їх можна **копіювати і змінювати
копію**, але не видалити — щоб система не залишилась без адміністратора.

**ФВ-5.9 Призначення ролей** — на **AD-групу** (основний спосіб для доменних
користувачів), на доменного користувача персонально або на **локальний обліковий
запис**. Модель прав однакова для всіх трьох випадків: як користувач
автентифікувався — на його права не впливає.

Призначення має необов'язковий строк дії (`ValidFrom` / `ValidTo`) — для тимчасового
доступу.

**ФВ-5.10 Прозорість прав.** UI має відповідати на питання
*«чому цей користувач бачить/не бачить це поле»*: показ ефективних прав
із зазначенням, який саме грант якої ролі спрацював.
Без цього налаштовуваний RBAC стає некерованим.

**ФВ-5.11 Симуляція.** Адміністратор може подивитися систему «очима користувача»
без входу під ним (`Impersonate (read-only)`), з обов'язковим записом в аудит.

### 5.2 Стани документа

```
      ┌────────┐  submit   ┌───────────┐  approve  ┌──────────┐
      │ Draft  ├──────────►│ Submitted ├──────────►│ Approved │
      └───┬────┘           └─────┬─────┘           └────┬─────┘
          ▲                      │ reject                │ reopen
          └──────────────────────┘                       │ (PeriodAdmin,
          ▲                                              │  з коментарем)
          └──────────────────────────────────────────────┘
```

**ФВ-5.12** У стані `Draft` дані існують, але **позначені як недійсні** —
не потрапляють у звіти, не передаються зовнішнім споживачам, у UI мають явну ознаку.

**ФВ-5.13** `Submitted` -> дані заморожені для автора, доступні носіям рівня `Approve`.

**ФВ-5.14** `Approved` -> дані стають дійсними, фіксується незмінна версія (snapshot).
Документ переходить у режим «тільки читання» для всіх, крім носіїв права
`Document.Reopen`.

**ФВ-5.15** `Reject` -> повернення в `Draft` з обов'язковим коментарем.

**ФВ-5.16** Переходи можливі на рівні: весь документ / окремий аркуш / окремий період —
**потребує уточнення** (див. §12).

**ФВ-5.17** Багатоетапне затвердження (2+ рівні) — конфігурується на рівні проєкту;
крок маршруту вимагає не «роль зі списку», а **наявність рівня `Approve`
на відповідному ресурсі** — тому маршрути не ламаються при перейменуванні ролей.

### 5.3 Валідація

Три рівні, усі керовані метаданими:

| Рівень | Коли | Приклад |
|--------|------|---------|
| **Комірка** | при вводі (клієнт) + при збереженні (сервер) | тип, діапазон (`0..744` годин), обов'язковість, значення зі списку, регулярний вираз |
| **Рядок / Таблиця** | при збереженні | «сума ITEM = значення GROUP», «якщо A заповнено, B обов'язкове» |
| **Документ** | при `Submit` | permit обрано і дійсний, рік у межах проєкту, усі обов'язкові аркуші заповнені |

**ФВ-5.18** `ValidationRule`: `Scope` (Cell/Row/Table/Document), `Severity`
(`Error` — блокує, `Warning` — потребує підтвердження, `Info`), `Expression`,
`MessageEn/Ru/Kz`.

**ФВ-5.19** `Submit` неможливий за наявності `Error`. `Warning` — з підтвердженням,
яке записується в аудит.

**ФВ-5.20** **Permit-правила** (перенос `ApplyPermitMonthLocks`):
* місяць редагується для рядка, лише якщо вікно дії дозволу перетинається з місяцем;
* зміна дозволу -> попередження зі списком місяців, які будуть заблоковані/очищені;
* fail-open при нерезолвленому дозволі.

### 5.4 Аудит

**ФВ-5.21** Кожна зміна значення комірки: хто, коли, старе -> нове, з якого IP,
у якому стані був документ і період, чи це пізня зміна (`IsLateEdit`).
Незмінний журнал (append-only, заборона `UPDATE`/`DELETE` через права БД).

**ФВ-5.22** UI: історія комірки, історія документа, порівняння версій.

**ФВ-5.23** Журнал інтеграції: кожен збір даних і кожна передача зовнішньому
споживачу — запит, відповідь, статус, тривалість, повторні спроби.

**ФВ-5.24** Аудит змін прав: створення/зміна ролі, зміна грантів, призначення
і відкликання ролей, кожна `Impersonate`-сесія.

## ФВ-6. Продуктивність і автентифікація

### 6.1 Два провайдери автентифікації

**ФВ-6.1** **Windows Authentication** (Kerberos, fallback NTLM) — SSO без форми входу
для доменних користувачів.

**ФВ-6.2** **Внутрішні (локальні) облікові записи** — адміністратор створює
користувача з логіном і паролем, призначає ролі, користувач працює.
Для підрядників, зовнішніх учасників і випадків, коли доменного облікового
запису немає.

**ФВ-6.3** Обидва провайдери випускають **одну й ту саму ідентичність застосунку**
(cookie з однаковими claims). Уся авторизація нижче не знає, яким способом
користувач увійшов. Ролі призначаються **однаково** на AD-групу, доменного
користувача і локального користувача.

**ФВ-6.4** Політика паролів (довжина, складність, історія, строк дії, блокування
після N спроб, TTL сесії) — **налаштовується адміністратором у UI**, а не в
конфігураційних файлах.

**ФВ-6.5** Зберігання паролів — `PasswordHasher<T>` (PBKDF2-HMAC-SHA256,
≥100 000 ітерацій) або Argon2id. Пароль ніколи не логується, не потрапляє
в аудит і не повертається API.

**ФВ-6.6** Опційно 2FA (TOTP) для локальних облікових записів; рекомендовано
обов'язкова для ролей із правами групи `Security`.

**ФВ-6.7** `SecurityStamp`: зміна пароля, ролей або блокування **негайно
інвалідує всі активні сесії** користувача.

**ФВ-6.8** Первинне налаштування: при першому запуску створюється локальний
обліковий запис `admin` зі згенерованим паролем (показується один раз,
обов'язкова зміна при вході) — щоб система була керована до налаштування AD-груп.

Детально — [11-security-model.md](11-security-model.md) §1.

### 6.2 ⚠ Наслідок для інтеграції з PI AF

Локальний користувач **не має Windows-ідентичності**, тому запит до PI Web API
від його імені за Kerberos неможливий у принципі.

**ФВ-6.9** Доступ до PI AF (обома транспортами — Web API і SQL DAS) виконується
**під сервісним обліковим записом** із правами читання в AF; реальний користувач
фіксується в аудиті ECR. PI SQL DAS (RTQP) додатково не потребує Kerberos-делегування
взагалі (ІНТ-10).

| Варіант | Оцінка |
|---------|--------|
| **A. Сервісний обліковий запис** (рекомендація) | працює для обох провайдерів, дозволяє connection pooling, просто налаштувати |
| B. Kerberos constrained delegation (S4U2Proxy) | **покриває лише доменних користувачів** — для локальних не працює взагалі, тому як єдина модель не підходить |

> Вимога внутрішньої автентифікації фактично **знімає варіант B** як цілісне
> рішення. Підтвердити з ІБ — див. §12.

### 6.3 Продуктивність

**ФВ-6.10 Цільові показники:**

| Операція | Ціль (p95) |
|----------|------------|
| Відкриття таблиці 500×60 | < 1.5 с |
| Збереження зміненого діапазону (100 комірок) | < 300 мс |
| Перерахунок формул на клієнті | < 100 мс |
| Пошук документа за бізнес-ключем (`FileNumber`) | < 200 мс |
| Експорт документа в `.xlsx` (усі аркуші) | < 10 с |
| Збір даних з PI AF за документ × 12 періодів (фоново) | < 60 с |
| Одночасних активних користувачів | 100 |

> Повний бюджет продуктивності з моделлю навантаження, розкладкою по шарах,
> планом навантажувальних тестів і sizing інфраструктури —
> **[14-performance.md](14-performance.md)**.
>
> Ключове: 100 користувачів ≈ 42 RPS у середньому і **~125 RPS у пік**
> (останні дні періоду), причому всі б'ють в **один і той самий період** —
> тобто в одні партиції. Пік треба тестувати окремим сценарієм.

**ФВ-6.11** Технічні засоби досягнення:
* віртуалізований grid (рендер лише видимих рядків);
* пагінація/lazy-load по таблицях, а не по всьому документу;
* `AsNoTracking` + проєкції в EF Core для читання;
* компільовані запити для гарячих шляхів;
* `SqlBulkCopy` для масових вставок;
* партиціонування `CellValue` по `PeriodKey` = `Year*100 + Sequence`;
* кеш метадат опублікованих версій у пам'яті: структурний шар — назавжди
  (immutable), презентаційний — інвалідується по `PresentationRevision`;
* `AccessProfile` користувача — кеш на сесію, інвалідація по `SecurityStamp`;
* батчинг запитів до PI AF при зборі (один `POST /batch` на пакет для Web API;
  set-based `WHERE` для SQL DAS);
* архівація закритих років (§5.1.1) — робочі таблиці не ростуть з роками.

**ФВ-6.12** Нефункціональні:
* доступність 99.5% у робочі години;
* RPO 15 хв, RTO 4 год;
* локалізація UI і метаданих: EN / RU / **KZ** для ECR; зберігання — JSON `…L10n`
  + реєстр `sys.Language`, тому додати мову = запис, а не міграція (§3.4 п.3).
  У чинних довідниках є `Name_EN`/`Name_RU`; KZ треба наповнити;
* журнали зберігаються 3 роки, дані — безстроково (архів — за окремим рішенням, §12 п.14).

## ФВ-7. Безпечна зміна структури «на льоту»

Наскрізна вимога. Технічні принципи — у §5.5 і в
[10-schema-evolution.md](10-schema-evolution.md).

**ФВ-7.1** Будь-яка зміна структури шаблону (аркуш, таблиця, колонка, рядок,
формула, правило, стиль) виконується **через UI, без релізу коду і без DDL**.

**ФВ-7.2** Перед застосуванням зміни система показує **звіт про вплив**:
клас ризику, скільки документів і комірок буде зачеплено, які дані можуть бути втрачені.

**ФВ-7.3** Зміни класу `Breaking` у версії, до якої вже прив'язані документи,
**заборонені технічно** — не попередженням, а відмовою операції.

**ФВ-7.4** Видалення елемента структури, на який є посилання з даних —
тільки soft delete. Дані залишаються доступними для читання.

**ФВ-7.5** Перехід документа на нову версію шаблону — **явна операція** з
попереднім переглядом (dry-run), підтвердженням і повним відкатом при помилці.
Часткове застосування заборонено.

**ФВ-7.6** Кожна зміна структури фіксується в аудиті: хто, коли, що саме,
який був звіт про вплив, чи було підтвердження.

**ФВ-7.7** Фонова перевірка інваріантів цілісності (щоночі) з журналом розбіжностей
і сповіщенням адміністратора.

**ФВ-7.8** Відкат: `TemplateVersion` можна перевести в `Deprecated`, але не видалити,
якщо є прив'язані документи. Документи продовжують працювати на своїй версії.

**ФВ-7.9 Два шари опублікованої версії.** Структурний шар (типи, ключі, формули,
зв'язки, `Error`-правила) — заморожений. **Презентаційний шар** (підписи, переклади,
стилі, порядок, `DisplayTemplate`, `Info`/`Warning`-правила) — **патчиться на льоту**
без нової версії, з аудитом і `PresentationRevision`. Це те, що робить систему
справді «на льоту» для повсякденних правок, не жертвуючи консистентністю даних
([10](10-schema-evolution.md) §2a).

## ФВ-8. Довідники та реєстри

Детально — **[12-reference-data.md](12-reference-data.md)**.

**ФВ-8.1 Універсальний механізм.** Плоский список (`Generic_EquipStatus`)
і складна сутність (`Permit` із правилами і вкладеними речовинами) — це **один
і той самий механізм**, різниця лише в кількості полів і зв'язків.
Адміністратор створює довідник у вебі, як таблицю: задає поля, типи, ключі,
посилання на інші довідники.

**ФВ-8.2 `RegistryDef`**: `Code` (ключ для `ColumnDef.LookupRegistryDefId`),
назви EN/RU/KZ, `Scope` (`Global`/`Project`), `SourceKind`
(`Local`/`External`/`Hybrid`), **`DisplayTemplate`** (`{Code} - {NameEn}` —
замінює формули `=TEXT(V2,"0")&" - "&W2`), `IsTemporal`, `IsHierarchical`,
`VersioningMode`.

**ФВ-8.3 `RegistryFieldDef`** — та сама форма, що й `ColumnDef`:
тип, обов'язковість, унікальність, `IsKey`, `IsDisplay`, `IsSearchable`,
**`LookupRegistryDefId`** (посилання на інший довідник) і `CascadeFromFieldId`
(каскадна фільтрація).

**ФВ-8.4 Зв'язки між довідниками** (`RegistryRelationDef`):

| Тип | Приклад із ECR |
|-----|----------------|
| `Cascade` | `Type -> Indicator`, `Entity -> Location` (зараз `lstType_Change` у формах) |
| **`Composition`** | `Permit -> Pollutant[]` — вкладена колекція |
| **`Association`** | `Permit × WaterBody -> Usage` (Intake/Discharge), зараз матриця `Configuration!BD:BL` |
| `Hierarchy` | `WasteGroup -> WasteItem` |

**ФВ-8.5 Правила довідника** (`RegistryRuleDef`): `ValidityWindow`
(вікно дії — живить `SourceWindow` у правилах доступу до періодів),
`RequiredWhen`, `UniqueWithin`, `Expression`, `CrossRegistry`.

**ФВ-8.6 Версійність — на двох рівнях:**

| Рівень | Механізм |
|--------|----------|
| **Структура** довідника | так само, як `TemplateVersion`: опублікована незмінна, зміна -> `CloneFrom` |
| **Записи** | `VersioningMode`: `None` / `SoftDelete` (аналог `Is_Available` в AF) / `Temporal` (`ValidFrom`/`ValidTo`) / `Full` (повна історія полів) |

**ФВ-8.7 Головне правило цілісності:**

> Запис довідника **ніколи не видаляється фізично**, якщо на нього посилаються дані.
> Документ, що посилався на значення, продовжує його резолвити.

Новий документ бачить у листбоксі лише активні на дату періоду значення;
старий документ показує знятe значення з позначкою «архівне»; збереження
з архівним значенням дає `Warning`, а не `Error`.

**ФВ-8.8 У комірці зберігається ID, а не текст.**

| | Зараз | Стане |
|---|---|---|
| Значення | `"Diesel - Дизель"` (текст) | `ValueRegistryEntryId = 42` (FK) |
| Перейменували значення в довіднику | історичні дані «відв'язалися» | зв'язок цілий, назва оновилася скрізь |
| Пошук | `LIKE '%Дизель%'` по всіх комірках | `WHERE ValueRegistryEntryId = 42` |

Це та сама проблема відсутньої ідентифікації, що й у рядках таблиць (ФВ-3.0),
і розв'язується так само.

**ФВ-8.9 Прив'язка до комірок.** Те, що зараз лежить у рядках 3–4 аркуша
`DropdownList` (`Contract_Area -> B, 6`; `Stationary_Type_of_Equipment -> E5, E146`),
стає полем `ColumnDef.LookupRegistryDefId` + `LookupFilter` + `CascadeFromColumnId` —
явно і типізовано, замість двох текстових комірок, які треба вручну тримати
в синхроні з макетом.

**ФВ-8.10 Зовнішні ідентифікатори.** GUID-и, розкидані по `Configuration!J3`,
`AW`, `BA` і `DropdownList!AL`, замінює `dic.RegistryExternalKey`:
`(DataSourceId, ExternalId, ExternalPath, SyncStatus)`. Один запис може мати
ID у кількох зовнішніх системах; зниклий у джерелі запис позначається
`Orphaned` явно, а не «тихо не оновлюється».

**ФВ-8.11 Синхронізація — конфігурація, не код.** `RegistrySyncMapping`
описує джерело, шаблон, мапінг полів, розклад і поведінку при зникненні
запису в джерелі (`OnMissingInSource = MarkOrphaned`). Замінює 5 модулів
синхронізації (≈4 400 рядків VBA).

**ФВ-8.12 UI:** конструктор довідника (поля, зв'язки, правила, мапінг),
редактор записів із фільтрами, перемикачем «станом на дату» для темпоральних,
вкладеними таблицями для `Composition`, редактором M:N для `Association`,
імпортом/експортом `.xlsx` і обов'язковим звітом **«Де використовується»**
перед зняттям значення.

# 5. Ключові технічні рішення

## 5.1 Стратегія зберігання даних

Оцінка обсягу — **~108–130 млн рядків `CellValue` на рік** залежно від заповненості
(див. `05-risks-and-gaps.md` §4 і `07-data-model.md` §11; порожні комірки
не матеріалізуються, тому реальна цифра, ймовірно, ближча до нижньої межі). Тому:

**Рішення: гібридна модель.**

| Що | Де | Чому |
|----|----|----|
| Метадані шаблонів | звичайні таблиці, immutable -> кеш назавжди | малий обсяг, часті `JOIN` |
| Заголовки документів, статуси | `doc.Document` + `doc.DocumentIndexValue` | пошук, фільтри без `JOIN` через комірки |
| **Значення комірок** | `doc.TableRow` (ідентичність `RowKey`) + `doc.CellValue`, **партиційовані по `PeriodKey` = `Year*100 + Sequence`**, PK `(PeriodKey, TableRowId, ColumnDefId)`, складений FK `(TableDefId, ColumnDefId)` | основний обсяг; комірка фізично не може потрапити в чужу колонку |
| «Значущі» поля для звітності | `DocumentIndexValue` (denormalized) або **indexed views** | швидкі агрегації |
| Історія змін | `aud.CellChange`, партиції по місяцях, columnstore на архів | append-only, стиснення |
| Закриті роки | `arc.*` (§5.1.1) | робочі таблиці тримають ~1 рік |

**Альтернатива, якщо `CellValue` виявиться завеликим:** зберігати рядок таблиці
як JSON у колонці `NVARCHAR(MAX)` з `OPENJSON`-індексами на 5–10 ключових полів.
Це компроміс між нормалізацією і обсягом. **Рішення приймається після навантажувального
тесту на реальних обсягах** (етап 0).

### 5.1.1 Архівування закритих років ⭐

Підхід, який уже застосовується в чинному рішенні і який зберігаємо:
**після завершення року і спливу offset дані переносяться з робочих таблиць
в архівні.**

```
                 31.12.2026     +45 днів (YearGraceOffsetDays, ФВ-1.8)
                      │                  │
  ─────── Active ─────┼───── Grace ──────┼──── Closed ────►
                      │                  │         │
                      │                  │    ArchiveJob
                      │                  │         ▼
   doc.CellValue (гарячі дані)      arc.CellValue (архів)
   партиції по PeriodKey            columnstore + стиснення
```

**АРХ-1** Архівування запускається **не за календарем, а за станом**:
проєкт перейшов у `Closed` (тобто рік завершився **і** сплив
`YearGraceOffsetDays`) -> у чергу на архівацію.

**АРХ-2** Архівні таблиці — дзеркало робочих у схемі `arc`:
`arc.TableInstance`, `arc.TableRow`, `arc.CellValue`, `arc.CellChange`.
Структура ідентична, але:
* **clustered columnstore index** замість rowstore (стиснення 5–10×,
  швидкі агрегації, повільні точкові update — що для архіву прийнятно);
* без `rowversion` і без тригерів;
* окрема файлова група, за потреби — окремий диск.

**АРХ-3 Архівація — транзакційна і перевірна:**
```
1. Порахувати контрольні суми на джерелі:
   COUNT_BIG(*), CHECKSUM_AGG(BINARY_CHECKSUM(*)), SUM(ValueNumeric)
   за списком партицій року (PeriodKey від YYYY01 до YYYY+кількість періодів)
2. Скопіювати батчами по ~500 тис. рядків:
   INSERT INTO arc.* WITH (TABLOCK) SELECT … FROM doc.* WHERE PeriodKey = @k
   (TABLOCK -> мінімальне логування і прямий запис у columnstore rowgroups)
3. Порахувати ті самі три контрольні суми на приймачі
4. Розбіжність -> ROLLBACK усього; aud.ConsistencyIssue(Critical); СТОП.
   Дані з doc.* НЕ видаляються — це головне правило процедури
5. Збіг -> TRUNCATE TABLE doc.* WITH (PARTITIONS (@from TO @to))
   для doc.CellValue, doc.TableRow, doc.TableInstance (спільна схема
   партиціонування ps_ByPeriodKey). Для aud.CellChange діапазон партицій
   рахується ОКРЕМО, за вікном ChangedAt (ps_AuditByMonth), а не за PeriodKey
6. Запис у itg.ArchiveRun: напрямок, рядків, контрольні суми, тривалість
```

> ⚠ **`SWITCH PARTITION` тут не застосовний, і це навмисно.** `SWITCH` вимагає
> однакової файлової групи та ідентичної структури індексів джерела і приймача,
> а `arc.*` за АРХ-2 — **clustered columnstore на окремій файловій групі**. Обидві
> умови порушені свідомо: різниця у стисненні й розміщенні і є сенсом архіву.
> `DELETE` батчами теж не підходить — на 108 млн рядків він роздуває журнал
> транзакцій і тримає блокування годинами. Тому саме
> `TRUNCATE TABLE … WITH (PARTITIONS)` (SQL Server 2016+): звільняє партиції
> майже миттєво і мінімально логується. Деталі — `reference/backend/B02` §6 (BR-06).

**АРХ-3a Вимоги до виконання процедури:**
* операція **відновлювана**: після збою продовжується з партиції, на якій
  зупинилася, а не починається спочатку;
* під час виконання проєкт має прапорець `IsArchiving`; поріг вибору джерела
  читання береться з `doc.Project.Status`/`itg.ArchiveRun`, **не з дати** —
  інакше читання ловить напівстан;
* повна зупинка системи **не потрібна**; потрібне вікно низької активності,
  бо вартість операції — IO від перекачування обсягу року.

**АРХ-4** Читання архіву **прозоре для користувача**: репозиторій сам обирає
джерело за `PeriodId`/`ProjectId`. UI лише позначає документ як «архівний»
і показує, що редагування недоступне без `Reopen`.

**АРХ-5 Розархівація.** Якщо `PeriodAdministrator` робить `Reopen` закритого
року — дані повертаються в робочі таблиці тією самою транзакційною процедурою
у зворотному напрямку. Без цього `Reopen` для архівного року був би неможливий.

**АРХ-6** Архів **ніколи не видаляється автоматично**. Політика видалення —
окреме рішення бізнесу, виконується вручну з підтвердженням.

### АРХ-7 Редакція SQL Server: базова — Standard, Enterprise використовується автоматично

**Вимога.** Система **повністю функціональна на SQL Server Standard 2016 SP1+**.
Якщо в контурі виявлено Enterprise, система **автоматично** вмикає операційні
можливості, які Standard не дає, — без перезбирання, без іншої гілки коду і без
ручного налаштування.

**Незмінний принцип: редакція впливає лише на операційні стратегії, ніколи —
на модель даних, семантику чи результати.** Схема, запити, розрахунки й числа
однакові в обох редакціях. Інакше довелося б тестувати два продукти.

**Визначення можливостей при старті.** Застосунок виконує запит і зберігає
результат у `SqlCapabilities` (singleton, оновлюється при старті й за командою
адміністратора):

```sql
SELECT SERVERPROPERTY('Edition')              AS Edition,
       SERVERPROPERTY('EngineEdition')        AS EngineEdition,   -- 3 = Enterprise/Developer
       SERVERPROPERTY('ProductMajorVersion')  AS MajorVersion,
       SERVERPROPERTY('ProductLevel')         AS ProductLevel,
       DATABASEPROPERTYEX(DB_NAME(),'IsReadCommittedSnapshotOn') AS Rcsi;
```

**Що вмикається на Enterprise:**

| Можливість | Standard (базовий режим) | Enterprise (автоматично) |
|---|---|---|
| Перебудова індексів | `OFFLINE`, по одній партиції, у вікні обслуговування | `WITH (ONLINE = ON, RESUMABLE = ON)` — без вікна |
| Ізоляція фонового перерахунку від інтерактивного піку | обмеження на рівні застосунку: стеля воркерів і розмір батча в дні піку | **Resource Governor**: окрема workload group для фонових задач |
| Паралелізм по партиціях | обмежений | повний — коротший `RecalculationJob` і агрегації `rpt.*` |
| Розмір батча архівації | ~500 тис. рядків | адаптивно більший |
| Стеля sizing | буфер-пул 128 ГБ, 24 ядра — враховується в рекомендаціях health-ендпоінта | обмеження ОС |

**Правила реалізації:**

1. **Жодного `IF Enterprise` в бізнес-коді.** Різниця локалізована в
   інфраструктурному шарі: обслуговування індексів, планувальник фонових задач,
   `ArchiveJob`. Use-cases про редакцію не знають.
2. **Явне перевизначення.** `Database:EditionMode` = `Auto` (типово) / `Standard` /
   `Enterprise`. Потрібне, коли DBA забороняє `ONLINE`-операції навіть на
   Enterprise, і для відтворення прод-поведінки в тестовому контурі.
3. **Developer/Evaluation повідомляють `EngineEdition = 3`**, тобто виглядають як
   Enterprise. У непродуктивних контурах це прийнятно; для прод-контуру режим
   фіксується явно через `EditionMode`.
4. **Перевірка при старті — блокуюча** (ФВ-7, «створити/перевірити модель даних»):
   * версія < 2016 SP1 на Standard → **старт зупиняється** з поясненням: у цій
     редакції немає партиціонування, columnstore і компресії, тобто модель
     архівації (АРХ-1…АРХ-6) не працює;
   * RCSI вимкнено → попередження рівня `Critical` у health і запис у журнал
     (вмикання — операція DBA, не застосунку);
   * відсутні файлові групи/схема партиціонування → зупинка з інструкцією.
5. **Health-ендпоінт показує фактичний режим**: редакція, версія, увімкнені
   можливості, і — окремим рядком — що система **втрачає** в поточному режимі
   (наприклад: «перебудова індексів потребує вікна обслуговування»).
6. **Навантажувальні тести (`14`) виконуються в режимі Standard.** Бюджет
   продуктивності має витримуватися на базовій редакції; Enterprise дає запас,
   а не умову.

> Пов'язане відкрите питання **B-1** (`17` §1) — не «яку редакцію обрати», а
> «яка редакція фактично в контурі»: від відповіді залежить лише те, чи потрібне
> вікно обслуговування, крім випадку Standard < 2016 SP1, який блокує модель.

**Що це дає:**

| | Без архівування | З архівуванням |
|---|---|---|
| Обсяг робочих таблиць | росте лінійно: 108 млн × N років | ~108 млн (поточний рік) + невеликий хвіст |
| Час запитів по поточному року | деградує з роками | стабільний |
| Обслуговування індексів | вікно росте щороку | стабільне |
| Історичні звіти | ті самі таблиці | columnstore — швидші агрегації, ніж у rowstore |

> Це знімає найгостріший ризик моделі даних (§8). Навіть якщо нормалізована
> модель на 108 млн рядків працює на межі — вона працює на межі **сталого**
> обсягу, а не зростаючого.

## 5.2 Рушій формул

| Варіант | Ліцензія | Плюси | Мінуси |
|---------|----------|-------|--------|
| **NCalc** (.NET) | MIT | легкий, швидкий, розширювані функції | немає Excel-функцій «з коробки» — реалізувати треба **11** (реальний набір шаблону), з них ~7 обчислювальних |
| ~~HyperFormula~~ | ⚠ **GPLv3** / комерційна | 400+ Excel-функцій | **GPLv3 неприйнятна для закритого корпоративного застосунку** |
| `@formulajs/formulajs` | MIT | 500+ Excel-функцій | лише бібліотека функцій, граф залежностей писати самим |
| `fast-formula-parser` | MIT | парсер + обчислювач із посиланнями | менша спільнота |
| **ClosedXML calc engine** | MIT | Excel-семантика | обмежений набір функцій, повільний |
| **Власний парсер (ANTLR)** | — | повний контроль | найдорожче |

**Рішення: серверний рушій — єдине авторитетне джерело істини.**

```
NCalc (сервер)         ← авторитетний результат, зберігається в CellValue
   ▲
   │ при збереженні / recalculate
   │
formulajs (клієнт)     ← лише миттєва візуальна підказка під час вводу
```

Клієнтське значення **ніколи не зберігається** — при збереженні воно замінюється
серверним. Це прибирає найбільший ризик проєкту (розбіжність двох рушіїв):
навіть якщо клієнт порахує інакше, у БД потрапить лише серверний результат,
а розбіжність буде видно одразу в UI.

**Обов'язковий тест еквівалентності:** **усі ~250 обчислювальних формул** чинного
шаблону + синтетичні крайові випадки (порожні, помилки, від'ємні, округлення)
прогоняються через NCalc, `formulajs` і Excel; розбіжності документуються.
Задача Етапу 0 (0.3).

## 5.3 Інтеграція з PI AF — стратегія

**Рішення: SQL — єдина система обліку (system of record). PI AF — ДЖЕРЕЛО даних,
не цільове сховище.**

```
                    ┌──────────────────────────────┐
   PI AF ──────────►│  PiAfConnector (адаптер)     │
   (сирі дані,      │  read-only, за розкладом     │
    довідники,      └──────────────┬───────────────┘
    tag-значення)                  │ нормалізація
                                   ▼
   Користувач ──────────────►  ┌─────────┐
   (веб, введення)             │   SQL   │  ← єдине джерело істини
                               └────┬────┘
                                    │
                    ┌───────────────┼───────────────┐
                    ▼               ▼               ▼
              Валідація        Формули         Розрахункові
              Workflow         Звіти           модулі (наст. фаза)
```

### Що змінилося порівняно з попередньою редакцією

Раніше передбачалося, що ECR публікує затверджені дані назад у PI AF.
За уточненням замовника **система обліку — SQL**, і введені користувачем дані
зберігаються напряму в SQL. PI AF залишається у ролі **джерела сирих даних**,
частина яких існує тільки там.

### 5.3.1 PiAfConnector — вимоги

**ІНТ-1** Адаптер реалізує інтерфейс `IExternalDataSource` і **не є частиною ядра**.
Ядро працює через абстракцію; вимкнення адаптера не ламає систему.

**ІНТ-2 Типи даних, які збираються з AF:**

| Тип | Що це | Періодичність |
|-----|-------|---------------|
| Довідники | Permits, Water bodies, Substances, Waste items, Dropdown-значення | за розкладом + вручну |
| Сирі значення | Показники, що існують тільки в AF (Event Frames, атрибути елементів, tag-значення) | за розкладом + за запитом |
| Налаштування періоду | `SETTINGS\GENERAL\CALCULATION_START/ENDDATETIME` | при відкритті проєкту |

**ІНТ-3 Зібрані сирі дані зберігаються в SQL у «сирому» вигляді**
(схема `ext`, таблиця `ext.RawDataPoint`) — **без інтерпретації**, з повним
збереженням джерела (`SourceSystem`, `SourcePath`, `SourceWebId`, `RetrievedAt`).
Мапінг «сире значення -> комірка документа» — окремий, конфігурований крок.

**ІНТ-4** Кожен запуск збору фіксується в `itg.DataCollectionRun`:
скільки отримано, скільки нових/змінених, помилки, тривалість.

**ІНТ-5** Збір ідемпотентний: повторний запуск за той самий період не створює дублікатів
(ключ `SourceSystem + SourcePath + Timestamp`).

**ІНТ-6 Два транспорти до PI AF** ⭐

Адаптер має **дві реалізації**, які обираються конфігурацією на рівні
`ext.DataSource` і можуть використовуватися одночасно для різних задач:

| | **PI Web API** | **PI SQL Client** (PI SQL Data Access Server / RTQP) |
|---|---|---|
| Протокол | REST/HTTPS, JSON | SQL через **PI SQL Client (ODBC)** — для RTQP саме ODBC, не OLE DB |
| Автентифікація | Windows (Negotiate) під сервісним обліковим записом | Windows (integrated) під сервісним обліковим записом; **Kerberos-делегування не потрібне** |
| Сильна сторона | метадані, запис, точкові операції, `POST /batch` | **масове читання**, `JOIN`, фільтрація і агрегація **на боці PI** |
| Слабка сторона | вивантаження великих обсягів — багато запитів і парсингу JSON | немає запису; залежить від встановленого клієнта на сервері |
| Де застосовуємо | синхронізація довідників, `SETTINGS`, перевірка метаданих, *(опційно)* зворотний запис | **початкова міграція історії**, регулярний масовий збір сирих даних, звіряння |

**ІНТ-7** Обидві реалізації — за **одним інтерфейсом** `IPiAfDataReader`.
Прикладний код не знає, який транспорт використовується; вибір робиться
конфігурацією і може бути змінений без правок коду.

```
Ecr.Adapters.PiAf/
  ├─ IPiAfDataReader.cs
  ├─ WebApi/    PiWebApiDataReader     — HttpClient + batch + Polly + failover
  ├─ Sql/       PiSqlClientDataReader  — DbConnection, параметризовані запити
  └─ PiAfDataSourceFactory.cs          — вибір за ext.DataSource.TransportKind
```

**ІНТ-8** Чому це важливо саме тут: чинне рішення вивантажує до 1000 Event Frames
і фільтрує їх **у клієнті** (`BuildEFMonthTreeByFileNumberFast`), бо Web API не вміє
фільтрувати за значенням атрибута. PI SQL Client дозволяє те саме зробити
**одним запитом із `WHERE` на боці PI** — це принципова різниця для міграції
історії та для регулярного збору.

**ІНТ-9** Обидва транспорти зберігають чинну технічну базу:
Windows Authentication, failover primary/secondary, retry з Polly,
`POST /batch` для Web API.

**ІНТ-10 Перевірені факти про PI SQL DAS (RTQP Engine)** (за документацією AVEVA):

| Факт | Наслідок для нас |
|------|------------------|
| ✅ **Не потребує налаштування Kerberos Delegation** для доступу до AF Server і PI Data Archive | знімає частину заперечень ІБ; добре лягає на модель із сервісним обліковим записом |
| ✅ Спрощена схема, працює швидше за попереднє покоління | саме те, що треба для масового читання |
| ⛔ **Тільки читання** — `INSERT`/`UPDATE`/`DELETE` не підтримуються | ідеально для ролі «джерело»; запис (якщо знадобиться) — **тільки через Web API** |
| ⛔ Asset-centric: прямого доступу до PI Points немає | точки мають бути замаплені на AF-атрибути |
| ℹ Клієнт для RTQP — **PI SQL Client (ODBC)** | не OLE DB; для OLE DB потрібне попереднє покоління |

**ІНТ-10a Ризик:** вимагає встановленого компонента і відповідної ліцензії PI.
**Перевірити доступність у контурі на Етапі 0** — якщо його немає, лишається
лише Web API, і оцінку міграції історії треба переглянути в бік збільшення.

**ІНТ-11 Зворотної публікації в AF немає** (рішення замовника 2026-09-03,
§12 п. 42).

PI AF — **виключно джерело читання**. Система в нього не пише нічого: ні даних,
ні довідників, ні на перехідний період. Отже:

* `IExternalDataSink` **не реалізується**. Порт лишається в переліку архітектурних
  швів (щоб інтеграція «назовні» мала де з'явитися, якщо колись знадобиться інший
  приймач), але реалізацій у обсязі немає;
* серіалізація в `Attribute_XXXX` = `;`-рядок (порядок полів з
  `ext.LegacyColumnMapping.LegacyFieldIndex`) зберігається **як утиліта валідації
  міграції** — побайтне порівняння перенесених даних зі старим форматом. Це
  тестовий інструмент, а не інтеграційний адаптер;
* **економія:** не проєктується, не будується і не супроводжується адаптер запису
  з ретраями, ідемпотентністю і розбором часткових помилок `POST /batch`.

**ІНТ-11a Наслідок, який треба закрити планом, а не кодом.** Оскільки записи в AF
немає, після cutover розділу дані ECR у AF **перестають оновлюватися**. Тому:

| Хто залежить від AF | Що з ним робимо |
|---|---|
| Дашборди PI Vision, AF Analyses, зовнішні звіти (питання I-1) | **переводяться на ECR** — через SSRS на `rpt.*` (ІНТ-12) або API. Це обов'язковий пункт runbook cutover'у розділу з виконавцем і датою |
| Excel-файли ще не мігрованих розділів, які читають довідники з AF | довідники в AF лишаються під **чинним процесом супроводу**. На час вікна співіснування (рівно два періоди) зміни вносяться вручну в обидві системи або заморожуються — пункт runbook |

**ІНТ-12 Звітність: SSRS лишається на новій моделі** (рішення замовника 2026-09-03).

Від SSRS **не відмовляємося** — він лишається звітною системою і працює на нових
структурах через схему `rpt.*`. Наслідки:

* `rpt.*` — **постійний публічний контракт**, а не тимчасовий міст. Вимоги до
  нього посилюються: стабільні імена і типи, версійність вʼюх (`rpt.v_*`), заборона
  ламких змін без міграції звітів;
* веб-переглядач звітів і конструктор звітів у вебі **виходять з обсягу** —
  **−5…−6 тижнів FE** із базових 86–108 (конструктор звітів у вебі) **плюс 8–10 тижнів FE і 3–4 BE, які інакше додалися б фазою 2** (веб-переглядач звітів), і ще 2–3 тижні BE на адаптері запису в AF, якого тепер немає. Це найбільше скорочення критичного шляху в проєкті;
* 166 RDL **перенацілюються** зі старих джерел на `rpt.v_*`. Ризик складності
  знімається пілотом на 10 звітах на Етапі 0 — і тепер це не «перевірка мосту»,
  а перевірка постійного рішення;
* **розмежування доступу до звітів лишається в SSRS** (папки, ролі SSRS).
  `IAccessDecisionService` на SSRS не поширюється — це треба сказати вголос:
  у `rpt.*` потрапляють **лише затверджені** зрізи, а рядковий доступ у звітах
  забезпечується параметрами звіту і правами SSRS, не нашим RBAC.

## 5.4 Міграція існуючих даних

Дані за 2025–2026 вже лежать у PI AF як `;`-рядки. План:

1. Вивантажити всі EF за роками через `POST /batch` (`GetEFYearAndValuesService`-аналог);
2. За `ext.LegacyColumnMapping.LegacyFieldIndex` розпарсити `;`-рядки назад у комірки;
3. Створити `doc.Document` зі статусом `Approved` (історичні дані вважаються затвердженими);
4. **Валідація зворотної конвертації**: заново згенерувати `;`-рядок і побайтно
   порівняти з оригіналом. Розбіжність -> запис у звіт міграції, ручний розбір.

Це найризикованіша частина. Планувати dry-run на копії AF.

## 5.4-A Вибір ORM: EF Core vs DataObjects.Net (Xtensive) ⭐

### Факти

| | **EF Core 10** | **DataObjects.Net 7** (Xtensive.Orm) |
|---|---|---|
| Ліцензія | MIT | **MIT з версії 6** (раніше платна) — перевірено |
| Стан | активний, LTS-цикл Microsoft | активний: 7.2.2, оновлено 06.2026 |
| СУБД | SQL Server, PostgreSQL, … | SQL Server, PostgreSQL, Oracle, MySQL, Firebird, SQLite |
| LINQ | зрілий | сильний (це історично його «фішка») |
| **Схема при старті** | немає «з коробки» — робиться вручну | **вбудовано: `DomainUpgradeMode`** |
| Міграції | явні версійовані файли, видно в PR | авто-diff моделі + upgrade handlers |
| Спільнота / наймання | дуже велика | вузька |

`DomainUpgradeMode` у DataObjects.Net:
* `Validate` — перевірити відповідність БД моделі, нічого не міняти, інакше виняток;
* `Perform` — доповнити/прибрати структури БД під модель;
* `PerformSafely` (типовий) — те саме, але дії, що ведуть до втрати даних,
  не виконуються без явного дозволу;
* `Recreate` — перестворити (тільки DEV).

### Рекомендація: **EF Core**

Головний аргумент — **архітектурний, а не смаковий**.

Основна перевага DataObjects.Net — автоматична еволюція схеми при старті.
Але в нашій архітектурі (§5.5) **фізична схема зафіксована**: ~40 таблиць,
які не змінюються при зміні шаблону. Додати колонку в звіт — це `INSERT`
у `cfg.ColumnDef`, а не `ALTER TABLE`.

> Тобто найсильніша сторона DataObjects.Net у цьому проєкті **майже
> не працює** — ми свідомо побудували систему так, щоб DDL не відбувався
> під час роботи.

Решта аргументів за EF Core:

1. **Основна складність тут не в ORM.** Це масові операції на 108 млн рядків,
   партиціонування, columnstore, `TRUNCATE … WITH (PARTITIONS)` при архівації,
   `SqlBulkCopy`. Це ближче до чистого SQL, і екосистема EF Core
   (`ExecuteUpdate`/`ExecuteDelete`, компільовані запити, зріла інтеграція
   з `Microsoft.Data.SqlClient`) тут відчутно багатша.
2. **Життєвий цикл системи — 10+ років.** Розробника з EF Core знайти
   легко, з DataObjects.Net — важко. Це не технічний, але реальний ризик.
3. **Явні міграції — це аудит.** Для системи з вимогою простежуваності
   версійований файл міграції, який видно в pull request, кращий за
   автоматичний diff моделі.
4. Уся решта стека (планувальник, логування, Testcontainers, health checks)
   документована переважно під EF Core.

### Коли варто передивитись це рішення

Якщо на Етапі 0 з'ясується, що потрібна **справді динамічна фізична схема**
(окрема таблиця під кожну звітну таблицю замість `CellValue`) — тоді
`DomainUpgradeMode.PerformSafely` стає вагомою перевагою, і DataObjects.Net
варто розглянути серйозно. Але саме такого підходу ми уникаємо свідомо (§5.5 §1).

**Дія:** зафіксувати EF Core; перевірку моделі при старті реалізувати
самостійно (нижче) — це ~150 рядків коду, а не привід міняти ORM.

## 5.4-B Створення і перевірка моделі даних при запуску ⭐

Вимога: **при запуску система має створити або перевірити модель даних.**

Йдеться про два різні рівні, які легко сплутати:

| Рівень | Що перевіряємо | Механізм |
|--------|----------------|----------|
| **Фізичний** | таблиці/колонки/індекси БД відповідають коду | EF Core migrations |
| **Логічний** | метадані шаблонів (`cfg.*`) цілісні і несуперечливі | власний `MetadataValidator` |

### Фізичний рівень: `SchemaBootstrapper`

```csharp
public enum SchemaStartupMode
{
    Validate,   // PROD: перевірити і впасти, якщо є розбіжність
    Migrate,    // TEST: застосувати очікувані міграції
    Recreate    // DEV: знести і створити заново
}
```

Алгоритм при старті:

```
1. Перевірити доступність БД (з retry — БД може підніматися довше застосунку)
2. applied  = context.Database.GetAppliedMigrations()
   pending  = context.Database.GetPendingMigrations()
3. Якщо в БД є міграції, ЯКИХ НЕМАЄ у збірці
      -> БД новіша за застосунок -> ФАТАЛЬНО, зупинка
         (типовий випадок: відкат релізу без відкату БД)
4. Режим Validate  (PROD):
      pending.Any() -> ФАТАЛЬНО, зупинка з переліком
5. Режим Migrate   (TEST):
      взяти розподілене блокування (sp_getapplock) ← кілька інстансів
      context.Database.Migrate()
      звільнити блокування
6. Перевірити наявність seed-даних:
      sec.Permission (каталог прав), вбудовані ролі,
      обліковий запис admin, дефолтна PeriodPolicy
      -> ідемпотентний seed, якщо чогось немає
7. Прогнати MetadataValidator (нижче)
8. Записати результат у health check /health/schema
```

**⚠ Чому `Migrate()` у PROD — антипатерн:**
* при кількох інстансах два процеси одночасно виконують DDL;
* застосунку потрібні права на зміну схеми — це заперечення від ІБ;
* немає можливості переглянути й погодити зміни до застосування;
* немає відкату.

**Рекомендація:** у PROD міграції накочує **конвеєр розгортання**
(`dotnet ef migrations bundle` — самодостатній exe, або DACPAC / DbUp),
а застосунок при старті лише **перевіряє** і падає при розбіжності.
Це і є «перевірити модель даних», але безпечно.

### Логічний рівень: `MetadataValidator`

Перевіряє при старті (і повторно при публікації версії шаблону):

* усі `FormulaDef.Expression` парсяться;
* немає циклів у графі формул і `TableRelationDef`;
* усі посилання між аркушами резолвяться;
* усі `LookupRegistryDefId` існують і опубліковані;
* немає `ColumnDef` без `TableDef`, `RowDef` без `TableDef`;
* немає опублікованих версій із порушеними інваріантами;
* `sec.RoleResourceGrant` не посилається на неіснуючі ресурси;
* є хоча б один активний носій права `Security.EditRoles`.

Результат — у `/health/metadata`. Помилки рівня `Critical` не дають
застосунку стартувати; `Warning` — логуються і показуються адміністратору.

## 5.5 Зміна структури «на льоту» без втрати консистентності ⭐

Це наскрізна вимога: структура шаблону змінюється постійно (нова колонка, нова
таблиця, змінений тип, перейменування), і це має відбуватися **без релізу коду,
без DDL і без ризику для вже введених даних**.

Детальний опис — у **[10-schema-evolution.md](10-schema-evolution.md)**.
Нижче — принципи, які закладаються в архітектуру.

### Принцип 1. Зміна структури = зміна ДАНИХ, а не DDL

**Фізична схема БД ніколи не змінюється при зміні шаблону.**
Немає динамічного `CREATE TABLE` / `ALTER TABLE`, немає таблиць «на колонку».
Додавання колонки в шаблон — це `INSERT` у `cfg.ColumnDef`.

Це знімає одразу цілий клас проблем: блокування схеми, несумісні міграції EF Core,
неможливість відкату, розповзання схеми між середовищами.

### Принцип 2. Опублікована версія шаблону незмінна (immutable)

```
TemplateVersion 1.0  [Published]  ← документи 2025 року назавжди прив'язані сюди
TemplateVersion 1.1  [Published]  ← документи 2026 року
TemplateVersion 1.2  [Draft]      ← редагується, документів немає
```

* **Структурно** редагувати можна лише версію у стані `Draft`, до якої не прив'язано
  жодного документа.
* Нова версія створюється **копіюванням попередньої** (`CloneFrom`) — це прямо
  відповідає вимозі «версійний або створюється новий на основі попереднього».
* `Publish` — незворотна операція, після неї **структурний шар** заморожений.
* **Презентаційний шар** (підписи, стилі, порядок, `Warning`-правила) опублікованої
  версії патчиться «на льоту» з аудитом — ФВ-7.9, [10](10-schema-evolution.md) §2a.
  Тригер у БД пропускає лише ці поля і відхиляє решту.

**Наслідок:** документ ніколи не «зламається» через те, що хтось змінив шаблон,
а повсякденні правки не вимагають нової версії.

### Принцип 3. Класифікація змін за ризиком

Кожна операція над структурою класифікується автоматично:

| Клас | Операції | Дія системи |
|------|----------|-------------|
| 🔵 **Presentation** | змінити підпис/переклад, стиль, ширину, порядок відображення, `DisplayTemplate`, додати `Info`/`Warning`-правило | дозволено **навіть в опублікованій версії** «на льоту»; аудит + `PresentationRevision` |
| 🟢 **Safe** (адитивна) | додати колонку (nullable)/рядок/таблицю/аркуш, розширити тип, розширити довідник | лише у `Draft`-версії; для існуючих документів нова комірка = порожня |
| 🟡 **Guarded** (потребує стратегії) | звузити тип (`String`->`Decimal`), додати `Required`, додати `Error`-правило, змінити довідник, зробити колонку обчислюваною | вимагає **стратегії міграції даних** і **звіту сумісності** перед публікацією |
| 🔴 **Breaking** | видалити колонку/рядок/таблицю, змінити `Code`/`RowKey`, змінити `LayoutKind`, змінити `LegacyFieldIndex` (в `ext`, але ламає round-trip) | у версії з документами **заборонено**; лише в новій версії + явний план міграції |

### Принцип 4. Soft delete замість фізичного видалення

`ColumnDef` / `RowDef` / `TableDef` ніколи не видаляються фізично, якщо на них
є посилання з `CellValue`. Замість цього — `IsDeleted = 1` + `DeletedInVersionId`.

Дані залишаються читабельними («історична колонка», показується як read-only
у документах старих версій), FK ніколи не «висить».

### Принцип 5. Перехід документа між версіями — явна операція

Документ **не мігрує автоматично**. Є операція `MigrateDocument(docId, targetVersionId)`:

```
1. Побудувати ChangeSet(fromVersion -> toVersion)
2. Прогнати DryRun: що додасться, що очиститься, що не мапиться
3. Показати користувачу звіт (кількість зачеплених комірок, попередження)
4. Підтвердження
5. Транзакційно: snapshot ДО -> застосувати мапінг -> перерахувати формули
   -> валідація -> commit або повний rollback
6. Запис у aud.DocumentEvent з посиланням на snapshot
```

Часткове застосування заборонено: або весь документ мігрує, або жоден рядок.

### Принцип 6. Цілісність на рівні БД, а не тільки коду

| Гарантія | Механізм |
|----------|----------|
| `CellValue.ColumnDefId` завжди існує | FK з `ON DELETE NO ACTION` + soft delete |
| Комірка належить колонці зі своєї таблиці | перевірка в domain + CHECK-обмеження через computed-колонку |
| Документ і його комірки — одна версія шаблону | `TableInstance.TemplateVersionId` денормалізована, звіряється |
| Немає «сиріт» після невдалої міграції | усе в одній транзакції + `RowVersion` |
| Тип значення відповідає `ColumnDef.DataType` | валідація на записі + фонова задача-верифікатор |

### Принцип 7. Постійна перевірка інваріантів

Фонова задача `ConsistencyCheckJob` (щоночі) перевіряє:

* немає `CellValue` з посиланням на `ColumnDef` іншої таблиці;
* немає `TableInstance` без `TemplateVersion`;
* немає значень, тип яких не відповідає `ColumnDef.DataType`;
* обчислювані комірки збігаються з результатом перерахунку формул;
* немає документів у `Approved` із незакритими `Error`-валідаціями.

Розбіжності -> у `aud.ConsistencyIssue` + сповіщення адміністратора.
**Це страховка від помилок у коді, а не заміна їм.**

### Що з цього випливає для коду

```csharp
// ❌ ТАК НЕ РОБИМО — динамічний DDL
await db.Database.ExecuteSqlRawAsync($"ALTER TABLE {t} ADD {col} decimal(18,4)");

// ✅ ТАК — зміна структури це операція над даними
var change = new AddColumnChange(tableDefId, code, dataType, ordinal);
var impact = await _schemaEvolution.AnalyzeAsync(change);   // клас ризику + звіт
if (impact.Class == ChangeClass.Breaking && version.HasDocuments)
    return Result.Fail(impact.Reasons);
await _schemaEvolution.ApplyAsync(change);                  // INSERT у cfg.ColumnDef
```

# 9. Критерії приймання (загальні)

1. Один повний звітний цикл (12 місяців × усі аркуші) проходить у новій системі
   з результатом, побайтно ідентичним експорту зі старої.
2. Усі 12 алгоритмів із §7 покриті автотестами.
3. Показники продуктивності ФВ-6.10 досягнуті на реальному обсязі даних
   (включно зі сценарієм «останній день періоду», [14](14-performance.md) §6).
4. Міграція історичних даних: 100% EF перенесено, round-trip-звірка без розбіжностей.
5. Аудит фіксує 100% змін значень.
6. Жодного пароля/секрету в репозиторії.
7. **Тест на універсальність:** проєкт з іншої предметної області (напр. «Бюджет»)
   заведено і заповнено **без жодного рядка нового коду**.
8. Архітектурні тести ([13](13-backend-assignment.md) §4) зелені; `Ecr.Domain`
   і `Ecr.Application` не посилаються на адаптер PI AF.
9. Ліцензійна перевірка в CI зелена; кожна залежність є в [15](15-verified-stack.md).
10. Презентаційна правка опублікованої версії (підпис, стиль) застосовується без
    нової версії і без міграції документів; структурна — відхиляється тригером БД.

# 13. Оцінка реалістичності реалізації

Чесна відповідь на питання «чи можна це зробити заявленою командою в заявлений строк».

## 13.1 Висновок

**Архітектура реалістична. Строки — ні, для заявленого складу команди.**

Кожне окреме рішення в цьому ТЗ — стандартна, багато разів реалізована практика
(metadata-driven модель, EAV зі складеним FK, immutable versions, RBAC з ресурсними
грантами, NCalc, ClosedXML, Negotiate + Cookie). Ризику «це неможливо» немає.
Ризик — у **сумі**.

> ⚠ **Редакція 2 (2026-09-03).** Перша редакція цього розділу оцінювала
> **половину системи** — Excel/VBA-контур. Після аналізу чинного бекенду ECR
> (SQL + CLR + PI AF + SSRS + ~100 джобів) у обсяг увійшли розрахунковий рушій,
> звітність регулятору і два конфігуратори. Наведені нижче цифри — переглянуті
> ([П-29](../backend/B10-decisions.md), джерело —
> [B22](../backend/B22-nocode-and-realism.md) §4). Це не подорожчання, а
> **перша оцінка повного обсягу**.

## 13.3 Команда vs строк

| Обсяг | Склад | Строк |
|---|---|---|
| Повний | 1 арх + 2 BE + **1 FE** + 1 QA | **28–34 міс.** — FE серіалізує все; не розглядається |
| Повний | 1 арх + 3 BE + **2 FE** + 1 QA | **20–24 міс.** — FE лишається критичним шляхом |
| Повний | 1 арх + **4 BE** + **3 FE** + 2 QA | **15–18 міс.** — збалансовано |
| **MVP** (§13.4a) | 1 арх + 3 BE + **2 FE** + 1 QA | **9–11 міс.** |

**86–108 тижнів FE для одного розробника — це 20–25 місяців послідовно.**
Склад «1 FE» — не вузьке місце, а неможливість: frontend стає критичним шляхом
удвічі довшим за все інше.

**Обсяг і склад — одне рішення, не два.** Реальний вибір:
**MVP + 2 FE (9–11 міс.)** або **повний обсяг + 3 FE (15–18 міс.)**. Комбінація
«повний обсяг + 2 FE» = 20–24 місяці — строк, який переживе зміну пріоритетів.

> **Коригування після рішень 2026-09-03.** Обсяг frontend зменшено: SSRS лишається
> звітною системою (§12 п. 43a), тому конструктор звітів у вебі виходить з обсягу
> (**86–108 → 80–102 тижні FE**), а фаза 2 (веб-переглядач, 8–10 FE + 3–4 BE) не
> додається взагалі. Плюс ~2–3 тижні BE, звільнені відмовою від запису в AF
> (п. 42). Це зсуває кожен рядок таблиці приблизно на **−1…−1.5 місяця**;
> діапазони лишено без змін, бо вони в межах похибки ±3 місяці.

**Невизначеність оцінки — близько ±3 місяці** ([B22](../backend/B22-nocode-and-realism.md) §4.5).
Три найбільші джерела знімаються на Етапі 0: скільки з 44 методологій лягають у
рівень 1 (±6–10 тижнів BE), чи покриває конвеєр Thermaloxidizer (±6–8 тижнів BE),
дозвіл ІБ на скрипти (±10–13 тижнів).

## 13.4 Головна рекомендація: вертикальний зріз першим

Найбільша небезпека універсальної системи — **побудувати весь generic-механізм
і лише потім з'ясувати, що він не лягає на реальні дані**.

Тому перше, що будується після Етапу 0, — не «конфігуратор цілком», а
**один розділ крізь усі шари**: `7. Water Report` (найскладніший — 394 рядки,
GROUP/ITEM/BALANCE, дозволи з вікнами дії, rollup у `7.0`):

```
Bootstrap-імпорт лише цього аркуша
  → cfg.* заповнено скриптом, без UI конструктора
  → doc.* + batch-PATCH + формули + валідація
  → мінімальний grid (без стилів, без редактора зв'язків)
  → RBAC базовий (дві ролі), Windows Auth
  → експорт .xlsx «тільки значення»
  → порівняння з еталоном: побайтно
```

Що це дає: модель даних, рушій виразів, права на комірках і бюджет продуктивності
перевірені на **реальних** даних до того, як інвестовано у UI конструктора,
редактор зв'язків і реєстри. Якщо модель не витягує — дізнаємося на 3-му місяці,
не на 9-му.

> **Рішення T-1 (2026-09-03): Water і Waste не деплояться старим способом.**
> Вони написані, але **не запущені в прод**, тому стають **першим розділом нової
> системи**. Наслідки, які треба врахувати одразу:
>
> 1. Вертикальний зріз перестає бути прототипом — він **іде в продуктив**. Отже
>    до нього додаються періоди, аудит, робочий процес затвердження і експорт;
>    це не «зріз за 3 місяці», а **перший реліз** (див. 13.4a).
> 2. Не створюються **+52 таблиці, +29 синків, +21 тригер**
>    ([B17](../backend/B17-ecr-transition.md) §10), які інакше довелося б
>    зносити через рік. Технічний борг не виникає взагалі.
> 3. **Джерело золотого набору змінюється.** Оскільки паралельного продуктивного
>    запуску не буде, еталонні числа знімаються з **написаної, але не задеплоєної
>    реалізації, прогнаної в тестовому контурі**. Цей код треба зберегти і
>    зробити відтворюваним — окрема задача Етапу 0, без неї `ER-C-11` (обов'язкова
>    числова сумісність) не має на чому перевірятися.
> 4. **Запасний план лишається дійсним і має бути явним:** якщо з'явиться
>    регуляторний строк для Water/Waste раніше за перший реліз, старий деплой
>    виконується як контingency. Код написаний, тож вартість — дні; але тоді
>    борг із п. 2 повертається, і його треба одразу фіксувати списком.

## 13.6 Що не є ризиком (щоб не переоцінювати)

* Навантаження 100 користувачів / ~42 RPS середнє / ~125 RPS пік — **скромне**
  для ASP.NET Core + SQL Server на заявленому залізі; головний ризик там —
  не RPS, а обсяг `CellValue`, і він знятий архівуванням.
* 11 Excel-функцій у NCalc — дні роботи, не тижні.
* Два провайдери автентифікації в одну cookie — штатний сценарій ASP.NET Core.
* Хостинг на IIS/Windows — стандарт; жодних екзотичних вимог.

   робіт у [08](08-roadmap.md) і [13](13-backend-assignment.md).
3. Пастки §13.5 пп. 1–5 закласти як явні задачі Етапу 0/1, а не «з'ясується по ходу».
