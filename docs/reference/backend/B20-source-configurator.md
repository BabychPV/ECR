# B20 — Конфігуратор джерел, збору і розкладу

> Вимога: **PI SQL Client для читання**, дані забирає **шедулер**, і все це
> **налаштовується в конфігураторі** — які саме сутності забирати, перевірка
> консистентності, налаштування самого шедулера.
>
> Деталізує [B06](B06-integration-ports.md) (порти) і [B15](B15-ecr-recalc-orchestration.md)
> (оркестрація) до рівня UI і контрактів. Транспорт підтверджено фактом:
> RTQP уже в продуктиві ([B14](B14-ecr-integration-and-data.md) §1).

---

## 1. Принцип: збір — це конфігурація, а не 63 процедури

Сьогодні кожне джерело даних — це **окремо написана процедура** (`AF_*_Sync`,
~400 рядків), окрема RTQP-в'юха на AF-сервері, окремий тригер, окремий рядок у
`JobsList` і окремий крок у джобі. Додати сутність = п'ять артефактів на двох
серверах (`pi-af-structure.md` §«Новий EF-шаблон → повний ланцюжок sync»).

**ER-S-01. Джерело, сутність, мапінг і розклад — записи в БД, а не код.**

```
ext.DataSource          ← куди підключаємось (PI AF / FLERT / інше)
   └ ext.SourceEntity   ← ЩО саме забираємо (шаблон AF, набір атрибутів)
        ├ ext.EntityFieldMap   ← як поля джерела лягають на нашу модель
        ├ ext.CollectionSchedule ← коли і як часто
        └ ext.ConsistencyRule    ← що перевіряти
```

Додати сутність = заповнити форму, натиснути «Перевірити», натиснути «Увімкнути».
Жодного розгортання на AF-сервері (**ER-I-01**: адаптер формує запит сам).

## 2. Джерело (`ext.DataSource`)

```sql
ext.DataSource
    Id, Code UQ ('PiAf_Prod', 'PiAf_Uat', 'Flert'),
    Kind          tinyint,      -- PiAf | Sql | File | Api
    TransportKind tinyint,      -- SqlClient (RTQP) | WebApi
    SecretName    nvarchar(100),-- ім'я секрету у сховищі; сам секрет — НЕ тут
    Endpoint      nvarchar(300),-- linked server / connection alias / URL
    SecondaryEndpoint nvarchar(300) NULL,
    AfServer, AfDatabase nvarchar(100),
    Catalog       nvarchar(50),  -- 'Master' для RTQP
    TimeoutSec, MaxBatchSize, MaxParallel int,
    IsActive bit
```

> ⚠ Це **не** редакція `ext.DataSource` з `architecture/07` §8
> (`PrimaryUrl`/`SecondaryUrl`/`SqlConnectionName`/`ConnectionJson`). Набір полів
> уніфіковано для обох транспортів (RTQP і Web API), а секрет замінено на його
> **імʼя**. Правка ТЗ — **П-36** ([B10](B10-decisions.md) §2.1); до її погодження
> чинною лишається редакція [07].

**Транспорт за замовчуванням — `SqlClient` (PI SQL Client / RTQP).** Web API
лишається лише там, де треба **писати** в AF (обмеження RTQP: read-only, ІНТ-10).

**Екран «Джерела»:**

| Дія | Що робить |
|-----|-----------|
| **Перевірити зв'язок** | пробний запит, таймаут 5 с, показує версію і затримку |
| **Показати каталог** | ⭐ читає з джерела список доступних шаблонів і їхніх атрибутів |
| **Failover** | primary/secondary, стан circuit breaker ([B06](B06-integration-ports.md) §3.2) |
| **Журнал** | останні прогони збору, помилки, перемикання |

> «Показати каталог» — ключова функція. Сьогодні, щоб дізнатися, які атрибути має
> шаблон AF, треба експортувати XML і читати його руками. Конфігуратор питає
> джерело напряму і показує список — і саме звідти беруться поля для мапінгу.

## 3. Сутність (`ext.SourceEntity`) — «що саме забираємо»

```sql
ext.SourceEntity
    Id, DataSourceId, Code,
    EntityKind    tinyint,       -- EventFrame | Element | Table | Stream
    SourceTemplate nvarchar(200), -- 'HSE_Land_Utility_9_05', 'Formula_El_V', 'PermitConstant'
    TargetKind    tinyint,        -- Registry | Methodology | RawData | Settings | Document
    TargetRef     nvarchar(200),  -- RegistryDef.Code / TableDef.Code / …
    FilterJson    nvarchar(max),  -- {"Category":"Tab_Data"} — звуження на боці джерела
    IncrementalBy nvarchar(100),  -- 'Modified' — колонка для інкрементного читання
    KeyFieldsJson nvarchar(400),  -- {"EFID","ATID"} — ключ ідемпотентності
    OnMissingInSource tinyint,    -- MarkOrphaned | Deactivate | Ignore
    IsActive bit
```

### 3.1 Каталог сутностей ECR — заповнюється формами, не кодом

| Клас | `EntityKind` | Приклади шаблонів | Куди |
|------|--------------|-------------------|------|
| Конфігурація розрахунку | `Element` | `Methodology_V`, `Formula_El_V`, `Constant_El_V`, `EmissionCalculationWork_Rules_V` | `calc.*` (режим `Mirror`, [B19](B19-calc-configurator.md) §7) |
| Довідники | `Element` / `EventFrame` | `Dictionary_Land_V`, `PermitConstant_V` | `dic.*` |
| Перміти | `EventFrame` | `PermitDocument_V`, `PermitEmissionValue_V`, `PermitDischargeValue_V`, `PermitMetaDataArea_V`, `PermitMetaDataLocation_V` | `dic.*` (реєстр `Permit`) |
| Дані RDS | `EventFrame` | `HSE_Land_*` (63), `HSE_401*`, `HSE_400_*`, `HSE_Thermaloxidizer*` | `doc.*` (на перехід) |
| Налаштування | `Element` | `Settings_General_V` (`Calculation_StartDateTime/EndDateTime/Offset`) | `Project.ExternalSettingsJson` |
| Керування | `Element` | `Recalculate_Land_V`, `Settings_RecalculateManual_V` | зникає ([B15](B15-ecr-recalc-orchestration.md) §2.3) |
| Потоки | `Stream` | FLERT: `FlareEventFull_*`, `FlareDailyReport_*` | `ext.RawDataPoint` — **лишається назавжди** |

Перелік узятий із фактичного експорту `PI AF/ECR_01_Air_PISqlClientExportedObjects.sql`
(26 в'юх) і `FLERT_NV_0114_PISqlClientExportedObjects.sql` (6 в'юх).

### 3.2 Мапінг полів

> `ext.EntityFieldMap` — це фізичне оголошення тієї самої сутності, яку ТЗ ФВ-8.11
> називає `cfg.RegistrySyncMapping`, а [B06](B06-integration-ports.md) §4 — `ext.DataMappingDef`.
> **Канонічна назва в пакеті — `ext.DataMappingDef`**; `EntityFieldMap` лишається
> як ім'я таблиці полів. Мапінг рівня сутності (шаблон, ключ, розклад, поведінка при
> зникненні) живе в `ext.SourceEntity` (§3), мапінг рівня поля — тут.

```sql
ext.EntityFieldMap        -- рядок = одне поле мапінгу ext.DataMappingDef
    Id, SourceEntityId,
    SourceField   nvarchar(200), -- 'FInfo_Text', 'ParameterValue', 'Land_NAE'
    SourceIndex   int NULL,      -- ← позиція в ';'-рядку (лише для legacy RDS)
    TargetField   nvarchar(200),
    DataType      nvarchar(50),
    TransformExpr nvarchar(1000) NULL,  -- мова виразів B03
    IsKey, IsRequired bit
```

**Позиційність живе в одному місці — `ext.LegacyColumnMapping.LegacyFieldIndex`**
([07] §8.1). `SourceIndex` тут — не друга копія, а **проєкція того самого поля**
у формі мапінгу: конфігуратор читає і пише `LegacyFieldIndex`. Сьогодні позиція
розмазана по 63 процедурах у вигляді `CASE WHEN rn = N`
([B12](B12-ecr-as-is-backend.md) §3.1); тут вона одна, видима і перевірна.

**Екран мапінгу:** ліворуч поля джерела (з каталогу §2), праворуч поля цілі,
посередині — попередній перегляд на **реальних 10 рядках**, узятих із джерела
просто зараз. Помилка мапінгу видно одразу, а не через місяць у звіті.

## 4. Розклад (`ext.CollectionSchedule`) — шедулер як конфігурація

```sql
ext.CollectionSchedule
    Id, SourceEntityId,
    Mode          tinyint,   -- Interval | Cron | OnDemand | AfterEntity
    IntervalSec   int NULL,
    CronExpr      nvarchar(100) NULL,
    DependsOnEntityId int NULL,  -- ланцюжок: спершу довідники, потім дані
    WindowFrom, WindowTo time NULL,  -- «не забирати в години пікового введення»
    MaxDurationSec int,
    Priority      tinyint,
    IsEnabled     bit
```

**Що конфігурується в UI:**

| Параметр | Приклад для ECR |
|----------|-----------------|
| Частота | довідники — щогодини; конфігурація розрахунку — щодня; RDS-дані — 5 хв |
| Вікно | FLERT-потоки — вночі; довідники — цілодобово |
| Залежності | `PermitConstant` → `PermitEmissionValue` (речовини перед лімітами) |
| Пріоритет | ручний збір > плановий |
| Ліміт часу | понад — задача завершується `Partial` зі звітом |

**Чому не «щохвилини все», як зараз.** Сьогодні 16 sync-джобів ходять раз на
хвилину незалежно від того, чи щось змінилося, — це фонове навантаження, яке
конкурує з розрахунком. Різні класи даних мають різну природну частоту, і
конфігуратор дозволяє її задати замість одного значення для всього.

### 4.1 Екран «Розклад»

* **Таймлайн** — коли що збирається, де перетини, де порожні вікна;
* **Наступний запуск** і **останній результат** по кожній сутності;
* **«Забрати зараз»** — ручний прогін із прогресом (замість очікування тіку);
* **Пауза** сутності або джерела цілком — без правки джобів;
* **Історія** — `itg.DataCollectionRun`: скільки отримано / нових / оновлених /
  помилок, тривалість, чи було перемикання на secondary.

## 5. Перевірка консистентності (`ext.ConsistencyRule`) — ER-S-02

Це третя частина вимоги і найцінніша: **система сама виявляє, що конфігурація
розійшлася з реальністю.**

### 5.1 Чотири рівні перевірок

| Рівень | Питання | Коли | Приклад збою, що вже траплявся |
|--------|---------|------|--------------------------------|
| **Схема джерела** | шаблон і всі поля мапінгу існують у джерелі? | при збереженні мапінгу + щодня | шаблон розширили на 4 атрибути — в'юха стара, колонки немає |
| **Типи** | значення справді парсяться у заявлений тип? | вибірково, при кожному зборі | `Substance_Code` — `String` в AF, `int` у нас → крок падає, а джоб зелений |
| **Ідемпотентність** | ключ справді унікальний у джерелі? | при першому зборі | дублі за `(EFID, ATID)` |
| **Дзеркальність** | те, що в нас, дорівнює тому, що в джерелі? | щодня | `AF_Constants_CheckDifferences` — уже є, стає загальним механізмом |

### 5.2 Перевірка «наше ⟷ джерело»

Узагальнення наявних `AF_Constants_CheckDifferences` / `AF_Formulas_CheckDifferences`
на **будь-яку** сутність:

```
для кожної активної SourceEntity з увімкненою перевіркою:
    вибірка з джерела (за ключем)  ⟷  наша копія
      є в джерелі, немає в нас     → Missing
      є в нас, немає в джерелі     → Orphaned
      є в обох, значення різні     → Drift  (з переліком полів)
    → itg.ConsistencyCheckRun + aud.ConsistencyIssue
```

**Нуль розбіжностей — норма.** Ненульове значення видно в UI і в метриці
`ecr.source.drift{entity}`; це той самий принцип, що `ConsistencyCheckJob`
([B07](B07-jobs-and-observability.md) §2.2): якщо перевірка щось знайшла — це баг, а не шум.

### 5.3 Перевірка перед увімкненням

Кнопка **«Перевірити конфігурацію»** на сутності, до першого збору:

```
✅ Джерело доступне (312 мс)
✅ Шаблон 'HSE_Land_Utility_9_05' існує
✅ Усі 37 полів мапінгу знайдено
⚠  Поле 'Land_Reserv2' є в джерелі, але не змаповане
❌ Поле 'Land_Measure_OperTime' у мапінгу відсутнє в джерелі
   (схоже на 'Land_Measure_OperatingTime' — виправити?)
✅ Ключ (EFID, ATID) унікальний на вибірці 1000 рядків
✅ Типи: 37/37 парсяться
✅ Ціль 'Utility_9_05' існує і має 37 відповідних колонок
```

Останній рядок помилки — не вигаданий приклад: це **точна причина** дефекту
IEC Час/Об'єм (`Land_Measure_OperTime` проти `Land_Measure_OperatingTime`),
який ховався за порожнім `TRY/CATCH` і занулював цілу таблицю. Перевірка
конфігурації ловить його **до** першого прогону.

## 6. Що це замінює — у цифрах

| Артефакт AS-IS | Кількість | Стає |
|----------------|----------:|------|
| RTQP-в'юхи на AF-сервері | 26 (ECR) + 6 (FLERT) | 0 — запит формує адаптер |
| Процедури `*_Sync` | 80 (63 land) | 1 `DataCollectionJob` + записи конфігурації |
| Тригери на `AF_*` | 71 | 0 |
| Рядки в `JobsList` | по одному на шаблон | `ext.SourceEntity` |
| Кроки в sync-джобах | 16 джобів × N кроків | `ext.CollectionSchedule` |
| Перевірки консистентності | 2 процедури (`*_CheckDifferences`) | загальний механізм на всі сутності |
| Місць правки при розширенні шаблону | 5 ланок на 2 серверах | 1 форма |

## 7. Порядок увімкнення нової сутності

```
1. Джерела → обрати джерело → «Показати каталог» → знайти шаблон
2. Нова сутність: EntityKind, шаблон, ціль, фільтр
3. Мапінг: підтягнути поля з каталогу → зіставити з ціллю
           (для legacy RDS — заповнити SourceIndex, звірити з ext.LegacyColumnMapping)
4. «Перевірити конфігурацію» → усе зелене
5. Розклад: частота, вікно, залежності
6. «Забрати зараз» на тестовому діапазоні → перегляд 10 рядків
7. Увімкнути → перший повний збір → itg.DataCollectionRun
8. Увімкнути перевірку консистентності
```

Сім кроків у вебі замість п'яти артефактів на двох серверах.

## 7а. Права

| Право | Хто типово | Що відкриває |
|-------|-----------|--------------|
| `Integration.ViewLogs` | оператор, підтримка | журнали збору, звіти консистентності |
| `Integration.RunCollection` | оператор | «Забрати зараз», пауза/відновлення джерела |
| `Integration.EditSources` | адміністратор інтеграцій | джерела, «Перевірити зв'язок», «Показати каталог» |
| `Integration.EditMappings` | адміністратор інтеграцій | мапінг полів, `SourceIndex`, «Перевірити конфігурацію» |
| **`Integration.EditSchedule`** | адміністратор інтеграцій | розклад збору; `IsDangerous = 1` — навантаження на джерело |

Секрети джерел не читає **жодне** право: `ext.DataSource` тримає лише
`SecretName`, значення живе у сховищі секретів ([B05](B05-security-runtime.md) §6).
Усе — через `IAccessDecisionService`, без прямих перевірок ролей.
Хто саме отримує ці права в проді — відкрите питання **S-4** (§9).

## 8. Реєстр рішень

| # | Рішення | Обґрунтування |
|---|---------|---------------|
| **ER-S-01** | Джерело, сутність, мапінг, розклад, перевірки — записи в БД, керовані з UI | сьогодні кожна сутність коштує 5 артефактів на 2 серверах |
| **ER-S-02** | Перевірка консистентності — загальний механізм на всі сутності, 4 рівні | наявні `*_CheckDifferences` покривають 2 сутності з ~80 |
| **ER-S-03** | «Показати каталог джерела» — обов'язкова функція конфігуратора | інакше поля мапінгу вводяться руками з експортованого XML |
| **ER-S-04** | Позиційність (`SourceIndex`) існує **лише** в мапінгу legacy RDS і видима в UI | сьогодні розмазана по 63 процедурах як `CASE WHEN rn = N` |
| **ER-S-05** | Частота збору задається **на сутність**, не одна для всіх | «щохвилини все» конкурує з розрахунком і не має підстав |
| **ER-S-06** | «Перевірити конфігурацію» до першого збору, з підказкою схожих імен | найдорожчі дефекти — це друкарські помилки в іменах полів, які ховалися за `TRY/CATCH` |

>
> | # | Статус | Рішення |
> |---|--------|---------|
> | **S-1 / №11** | ✅ **ВИРІШЕНО** (замовник, 2026-09-03) | **Зворотної публікації в AF немає взагалі** — ні даних, ні довідників, ні на перехідний період. PI AF лишається **виключно джерелом читання**. `IExternalDataSink` **не реалізується** (порт лишається як архітектурний шов, реалізацій у обсязі немає); серіалізація в `;`-рядок зберігається **як утиліта валідації міграції** — побайтне порівняння зі старим форматом. Економія: не проєктується адаптер запису з ретраями, ідемпотентністю і розбором часткових помилок `POST /batch`. Два наслідки закриваються **планом, а не кодом**: (1) споживачі AF (I-1) **мають бути переведені** на SSRS/`rpt.*` або API — обов'язковий пункт runbook cutover'у з виконавцем і датою, бо після cutover дані в AF просто перестануть оновлюватися; (2) довідники в AF для **ще не мігрованих** розділів лишаються під чинним процесом супроводу — на вікно співіснування (два періоди) зміни вносяться в обидві системи вручну або заморожуються. Зафіксовано: ТЗ §12 п. 42/42a/42b, ІНТ-11, ІНТ-11a |
> | **Одиниці** | ✅ **додано 2026-09-03** | `ext.EntityFieldMap` отримує `SourceUnitId` / `TargetUnitId` (→ `uom.Unit`). Конверсія виконується **при завантаженні** і фіксується в журналі збору; **сирі дані в `ext.*` зберігаються в одиниці джерела** — інакше повторний перерахунок з архіву дасть інший результат. Якщо джерело змінило UOM атрибута, збір **зупиняється з помилкою**, а не конвертує «як здається». Атрибути PI AF мають власний UOM — це найчастіше джерело мовчазних розбіжностей у числах. Див. `../tz/02-requirements.md` ФВ-16.9 |
> | **S-2** | ❓ відкрито, метод готовий | Вивантажити перелік атрибутів ECR-бази AF з джерелом і типом (PI Point / формула / ручний ввід) і згрупувати в класи — природна частота у кожного атрибута вже є. Правило: **не частіше, ніж потребує звіт, плюс один рівень деталізації**. Зараз збір щохвилини без підстав; перехід до природної частоти зменшує обсяг сирих даних на порядки |
> | **S-3** | ✅ **вирішено** | **Так, і система має бути до цього байдужа — питання знімається дизайном.** Збір: **ідемпотентний** (upsert за природним ключем), **catch-up** (після відновлення дозабирає пропущений діапазон), **із журналом покриття** (видно, за які інтервали дані є). Тоді простій AF — затримка, а не втрата. З PI-адміном лишається погодити одне: **максимальну тривалість вікна**, після якої catch-up не встигає до строку звітності |
> | **S-4** | ❓ відкрито, рекомендація готова | Право `Integration.Manage`, 1–2 іменовані особи. Мапінг — **не налаштування, а частина визначення даних**: помилковий мапінг тихо пише правильні числа в неправильне місце. Тому аудит із diff «до/після», заборона змін під час відкритого періоду для задіяних реєстрів (як I-2), відкат, і обов'язковий попередній перегляд на реальних даних |

## 10. Чек-лист

- [ ] Жодного артефакту, який треба розгортати на AF-сервері
- [ ] Каталог джерела читається з самого джерела, не з експорту
- [ ] Мапінг має попередній перегляд на реальних рядках
- [ ] «Перевірити конфігурацію» ловить неіснуюче поле і пропонує схоже
- [ ] Розклад — на сутність, із залежностями і вікнами
- [ ] Перевірка «наше ⟷ джерело» працює на будь-якій сутності
- [ ] Ненульовий drift видно в UI і в метриці
- [ ] Ручний збір доступний із UI, з прогресом
