## 1. Що ми знаємо і чого не знаємо

### Знаємо (з ТЗ §1.4 і roadmap)

* Розрахункові модулі емісій **переносяться з PI AF у backend** — це вирішено
  (ТЗ §12, п.3).
* Це **наступна фаза**; зараз потрібна лише архітектурна готовність.
* `ICalculationModule` — **окрема** точка розширення від `IFormulaEngine`
  ([13] §6): не можна припускати, що всі обчислювані значення виражаються
  формульним синтаксисом.
* Результати зберігаються як звичайні `CellValue` з `IsCalculated = 1`
  (roadmap, «наступна фаза»).
* Потрібна **версійність методик розрахунку** (ТЗ §1.4).

### Не знаємо (і не вигадуємо)

| # | Питання | Хто відповість |
|---|---------|----------------|
| 1 | Які саме методики, скільки їх, наскільки складні | аналіз поточного бекенду |
| 2 | Де зараз живуть коефіцієнти — в AF, у БД, у коді | аналіз |
| 3 | Чи потрібен перерахунок «заднім числом» при зміні методики | бізнес |
| 4 | Чи розрахунок працює на рівні комірки, рядка, таблиці чи документа | аналіз |
| 5 | Які сирі дані потрібні на вході і звідки | аналіз + §12 п.3 [13] |
| 6 | Чи є вимога відтворюваності («покажи, як це число вийшло в 2024») | регулятор / бізнес |

> **Правило цього документа:** нижче спроєктовано так, щоб відповідь «так» або
> «ні» на кожне з питань 1–6 змінювала **вміст** схеми `calc`, але не ядро
> і не `doc.*`. Зокрема, питання 6 (відтворюваність) вирішене «так» наперед —
> бо дешевше закласти журнал розрахунку одразу, ніж додати його потім до
> історичних даних, яких уже немає.

## 2. Точка розширення

```csharp
public interface ICalculationModule
{
    string Code { get; }                    // "AirEmission.Flare", "Water.Discharge"
    string MethodologyVersion { get; }      // "2026.1"
    Task<CalculationResult> CalculateAsync(CalculationContext ctx, CancellationToken ct);
}

public sealed record CalculationContext(
    long   DocumentId,
    int    PeriodKey,
    int    TableInstanceId,
    string RowKey,
    IReadOnlyDictionary<string, object?> Inputs,   // значення комірок + сирі дані
    IReadOnlyDictionary<string, object?> Coefficients,
    IServiceProvider Services);

public sealed record CalculationResult(
    IReadOnlyDictionary<string, object?> Outputs,  // columnCode → значення
    IReadOnlyList<CalculationStep> Trace,          // ⭐ для відтворюваності
    IReadOnlyList<CalculationIssue> Issues);
```

### 2.1 Чому `Trace` — не опція

`CalculationStep { Order, Description, Expression, Inputs, Output }` — це журнал
«як вийшло це число». Для екологічної звітності питання «поясніть розрахунок»
надходить від регулятора **через роки** після самого розрахунку. Якщо журналу
немає, відповідь можна дати лише запустивши код тієї версії на тих даних —
тобто фактично ніяк.

Зберігається в `calc.CalculationRun.TraceJson` (стиснутий), із retention
не меншим, ніж у самих даних.

### 2.2 Прив'язка до структури

Розрахунок не «вгадується» — він **прив'язується конфігурацією**:

```sql
CREATE TABLE cfg.CalculationBinding
(
    Id             int IDENTITY PRIMARY KEY,
    TableDefId     int          NOT NULL,
    ModuleCode     nvarchar(100) NOT NULL,        -- ICalculationModule.Code
    MethodologyId  int          NOT NULL,          -- calc.MethodologyVersion
    TriggerKind    tinyint      NOT NULL,          -- OnDemand=0, OnChange=1, Scheduled=2
    InputMapJson   nvarchar(max) NOT NULL,         -- columnCode/rawPath → параметр модуля
    OutputMapJson  nvarchar(max) NOT NULL,         -- результат → columnCode
    Scope          tinyint      NOT NULL,          -- Row=0, Table=1, Document=2
    IsActive       bit          NOT NULL
);
```

Це **структурний** шар шаблону: змінюється тільки в `Draft`-версії, класифікується
як `Guarded` або `Breaking` ([10] §3) — бо зміна прив'язки змінює числа у звіті.

`ColumnDef.DataType` отримує значення `Calculated` — і саме тому `DataType`
у ТЗ §3.4 зроблено **кодом, а не закритим enum**: додати новий тип обчислюваного
поля можна без міграції схеми.

## 3. Попередня схема `calc`

```
calc.MethodologyDef        методика: код, назва, галузь, опис, орган, що затвердив
 └ calc.MethodologyVersion версія методики: ValidFrom/ValidTo, статус, документ-основа
     ├ calc.CoefficientSet набір коефіцієнтів версії (напр. по типах палива)
     │   └ calc.Coefficient  ключ → значення, одиниця, джерело, ValidFrom/ValidTo
     └ calc.FormulaSpec     опис кроків розрахунку (декларативний або посилання на модуль)

calc.CalculationRun        факт розрахунку: коли, ким/чим, яка методика,
 │                         який документ/період/таблиця/рядок, статус, тривалість
 ├ calc.CalculationInput   зафіксовані ВХІДНІ значення (зліпок!)
 ├ calc.CalculationOutput  результати → куди записано (CellValue)
 └ TraceJson               покроковий журнал
```

### 3.1 Чому вхідні дані фіксуються зліпком

Без цього відтворюваність неможлива: комірка, з якої брали значення, могла
бути змінена наступного дня. `calc.CalculationInput` зберігає **те, що було
на момент розрахунку** — і тоді «перерахувати так само» і «перерахувати
на актуальних даних» стають двома різними, свідомо обраними операціями.

Обсяг: розрахунків на порядки менше, ніж комірок, тому ціна прийнятна.

### 3.2 Темпоральність коефіцієнтів

`Coefficient.ValidFrom/ValidTo` + резолвінг «станом на дату періоду» — той самий
механізм, що й у темпоральних реєстрах ([12] §5.3). Це свідомо: якщо коефіцієнти
виявляться простими, вони можуть узагалі жити як `RegistryDef` із
`VersioningMode = Temporal`, і схема `calc` скоротиться.

> **Розвилка, яку залишаємо відкритою:** можливо, `calc.Coefficient*` не потрібні
> зовсім — і коефіцієнти краще вести як звичайні реєстри, які адміністратор
> редагує у вебі тим самим UI, що й `Permit`. Рішення — після аналізу
> поточного бекенду (питання 2 у §1).

## 4. Як розрахунок співіснує з формулами

| | `IFormulaEngine` | `ICalculationModule` |
|---|---|---|
| Що це | вираз користувача в `FormulaDef` | код (або декларативна методика) у збірці |
| Хто змінює | адміністратор у вебі | розробник / методолог, з версіонуванням |
| Коли | інкрементно, при кожному записі | за тригером прив'язки, часто у фоні |
| Вхід | комірки того самого документа | комірки + сирі дані `ext.*` + коефіцієнти |
| Вихід | одне значення | набір значень + журнал |
| Помилка | `#VALUE`, `Warning` | `CalculationIssue`, статус `Failed` у `CalculationRun` |

**Спільне:** обидва пишуть результат **через `ICellStore.ApplyAsync`**
(B04 §1) з `Origin = Calculation`, тобто з аудитом і перевіркою інваріантів.
Жодного «прямого запису бо швидше».

**Порядок:** розрахунковий модуль виконується **до** формул, що від нього
залежать. У графі залежностей (B03 §5) вузол модуля — це звичайний вузол
із входами і виходами; топологічний сорт при `Publish` враховує його нарівні
з формулами.

## 5. Що зробити вже зараз (щоб потім не переробляти)

Це і є практична частина документа на найближчі місяці:

1. **Зарезервувати схему `calc`** у міграціях (порожню) і файлову групу.
   Створення схеми пізніше — це міграція на живій БД із 108 млн рядків.
2. **`ColumnDef.DataType` — код, не enum.** Уже вимагається ТЗ §3.4; перевірити,
   що модель це дозволяє (немає `switch` без `default` по типах).
3. **`IFormulaEngine` і `ICalculationModule` — два різні порти** ([13] §6).
   Не «розрахунок як функція формули».
4. **Граф залежностей приймає вузли не-формул** — тобто `cfg.FormulaDependency`
   (B03 §4.2) має поле `SourceKind` (`Formula` / `CalculationBinding`),
   інакше при появі модулів доведеться переробляти граф і `EvaluationOrder`.
5. **`Origin = Calculation`** у `CellWriteBatch` — уже закладено (B04 §1).
6. **Не зашивати припущення «усі обчислення — рядкові».** `CalculationBinding.Scope`
   допускає `Table` і `Document`.

Пункти 1 і 4 — єдині, що коштують чогось зараз (кілька годин). Решта — це
«не зробити помилку», а не «зробити роботу».

## 6. Що має дати аналіз поточного бекенду

Перелік для сесії аналізу — щоб з неї повернутися з відповідями, а не з описом:

| # | Питання | Чому важливо для схеми |
|---|---------|------------------------|
| 1 | Перелік методик і їхня складність (формула / таблиця / алгоритм) | чи потрібен `FormulaSpec` як декларація, чи лише код |
| 2 | Де зберігаються коефіцієнти і хто їх змінює | `calc.Coefficient*` чи звичайний реєстр |
| 3 | Частота і обсяг перерахунку (рядок / документ / усе) | синхронно чи фоново, і яка черга |
| 4 | Чи є перерахунок історії при зміні методики | потрібен `calc.RecalculationPlan` із dry-run |
| 5 | Які сирі дані з AF потрібні на вході | обсяг `ext.RawDataPoint` і склад збору ([13] §12, п.3) |
| 6 | Вимоги до відтворюваності і retention журналу | обсяг `TraceJson` |
| 7 | Чи лишається щось у AF після перенесення | доля `IExternalDataSink` ([13] §12, п.2) |
| 8 | Чи є зв'язок методик із дозволами (`Permit`) і ставками | чи `calc` посилається на `dic.*` |

> Питання 5 і 7 — це рівно ті, від яких залежить **обсяг робіт по адаптеру**
> PI AF. Ядро не постраждає від жодної відповіді — це було метою винесення
> PI AF за `IExternalDataSource` ([13] §12).
