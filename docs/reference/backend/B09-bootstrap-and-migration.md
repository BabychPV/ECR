# B09 — Bootstrap структури і міграція історії

> Закриває §11 [13] п. **14** (межа автоматики vs ручної звірки при bootstrap із VBA).
> Дві утиліти, які визначають, чи буде проєкт мати з чим працювати:
> `Ecr.Bootstrap.Excel` (структура і довідники) і `Ecr.Migration.PiAf` (історія).

---

## 1. Чому це не «просто скрипт»

Ручне заведення структури = ~90 таблиць × ~40 колонок ≈ **3 600 записів**
плюс стилі, правила валідації, довідники, зв'язки. Це не «довго» — це
**гарантовано з помилками**, які виявляться на етапі звірки з реальними даними.

Але й повна автоматика неможлива: порядок полів у `;`-рядку **різний для кожної
з ~90 таблиць** і ніде не задокументований, крім самого VBA ([13] §8, п.4).
Тому потрібна чесна межа.

## 2. Межа автоматики (BR-18)

### 2.1 Повна автоматика — довіряємо без звірки

| Що витягуємо | Джерело | Куди |
|--------------|---------|------|
| Аркуші, їхній порядок | структура `.xlsx` | `cfg.SheetDef` (+ `ext.LegacySheetMapping`) |
| Межі таблиць | `templateRow` із `Configuration.bas` | `cfg.TableDef` (+ `ext.LegacyTableMapping`) |
| Колонки, заголовки, ширини | рядки заголовків, `cols` | `cfg.ColumnDef` |
| Числові формати | `styles.xml` | `ColumnDef.DisplayFormat` |
| Стилі | `styles.xml`, згортання тисяч комбінацій | ~40 `cfg.StyleDef` |
| Умовне форматування | `conditionalFormatting` | `cfg.ConditionalFormatDef` |
| Правила валідації | Data Validation (`type=list`, `decimal 0..744`) | `cfg.ValidationRule` |
| Прив'язка списків до комірок | `DropdownList` рядки 2–4 | `ColumnDef.LookupRegistryDefId` |
| Значення довідників | `DropdownList` A…AG, `Configuration` R…BL | `cfg.RegistryDef` + `dic.RegistryEntry` |
| Зовнішні ID | `DropdownList!AL`, `Configuration!AW`,`BA`,`J3` | `dic.RegistryExternalKey` |
| Формули (крім `VLOOKUP`) | `.xlsx` | `cfg.FormulaDef` |
| Рядки-заголовки | `hdrRows` у `Protection.bas` | `cfg.PeriodAccessRuleDef(HeaderRows)` |
| Заблоковані діапазони | `Sheet_Config.Init*` | `ColumnDef.IsReadOnly` / `RowDef.IsReadOnly` |

Це детерміновані джерела: або значення є, або його немає. Помилка тут — це
баг імпортера, який ловиться тестом на еталонному файлі.

### 2.2 Напівавтоматика — витягуємо, але **звіряємо кожну таблицю**

| Що | Чому не можна довіряти |
|----|------------------------|
| **`LegacyFieldIndex`** — порядок полів у `;`-рядку | `MapAttributes` у 19 модулях містить `Select Case templateRow` з різними наборами діапазонів; це семантика коду, а не дані |
| `RowKey` для фіксованих рядків | у `7. Water Report` це ID із композита `"7001001 - Name"`; в інших аркушах може бути інше |
| `RowType` (`Group`/`Item`/`Balance`/`Note`) | у Water Report — колонка C; в інших — виводиться з формул і стилів |
| `TableRelationDef` | виводиться з графа формул (7 ребер, [15] §5) — але тип зв'язку (`Rollup` vs `Mirror`) визначає людина |
| `ext.LegacyTableMapping` (AF-шаблони) | береться з `Configuration.bas`, але продубльовано в `BulkSave.bas` і `Action.InitTemplatesMap` — **три джерела, які можуть розходитися** ([05] §1, п.10) |

**Механіка звірки — автоматизована, рішення — людське:**

```
1. VbaMapAttributesParser: state machine по кожному HSE_*.bas
     Select Case templateRow → гілка
       послідовність partList.Add CellValueForExport(sheet.Cells(i, N))
       → впорядкований список номерів колонок Excel
       → LegacyFieldIndex = позиція в списку
     confidence: High   — гілка розібрана повністю, немає умовних вставок
                 Medium — є If/умовні Add
                 Low    — цикли, виклики хелперів, динаміка
2. Три джерела мапінгу таблиць звіряються між собою → звіт розбіжностей
3. Round-trip-звірка на РЕАЛЬНИХ даних:
     взяти по 3 існуючі Event Frame на кожну з ~90 таблиць
     розпарсити ;-рядок за витягнутим LegacyFieldIndex
     зібрати назад → побайтне порівняння
     збіг → таблиця «зелена»; розбіжність → у чергу ручного розбору
4. Звіт: скільки таблиць зелених автоматично, скільки потребують уваги
```

**Бюджет: 2–3 тижні** (ТЗ §13.5 п.4), і це не «дні». Крок 3 — головний:
він перетворює ручну звірку 90 таблиць на розбір лише тих, що не зійшлися.

### 2.3 Не імпортується — але звітується

Обов'язковий звіт (ФВ-2.10, [13] §9.1), який **бізнес має підтвердити**:

| Що | Обсяг | Рішення |
|----|-------|---------|
| Defined names із `#REF!` | **87 із 287 (30 %)** | не переносяться |
| Зовнішні книги | 16, `externalLinks` 6.41 МБ, з них один 5.9 МБ | не переносяться — **у формулах не використовуються жодного разу** |
| `vbaProject.bin` | 2.99 МБ | не переноситься |
| Legacy-аркуші `9c. Fugitive leaks`, `HSE_373/400/401_Air` | — | **відкрите питання** ([13] §12, п.9) — переносити чи архівувати |
| Розбухлі стилі | `styles.xml` 1.23 МБ → ~40 `StyleDef` | згортаються |

> Без цього звіту через півроку виникне питання «а куди поділося ось це»,
> і відповісти буде нічим. Звіт — артефакт приймання Етапу 0.

## 3. `Ecr.Bootstrap.Excel` — вимоги до утиліти

| Вимога | Чому |
|--------|------|
| **Ідемпотентність** | запуск двічі на тому самому файлі дає той самий результат; повторний запуск після правки — оновлює, а не дублює |
| **Вихід — SQL-скрипт або `Draft`-версія**, ніколи не `Published` | результат треба переглянути перед публікацією |
| **Детермінований порядок** | щоб `diff` двох прогонів був читабельним |
| **`--dry-run`** | звіт без запису |
| **Звіт у машиночитному форматі** (JSON) + людському (Markdown) | перший — для CI, другий — для бізнесу |
| **`confidence` на кожному витягнутому елементі** | щоб було видно, що перевіряти в першу чергу |
| Не залежить від Excel/COM | працює на `.xlsx`-структурі (ClosedXML/OpenXML) — інакше не запуститься в CI |

## 4. `Ecr.Migration.PiAf` — історія 2025–2026

### 4.1 Конвеєр

```
1. Інвентаризація: скільки EF за роками, за шаблонами, за File Number
     Web API: eventframes/search батчами
     SQL DAS (якщо є): один запит із WHERE — на порядок швидше
2. Вивантаження: сирі EF + атрибути → ext.RawDataPoint
     ⭐ спершу СИРЕ, потім інтерпретація (B06 §4)
3. Парсинг ;-рядків за ext.LegacyColumnMapping.LegacyFieldIndex
4. ⚠ Зіставлення текстів довідників з ID  ← найважчий крок, див. §4.2
5. Створення doc.Document (Status = Approved — історія вважається затвердженою)
     + TableInstance / TableRow / CellValue (SqlBulkCopy)
6. Round-trip: згенерувати ;-рядок заново з CellValue → побайтно порівняти
     розбіжність → звіт, ручний розбір
7. Звіт міграції: перенесено / розбіжностей / не зіставлено
```

### 4.2 Крок, який недооцінюють (BR-19)

У чинних даних лежить **`"Diesel - Дизель"`**, а не ID ([13] §9.2, roadmap 5.3a).
Тобто перед створенням `CellValue.ValueRegistryEntryId` треба знайти запис
реєстру за **відображуваним текстом** — а він міг змінитися з часів запису.

Стратегія зіставлення, за спаданням надійності:

```
1. Точний збіг DisplayText поточної версії реєстру
2. Точний збіг за розібраним композитом: "7001001 - Name" → ключ "7001001"
3. Збіг із ІСТОРИЧНИМ значенням (dic.RegistryEntryHistory / темпоральні записи)
4. Нормалізований збіг: trim, подвійні пробіли, регістр, тире/дефіс
5. Не зіставлено → aud.OrphanedValue + рядок у звіті + значення зберігається
   ЯК ТЕКСТ у ValueString із прапорцем «не зіставлено»
```

Крок 5 — принциповий: **не втрачаємо дані і не вигадуємо ID**. Документ з
незіставленим значенням відкривається, показує текст із позначкою і дає
`Warning`, а не `Error` (ФВ-8.7).

Оцінка обсягу ручного розбору робиться на **dry-run** (задача 0.7 roadmap) —
до того, як планувати Етап 5.

### 4.3 Правила безпеки міграції

| Правило | Чому |
|---------|------|
| **Dry-run на копії AF** перед реальним прогоном | ТЗ §5.4; це найризикованіша частина проєкту |
| Заморозка AF на час міграції | інакше «перенесли, а потім там ще дописали» |
| Round-trip обов'язковий і побайтний | єдиний спосіб довести, що інтерпретація правильна |
| Розбіжність не «виправляється автоматично» | у звіт і на ручний розбір; автовиправлення тут = тихе спотворення історії |
| Міграція відновлювана | по документах, з чекпойнтами; збій на 700-му не означає почати спочатку |
| Сирі дані **лишаються** в `ext.RawDataPoint` | якщо інтерпретацію доведеться переграти, у PI повторно не йдемо |

### 4.4 Критерій приймання

Roadmap Етап 5: **100 % EF перенесено, round-trip без розбіжностей** — або кожна
розбіжність задокументована і **прийнята бізнесом**. Друге формулювання
важливіше за перше: у 45 000 рядків VBA неминуче знайдеться пара місць із
нестандартною поведінкою, і мета — знати про них, а не мати нуль у звіті.

## 5. `Ecr.DataGen` — генератор для навантажувального тесту

Формально не про міграцію, але робиться тією ж командою і на тих же метаданих.

| Вимога | Значення |
|--------|----------|
| Розподіл рядків на таблицю | **знятий із реального шаблону**, не рівномірний: медіана ~30, хвіст до 471 |
| Заповненість | параметр: 35 / 60 / 90 % — саме від нього залежить, чи проходить бюджет |
| Розподіл типів | як у реальних колонках (числа переважають) |
| Обсяг | 100 / 300 / 500 документів × 90 таблиць × 12 періодів |
| Швидкість | `SqlBulkCopy`, ~1 година на повний набір — інакше експериментувати неможливо |
| Детермінованість | seed → відтворюваний набір, щоб порівнювати заміри між прогонами |

Оцінка ТЗ §13.5 п.9 — **~1 тиждень**. Це реалістично **за умови**, що генератор
використовує ті самі метадані `cfg.*`, що й bootstrap, а не власну модель.

## 6. Порядок і залежності

```
0.6  Bootstrap структури  ─┬─► 0.1 Навантажувальний тест (потрібні cfg.* і DataGen)
0.6a Bootstrap довідників ─┤
                           └─► 0.5 Вертикальний зріз (потрібен 7. Water Report у cfg.*)
0.7  Dry-run вивантаження ────► оцінка Етапу 5
```

**Bootstrap — на критичному шляху Етапу 0**, і це часто недооцінюють: без
заведеної структури немає ні навантажувального тесту на реалістичних даних,
ні вертикального зрізу. Тому він починається **першим тижнем**, паралельно
з налаштуванням CI.

## 7. Чек-лист

- [ ] Bootstrap ідемпотентний і має `--dry-run`
- [ ] Вихід — `Draft`-версія, ніколи не `Published`
- [ ] `confidence` проставлено на кожному напівавтоматичному елементі
- [ ] Три джерела мапінгу таблиць звірені, розбіжності — у звіті
- [ ] Round-trip на 3 реальних EF на кожну з ~90 таблиць виконано
- [ ] Звіт про невимпортоване (87 `#REF!`, 16 книг) підтверджений бізнесом
- [ ] Незіставлені значення довідників зберігаються як текст, а не втрачаються
- [ ] Міграція відновлювана з чекпойнта
- [ ] Dry-run на копії AF проведено до реального прогону
