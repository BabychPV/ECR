# B19 — Конфігуратор сутностей розрахунку

> Вимога: **інструмент для оперування всіма сутностями** (методології, константи,
> формули, правила) з веб-редактором, версійністю і поясненням; **механізм належності
> формул/методологій до таблиць через правила**; підхід **no-code**, а де він не
> витягує — **редагований C#-код**.
>
> Деталізує [B13](B13-ecr-calculation-engine.md) §5 (схема `calc`) до рівня UI і
> контрактів. Модель сутностей звірена з `PI AF/ECR_01_Air_PISqlClientExportedObjects.sql`
> (в'юхи `Constant_El_V`, `Formula_El_V`, `EmissionCalculationWork_Rules_V`,
> `Methodology_V`) і `skills/ecr-methodology/references/pi-af-structure.md`.

---

## 1. Що саме має вміти інструмент

| Сутність | Операції | Версійність |
|----------|----------|-------------|
| **Методологія** (`ECW_C05_01`, `HSE400`, …) | створити, клонувати, опублікувати, вивести з обігу | версії з вікном дії |
| **Формула** | створити, редагувати вираз, тестувати, видалити | версії з вікном дії |
| **Константа** | створити, задати значення **по категоріях**, редагувати | версії з вікном дії |
| **Правило** | створити, зіставити з таблицею і значеннями, перевірити покриття | версії з вікном дії |
| **Категорія** | створити, задати вираз вибору | у складі версії методології |
| **Скрипт (C#)** | написати, скомпілювати, протестувати, опублікувати | версії з вікном дії |
| **Прив'язка до таблиці** | зв'язати методологію з `TableDef` через правила | у складі версії |

Це рівно те, що сьогодні робить розширення **Methodologies** у PI Vision
(User Manual §2.1.9) — плюс те, чого там немає: тестування перед публікацією,
аналіз покриття правил, пояснення до зміни і повний аудит.

## 2. Модель сутностей (звірена з AF)

### 2.1 Що є в AF сьогодні

Дерево (`pi-af-structure.md`):

```
Methodologies\EmissionCalculationWork\<Category>\<ECW_Cxx>        Template = Methodology
  \V1                                                             ← версія (Methodology_V)
    \Constants\<Name>_<ECW_Cxx>_\<CategoryKey>\V1                 Constant_El / ConstantsCategory / Constant_El_V
    \Formulas\<FName>\V1                                          Formula_El / Formula_El_V
    \Rules\Rule_NNN\V1                                            EmissionCalculationWork_Rules[_V]
```

Атрибути (точний перелік із RTQP-в'юх):

| В'юха | Атрибути |
|-------|----------|
| `Methodology_V` | `MetName`, `MetCustomName`, `VersName`, `Status`, `StartDate`, `EndDate`, `UserLastModify`, `UserNameActive`, `IsMetadataRecordEnabled`, `IsMetadataRecordUserCount`, `IsMetadataRecordFinalCount` |
| `Formula_El_V` | `FInfo_Name`, `FInfo_UniqueName`, `FInfo_CustomName`, **`FInfo_Text`**, **`FInfo_Arguments`**, `FInfo_StartDate`, `FInfo_EndDate`, `FInfo_Version`, `FInfo_IsAvailable`, `FInfo_Report`, `FInfo_UsedInJobs`, `FInfo_ExtField`, `FInfo_Description`, + `MInfo_Name/Status/Version` |
| `Constant_El_V` | `CInfo_Parameter`, `CInfo_Name`, `CInfo_UniqueName`, `CInfo_CustomName`, **`CInfo_Value`**, **`CInfo_Category`**, `CInfo_StartDate`, `CInfo_EndDate`, `CInfo_Version`, `CInfo_IsAvailable`, `CInfo_Formula`, `CInfo_Gas`, `CInfo_SetName`, `CInfo_Unit`, `CInfo_ExtField`, `CInfo_Description`, + `MInfo_*` |
| `EmissionCalculationWork_Rules_V` | `RInfo_Name`, `RInfo_UniqueName`, `RInfo_CustomName`, **`RuleArg_TableLandFromDB`**, **`RuleArg_Parameters`**, **`RuleArg_Values`**, `RInfo_StartDate`, `RInfo_EndDate`, `RInfo_Version`, `RInfo_IsAvailable`, + `MInfo_*` |

Плюс на кожному елементі AF є `Name`, `Description`, `Comment` — тобто **поле для
пояснення вже існує** і його треба зберегти при переносі.

### 2.2 Три речі, які в AF працюють, і одна, яка ні

**Працює і зберігається:**

1. **Вікна дії на кожній сутності** (`*_StartDate`/`*_EndDate`) — версія формули,
   константи чи правила діє на певний період. Це вже правильна модель.
2. **Константи по категоріях** — одна константа має різні значення для різних
   `CategoryKey` (локація, сезон, група NAE). Це не «дублювання», це вимірність.
3. **`Description`/`Comment`** — пояснення на елементі.

**Не працює:**

4. **Ідентичність через шлях.** Ім'я формули = ім'я папки перед `\V1`;
   `FInfo_Name`, `MInfo_*`, `CInfo_Category` — обчислювані `ConfigString` зі шляху.
   Наслідок: перейменування папки мовчки переписує ідентичність, а зв'язок
   «формула ↔ методологія» тримається **збігом рядків**, а не посиланням.
   Той самий дефект дає `ConstantsTrigger`, який шукає залежні формули через
   `CHARINDEX(ім'я_константи, FInfo_Arguments)` ([B12](B12-ecr-as-is-backend.md) §3.3).

**ER-K-01. У новій моделі ідентичність — сурогатний ключ, ім'я — атрибут.**
Перейменувати формулу можна; посилання на неї не ламаються, бо вони на `Id`.
Це той самий принцип, що `RowKey` для рядків і `ColumnDef.Code` для полів ([B12](B12-ecr-as-is-backend.md) §7).

## 3. Версійність: два різні часи + пояснення (ER-K-02)

Вимога «версійність (дати БД і пояснення)» розкладається на **три** осі, які
не можна змішувати:

| Вісь | Поле | Питання, на яке відповідає |
|------|------|----------------------------|
| **Бізнес-час** | `ValidFrom` / `ValidTo` | з якого по яке число ця версія **застосовується до даних** |
| **Системний час** | `CreatedAt` / `CreatedBy`, `PublishedAt` / `PublishedBy` | коли її **завели в систему** і хто |
| **Пояснення** | `ChangeReason` (обов'язкове), `Description`, `SourceRef` | **чому** змінили і на що спираємось |

```sql
-- спільний шаблон для всіх версійованих сутностей calc.*
ValidFrom      date          NOT NULL
ValidTo        date          NULL        -- NULL = безстроково
Status         tinyint       NOT NULL     -- Draft | Published | Deprecated
CreatedAt      datetime2(3)  NOT NULL
CreatedByUserId int          NOT NULL
PublishedAt    datetime2(3)  NULL
PublishedByUserId int        NULL
ChangeReason   nvarchar(1000) NOT NULL   -- ⚠ обов'язкове при публікації
SourceRef      nvarchar(400)  NULL        -- «WI §11.12.2», наказ, лист — на що спираємось
SupersedesVersionId int       NULL
ContentHash    varbinary(32)  NOT NULL
```

**Чому `ChangeReason` обов'язкове.** Через рік питання «чому коефіцієнт став 0.87»
виникає гарантовано, а відповідь «бо хтось змінив 14.03» — це не відповідь.
Сьогодні в AF є `Comment`, але він необов'язковий і здебільшого порожній.

**Правило непересічності (перевіряється при публікації):** для одного `(Def, CategoryKey)`
вікна `[ValidFrom, ValidTo]` різних `Published`-версій **не перетинаються**.
Інакше «яка версія діє на вересень» має два відповіді — і сьогодні саме це дає
клас помилок «`MAX(Methodology)` відкинув потрібну гілку».

**Три стани і що можна:**

| Стан | Редагувати | Застосовується до розрахунку | Видалити |
|------|:----------:|:----------------------------:|:--------:|
| `Draft` | ✅ вільно | ❌ | ✅ |
| `Published` | ❌ (лише `Description`) | ✅ у своєму вікні | ❌ |
| `Deprecated` | ❌ | ❌ для нових прогонів; історичні результати лишаються | ❌ |

Це той самий контракт, що `TemplateVersion` у ядрі ([10] §2a): структурний шар
заморожений, презентаційний (підпис, опис) — ні.

## 4. Драбина виразності: no-code → скрипт → модуль (ER-K-03)

Вимога «no-code якщо можливо, інакше редагований C#» реалізується **трьома
рівнями**, і система підказує, коли рівня не вистачає.

```
Рівень 1  ФОРМУЛА          no-code, ~90 % випадків
          NCalc-вираз: @Arg, CST.Const, !Formula, 24 функції
          редактор із автодоповненням і валідацією
                    │  не вистачає виразності?
                    ▼
Рівень 2  СКРИПТ (C#)      low-code, редагується у вебі, зберігається як ДАНІ
          обмежений API, компіляція при публікації, тести обов'язкові
                    │  потрібні зовнішні джерела / багатоетапна оркестрація?
                    ▼
Рівень 3  МОДУЛЬ (C#)      код у збірці, реліз через CI
          виконавець конвеєра (один на систему) + інфраструктура;
          ICalculationModule — 4 складні розділи (HSE400, TOx, 2× Flaring),
          якщо конвеєр їх не покриє (N-1)
```

**Правило вибору рівня — не смак, а критерій:**

| Ознака | Рівень |
|--------|:------:|
| результат = вираз над полями рядка і константами | 1 |
| потрібні розгалуження, цикл по речовинах, проміжні змінні, робота з рядками | 2 |
| дані з інших таблиць/періодів, зважені середні по потоках, багатоетапна оркестрація над **внутрішніми** джерелами | 1–2 (декларативний конвеєр, [B22](B22-nocode-and-realism.md) §2) |
| новий протокол, новий формат файлу, нова інфраструктура або оркестрація із **зовнішньою** системою | 3 |

> Сьогодні **все**, що складніше за вираз, автоматично стає рівнем 3 — окремим
> класом `ECW_C**` у збірці, з релізом і передеплоєм. Саме тому їх 44.
> Рівень 2 прибирає більшість із них.

### 4.1 Рівень 1 — редактор формул

Перенос того, що вже є в PI Vision, плюс те, чого немає:

| Є в PI Vision | Додається |
|---------------|-----------|
| автодоповнення `CST.` / `!` / `@` | підказка типу і одиниці аргументу |
| валідація операторів, функцій, аргументів | **перевірка, що всі токени є в `Arguments`** (сьогодні розходження мовчазне) |
| версії формули | **тестовий прогін на реальному рядку** до публікації |
| — | попередження про цілочисельне ділення (`365/31 = 11`) |
| — | «де використовується»: які правила/таблиці/періоди зачепить зміна |

### 4.2 Рівень 2 — скрипт C# як дані

**Що це.** Тіло методу, яке пишеться у веб-редакторі, зберігається в
`calc.ScriptVersion.SourceCode`, компілюється **при публікації** (не при кожному
прогоні) і виконується у worker-процесі ([B13](B13-ecr-calculation-engine.md) §2, ER-C-02).

```csharp
// те, що бачить і редагує користувач — тільки тіло:
decimal fuel = Args.Decimal("FuelConsumption");
decimal hours = Args.Decimal("OperatingTime");
if (hours <= 0) { Warn("Нульовий час роботи"); return; }

foreach (var s in Substances)                    // речовини методології
{
    decimal ef = Const.Value("EF_" + s.Code);    // константа за категорією
    Emit(s, tons: fuel * ef / 1000m, gsec: fuel * ef / (hours * 3600m));
}
```

**Контекст скрипта — вузький і явний** (`ICalculationScriptContext`):

| Член | Що дає |
|------|--------|
| `Args` | типізований доступ до полів рядка джерела (`Decimal`, `String`, `Date`, `IsEmpty`) |
| `Const` | константи методології, вже резолвлені за категорією і датою |
| `Formula` | результат формули рівня 1 тієї самої методології (`!Name`) |
| `Substances` | речовини, оголошені методологією |
| `Period` | межі періоду, кількість днів/годин |
| `Header` | поля шапки документа |
| `Emit(substance, tons, gsec)` | записати результат |
| `Warn(msg)` / `Fail(code, msg)` | `CalculationIssue` |
| `Trace(step, value)` | крок у журнал відтворюваності |

**Чого в контексті немає і не буде:** файлової системи, мережі, БД, рефлексії,
процесів, часу (`DateTime.Now` — тільки `Period`), випадковості. Це не «не
рекомендовано» — цього немає в наборі посилань, і аналізатор відхиляє спробу
дотягнутися.

**Життєвий цикл скрипта:**

```
Draft → редагування у вебі (Monaco, C#-підсвітка, помилки компілятора інлайн)
      → Компіляція        (Roslyn; whitelist посилань і usings; заборонені API — помилка)
      → Тестовий прогін   (обов'язково: ≥1 набір входів із очікуваним результатом)
      → Публікація        (ChangeReason обов'язковий; ContentHash; версія заморожена)
      → Виконання         (кешована скомпільована збірка; ліміт часу і пам'яті на виклик)
```

### 4.3 Безпека рівня 2 — чесно про межі (ER-K-04)

**Roslyn сам по собі не є пісочницею.** Компіляція з обмеженим набором посилань
відсікає більшість, але не все: рефлексію можна дістати транзитивно, а нескінченний
цикл не ловиться аналізатором. Тому захист — багатошаровий, і жоден шар не
оголошується достатнім:

| Шар | Що дає |
|-----|--------|
| **Whitelist посилань і `using`** | немає `System.IO`, `System.Net`, `System.Reflection`, `System.Diagnostics`, `System.Runtime.InteropServices` |
| **Roslyn-аналізатор при компіляції** | заборона `unsafe`, `stackalloc`, `dynamic`, `typeof`, `nameof`-рефлексії, `P/Invoke`, `Task`/`Thread`, `while(true)` без лічильника |
| **Виконання у worker-процесі** | окремий процес під **обліковим записом з мінімальними правами**, без доступу до мережі і до БД, крім свого каналу |
| **Ліміти на виклик** | час (типово 2 с), пам'ять, кількість `Emit` |
| **Право `Calculation.EditScript`** | `IsDangerous = 1` ([11] §3): видається окремо, не входить у `TemplateAdministrator` |
| **Аудит** | кожна правка і публікація — у `aud.*`, з diff-ом коду |
| **Обов'язковий тест** | опублікувати скрипт без жодного зеленого тесту неможливо |

> Формулювання для ІБ: **рівень 2 — це не «користувач пише код на сервері», а
> «методолог задає правило розрахунку виразнішою мовою, під контролем компілятора,
> тестів, окремого права і ізольованого процесу».** Але це все одно виконання коду,
> і воно потребує окремого погодження — питання K-1.

Якщо ІБ скаже «ні» — лишається рівень 1 + рівень 3, і частина з 44 методологій
залишиться класами. Архітектура від цього не змінюється: рівень 2 — окремий
`ICalculationModule`, який можна не вмикати.

## 5. Належність до таблиць через правила (ER-K-05)

Це другий блок вимоги: **як формули і методології «прилипають» до таблиць**.

### 5.1 Модель

Сьогодні: `RuleArg_TableLandFromDB` (ім'я таблиці рядком) + `RuleArg_Parameters`
(`Land_NAE;`) + `RuleArg_Values` (`6560;`), а методологія береться **зі шляху** правила.

Стає:

```sql
calc.RuleDef
    Id, MethodologyVersionId,          -- ← явне посилання, не шлях
    Code                nvarchar(100), -- 'Rule_017'
    SourceTableDefId    int,           -- ← FK на cfg.TableDef, не рядок
    MatchJson           nvarchar(max), -- {"Land_NAE":{"entryIds":[1042,1043]},
                                       --  "Land_TypeFuel":{"entryIds":[77]}}
    Priority            int,
    ValidFrom, ValidTo, Status, ChangeReason, …
```

`MatchJson` — набір умов «колонка ∈ значення», з'єднаних `AND`. Умова на колонку,
якої немає в `TableDef`, — **помилка публікації**, а не порожній результат.

**Значення умови — `ValueRegistryEntryId`**, а не текст. Реєстр береться з
`ColumnDef.LookupRegistryDefId`; текстові коди (`"6560"`, `"Diesel"`) приймає
**лише імпортер міграції** з AF і одразу резолвить у `Id`. Незіставлений код —
помилка міграції, а не мовчазний промах правила. Це та сама вимога, що й для
даних: посилання на довідник живе як `Id`, а перейменування запису реєстру
не ламає жодного правила.

### 5.2 Інваріант «рівно одне правило»

Сьогодні це runtime-помилки: `No matching rule` (0 збігів) і `Rule conflict` (≥2).
Обидві переїжджають у **аналіз при публікації**:

```
Публікація версії методології / зміна правила
   │
   ├─ ПЕРЕТИН: для кожної пари правил на одній таблиці з перетином вікон дії
   │           перевірити, чи існує комбінація значень, яку матчать обидва
   │           → перетин ⇒ відмова публікації зі списком конфліктних значень
   │
   └─ ПОКРИТТЯ: для кожної таблиці — які РЕАЛЬНІ комбінації значень
               (SELECT DISTINCT по колонках правил за останній рік)
               не матчить жодне правило
               → звіт «непокриті рядки: NAE 6702 — 143 рядки, 4 файли»
```

**Аналіз покриття — на реальних даних**, а не на теоретичній множині: саме він
відповідає на питання «чи все, що є в таблиці, буде порахованим», і саме його
сьогодні заміняє чекання помилки в `LogCalculationErrors`.

### 5.3 Екран «Прив'язка»

| Елемент | Що показує |
|---------|-----------|
| **Матриця «таблиця × методологія»** | які таблиці обслуговує кожна методологія і скільки правил |
| **Редактор правила** | таблиця → колонки (з підказкою реальних значень) → значення → вікно дії |
| **Перевірка на льоту** | перетин із наявними правилами — до збереження |
| **Покриття** | по кожній таблиці: % рядків, які матчаться; список непокритих комбінацій |
| **«Що зачепить ця зміна»** | скільки рядків, документів, періодів перерахується |
| **Симуляція** | обрати конкретний рядок → показати, яке правило спрацює і яка методологія |

## 6. Тестування як частина конфігурації (ER-K-06)

Опублікувати не можна без зеленого тесту. Тест — теж дані:

```sql
calc.TestCase   Id, MethodologyVersionId, Name,
                InputsJson,        -- {"FuelConsumption": 1200.5, "OperatingTime": 640}
                ExpectedJson,      -- {"NOx": {"tons": 1.4406, "gsec": 0.000625}}
                Tolerance decimal, -- відносна похибка
                SourceRef,         -- «Excel-приклад WI §5.1», «еталон 2026-03»
                IsRequired bit
```

Три походження тестів:

1. **З документа методології** — приклад із Work Instruction (найцінніші);
2. **З чинних даних** — реальний рядок + результат чинного CLR (генеруються масово
   при міграції, [B13](B13-ecr-calculation-engine.md) §8 — це і є золоте порівняння,
   зафіксоване як тести);
3. **Написані вручну** — крайові випадки: нуль, порожньо, від'ємне, дуже велике.

Прогін тестів — при кожній публікації **всієї версії методології**, не лише
зміненої формули: зміна константи ламає формулу, яку ніхто не чіпав.

## 7. Режим співіснування: конфігуратор і AF

Поки майстер конфігурації — PI AF ([B14](B14-ecr-integration-and-data.md) §5), конфігуратор працює **у режимі
дзеркала**:

| Режим | Що можна в UI | Джерело істини |
|-------|---------------|----------------|
| `Mirror` | тільки перегляд + тести + аналіз покриття | PI AF (синхронізація) |
| `Hybrid` | нові методології — в ECR; наявні — з AF | обидва, за сутністю |
| `Master` | повний CRUD | ECR; синхронізація вимкнена |

Режим — поле на рівні **групи методологій** (`MethodologyDef.GroupCode`), тому
перехід іде розділами, а не «усе разом». Спроба редагувати сутність у режимі
`Mirror` дає зрозумілу відмову з поясненням, де редагувати.

## 8. Схема (доповнення до [B13](B13-ecr-calculation-engine.md) §5.1)

```sql
calc.ScriptDef         Id, OwnerKind tinyint (Methodology|Report|Mapping), OwnerId int,
                       Code, Description
                       -- поліморфний власник: скрипт потрібен і методології (B13),
                       -- і держформі (B16 §2 rpt.ReportRule.ScriptVersionId),
                       -- і мапінгу (B20 §3.2 TransformExpr)
calc.ScriptVersion     Id, ScriptDefId, SourceCode nvarchar(max),
                       CompiledHash varbinary(32), CompiledAt,
                       ValidFrom, ValidTo, Status, ChangeReason, SourceRef,
                       CreatedAt/By, PublishedAt/By, SupersedesVersionId

calc.MethodologyVersion  (див. [B13](B13-ecr-calculation-engine.md) §5.1)
                       -- NumericMode (Legacy|Strict) редагується у вебі, але
                       -- перемикання класифікується як Breaking: ChangeReason,
                       -- аналіз впливу, нова ValidFrom; заднім числом — ніколи

calc.TestCase          (див. §6)
calc.TestRun           Id, MethodologyVersionId, RunAt, Passed, FailedJson

calc.RuleDef           (див. §5.1)
calc.RuleCoverageSnapshot  Id, MethodologyVersionId, SourceTableDefId, AnalyzedAt,
                       RowsTotal, RowsMatched, UncoveredJson

cfg.CalculationBinding Id, TableDefId, MethodologyGroupCode,
                       TriggerKind (OnChange|Scheduled|OnDemand|AfterBinding),
                       ScheduleMode (Interval|Cron) NULL, IntervalSec NULL,
                       CronExpr NULL, WindowFrom/WindowTo time NULL,
                       DependsOnBindingId NULL,      -- ланцюжок замість каденції джобів
                       Priority tinyint, MaxDurationSec int,
                       InputMapJson, OutputMapJson, Scope (Row|Table|Document), IsActive
```

Спільний версійний шаблон §3 застосовується до `MethodologyVersion`, `FormulaDef`,
`ConstantValue`, `RuleDef`, `ScriptVersion` — однаково, без винятків.

## 10. Реєстр рішень

| # | Рішення | Обґрунтування |
|---|---------|---------------|
| **ER-K-01** | Ідентичність сутності — сурогатний ключ; ім'я — атрибут, який можна змінювати | в AF ідентичність зі шляху, тому перейменування ламає зв'язки, а залежності тримаються `CHARINDEX` по тексту |
| **ER-K-02** | Три осі версії: бізнес-час (`ValidFrom/To`), системний час, **обов'язкове `ChangeReason`** | «чому змінили коефіцієнт» — питання, яке виникає через рік; сьогодні `Comment` є, але порожній |
| **ER-K-03** | Драбина: формула → скрипт C# (дані) → модуль (збірка), з критерієм вибору рівня | сьогодні все, складніше за вираз, стає класом у збірці — звідси 44 класи |
| **ER-K-04** | Скрипт виконується в ізольованому worker-процесі з whitelist-посиланнями, аналізатором, лімітами, окремим правом і обов'язковим тестом | Roslyn не є пісочницею; безпека — багатошарова, і це треба сказати ІБ прямо |
| **ER-K-05** | Правило посилається на `TableDefId` і `MethodologyVersionId` явно; `MatchJson` замість трьох текстових полів | текстові поля дають runtime-помилки замість помилок публікації |
| **ER-K-06** | Публікація неможлива без зелених тестів; тести — дані, у т.ч. згенеровані з чинного CLR | золоте порівняння перетворюється на постійний захист від регресії |
| **ER-K-07** | Перетин правил і покриття таблиці перевіряються **на реальних даних** при публікації | «No matching rule» має бути видно до прогону, а не в журналі помилок |
| **ER-K-08** | Режим конфігуратора (`Mirror`/`Hybrid`/`Master`) — на групу методологій | перехід іде розділами разом із cutover |
| **ER-K-09** | **Періодичність розрахунку — поле прив'язки**, а не окремий джоб: `TriggerKind` + розклад у `cfg.CalculationBinding` ([B13](B13-ecr-calculation-engine.md) §5.1) | сьогодні «як часто» зашито в 56 джобів SQL Agent і змінюється тільки адміністратором БД |

## 12. Чек-лист

- [ ] Ідентичність — сурогат; перейменування не ламає посилань (тест)
- [ ] `ChangeReason` обов'язкове при публікації **кожної** сутності
- [ ] Вікна дії `Published`-версій не перетинаються (перевірка при публікації)
- [ ] Редактор формул перевіряє, що всі токени виразу є в `Arguments`
- [ ] Скрипт компілюється при публікації, не при виконанні
- [ ] Заборонені API відхиляються аналізатором, а не документацією
- [ ] Скрипт виконується в процесі без доступу до мережі і БД
- [ ] Публікація без зеленого тесту неможлива
- [ ] Перетин правил і покриття таблиці показані до публікації
- [ ] У режимі `Mirror` UI пояснює, де редагувати насправді
