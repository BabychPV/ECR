## 3. Формат `ChangeSet` і `MigrationPlan` (§11 [13] п. 7)

### 3.1 Принцип: детермінованість і відтворюваність

```
ChangeSet    = f(fromVersionId, toVersionId)              — чиста функція
MigrationPlan = f(ChangeSet, documentId, стратегії)        — чиста функція
```

Обидва — **детерміновані**: той самий вхід дає той самий вихід, включно з порядком
елементів. Це дозволяє порівнювати dry-run із фактичним застосуванням і довести,
що застосували саме те, що показали користувачу.

### 3.2 `ChangeSet`

```jsonc
{
  "schemaVersion": 1,
  "fromVersionId": 7, "toVersionId": 8,
  "computedAt": "2026-09-02T10:00:00Z",
  "contentHash": "sha256:…",              // від відсортованого списку items
  "items": [
    { "seq": 1, "entityType": "ColumnDef", "changeType": "Add",
      "class": "Safe",
      "target": { "tableCode": "WaterReport.Main", "code": "Comment" },
      "after": { "dataType": "String", "isRequired": false },
      "impact": { "documents": 0, "cells": 0, "periods": 0 } },

    { "seq": 2, "entityType": "ColumnDef", "changeType": "NarrowType",
      "class": "Guarded",
      "target": { "tableCode": "WaterReport.Main", "code": "Hours" },
      "before": { "dataType": "String" },
      "after":  { "dataType": "Decimal", "precision": 18, "scale": 4 },
      "requiresStrategy": ["OnConversionFailure"],
      "impact": { "documents": 42, "cells": 128430, "periods": 9 } },

    { "seq": 3, "entityType": "RowDef", "changeType": "SoftDelete",
      "class": "Breaking",
      "target": { "tableCode": "WaterReport.Main", "rowKey": "7001099" },
      "impact": { "documents": 42, "cells": 2520, "periods": 9 } }
  ]
}
```

`impact` — кількісний аналіз впливу, який показує «звіт про вплив»
([B21](B21-frontend-spec.md) §4). Рахується на запит
`GET /api/v1/templates/{id}/versions/{v}/impact` ([B01](B01-backend-blueprint.md) §5)
і кешується на `contentHash`; для класу `Safe` завжди нулі.

Зберігається в `aud.SchemaChange.BeforeJson`/`AfterJson` (поелементно) і цілком —
у `cfg.TemplateVersionDiff` для повторного показу.

### 3.3 `MigrationPlan`

```jsonc
{
  "schemaVersion": 1,
  "documentId": 42, "fromVersionId": 7, "toVersionId": 8,
  "changeSetHash": "sha256:…",            // ← прив'язка до конкретного ChangeSet
  "strategies": { "WaterReport.Main.Hours": { "onConversionFailure": "KeepAsText" } },
  "dryRun": {
    "cellsMapped": 128430,
    "cellsCreated": 2100,
    "cellsOrphaned": 312,
    "typeConflicts": 4,
    "formulasUnresolved": 0,
    "samples": { "orphaned": ["н/д", "-", "2,5 (прибл.)"] },
    "estimatedDurationMs": 45000
  },
  "confirmedBy": null, "confirmedAt": null
}
```

**Правила:**

* план зберігається (`doc.DocumentMigrationPlan`) і має TTL: якщо між dry-run
  і застосуванням структура або дані змінилися, `changeSetHash`/`RowVersion`
  не збігаються → план **недійсний**, треба перебудувати. Інакше користувач
  підтверджує один звіт, а застосовується інший;
* застосування — одна транзакція; часткове заборонено ([10] §6);
* snapshot «до» → `doc.DocumentSnapshot(SnapshotReason = BeforeMigration)`;
* осиротілі значення → `aud.OrphanedValue`, не видаляються;
* мігрований документ **завжди** повертається в `Draft`.

> блокування по `RowVersion` (BR-12). Дізнатися про це на Етапі 4 буде дорого.

## 5. Що переглядати не варто

Рішення з ТЗ §12 і [13] §12 (20+ пунктів) прийняті на підставі перевірених
першоджерел ([15]) і не переглядаються без вагомої причини. Зокрема, три,
які найчастіше хочеться «покращити»:

| Рішення | Чому не чіпаємо |
|---------|-----------------|
| **EF Core, не DataObjects.Net** | головна перевага DataObjects.Net — автоеволюція схеми — у нас **свідомо не працює**: фізична схема зафіксована (ТЗ §5.4-A) |
| **Структура = дані, жодного DDL під час роботи** | динамічний `ALTER TABLE` бере Sch-M lock, розсинхронізує міграції EF і розводить середовища ([10] §1) |
| **Сервісний обліковий запис до PI, не Kerberos-делегування** | локальні користувачі не мають Windows-ідентичності — делегування не покриває їх **у принципі** (ФВ-6.9) |
