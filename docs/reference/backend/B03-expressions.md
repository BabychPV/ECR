# B03 — Мова виразів, граф залежностей, перерахунок

> Закриває §11 [13] пп. **3** (синтаксис виразів, чи один парсер на все)
> і **13** (семантика діапазонів у формулах).

---

## 1. Рішення: одна мова, один парсер, п'ять контекстів (BR-09)

У системі п'ять незалежних місць з виразами користувача (B01 §2.1 + діалект
методологій, [B13](B13-ecr-calculation-engine.md) §3). Рішення —
**одна граматика і один парсер** у збірці `Ecr.Expressions`; відрізняються лише
**контекст розв'язання посилань** і **очікуваний тип результату**.

| Контекст | Що доступно | Результат |
|----------|-------------|-----------|
| `Formula` | комірки таблиці, `[__Header]`, `[Period:…]`, `[PrevProject]`, реєстри, агрегати | скаляр |
| `Validation` | те саме + `[Row]`, `[Value]`, `[Old]` | `bool` |
| `RowFilter` | `[Row]`, `[User]`, реєстри. **Без** агрегатів і крос-періодних посилань | `bool` |
| `ConditionalFormat` | `[Value]`, `[Row]`, `[Column:…]` | `bool` |
| **`Methodology`** ⭐ | `@Arg` (поле рядка джерела), `CST.Name` (константа), `!Formula` (інша формула методології), літерали | скаляр |

Обмеження контексту — це не синтаксис, а **перевірка на етапі семантичного
аналізу**. Тому вираз `SUM(...)` у `RowFilter` не «не розпарситься», а дасть
зрозумілу помилку «агрегати недоступні у фільтрі рядків» — з позицією в тексті.

**Чому не п'ять парсерів.** Крайові випадки (порожнє значення, помилка,
`NULL` vs `IsEmpty`, порівняння різних типів, локаль десяткового роздільника)
мають поводитися **однаково** скрізь. Чотири реалізації — це чотири різні
відповіді на питання «чому валідація каже, що сума не сходиться, а формула
показує, що сходиться».

## 2. Роль NCalc (BR-10)

ТЗ §12 п.9 фіксує NCalc. Уточнення ролі: **NCalc — обчислювач скалярних
виразів, а не парсер нашої мови.**

```
текст виразу
   │
   ▼
 ЛЕКСЕР + ПАРСЕР (наш)        ← розуміє [Sheet].[Table].[Row].[Col],
   │                            діапазони, [Period:-1], [__Header], [User]
   ▼
   AST (наш)                  ← семантичний аналіз: типи, контекст, цикли
   │
   ├──► ЗАЛЕЖНОСТІ ────────► cfg.FormulaDependency (при Publish)
   │
   ▼
 КОМПІЛЯЦІЯ у план обчислення
   │
   ▼
 NCalc: арифметика, порівняння, вбудовані функції
        посилання вже розв'язані в параметри
```

**Чому саме так, а не «віддати рядок у NCalc».** NCalc не знає нашого
синтаксису посилань і не вміє будувати граф залежностей. Якщо просто підставляти
значення текстом перед викликом — отримаємо ін'єкцію і неможливість
інкрементного перерахунку. Наш парсер потрібен у будь-якому разі; NCalc
економить нам арифметику, пріоритети операцій і крайові випадки чисел.

Функції реалізуються через `EvaluateFunctionHandler` — 11 із чинного шаблону
плюс шість «очевидних» (ТЗ ФВ-3.4):

```
Діалект A (шаблони), обов'язкові з файлу:
  SUM · LEFT · VALUE · IFERROR · ROUNDDOWN · TEXT · CHAR · CONCATENATE
  TEXTBEFORE · TEXTAFTER      (VLOOKUP не реалізуємо — він зникає, див. §6)
Діалект A, додані:            IF · ROUND · AVERAGE · MAX · MIN · ABS

Діалект B (методології), 24 функції — точний набір редактора PI Vision:
  Abs Acos Asin Atan Ceiling Cos Exp Floor IEEERemainder Ln Log Log10
  Max Min Pow Round Sign Sin Sqrt Tan Truncate  +  in  if  ifs
```

**Два діалекти — один парсер.** Діалект B відрізняється лише синтаксисом посилань
(`@Arg` / `CST.Name` / `!Formula`) і набором функцій; лексер, AST і семантичний
аналіз спільні. Три семантичні пастки діалекту B (цілочисельне ділення NCalc,
`FInfo_Arguments` як джерело істини про аргументи, `CInfo_Value` як `nvarchar`)
описані в [B13](B13-ecr-calculation-engine.md) §3 і переносяться 1:1.

## 3. Граматика (ескіз, EBNF)

```ebnf
expr        := orExpr
orExpr      := andExpr ( ("OR"|"||") andExpr )*
andExpr     := cmpExpr ( ("AND"|"&&") cmpExpr )*
cmpExpr     := addExpr ( ("="|"<>"|"<"|"<="|">"|">=") addExpr )*
addExpr     := mulExpr ( ("+"|"-"|"&") mulExpr )*
mulExpr     := unary   ( ("*"|"/") unary )*
unary       := ("-"|"NOT")? primary
primary     := number | string | bool | "NULL"
             | funcCall | reference | "(" expr ")"
funcCall    := IDENT "(" ( expr ( ";" expr )* )? ")"      (* ';' — як в Excel-локалі *)

reference   := "[" refPart ( "]" "." "[" refPart )* "]"
refPart     := IDENT | rowRange | periodRef | special
rowRange    := ROWKEY ":" ROWKEY                          (* 7001001:7001005 *)
periodRef   := "Period" ( ":" ( SIGNED_INT | "First" | "Last" | "Current" ) )?
special     := "__Header" | "CurrentRow" | "Row" | "Value" | "Old"
             | "User" | "PrevProject" | "Column:" IDENT
```

**Роздільник аргументів — `;`**, як у чинних формулах шаблону (локаль користувачів).
Десятковий роздільник у літералах — **завжди `.`**, незалежно від локалі: інакше
той самий вираз означає різне на різних машинах. Це фіксується в тестах.

### 3.1 Приклади

```
SUM([Water_07].[Main].[7001001:7001005].[{Period}])
IFERROR(VALUE(LEFT([Row].[ReportId]; 7)); 0)
[Row].[Total] = [Row].[Q1] + [Row].[Q2] + [Row].[Q3] + [Row].[Q4]
[Row].[Balance] + [Water_07].[Main].[CurrentRow].[MonthValue].[Period:-1]
[PrevProject].[Water_07].[Main].[7001001].[MonthValue].[Period:Last]
IF([__Header].[Contract].[OnshoreOffshore] = "Offshore"; [Value] * 1.15; [Value])
[Row].[PermitId] IN [User].[AllowedPermits]
```

### 3.2 Семантика порожнього і помилки

Найважливіша частина — саме тут розходяться рушії. Правила беруться з поведінки
чинного рішення ([04] §8) і фіксуються автотестами:

| Ситуація | Значення в обчисленні | Що зберігається |
|----------|----------------------|-----------------|
| Комірки немає в БД | `DefaultValue` або `NULL` | нічого |
| `IsEmpty = 1` | `NULL` | явна порожнеча |
| `NULL` в арифметиці | трактується як `0` **у `SUM`**, як `NULL` — у решті | — |
| `NULL` у порівнянні | результат `false`, не помилка | — |
| Ділення на нуль | `#DIV/0` → перехоплюється `IFERROR` | комірка `IsCalculated`, значення `NULL`, `wf.ValidationResult` із `Warning` |
| Помилка типу | помилка публікації, якщо статична; `#VALUE` у runtime | те саме |

> Правило «`NULL` у `SUM` = 0, у решті = `NULL`» — це поведінка Excel, і воно
> **не інтуїтивне**. Саме тому воно тут записане, а не «зрозуміло само собою».

## 4. Діапазони рядків (BR-11) — закриває §11 п.13

### 4.1 Проблема

Excel `SUM(I7:I11)` — позиційний діапазон. У нас рядки ідентифікуються `RowKey`,
а `Ordinal` — лише порядок відображення і **презентаційне поле**, яке можна
міняти в опублікованій версії ([10] §2a). Якщо діапазон обчислювати за `Ordinal`
у runtime, то зміна порядку рядків (презентаційна, «безпечна») **мовчки змінить
результат формули**. Це найгірший клас багів: даних не зіпсовано, а числа інші.

### 4.2 Рішення

**Діапазон розкривається в явний список `RowKey` на момент `Publish`
і зберігається.** У runtime діапазонів не існує.

```sql
CREATE TABLE cfg.FormulaDependency
(
    Id            int IDENTITY PRIMARY KEY,
    SourceKind    tinyint       NOT NULL,  -- 0 Formula, 1 CalculationBinding (П-13)
    FormulaDefId  int           NULL,      -- для SourceKind = 0
    BindingId     int           NULL,      -- cfg.CalculationBinding, для SourceKind = 1
    FilterJson    nvarchar(max) NULL,      -- предикат для RowMode = Dynamic (§4.3)
    DependsOnKind tinyint       NOT NULL,  -- 0 Cell, 1 Header, 2 Registry,
                                           -- 3 CrossPeriod, 4 CrossProject
    TableDefId    int           NULL,
    RowKey        nvarchar(100) NULL,      -- конкретний рядок, НЕ діапазон
    ColumnDefId   int           NULL,
    PeriodOffset  smallint      NULL,      -- для [Period:-1] → -1
    SortOrder     int           NOT NULL   -- позиція в розкритому діапазоні
);
CREATE INDEX IX_FormulaDependency_Reverse
    ON cfg.FormulaDependency (TableDefId, RowKey, ColumnDefId)
    INCLUDE (FormulaDefId);
```

**Наслідки, які треба усвідомити:**

1. Зміна `Ordinal` після публікації **не змінює** результати формул — саме те,
   що й обіцяно в [10] §2a («презентаційна зміна не може вплинути на дані»).
2. Додавання рядка в діапазон = **структурна** зміна → нова версія. Це логічно:
   «сюди тепер входить ще один рядок» — це зміна змісту звіту, а не оформлення.
3. `IX_FormulaDependency_Reverse` дає **зворотний** пошук: «які формули залежать
   від цієї комірки» — основа інкрементного перерахунку (§5).
4. Розкритий діапазон видно в UI («формула охоплює рядки 7001001…7001005»),
   що знімає цілий клас питань «а чому не порахувалося».

### 4.3 Динамічні рядки (`RowMode = Dynamic`)

Для таблиць, де користувач додає рядки, статичного списку `RowKey` не існує.
Там діапазон записується **предикатом**, а не переліком:

```
SUM([Table].[Rows WHERE RowType='Item'].[MonthValue])
→ DependsOnKind = Cell, RowKey = NULL, + FilterJson {"RowType":"Item"}
```

Зворотний пошук у цьому випадку працює по `(TableDefId, ColumnDefId)` з
перевіркою предиката на конкретному рядку. Дорожче, але таких формул мало
(у чинному шаблоні — жодної: усі GROUP-підсумки над фіксованими рядками).

## 5. Граф залежностей і перерахунок

### 5.1 Побудова — при `Publish`, не в runtime

```
Publish:
  1. Розібрати всі FormulaDef → AST
  2. Витягти залежності → cfg.FormulaDependency (з розкритими діапазонами)
  3. Додати ребра з cfg.TableRelationDef (Rollup / Mirror / MetadataSource)
  4. Топологічний сорт → FormulaDef.EvaluationOrder
  5. Цикл → Publish відхиляється зі списком ланцюжка
```

Топологічний порядок рахується **один раз назавжди** — версія структурно
незмінна. У runtime він просто читається з кешованих метаданих ([14] §3.4).

### 5.2 Інкрементний перерахунок

```
ApplyAsync(batch) → змінені CellRef[]
   │
   ▼
ReadDependentsAsync: обхід IX_FormulaDependency_Reverse у ширину
   │   (з обмеженням глибини і захистом від повторів)
   ▼
розділити на дві групи:
   A. у межах ЦЬОГО TableInstance      → рахуємо СИНХРОННО, у тій самій транзакції
   B. поза ним (Rollup 7.0, Mirror 7a) → позначаємо «брудним», рахуємо ВІДКЛАДЕНО
   ▼
A: сортувати за EvaluationOrder, обчислити, записати CellValue(IsCalculated=1)
B: doc.TableInstance.IsDirty = 1 → RecalculationJob (debounce ~300 мс)
```

**Чому саме такий поділ.** Бюджет запису — 300 мс ([14] §2 п.5). Перерахунок
GROUP-підсумків усередині таблиці — це десятки комірок і вкладається. Rollup
`7.0 Water consolidation` із `7. Water Report` — це інша таблиця, інший
`TableInstance`, потенційно інші права, і робити його синхронно означає, що
кожна вставка з буфера обміну тягне за собою чужу таблицю. Користувач бачить
`7.0` як «перераховується…» і за секунду — готове.

Це прямо відповідає `TableRelationDef.OnSourceChange = Propagate` ([09] §5.4):
поширення є, воно просто асинхронне.

### 5.3 Крос-періодні і крос-проєктні посилання

`FormulaDef.RefMode` ([07] §2):

| Режим | Поведінка | Коли |
|-------|-----------|------|
| `Snapshot` (типово) | значення копіюється при **генерації документа** і далі не змінюється | «залишок з минулого року» — затверджене минуле не має «пливти» |
| `Live` | резолвиться при кожному перерахунку | внутрішньорічні посилання `[Period:-1]`, де попередній місяць ще правлять |

`Snapshot` матеріалізується в `doc.CellValue` з `IsCalculated = 1` і **не має
залежностей** у графі — інакше зміна минулого року каскадом переписала б
поточний. Оновити знімок можна лише явною операцією «оновити перенесені залишки»
з підтвердженням.

### 5.4 Захист від патологій

| Ризик | Захист |
|-------|--------|
| Ланцюжок на сотні рівнів | обмеження глибини обходу (конфіг, типово 100) → `Warning` при `Publish` |
| Формула на 10 000 залежностей | ліміт на кількість залежностей однієї формули (типово 5 000) → відмова при `Publish` |
| Перерахунок «усього документа» | заборонено як операція за замовчуванням; є явна `POST /recalculate` як фонова задача |
| Розбіжність із матеріалізованим значенням | `ConsistencyCheckJob` інваріант 6 ([10] §7) |

## 6. Що зникає разом із `VLOOKUP`

429 `VLOOKUP` у чинному шаблоні — це **не обчислення**, а прив'язка до довідника
([15] §4). Ми їх не реалізуємо. Замість них:

```
Було:  =IFERROR(VLOOKUP(D6; Configuration!$R$2:$U$11; 2; FALSE); "")
Стало: ColumnDef "WaterGroup" { DataType = Lookup,
                                LookupRegistryDefId = Registry "WaterGroup" }
       + RegistryDef.DisplayTemplate = "{Code} - {NameEn}"
```

Так само зникають `CONCATENATE`/`TEXT` там, де вони будували відображуваний
текст (`=TEXT(V2;"0")&" - "&W2`) — це `DisplayTemplate`.

**Наслідок для bootstrap-імпортера** (B09): формула з `VLOOKUP` не переноситься
в `FormulaDef`, а перетворюється на `ColumnDef.LookupRegistryDefId`. Це має
бути окрема гілка з окремим звітом — щоб було видно, що саме так інтерпретовано,
і щоб бізнес міг перевірити.

Реально обчислювальних формул лишається **~250**, і майже всі — `SUM` по
GROUP-рядках.

## 7. Тест еквівалентності (задача 0.3 roadmap)

Обов'язковий, і його результат — вхід до рішення про готовність рушія.

```
вхід:  ДІАЛЕКТ A — усі ~250 обчислювальних формул чинного шаблону
       ДІАЛЕКТ B — усі формули методологій із AF_Formulas.FInfo_Text
       + ~150 синтетичних крайових випадків:
            порожньо · NULL · від'ємні · нуль · дуже великі
            текст у числовій колонці · #N/A · #REF!
            округлення .5 · 10 знаків після коми · експонента
прогін: NCalc (наш рушій) | formulajs (клієнт) | Excel (еталон)
вихід:  звіт розбіжностей із класифікацією
```

**Критерій приймання:** нуль розбіжностей класу «інше число»; розбіжності класу
«інше подання того самого числа» — задокументовані; розбіжності `formulajs`
проти сервера — задокументовані як **очікувані** (клієнт — лише підказка,
ТЗ §5.2) і показуються користувачу як попередження.

Окремо перевіряється **формат експорту значення** (алгоритм 1 із ТЗ §7):
помилка → `""`, порожньо → `"NULL"`, число → плоский десятковий за форматом
комірки. Від нього залежить сумісність із даними в AF, тому це не «десь у
`Ecr.Excel`», а окремий тестований компонент `ValueExportFormatter` у
`Ecr.Expressions` — ним користуються експорт і **утиліта валідації міграції** (відтворення `;`-рядка); зворотної публікації в AF немає (D-44).

## 8. Чек-лист

- [ ] Одна збірка `Ecr.Expressions`; **п'ять** контекстів, один парсер, два діалекти
- [ ] Реалізація рушія — за портом `IFormulaEngine` ([13] §6)
- [ ] Помилка парсингу містить позицію в тексті і зрозумілу причину
- [ ] Обмеження контексту перевіряються семантичним аналізом, не синтаксисом
- [ ] Діапазони розкриті в `cfg.FormulaDependency` на момент `Publish`
- [ ] Зворотний індекс залежностей існує і використовується для інкрементного перерахунку
- [ ] Крос-таблична пропагація — асинхронна, з debounce
- [ ] `Snapshot`-посилання не мають ребер у графі
- [ ] Десятковий роздільник у літералах — завжди `.`; роздільник аргументів — `;`
- [ ] Тест еквівалентності на всіх ~250 формулах зелений
- [ ] `ValueExportFormatter` покритий тестами на реальних значеннях із чинного файлу
