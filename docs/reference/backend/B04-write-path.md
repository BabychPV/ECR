# B04 — Шлях запису: конкурентність, транзакції, валідація, аудит

> Закриває §11 [13] пп. **4** (модель конкурентності), **5** (транзакційні межі),
> **10** (формат аудиту).
> Це найгарячіший код у системі: бюджет — **300 мс p95 на 100 комірок**
> при **125 RPS** в одну партицію ([14] §2 п.5, §1.3).

---

## 1. Одна операція запису, а не десять

Усі способи змінити дані зводяться до **одного** внутрішнього виклику
`ICellStore.ApplyAsync(CellWriteBatch)`:

| Джерело | Як потрапляє |
|---------|--------------|
| Правка комірки в grid | `PATCH /cells` з одним елементом |
| Вставка діапазону з Excel | `PATCH /cells` зі 100–2000 елементами |
| Fill down/right | те саме |
| Імпорт `.xlsx` | фонова задача → батчі по ~2000 |
| Мапінг сирих даних із AF | фонова задача → батчі |
| Перерахунок формул | той самий батч, `Origin = Calculation` |
| Міграція документа на нову версію | той самий батч, `Origin = Migration` |

**Чому це принципово.** Аудит, валідація, перевірка прав, оптимістичне
блокування і перерахунок мають виконуватися **однаково** незалежно від того,
звідки прийшла зміна. Кожен обхідний шлях («імпорт пише напряму, бо швидше») —
це дірка в аудиті, яку виявляють через рік.

`CellWriteBatch.Origin` (`UserEdit` / `Import` / `Calculation` / `Migration` /
`ExternalMapping`) потрапляє в аудит і керує дрібними відмінностями: наприклад,
обчислені комірки не перевіряються на `IsReadOnly`.

## 2. Конкурентність (BR-12): `RowVersion` на **рядку**

### 2.1 Вибір рівня

| Рівень | Оцінка |
|--------|--------|
| Комірка | найточніше, але 100 комірок = 100 токенів у запиті і 100 перевірок. Надлишково: два оператори рідко правлять **одну комірку**, зате часто — одну таблицю |
| **Рядок** | **обрано.** Природна одиниця: `RowKey` = позиція звіту, і саме за неї «відповідає» користувач. Конфлікт означає щось змістовне: «ви обидва правили рядок 7001001» |
| `TableInstance` | занадто грубо: два оператори в одній таблиці конфліктують постійно, хоча правлять різні рядки. У ECR це типовий сценарій (велика таблиця `9. Utility`) |
| Документ | непридатне |

### 2.2 Контракт

```jsonc
PATCH /api/v1/documents/42/cells
If-Match: "ti:9001:0x00000000000A1B2C"        // версія TableInstance — структурна
{
  "tableInstanceId": 9001,
  "periodKey": 202609,
  "origin": "UserEdit",
  "rows": [
    { "rowKey": "7001001", "baseVersion": "0x0000000000A1B200",
      "cells": [ { "columnCode": "MonthValue", "value": 125.5 },
                 { "columnCode": "Note",       "value": null } ] },
    { "rowKey": "7001002", "baseVersion": "0x0000000000A1B201",
      "cells": [ { "columnCode": "MonthValue", "isEmpty": true } ] }
  ]
}
```

* `If-Match` на `TableInstance` ловить **структурні** зміни (додали/видалили рядки).
* `baseVersion` на рядку ловить **змістовні** конфлікти.
* `value: null` — стерти значення; `isEmpty: true` — явна порожнеча
  (аналог `"NULL"` у чинному експорті); **відсутність поля** — не чіпати.
  Це три різні операції (B01 §5).

### 2.3 Відповідь на конфлікт

```jsonc
409 Conflict
{
  "errorCode": "ECR-CELL-0409",
  "conflicts": [
    { "rowKey": "7001001",
      "columnCode": "MonthValue",
      "yourValue": 125.5,
      "theirValue": 130.0,
      "theirUser": "AGS\\ivanov",
      "theirChangedAt": "2026-09-02T10:15:33Z",
      "currentVersion": "0x0000000000A1B2FF" }
  ]
}
```

**Увесь батч відхиляється** — часткове застосування заборонено (B01 §5).
Клієнт показує розбіжності і дає вибрати; «перезаписати мовчки» немає як опції.

### 2.4 «Дотик» рядка

`rowversion` на `doc.TableRow` не змінюється сам, коли ми пишемо в `doc.CellValue`.
Тому процедура запису **завжди** оновлює `TableRow.ModifiedAt` для зачеплених
рядків — це і піднімає `RowVersion`. Забути про це = зламати оптимістичне
блокування тихо, і тест на це обов'язковий.

## 3. Валідація: що коли

| Рівень | Коли | Блокує? | Де зберігається |
|--------|------|---------|-----------------|
| **Комірка** (тип, діапазон, список, regex, обов'язковість) | **до** запису, у тій самій операції | так → 422, батч не застосовано | не зберігається |
| **Рядок / Таблиця** (`сума ITEM = GROUP`, «якщо A, то B») | після запису, у **тій самій транзакції**, для зачеплених рядків | ні (`Error` фіксується, але запис лишається) | `wf.ValidationResult` |
| **Документ** | при `Submit` (і на вимогу) | `Error` блокує `Submit` | `wf.ValidationResult` |

### 3.1 Чому рядкова валідація не блокує запис

Звіт заповнюють поступово. Якщо правило «сума ITEM = значення GROUP» блокуватиме
запис, користувач не зможе ввести **перший** рядок — сума ще не сходиться.
Тому: записуємо, фіксуємо `Error` у `wf.ValidationResult`, показуємо в UI,
і не даємо `Submit`. Це саме та поведінка, яку описує ФВ-5.19.

Комірковий рівень навпаки — блокує: `"abc"` у числовій колонці не має потрапити
в БД взагалі, інакше інваріант 5 ([10] §7) порушується прямо в момент запису.

### 3.2 422 з прив'язкою до комірки

```jsonc
422 Unprocessable Entity
{
  "errorCode": "ECR-CELL-0422",   // код із каталогу build/02-contracts.md#error-codes
  "errors": [
    { "path": "rows[0].cells[0]", "rowKey": "7001001", "columnCode": "Hours",
      "code": "RANGE", "severity": "Error",
      "message": "Значення має бути в межах 0…744",
      "params": { "min": 0, "max": 744 } }
  ]
}
```

`message` віддається мовою з `Accept-Language` ([13] §7), але `code` і `params`
стабільні — щоб клієнт міг підсвітити комірку і показати власний текст.

## 4. Транзакційні межі (BR-13)

### 4.1 Що всередині транзакції

> `doc.usp_ApplyCellBatch` — **доступ до даних**, не логіка: він приймає готовий
> набір і виконує `MERGE`. Рішення «яке значення записати», «чи дозволено» і
> «що перерахувати» ухвалює сервіс до виклику ([B22](B22-nocode-and-realism.md) §3.4).

```
BEGIN TRAN  (READ COMMITTED SNAPSHOT)

  1. SELECT … FROM doc.TableRow WITH (UPDLOCK)
     WHERE PeriodKey=@pk AND TableInstanceId=@ti AND RowKey IN (…)
       → перевірка baseVersion; розбіжність → ROLLBACK, 409

  2. doc.usp_ApplyCellBatch @Cells TVP
       MERGE у doc.CellValue (INSERT / UPDATE / DELETE для value:null)
       OUTPUT старих значень у @Changed

  3. UPDATE doc.TableRow SET ModifiedAt = @now WHERE …     -- підняти RowVersion

  4. INSERT aud.CellChange SELECT … FROM @Changed          -- один set-based INSERT

  5. Перерахунок формул у межах цього TableInstance
       (крок 2 повторно, Origin = Calculation, без аудиту прав)

  6. Валідація рядків/таблиці для зачеплених рядків
       MERGE у wf.ValidationResult

  7. UPDATE doc.TableInstance SET LastCalculatedAt, RowVersion

COMMIT
```

### 4.2 Що поза транзакцією

| Крок | Чому назовні |
|------|--------------|
| Перевірка прав, стану періоду і документа | читання з кешу, не потребує транзакції; робиться **до** неї |
| Валідація рівня комірки | до транзакції — щоб не відкривати її заради відхилення |
| Позначення крос-табличних залежностей «брудними» | окремий короткий `UPDATE` після `COMMIT`; втрата прапорця не критична — `ConsistencyCheckJob` це підбере |
| Постановка `RecalculationJob` | після `COMMIT` (інакше задача може стартувати раніше, ніж дані видно) |
| Метрики, логи, трасування | назовні завжди |

### 4.3 Рівень ізоляції

**`READ COMMITTED SNAPSHOT` на рівні БД** (`ALTER DATABASE … SET READ_COMMITTED_SNAPSHOT ON`).

Обґрунтування: у піковий день 100 користувачів читають і пишуть **одну партицію**
([14] §1.3). Під звичайним `READ COMMITTED` читачі блокуються писарями, і
відкриття таблиці починає стрибати. RCSI прибирає це ціною навантаження на
`tempdb` — тому `tempdb` на швидкому диску і 8 файлів ([14] §5).

`UPDLOCK` на кроці 1 потрібен саме тому, що під RCSI звичайне читання не блокує:
без нього два паралельні батчі на один рядок обидва пройдуть перевірку версії.

### 4.4 Розмір батча і тайм-аут

| Параметр | Значення | Чому |
|----------|----------|------|
| Максимум комірок в одному `PATCH` | 2 000 | вставка з Excel діапазону 100×20; більше — це імпорт, і йому місце у фоні |
| Максимум рядків | 500 | стільки ж, скільки віддає одна «сторінка» таблиці |
| Тайм-аут транзакції | 10 с | якщо не вклалися — щось не так, і краще впасти, ніж тримати блокування |
| Ретрай на deadlock | 2 спроби з jitter | взаємні блокування можливі при перерахунку rollup-ів |

## 5. Аудит (BR-14) — закриває §11 п.10

### 5.1 Синхронно, але набором

[14] §8 називає антипатерном «логувати кожну зміну комірки синхронно в БД».
Уточнення: антипатерн — це **окремий `INSERT` на комірку**. Один set-based
`INSERT … SELECT FROM @Changed` на весь батч — це один запит і десятки мілісекунд.

**Рішення: аудит пишеться в тій самій транзакції, одним запитом.**

Альтернатива (черга/outbox) відкидається: аудит змін даних — вимога ФВ-5.21
(«незмінний журнал 100% змін»), і асинхронний запис означає вікно, у якому
зміна є, а сліду немає. Для системи з екологічною звітністю це неприйнятний
компроміс заради ~20 мс.

Асинхронно пишуться **інші** журнали: `itg.DataCollectionRun`, метрики,
`sec.AuthAuditEntry` — там втрата останнього запису при аварії не змінює нічого.

### 5.2 Формат запису

```sql
CREATE TABLE aud.CellChange
(
    ChangedAt        datetime2(3)   NOT NULL,   -- партиційний ключ
    Id               bigint         NOT NULL,   -- SEQUENCE
    PeriodKey        int            NOT NULL,
    TableInstanceId  bigint         NOT NULL,
    TableRowId       bigint         NOT NULL,
    RowKey           nvarchar(100)  NOT NULL,   -- денормалізовано: рядок може бути видалений
    ColumnDefId      int            NOT NULL,
    OldValue         nvarchar(1000) NULL,       -- канонічне текстове подання
    NewValue         nvarchar(1000) NULL,
    ChangedByUserId  int            NOT NULL,   -- sec.User.Id, НЕ Sid (локальні його не мають)
    Origin           tinyint        NOT NULL,   -- UserEdit/Import/Calculation/Migration/…
    DocumentStatusAtChange tinyint  NOT NULL,
    PeriodStateAtChange    tinyint  NOT NULL,
    IsLateEdit       bit            NOT NULL,
    LateEditReason   nvarchar(1000) NULL,
    ClientIp         nvarchar(45)   NULL,
    CorrelationId    uniqueidentifier NOT NULL,

    CONSTRAINT PK_CellChange PRIMARY KEY CLUSTERED (ChangedAt, Id)
        ON ps_AuditByMonth(ChangedAt)
) ON ps_AuditByMonth(ChangedAt);
```

**Три рішення, які варто пояснити:**

1. **`ChangedByUserId`, а не `ChangedBySid`.** [07] §7 пропонує SID. Але локальні
   облікові записи SID не мають ([11] §8), а модель вимагає, щоб доменний і
   локальний користувач були рівноправні. Внутрішній `Id` — єдиний ключ, що
   працює для обох. Це узгоджується з приміткою в [07] §6 («на нього посилається
   весь аудит»), і поширюється на **всі** таблиці аудиту.
2. **Значення як текст, а не типізовані колонки.** Аудит читають, а не агрегують.
   Канонічне подання (те саме, що дає `ValueExportFormatter`, B03 §7) робить
   історію комірки читабельною і не залежною від типу, який міг змінитися.
3. **`Origin`.** Без нього неможливо відповісти на питання «це людина змінила
   чи перерахунок» — а воно виникає першим при розборі розбіжності.

### 5.3 Індекси і retention

| Що | Рішення |
|----|---------|
| Індекс | кластерний `(ChangedAt, Id)` + **один** некластерний `(TableRowId, ColumnDefId, ChangedAt DESC)` — для екрана «історія комірки» |
| Партиціонування | по місяцях (`ps_AuditByMonth`) |
| Стиснення | `PAGE` на свіжих партиціях; **columnstore** на партиціях старших 3 місяців (перебудова щомісяця регламентною задачею) |
| Retention | ⚠ **відкрито (B-3)**: ФВ-6.12 «журнали — 3 роки» не розрізняє журнали і **зміни даних**. Проєктне припущення до відповіді — зберігати безстроково, з архівацією в `arc.CellChange` разом із роком; підтвердити на Етапі 0 ([B10](B10-decisions.md) §4.2) |
| Права | `INSERT` + `SELECT`; `UPDATE`/`DELETE` відкликані (B01 §6.4) |
| Обсяг | ~2× від `CellValue` ([07] §11) → окрема файлова група `AUDIT` |

### 5.4 `IsLateEdit`

Обчислюється в момент запису, з розв'язаного стану періоду:

```
IsLateEdit = Period.State = Grace
          OR Period.ReopenedUntil IS NOT NULL AND now <= ReopenedUntil
```

Якщо `PeriodPolicy.RequireReasonInGrace = 1` — `LateEditReason` обов'язковий,
і його відсутність дає 422 **до** транзакції. Це прямо покриває питання аудиту
«які дані правили після закриття періоду», на яке чинна система відповіді не має
([04] §6.2).

## 6. Генерація документа і ліниві комірки

`DocumentGenerator` ([09] §3) **не матеріалізує порожні комірки** — це головна
економія обсягу ([14] §3.1). Наслідки для шляху запису:

| Ситуація | Поведінка |
|----------|-----------|
| Запис у комірку, якої немає | `MERGE` вставляє |
| Запис `null` у комірку, якої немає | нічого не робиться |
| Запис `null` в існуючу | **`DELETE`** рядка `CellValue`, не `UPDATE … = NULL` |
| `isEmpty: true` | рядок існує з `IsEmpty = 1` — це змістовне «явно порожньо» |
| Читання відсутньої | `ColumnDef.DefaultValue` |

`DELETE` замість `UPDATE NULL` — щоб таблиця не накопичувала порожні рядки за
роки правок. Аудит при цьому пишеться нормально (`NewValue = NULL`), тобто
слід не втрачається.

`doc.TableRow` для `RowMode = Fixed` створюється **одразу** при генерації
(їх мало — ~30 на таблицю, ~16 млн на рік) — без них немає до чого прив'язувати
`RowVersion` і немає стабільного `RowKey`.

## 7. Взаємодія з правами (коротко; деталі — B05)

```
до транзакції:
   AccessProfile (кеш)  →  рівень на Table/Column
   IAccessDecisionService.CanEdit(profile, cell, docState, periodState)
        → EditDecision(Allowed, Reason)
   якщо хоч одна комірка батча заборонена → 403 з переліком і причинами
```

**Перевірка одна на батч, не на комірку.** Профіль уже розгорнутий у мапу
`resourceKey → level`; перевірка комірки — це пошук у словнику плюс кілька
булевих умов, тобто наносекунди. Що дорого — це **побудова** профілю, і вона
робиться раз на сесію ([14] §3.3).

Обчислені комірки (`IsCalculated = 1`) не проходять перевірку `IsReadOnly` —
їх пише система, а не користувач; але вони перевіряються на те, що користувач
взагалі має право писати в цю таблицю.

## 8. Чек-лист

- [ ] Усі шляхи зміни даних проходять через `ICellStore.ApplyAsync`
- [ ] `RowVersion` на рядку; `If-Match` на `TableInstance`
- [ ] `TableRow.ModifiedAt` оновлюється при кожній зміні комірок рядка (тест!)
- [ ] Часткове застосування батча неможливе
- [ ] `value: null` / `isEmpty: true` / відсутнє поле — три різні операції (тест!)
- [ ] Комірковий рівень валідації блокує запис; рядковий — ні
- [ ] Аудит — у тій самій транзакції, одним set-based `INSERT`
- [ ] `ChangedByUserId` (internal Id), не SID
- [ ] `READ_COMMITTED_SNAPSHOT` увімкнено; `UPDLOCK` на перевірці версій
- [ ] Крос-таблична пропагація — після `COMMIT`, асинхронно
- [ ] Перевірка прав — одна на батч
