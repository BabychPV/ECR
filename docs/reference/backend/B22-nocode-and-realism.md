## 1. Інвентар no-code: що є конфігурацією, а що кодом

### 1.1 Правило вибору рівня

Драбина з [B19](B19-calc-configurator.md) §4 поширюється на **всю систему**, не лише на розрахунки:

| Рівень | Що це | Хто змінює | Цикл зміни |
|:------:|-------|-----------|------------|
| **1. Конфігурація** | записи в БД, редаговані у вебі: структура, стилі, формули, правила, реєстри, звіти, розклад, права | адміністратор / методолог | хвилини, без релізу |
| **2. Скрипт C#** | тіло методу як **дані**, вузький контекст, компіляція при публікації, обов'язкові тести | методолог із правом `*.EditScript` | години, без релізу |
| **3. Модуль** | збірка в рішенні | розробник | реліз |

**Критерій, а не смак:**

* результат виражається над полями рядка, константами і довідниками → **1**;
* потрібні розгалуження, цикли, проміжні змінні, нестандартна форма → **2**;
* потрібен новий **протокол**, новий **формат файлу**, нова **інфраструктура**
  або багатоетапна оркестрація з зовнішніми джерелами → **3**.

### 1.3 Що лишається кодом **назавжди** — і чому це правильно

| Що | Чому не конфігурація |
|----|----------------------|
| Транспорти і протоколи | протокол — це не параметр; новий протокол = нова бібліотека |
| Рушій виразів і компілятор | те, що виконує конфігурацію, само конфігурацією бути не може |
| Планувальник, черга, транзакції, партиціонування | інфраструктурні інваріанти; помилка тут коштує даних |
| Рендеринг у формати файлів | формат `.xlsx`/PDF — зовнішній стандарт |
| Примітиви безпеки | «налаштовуваний механізм автентифікації» — це антипатерн |

> **Межа проста:** конфігурацією стає **предметна** логіка (що рахуємо, за якими
> правилами, як показуємо); кодом лишається **механіка** (як виконуємо, як
> зберігаємо, як говоримо з протоколом). Сьогодні вони перемішані — саме тому
> «додати колонку в аркуш» коштує вісім правок у п'яти артефактах на двох серверах.

## 2. Уніфікований конвеєр — те, що прибирає bespoke-модулі (ER-N-01)

### 2.1 Спостереження

Три різні місця пакета описують по суті **одне й те саме**:

| Місце | Що робить |
|-------|-----------|
| `ext.DataMappingDef` (реалізація — `ext.EntityFieldMap`, [B20](B20-source-configurator.md) §3.2) | джерело → фільтр → перетворення → ціль |
| `rpt.ReportRule` ([B16](B16-ecr-reporting.md) §2) | джерела → join → фільтр → агрегація → колонки звіту |
| bespoke-модулі ([B13](B13-ecr-calculation-engine.md) §4.2) | джерела → join із gas composition → групування по trains/режимах → формули → результат |

Це **конвеєр даних**: `Source → Join → Filter → Group → Compute → Emit`.
Реалізовувати його тричі (двічі як конфігурацію, раз як код) — марно.

### 2.2 Рішення

**Один декларативний конвеєр**, який обслуговує мапінг, звіти і складні розрахунки:

```jsonc
{
  "code": "TOx.Monthly",
  "steps": [
    { "op": "source", "as": "ev",   "from": "ext.RawDataPoint",       "filter": "[SourceEntity]='FLERT.FlareEvent'" },
    { "op": "source", "as": "gas",  "from": "calc.CalculationResult", "filter": "[MethodologyGroupCode]='HSE400'" },
    { "op": "join",   "left": "ev", "right": "gas", "on": "[ev].[StreamId] = [gas].[StreamId]" },
    { "op": "filter", "expr": "[ev].[Duration] > 0" },
    { "op": "group",  "by": ["Train", "Mode", "PeriodKey"] },
    { "op": "compute","as": "Volume", "agg": "SUM", "expr": "[ev].[Flow] * [ev].[Duration]" },
    { "op": "compute","as": "Density","agg": "WEIGHTED_AVG", "expr": "[gas].[Density0]", "weight": "[ev].[Flow]" },
    { "op": "script", "ref": "TOx.Correction" },        // ← рівень 2, там де правило не виражає
    { "op": "emit",   "target": "calc.CalculationResult" }
  ]
}
```

**Що це дає:**

* 4 bespoke-модулі перестають бути 4 модулями коду: їхня оркестрація стає
  визначенням, а кодом лишається **виконавець конвеєра** — один на всю систему;
* нестандартні місця вставляються кроком `script` (рівень 2), а не переписуванням
  усього модуля;
* та сама механіка обслуговує звіти і мапінг — **одна реалізація замість трьох**;
* конвеєр видно в UI як послідовність кроків із попереднім переглядом на кожному.

### 2.3 Чесна оцінка ризику

Побудова узагальненого конвеєра — це побудова **мови**. Такі речі мають
властивість перетворюватися на гіршу версію SQL, якщо їх узагальнювати без межі.

**Три обмеження, які тримають ризик:**

1. **Набір операцій закритий** — 7 (`source`, `join`, `filter`, `group`, `compute`,
   `script`, `emit`). Нова операція = рішення архітектора, не «додамо на льоту».
2. **Немає гілок і циклів** — розгалуження живе в кроці `script`, а не в конвеєрі.
   Конвеєр лишається лінійним DAG-ом, який можна показати, перевірити і пояснити.
3. **Конвеєр не є універсальним обчислювачем** і не претендує ним бути: якщо
   форма задачі в нього не лягає — це рівень 3, і це нормально.

**Вартість:** 8–10 тижнів BE. **Окупність:** він потрібен для `rpt` і `ext` у
будь-якому разі; на bespoke-модулях економить ще ~6–8 тижнів і, головне, прибирає
клас «щоб змінити розрахунок 30X, потрібен реліз збірки».

⚠ Якщо на Етапі 0 виявиться, що конвеєр не покриває Thermaloxidizer (найскладніший
із чотирьох) — рішення відкочується до «модуль коду», а конвеєр лишається для
`rpt` і `ext`. Це рішення оборотне; перевірка — задача Етапу 0 (питання X-1 у §3 — не плутати з N-1; ідентифікатори X-* стосуються знайдених
невідповідностей, N-* — відкритих питань §6).

| **Числа** | 8 функцій `fn_Air_*` замість 11; «63 звітів» замість 127; «пʼять портів» замість шести; «24+» RTQP-вʼюх замість 32 | B12, B16, B10, B01, B14 |
| **Битті посилання** | `[13] §13.2/§13.3` — таких розділів немає, вони в `[06]` | 6 файлів |
| **Прогалини** | немає прав `Report.*`; немає `lateEditReason` у контракті grid; B11 не містив робіт ФВ-9…ФВ-14; B03 мав чотири контексти замість пʼяти | B10, B16, B21, B11, B03 |
| **Дрейф імен** | `ext.EntityFieldMap` / `ext.DataMappingDef` / `cfg.RegistrySyncMapping`; `SubstanceEntryId` / `SubstanceRegistryEntryId` | зведено |

> Дві правки варті окремої згадки, бо змінюють проєктне рішення, а не текст:
> **(1)** `rpt.v_<Report>` генерує офлайн-інструмент у міграцію — отже «нова
> держформа без релізу» означає «без релізу **коду сервісу**», але з одним
> згенерованим артефактом розгортання (або без нього, якщо піти на XML-датасет);
> **(2)** схеми `calc` і `rpt` явно віднесені до **ECR-специфічних розширень**
> того самого статусу, що `ext` — домен-агностичним лишається ядро
> `cfg`/`doc`/`dic`/`sec`/`wf`.

### 3.5 Межа «що дозволено в БД» (ER-N-02)

Питання виникло тричі, тож формулюється один раз:

| Дозволено в БД | Заборонено в БД |
|----------------|-----------------|
| зберігання, типи, ключі, FK, `CHECK` | будь-яка предметна логіка |
| індекси, партиції, стиснення, архівація | обчислення показників, агрегації звітів |
| тригери **цілісності** (immutability опублікованої версії) | тригери, що ставлять задачі в чергу |
| процедура пакетного запису (`MERGE` з TVP) — **доступ**, без правил | процедури з правилами: «якщо permit не діє — не брати» |
| вʼюхи-проєкції: `WHERE` по параметру, `PIVOT` зрізу | вʼюхи з `JOIN` до бізнес-таблиць і `CASE` |
| CLR | ⛔ **немає взагалі** — обидві збірки `UNSAFE` зникають |

**Перевіряється двома тестами по міграціях:**
1. **Структурний.** Немає жодного `CREATE PROCEDURE` / `FUNCTION` / `TRIGGER` /
   `ASSEMBLY` поза білим списком: `doc.usp_ApplyCellBatch` (пакетний запис),
   тригери immutability на `cfg.*`, процедури архівації `arc.*`,
   `PartitionMaintenance`. Будь-який новий обʼєкт у цих класах — червона збірка,
   доки його не додано до білого списку з обґрунтуванням.
2. **Вʼюхи — лише проєкції.** Тіло кожної вʼюхи не містить агрегатних функцій,
   `CASE`, `ROW_NUMBER`/`RANK`, підзапитів і `JOIN` до таблиць поза власною
   схемою вʼюхи.

> **Чому не «немає предметних термінів у міграціях».** Такий тест непрацездатний:
> під нього підпадають **таблиці**, які за проєктом зобовʼязані містити ці
> терміни (`calc.CalculationResult.SubstanceRegistryEntryId`, `EmissionTons`).
> Схеми `calc` і `rpt` — **ECR-специфічні розширення**, того самого статусу, що
> `ext`: домен-агностичним лишається ядро (`cfg`, `doc`, `dic`, `sec`, `wf`).
> Заборона предметних імен діє на **типи** в `Ecr.Domain`/`Ecr.Application`
> (архітектурний тест [B01](B01-backend-blueprint.md) §2.2, правило 11), а не на
> схеми БД.

## 4. Реальність реалізації

### 4.1 Обсяг backend

`architecture/06` §13.2 називав 12 підсистем. Після цього пакета їх **17**:

1–12 — як у [06] §13.2 · 13. **Рушій розрахунків** (`calc.*`, generic-модуль,
резолвінг версій) · 14. **Конвеєр** (§2) · 15. **Рушій звітності** (`rpt.*`,
матеріалізація, агрегації) · 16. **Компілятор і пісочниця скриптів** ·
17. **Конфігуратор джерел** (каталог, мапінг, розклад, консистентність).

### 4.2 Обсяг frontend — головна зміна

| # | Область | Тижнів FE |
|---|---------|----------:|
| 1 | **Grid-редактор** (paste, fill, undo, віртуалізація, права по комірках) | 10–12 |
| 2 | Конструктор шаблону (дерево, колонки, рядки, стилі) | 8–10 |
| 3 | Конструктор реєстрів + редактори (темпоральні, вкладені, M:N) | 8–10 |
| 4 | **Конфігуратор методологій** (формули, константи, категорії) | 8–10 |
| 5 | Адміністрування безпеки (ролі, матриця, ефективні права) | 6–8 |
| 6 | Workflow + імпорт із diff + експорт + i18n | 6–8 |
| 7 | Редактор зв'язків (граф + майстер) | 5–6 |
| 8 | **Конфігуратор джерел** (каталог, мапінг, попередній перегляд) | 5–6 |
| 9 | **Редактор конвеєра** (кроки, перегляд на кожному) | 5–6 |
| 10 | **Редактор скриптів** (Monaco, компіляція, тести) | 4–5 |
| 11 | **Правила: матриця, покриття, симуляція** | 4–5 |

| 13 | Періоди + матриця доступу | 3–4 |
| 14 | **Розклад збору** (таймлайн) | 3–4 |
| 15 | **Перерахунок: запуск, черга, прогрес, історія** | 3–4 |
| 16 | Операційний дашборд + консистентність | 3–4 |
| | **Разом** | **86–108** |
| 17 | *(фаза 2)* Переглядач звітів + експорт | *8–10* |

**86–108 тижнів чистої розробки FE.** Для одного розробника це **20–25 місяців
послідовно** — тобто заявлений склад «1 FE» не просто вузьке місце, а
**неможливість**: frontend стає критичним шляхом удвічі довшим за все інше.

### 4.3 Склад команди і строк

| Склад | Строк | Коментар |
|-------|-------|----------|
| 1 арх + 2 BE + **1 FE** + 1 QA | **28–34 міс.** | FE серіалізує все; не рекомендується |
| 1 арх + 3 BE + **2 FE** + 1 QA | **20–24 міс.** | FE ще критичний шлях |
| 1 арх + **4 BE** + **3 FE** + 2 QA | **15–18 міс.** | збалансовано; рекомендація |
| **MVP** (склад — §4.4), 1 арх + 3 BE + 2 FE + 1 QA | **9–11 міс.** | покриває Land + Water + Waste, звітність фаза 1, реєстри, RBAC, періоди, grid; без конструктора звітів, конвеєра, скриптів і 30X/TOx/HSE400 |

> Для порівняння: `architecture/06` §13.3 давав 14–16 місяців для складу з 1 FE —
> **до того**, як в обсяг увійшли розрахунковий бекенд, звітність і конфігуратори.
> Це не подорожчання, а перша оцінка повного обсягу.

### 4.4 Якщо строк критичний — що виносити з першої черги

Порядок за співвідношенням «вартість / втрата»:

| Виносимо | Економія | Що втрачаємо | Ризик |
|----------|---------:|--------------|-------|
| **Фаза 2 звітності** (веб-переглядач) | 8–10 FE + 3–4 BE | SSRS лишається ще на цикл | низький |
| **Рівень 2 (скрипти)** | 4–5 FE + 6–8 BE | частина методологій лишається класами; кожна зміна — реліз | середній |
| **Конструктор звітів у вебі** | 5–6 FE | нова держформа = задача розробника | середній |
| **Конвеєр** (§2) | 5–6 FE + 8–10 BE | ER-N-01 не досягається: `rpt` (B16) і `ext` (B20) доводиться робити кожен окремим механізмом; 4 складні розділи лишаються кодом (+4–6 BE понад рядок нижче) | середній |
| **Конструктор шаблонів у вебі** | 8–10 FE | структура заводиться bootstrap-скриптами | **високий** — це серце «структура = дані» |
| Модулі 30X/TOx/HSE400 | **6–8 BE** (як конвеєри + скрипти, [B18](B18-tz-addendum-ecr.md) §14.11); 10–14 BE, якщо конвеєр теж винесено і їх роблять модулями коду | найскладніші розділи лишаються на старому бекенді довше | середній |

**Рекомендований MVP:** Land + Water + Waste, розрахунок (рівень 1), звітність
фаза 1, реєстри, RBAC, періоди, grid. **Без** конфігуратора звітів, конвеєра,
скриптів і 30X/TOx. Далі — нарощування, бо архітектура адитивна.

### 4.5 Що робить оцінку хиткою

Чесно про невизначеність:

| Невідоме | Вплив на строк | Знімається |
|----------|----------------|------------|
| Скільки з 44 методологій лягають у рівень 1 (питання C-1/K-4) | ±6–10 тижнів BE | суцільний перегляд класів, Етап 0 |
| Чи покриває конвеєр Thermaloxidizer (N-1, §2.3) | ±6–8 тижнів BE | прототип на 1 модулі, Етап 0 |
| Дозвіл ІБ на скрипти (K-1) | ±10–13 тижнів | запит на Етапі 0 |
| Модель зберігання комірок (BR-01) | ±4–6 тижнів BE | замір на 108 млн рядків, Етап 0 |
| Фаза 2 звітності в першій черзі (R-5) | ±11–14 тижнів | рішення бізнесу |
| Реальна складність 166 RDL при переході на вʼюхи | ±3–5 тижнів | пілот на 10 звітах, Етап 0 |

**Сума невизначеності — близько ±3 місяці.** Тому §4.3 подано діапазонами, і
перші три рядки таблиці мають бути закриті **на Етапі 0**, до фіксації плану.

## 5. Реєстр рішень

| # | Рішення | Обґрунтування |
|---|---------|---------------|
| **ER-N-01** | Один декларативний конвеєр обслуговує мапінг, звіти і складні розрахунки; набір операцій закритий, гілок немає | три місця описували одну механіку; узагальнення без меж перетворюється на гіршу версію SQL |
| **ER-N-02** | Явна межа «що дозволено в БД»: зберігання, цілісність, доступ — так; предметна логіка — ні; CLR — немає взагалі | питання виникало тричі в різних документах |
| **ER-N-03** | Драбина рівнів застосовується до **всієї** системи, не лише до розрахунків | інакше «no-code» лишається гаслом для одного модуля |
| **ER-N-04** | Інвентар §1.2 — контрольний список: кожна нова функція отримує рівень при проєктуванні | без цього рівень 3 повзе назад за замовчуванням |
| **ER-N-05** | Оцінка подається діапазоном із переліком того, що її звужує на Етапі 0 | шість невідомих на ±3 місяці — це не «уточнимо по ходу» |
| **ER-N-06** | `calc` і `rpt` — **ECR-специфічні розширення**, не домен-агностичне ядро; заборона предметних імен діє на типи `Ecr.Domain`/`Ecr.Application`, не на схеми БД | інакше власні таблиці результатів порушують власний тест |
| **ER-N-07** | `rpt.v_<Report>` генерує офлайн-інструмент у міграцію; сервіс DDL не виконує | єдиний спосіб дати SSRS широкий набір колонок, не порушивши «жодного DDL з коду» |
