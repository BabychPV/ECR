# B06 — Порти інтеграції: зовнішні джерела, PI AF, стійкість

> Закриває §11 [13] п. **9** (політика ретраїв до PI AF: таймаути, backoff,
> circuit breaker, поведінка при частковій відмові).
> Головна вимога до цього шару — **його можна викинути, і ядро не помітить**
> (ТЗ ІНТ-1). Це не гасло: чотири питання [13] §12, від яких залежав цей шар,
> **закриті** у версії 2.0 пакета ([B00](B00-INDEX.md) §4,
> [B18](B18-tz-addendum-ecr.md) §14.9) — і адаптер спроєктований так, що
> переживає будь-яку з відповідей.

## 1. Межа: що ядро знає про зовнішній світ

```
Ecr.Application                    Ecr.Adapters.PiAf
 ┌──────────────────────┐           ┌────────────────────────────────┐
 │ IExternalDataSource  │◄──────────┤ PiAfDataSource                 │
 │ IExternalDataSink    │◄──────────┤ PiAfDataSink   (опційно)       │
 │ (порти, DTO ядра)    │           │  ├ IPiAfDataReader             │
 └──────────────────────┘           │  │   ├ PiWebApiDataReader      │
        ▲                           │  │   └ PiSqlClientDataReader   │
        │ ядро не знає нічого       │  └ ext.Legacy*Mapping (володіє) │
        │ про Event Frame, WebId,   └────────────────────────────────┘
        │ Attribute_XXXX, ODBC
```

Ядро оперує лише поняттями: **джерело**, **збір**, **сирий результат**,
**мапінг у комірку**. Слова `EventFrame`, `WebId`, `Attribute_0010`,
`;`-рядок не існують за межами `Ecr.Adapters.PiAf` і схеми `ext`.

Перевіряється архітектурним тестом (B01 §2.2, правило 11).

## 2. Два транспорти за одним інтерфейсом

`IPiAfDataReader` із [13] §6, дві реалізації, вибір за `ext.DataSource.TransportKind`.

| | `PiWebApiDataReader` | `PiSqlClientDataReader` |
|---|---|---|
| Транспорт | HTTPS, `POST /batch`, JSON | ODBC (**PI SQL Client**, RTQP), параметризований SQL |
| Автентифікація | Negotiate під **сервісним обліковим записом** | Windows integrated під тим самим; **делегування не потрібне** (ІНТ-10) |
| Сильна сторона | метадані, точкові операції, `SETTINGS`, *(опційно)* запис | масове читання: `WHERE`/`JOIN`/агрегація **на боці PI** |
| Обмеження | немає фільтрації за значенням атрибута → вивантаження і фільтрація у клієнті | **тільки читання**; потребує встановленого клієнта і ліцензії |
| Де застосовуємо | синхронізація довідників, `CALCULATION_START/ENDDATETIME`, перевірка метаданих | міграція історії, регулярний масовий збір, звіряння |

### 2.1 RTQP — підтверджено в продуктиві

✅ Питання «чи доступний PI SQL DAS (RTQP)» (ТЗ §12 п.13) **закрито фактом**:
RTQP наявний і чинний — 63 sync-процедури читають AF через `OPENQUERY` до
`[Master].[Category].*_V` (`AF_Land_ID_FileNum_Get`, `SQL/DB.txt:58194`);
див. [B14](B14-ecr-integration-and-data.md) §1 і ER-I-07.

**Дія:** `PiSqlClientDataReader` — **основний** транспорт масового читання і
міграції історії; `PiWebApiDataReader` потрібен лише там, де треба **писати**
в AF (RTQP read-only, ІНТ-10). Оцінку міграції історії переглядати вгору не треба.

⚠ Лишається технічна пастка, не питання: чинні RTQP-вʼюхи живуть **у самій
AF-базі**, тому їх доводиться створювати на кожному середовищі окремо. У новій
системі адаптер формує запит сам — артефактів у базі джерела немає (ER-I-01).

## 3. Політика стійкості (BR-16) — закриває §11 п.9

### 3.1 Конвеєр Polly (`ResiliencePipeline`)

Порядок обгорток має значення: зовнішній — найдовший.

```
Bulkhead (обмеження паралелізму)
  └─ Circuit breaker
       └─ Retry (з jitter)
            └─ Timeout (на спробу)
                 └─ HttpClient / DbConnection
```

| Політика | Параметри (типові, налаштовуються на `ext.DataSource`) |
|----------|--------------------------------------------------------|
| **Timeout на спробу** | Web API: 30 с (batch — 60 с); SQL Client: 120 с (масове читання довге за природою) |
| **Retry** | 3 спроби, експоненційний backoff 2 с → 4 с → 8 с, **jitter ±25 %** |
| Що ретраїмо | таймаут, розрив сокета, DNS, HTTP 408 / 429 / 500 / 502 / 503 / 504; ODBC transient |
| Що **не** ретраїмо | 400 (наш баг), **401 / 403** (обліковий запис/права — ретрай нічого не змінить, крім блокування облікового запису), 404, 409 |
| **Circuit breaker** | 50 % відмов на вибірці ≥ 10 запитів за 30 с → розрив на 60 с → half-open (1 пробний) |
| **Bulkhead** | максимум 4 паралельні запити на джерело; черга 16, далі — відмова |
| **Загальний бюджет** | на одну логічну операцію збору — 5 хв; далі задача завершується з частковим результатом і звітом |

### 3.2 Failover primary/secondary

Чинна логіка ([01] §6: `Configuration!B3` / `B12`, TTL 60 000 мс) зберігається,
але переноситься в адаптер:

```
CircuitBreaker(primary) розірвано  →  перемкнутися на secondary
   позначити ext.DataSource.ActiveEndpoint = Secondary, ActiveUntil = now + 60 с
   через 60 с — пробний запит до primary (half-open)
   успіх → повернутися; невдача → продовжити на secondary
```

Стан ендпоінта — **у пам'яті інстансу**, не в БД: це технічний стан, який має
бути швидким і не переживати рестарт. Але **кожне перемикання** пишеться в
`itg.DataCollectionRun` і в метрику — інакше «іноді повільно» ніколи не пояснити.

### 3.3 Часткова відмова (найважливіше)

PI Web API `POST /batch` повертає **207 Multi-Status**: частина підзапитів
успішна, частина ні. Це нормальний, а не винятковий стан.

**Рішення: збір ідемпотентний і відновлюваний, часткові результати зберігаються.**

```
CollectAsync:
   розбити роботу на одиниці (елемент / шаблон / період)
   для кожної:
        успіх   → ext.RawDataPoint (SqlBulkCopy, UQ = ідемпотентність)
                  itg.CollectionItem: Ok
        відмова → itg.CollectionItem: Failed + причина, БЕЗ зупинки решти
   у кінці:
        itg.DataCollectionRun: Status = Ok | Partial | Failed
        Partial → задача перезапускається за розкладом і доробляє лише Failed
```

**Чому не «все або нічого».** Збір сирих даних — не транзакція над обліковими
даними; це читання зі стороннього джерела. Якщо з 90 таблиць 3 не віддалися,
правильна поведінка — зберегти 87 і чесно сказати про 3, а не втратити все.
Протилежна логіка діє для **запису** даних документа (B04): там часткове
застосування заборонено.

### 3.4 Ідемпотентність

```sql
CONSTRAINT UQ_RawDataPoint UNIQUE (DataSourceId, SourcePath, [Timestamp])
```

Повторний запуск за той самий період не створює дублікатів (ТЗ ІНТ-5).
Реалізація: `SqlBulkCopy` у тимчасову таблицю → `MERGE` за унікальним ключем.
`MERGE`, а не `INSERT … WHERE NOT EXISTS`: значення в джерелі могло змінитися
(перерахунок у PI), і ми хочемо це побачити — `MERGE` оновлює і фіксує
`ItemsUpdated` у `itg.DataCollectionRun`.

### 3.5 Ніколи не в HTTP-запиті

Виклик PI AF **не робиться синхронно в обробнику HTTP-запиту користувача**
([14] §8). Причина проста: зовнішня система тримає наш пул потоків, і одна
її гикавка кладе весь застосунок.

Виняток один — `CheckHealthAsync` на екрані адміністратора, з жорстким
таймаутом 5 с і без ретраїв.

Кнопка «зібрати зараз» → 202 + `jobId`, прогрес через `/api/v1/jobs/{id}`.

## 4. Сирі дані і мапінг — два різні кроки

```
       PI AF                       SQL                        SQL
  ┌────────────┐   Collect   ┌──────────────┐   Map     ┌──────────────┐
  │ EF, атрибути│───────────►│ext.RawDataPoint│────────►│ doc.CellValue│
  │ tag-значення│  без інтер- │  як прийшло   │ за       │              │
  └────────────┘  претації   └──────────────┘ ext.Data  └──────────────┘
                                               MappingDef
```

**Чому саме два кроки** (ТЗ ІНТ-3):

* інтерпретація змінюється частіше, ніж джерело: перемапити можна без
  повторного походу в PI;
* при розборі розбіжності видно **що саме прийшло**, а не «що ми з цього
  зрозуміли»;
* зміна структури шаблону не робить раніше зібране непридатним.

`ext.DataMappingDef` — конфігурація, не код ([07] §8): `SourcePathPattern` →
`(TargetTableDefId, TargetRowKey, TargetColumnDefId)` + `TransformExpression`
(та сама мова виразів, B03).

Запис у `doc.CellValue` йде **через `ICellStore.ApplyAsync`** з
`Origin = ExternalMapping` (B04 §1) — з аудитом, валідацією і перерахунком,
як будь-яка інша зміна.

## 5. Синхронізація довідників

Один generic-синхронізатор замість п'яти модулів VBA (≈4 400 рядків),
керований конфігурацією збору: `ext.SourceEntity(TargetKind = Registry)` +
`ext.DataMappingDef` + `ext.CollectionSchedule` ([B20](B20-source-configurator.md) §3–§4).
Це реалізація `cfg.RegistrySyncMapping` із ТЗ ФВ-8.11 ([12] §8) — та сама
конфігурація, розкладена по трьох таблицях замість однієї.

```
SyncRegistryJob(registryDefId):
   mapping = cfg.RegistrySyncMapping
   external = IExternalDataSource.CollectAsync(kind: Dictionary, template: mapping.ExternalTemplate)
   зіставлення за dic.RegistryExternalKey (DataSourceId, ExternalId)
       є у нас і в джерелі      → оновити поля за FieldMappings
       немає у нас              → створити запис + ExternalKey
       немає в джерелі          → OnMissingInSource:
                                     MarkOrphaned  (типово) — SyncStatus = Orphaned
                                     Deactivate    — IsAvailable = 0
                                     Ignore
   cfg.RegistryDef.DataRevision += 1        ← самоінвалідація кешу (B05 §5.2)
   itg.DictionarySyncRun: Added / Updated / Deactivated / Status
```

**Ніколи не видаляємо фізично** (ФВ-8.7): запис, на який посилаються дані,
лишається назавжди. `Orphaned` — це видимий стан, а не тиша.

### 5.1 Відкрите питання, під яке спроєктовано

«Довідники: master в AF чи в ECR» ([13] §12) — **закрито: master — ECR**,
перехід поетапний через `SourceKind` ([B14](B14-ecr-integration-and-data.md) §5).
Відкритим лишається лише строк перемикання фази для кожного реєстру (питання I-2).
Історичне формулювання нижче лишене як обґрунтування того, чому `SourceKind` —
поле налаштування, а не припущення в коді; воно може
змінитися після аналізу поточного бекенду. Тому напрямок задається полем
`RegistryDef.SourceKind` (`Local` / `External` / `Hybrid`, [12] §8), а не
архітектурним припущенням. Перехід «AF → ECR як master» = зміна значення поля
плюс вимкнення `RegistrySyncMapping`. Код не змінюється.

## 6. Зворотна публікація в AF (`IExternalDataSink`) — опційно

> ## ⬛ Оновлено 2026-09-03 — розділ втратив чинність
>
> Рішення замовника **D-44**: **зворотної публікації в AF немає взагалі** — ні даних,
> ні довідників, ні на перехідний період. `IExternalDataSink` **не реалізується**
> (порт лишається як архітектурний шов без реалізацій). Довідники в AF для ще не
> мігрованих розділів лишаються під чинним процесом супроводу (D-45). Описаний
> нижче алгоритм `PublishAsync` зберігає цінність лише як специфікація
> **утиліти валідації міграції** — відтворення `;`-рядка для побайтного порівняння.
> Джерело істини — [`../tz/10-decisions.md`](../../tz/10-decisions.md).


ТЗ ІНТ-11: потрібна лише на перехідний період, поки живі PI-звіти і розрахункові
модулі в AF. Питання «чи потрібна взагалі» **закрито: так, але вузько** — лише
довідники і налаштування, які читає Excel; результати назад не публікуються
([B14](B14-ecr-integration-and-data.md) §9, ER-I-06). Відкритим лишається обсяг
споживачів AF — питання I-1.

**Рішення: реалізувати як окрему збірку-плагін, увімкнену прапорцем джерела.**

```
IExternalDataSink.PublishAsync(TableInstance)
   → зібрати ;-рядок за ext.LegacyColumnMapping.LegacyFieldIndex
       (порядок полів — індивідуальний для кожної з ~90 таблиць!)
   → значення форматувати ValueExportFormatter (B03 §7) — байт у байт як VBA
   → підмішати метадані з __Header (SyncMode = Copy тільки тут, [09] §5.2)
   → ім'я EF: <base>_<user>_<yyyy_mm_dd_HH_MM_SS>   (алгоритм 2 ТЗ §7)
   → POST /batch: create EF → read → read attrs → POST /streamsets/value
   → itg.ExternalPublication: запит, відповідь, статус, тривалість, спроби
```

Критерій приймання (roadmap Етап 3): значення `Attribute_XXXX` в AF **побайтно
ідентичні** тим, що записував старий Excel. Це перевіряється автотестом на
реальних прикладах, а не оглядом.

> Якщо бізнес відповість «не потрібна» — збірка не збирається в реліз,
> `itg.ExternalPublication` лишається порожньою, ядро не змінюється.
> Саме заради цього sink — окремий порт, а не метод у `IExternalDataSource`.

## 8. Спостережуваність адаптера

| Метрика | Навіщо |
|---------|--------|
| `ecr.external.request.duration` (за джерелом, транспортом, операцією) | бюджет п.13 [14] §2 — 60 с на документ × 12 періодів |
| `ecr.external.circuit.state` | видно момент розриву |
| `ecr.external.failover.count` | «іноді повільно» перестає бути містикою |
| `ecr.external.items.{fetched,new,updated,failed}` | здоров'я збору |
| Трасування | `CorrelationId` наскрізь: HTTP → задача → адаптер → PI |

`/health/external` — стан кожного `ext.DataSource`: доступність, останній
успішний збір, стан circuit breaker. Не блокує `/health/ready`: недоступність
PI **не означає**, що ECR непрацездатний — ядро працює без адаптера, і це
перевіряється тестом.

## 9. Чек-лист

- [ ] Ядро не містить типів із `Af`/`PiAf`/`Legacy` у назві (архітектурний тест)
- [ ] Вимкнення адаптера не ламає жоден сценарій, крім збору (інтеграційний тест)
- [ ] 401/403 не ретраяться
- [ ] Часткова відмова зберігає успішну частину і доробляється при перезапуску
- [ ] Ідемпотентність збору перевірена тестом «запустити двічі → та сама кількість»
- [ ] Жодного виклику PI у HTTP-обробнику, крім `CheckHealth`
- [ ] Failover фіксується в журналі і в метриці
- [ ] Сирі дані зберігаються без інтерпретації; мапінг — окремий крок
- [ ] `SourceKind` — поле, а не припущення в коді
- [ ] Round-trip `;`-рядка (якщо sink увімкнено) побайтно збігається
