# B15 — Оркестрація перерахунку та експлуатація ECR

> Заміна 100 джобів SQL Agent + `JobsQueue`/`WatchdogStatus` + CLR-у-процесі
> на `IJobScheduler` ([B07](B07-jobs-and-observability.md)) з worker-пулом.
> Факти AS-IS — [B12](B12-ecr-as-is-backend.md) §2, §3.2.
> Розклад **збору** налаштовується окремо — [B20](B20-source-configurator.md) §4;
> тут — оркестрація **перерахунку**.

---

## 1. Що саме замінюємо

```
AS-IS                                          TO-BE
─────                                          ─────
71 тригер на AF_*                              подія застосунку (зміна даних)
   ↓ рядок 'StartDate:…;EndDate:…;LandTable:…'    типізований JobArgs
JobsQueue (Status 1→2→3), JobsList, JobsLog    черга IJobScheduler + itg.*
JobQueue_Optimize   (30 с)                     злиття діапазонів у планувальнику
JobQueue_Execution  (30 с, курсор)             диспетчер worker-пулу
   ↓ sp_start_job                               призначення задачі worker-у
76 calc-джобів SQL Agent (1 хв)                worker-процеси з лімітом паралелізму
   ↓ JobTryExecute → Utility_JobExecute         прямий виклик ICalculationModule
   ↓ sp_executesql 'EXEC DllProject_… '
CLR у спільному AppDomain SQL Server           окремий процес .NET 10
WatchdogStatus(_Land).IsBusy                   applock + стан прогону в itg.*
ECR_ManualRecalc (10 с) ← AF_RecalcManualInfo  UI → команда → черга (миттєво)
```

**Латентність, яку це прибирає:** сьогодні «поставив у чергу → почалось» —
до **~1.5 хв** (тік `ECR_Execution` 30 с + каденція calc-джоба 1 хв,
`Performance_Analysis_ECR_Pipeline.md` §1). Ціль — **секунди**: задача потрапляє
до вільного worker-а одразу.

## 2. Модель задачі (ER-J-01)

### 2.1 Одиниця роботи

```csharp
public sealed record CalculationJobArgs(
    string   ModuleCode,        // 'ecr.methodology.datadriven' | 'ecr.hse400' | …
    int      ProjectId,
    int[]    PeriodKeys,        // 202601…202612 — явно, не «діапазон дат рядком»
    int?     SourceTableDefId,  // ← LandTable
    long[]?  DocumentIds,       // ← FileNumbers
    JobOrigin Origin);          // Trigger | Schedule | Manual | Migration
```

Типізований контракт замість рядка, який тричі складається і двічі розбирається
текстом ([B12](B12-ecr-as-is-backend.md) §3.2). Валідація — на межі API, а не
`CHARINDEX` у чотирьох місцях.

### 2.2 Три режими

| Режим | Тригер | Обсяг | Пріоритет |
|-------|--------|-------|-----------|
| **Інкрементний** | зміна даних документа / довідника / методології | лише зачеплені `(модуль × період × рядки)` | високий |
| **Плановий повний** | нічний розклад | усі модулі × усі періоди року | низький |
| **Ручний** | UI («Перерахувати») | те, що обрав користувач | високий, окрема квота |

Ручний режим у чинній системі йде окремою гілкою (`AF_RecalcManualInfo` →
`Utility_Recalc_Sync` → `Utility_RecalcValidate` → `Utility_RecalcJobMonitor`,
опитування кожні 10 с) і має **нижчий пріоритет** та не зливається з автоматичним
(`ECR_v_1_17` §7.2.2). У новій моделі це просто `Origin = Manual` + окрема квота
worker-ів: користувач, який натиснув кнопку, не має чекати за нічним прогоном.

### 2.3 Злиття і розбиття

`JobQueue_Optimize` (злиття перекритих діапазонів у `MIN(Start)`/`MAX(End)`) і
split (на 5 частин або по місяцях) — обидва механізми **зберігаються за змістом,
але переїжджають у планувальник**:

* **злиття**: задачі з однаковим `(ModuleCode, SourceTableDefId)` і перетином
  `PeriodKeys` зливаються в одну до постановки — та сама економія, але над
  **множиною періодів**, а не над рядком дат;
* **розбиття**: `PeriodKeys` — уже природна одиниця паралелізму. Задача на 12
  періодів стає 12 незалежними одиницями без «видалити батьківський рядок і
  створити `_1…_12`». Split-джоби `ECR_Air_Calc_*_Job_1…_12` зникають як сутність
  (56 → ~14 логічних модулів).

### 2.4 Залежності

`calc.MethodologyDependency` ([B13](B13-ecr-calculation-engine.md) §4.3) дає
планувальнику явний граф: `HSE400 → {Thermaloxidizer, Flaring 30X}`.
Сьогодні цей порядок тримається каденцією джобів і знанням у голові
(«HSE400 перший, Thermaloxidizer останній»). Тепер — топологічний порядок,
який планувальник поважає, і жодного «зачекаємо хвилину, воно саме підхопиться».

## 3. Конкурентність і серіалізація (ER-J-02)

| Гарантія | AS-IS | TO-BE |
|----------|-------|-------|
| Не запускати те саме двічі | `IF NOT EXISTS (Status = 3 для Job_Id)` — **один осиротілий рядок блокує весь джоб** | `sp_getapplock` на `(ModuleCode, SourceTableDefId, PeriodKey)` + TTL; orphan детектується за відсутністю живого worker-а |
| Не перекривати синк і розрахунок | `WatchdogStatus.IsBusy` | стан прогону в `itg.CalculationRunState`, видимий у health |
| Обмеження паралелізму | немає — звідси OOM | явний ліміт worker-ів і пам'яті на процес |
| Живість | `MAX(session_id)` + `sysjobactivity` (евристика) | heartbeat worker-а; немає heartbeat → задача повертається в чергу |
| Повторний запуск | `at-least-once` без ідемпотентності → дублі/помилки | `at-least-once` + ідемпотентність за `RunId`/`IsCurrent` ([B13](B13-ecr-calculation-engine.md) §5.2) |

**Класи проблем, які зникають за побудовою** (усі — з `skills/ecr-jobs-ops`):
ghost-джоби в `sysjobactivity`, phantom «джоб не зупиняється», застрягла черга
через `Status = 3`, `sp_stop_job` відмовляє, каскад `701 → 6535 → 233`.
Вони існують тому, що виконавцем є **SQL Agent + CLR у SQL Server**; з окремим
worker-процесом їх просто немає.

## 4. Прозорість збоїв (ER-J-03)

Дві конкретні пастки чинної системи, які треба закрити явно:

1. **`on_fail_action = 3` («перейти до наступного кроку»)** робить джоб зеленим,
   навіть коли крок упав. Так водний синк ховав помилку `Substance_Code`
   (кейс 2026-08-17). → **Задача, крок якої впав, має статус `Failed`**; часткові
   успіхи допускаються лише там, де вони змістовні (збір із зовнішнього джерела,
   [B06](B06-integration-ports.md) §3.3), і тоді результат — `Partial` зі звітом.
2. **Обробник помилок, який падає сам.** `Utility_CheckTriggerStatus` кидав
   `THROW`, `AF_Land_Watchdog_Initialize` не повертав `OUTPUT`-параметри, `@JobId`
   лишався `NULL`, `INSERT` у `JobsLog(JobId NOT NULL)` валився — і справжня
   причина зникала (кейс 2026-08-24). → **Журналювання збою не має залежати від
   успіху попередніх кроків**: контекст задачі формується до виконання і
   пишеться завжди.

## 5. Задачі ECR понад базовий перелік [B07](B07-jobs-and-observability.md) §2

| Задача | Замінює | Каденція |
|--------|---------|----------|
| `CalculationJob` | 76 calc-джобів | за подією / розкладом |
| `DataCollectionJob` | 16 sync-джобів | за розкладом джерела |
| `FullRecalculationJob` | `ECR Manual Maintenance Job` (крок «final recalculation») | щоночі |
| `ResultRetentionJob` | — (нове) | щотижня — прибирає неактуальні `RunId` |
| `MethodologyValidationJob` | перевірка **внутрішньої цілісності** `calc.*`: вирази парсяться, правила не перетинаються, константи числові | після зміни `calc.*` |

> Не плутати з перевіркою **«наше vs джерело»** ([B20](B20-source-configurator.md) §5.2),
> яка узагальнює `AF_*_CheckDifferences`: там питання «чи збігається наша копія з AF»,
> тут — «чи конфігурація сама по собі несуперечлива».

**Що зникає:** `ECR CleanUp Logs` (retention — політика, не джоб),
`ECR_Utility_RequeueFailedJobs` (ретраї — у планувальнику),
`ECR StartUp` (стан не втрачається при рестарті),
`ECR_ManualRecalc` (опитування замінюється командою).

⚠ **`ECR Manual Maintenance Job` робить `shrink` бази щоночі** (`Jobs.txt`).
Це антипатерн: shrink фрагментує індекси, які той самий джоб потім перебудовує.
У новій системі обслуговування — без shrink; зростання файлу керується
архівацією ([B02](B02-persistence.md) §6), а не стисканням.

## 6. Нотифікації і моніторинг (ER-J-04)

Сьогодні алерти живуть **у PI AF**: елемент `Notifications`, п'ять аналізів
(`Check_Data_Consistency`, `Check_FrozenQueue`, `Check_Jobs_Error`, `Check_Logs`,
`Check_System_State`)
→ `AFNotificationRule` → група `ECR Admin` → листи. Mute-вікно прив'язане до
`Hour('*') = 0`, а нічний перерахунок стартує о **01:15** — звідси щонічний шум
(`deliverables/Notifications_MuteWindow/`).

**TO-BE:** алерти — частина системи, не зовнішньої платформи:

* джерело — `aud.ConsistencyIssue`, `calc.CalculationIssue`, стан задач, health-checks;
* mute — **за станом**, а не за годиною: поки триває `FullRecalculationJob`,
  алерти класу «дані неконсистентні» пригнічуються автоматично;
* канал — той самий (пошта/Teams), але правило живе поруч із причиною.

Це прибирає клас «лист прийшов о 01:15, бо вікно тиші від старого розкладу».

### 6.1 Телеметрія перерахунку

`RecalcDataVolume` + `Utility_RecalcStatistics` (уже в проді, `ecr-recalc-data-volume`)
→ метрики OpenTelemetry і дашборд «бюджет vs факт» ([B07](B07-jobs-and-observability.md) §5.1):

| Метрика | Навіщо |
|---------|--------|
| `ecr.calc.run.duration{module}` | тривалість модуля; ціль повного прогону — §7 |
| `ecr.calc.rows_written` | заміна знімків `RecalcDataVolume` |
| `ecr.calc.issues{severity}` | заміна `LogCalculationErrors` як показника здоров'я |
| `ecr.jobs.queue_depth`, `ecr.jobs.lease_expired` | orphan-детекція |

Два факти, які треба зберегти при переносі телеметрії
(`ecr-recalc-data-volume`): маркер кінця циклу — **завершення останнього модуля
за топологічним порядком**, а не тиша в черзі; і будь-який достроковий вихід
вартового **має лишати слід** — «вартовий, який мовчки нічого не зробив,
невідрізненний від справного».

## 7. Бюджет

| Показник | Сьогодні | Ціль |
|----------|---------:|------|
| Латентність «зміна → почався перерахунок» | ~90 с | **< 10 с** |
| Латентність ручного перерахунку | до 10 с опитування + 90 с | **< 5 с** до старту |
| Повний річний перерахунок | вимірюється `Utility_RecalcStatistics`; вікно ~01:15→ранок | **не гірше**, за меншого ризику OOM |
| Паралелізм | неконтрольований (split × каденція) → OOM | керований ліміт worker-ів |
| Видимість збою | джоб зелений при `on_fail_action = 3` | 100 % збоїв видимі |

> Цільові числа тривалості повного прогону навмисно не фіксуються тут: чинного
> заміру в репозиторії немає (є інструмент, але не результат). Це перше, що треба
> зняти на Етапі 0 — інакше «не гірше» нічим перевірити (питання J-1).

## 8. Реєстр рішень

| # | Рішення | Обґрунтування |
|---|---------|---------------|
| **ER-J-01** | Типізований `CalculationJobArgs`; `PeriodKeys` замість рядка дат | рядковий контракт складається/розбирається у 4 місцях і дає клас помилок |
| **ER-J-02** | Виконавець — worker-процес; серіалізація через applock + heartbeat | ghost/phantom/OOM — наслідки виконання в SQL Agent + CLR |
| **ER-J-03** | Збій задачі завжди видимий; журнал збою не залежить від попередніх кроків | `on_fail_action = 3` і падіння обробника ховали причини |
| **ER-J-04** | Алерти і mute — у системі, за станом, а не в AF за годиною | шум о 01:15 від старого вікна |
| **ER-J-05** | Split-джоби зникають: `PeriodKeys` — природна одиниця паралелізму | 56 land-джобів → ~14 модулів |
| **ER-J-06** | Обслуговування БД без `shrink` | shrink фрагментує те, що потім перебудовується |

Потрібне **вікно низької активності** (вартість — IO), а не простій |
> | **J-4** | ❓ відкрито | Дефолт: AD-група `ECR Admins` + пошта + канал моніторингу. Питання, яке треба поставити першим: **хто сьогодні дізнається про збій чинного розрахунку?** Якщо відповідь «ніхто» — це створення чергування, а не вибір адресата |
