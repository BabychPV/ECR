# Реліз-нотатки: RC20 (rc/2026-11-08): «передача місяця», діапазони за ключами публікації, квота verify/validate

Кандидат RC20 (PR #501) = RC19 (`main` = `f2d54772`, PR #500) плюс робота `dev/integration` після RC19 (близько 110 комітів без мерж-комітів). Попередній пакет — `rc-2026-11-07.md`.

**Обсяг.** База порівняння — `origin/main` = `f2d54772`. Кандидат нарізано з вершини `dev/integration` (`rc/2026-11-08`). Нова міграція EF одна: `20261011193039_EA1EditAssignment` (чотири нові таблиці «передачі місяця»). Контракт API змінено адитивно (див. розділ «Контракт API»).

## Що нового й виправлено (за напрямами)

### 1. «Передача місяця» (EA): керування доступом до редагування

Власник документа (або користувач із `Manage` проєкту) передає редагування звітного місяця конкретним виконавцям, а сервер лишається єдиним арбітром доступу.

- **Сутності й міграція:** `EditAssignment`, `EditAssignmentRecipient`, `EditorSet`, `EditorSetMember` (міграція `20261011193039_EA1EditAssignment` — **єдина нова** в цьому RC). Переходи станів: Передано → Заповнено → Валідовано / Повернуто (Fill/Validate/Return), повторна передача.
- **Правила й причини відмови:** нові причини `EditDenyReason` 16–19: `LockedByOwner`, `AssignmentFilled`, `AssignmentValidated`, `AssignmentExpired`. Передача піднімає Read → Write лише в межах переданого зрізу/місяця; чисті правила — `EditAssignmentGuard`.
- **Перевірка під блокуванням аркуша:** рішення про доступ і запис повторюється під блокуванням аркуша (закрито TOCTOU між перевіркою і записом), включно з поштучним шляхом і `CreateRow`; порядок блокувань фіксований (документ → передача → виконавці), видалення документа бере те саме блокування.
- **API керування:** `/documents/{id}/edit-assignments…` (створення/upsert, Fill, Validate, Return, повтор, `apply-set`, `copy` на інші зрізи), `/me/edit-assignments` (мої передачі), `/me/editor-sets` (набори виконавців: створення, зміна зі старою версією → 409, видалення лишає передачі), кандидати у виконавці (`candidates`). Прихований аркуш не розкривається, чужий набір — 404.
- **Клієнт:** шторка «Доступ до редагування» (матриця місяць × виконавець × статус), майстер передачі, смуга виконавця над таблицею документа («Заповнено»), діалоги «Валідувати» / «Повернути» з причиною, секції передач у «Мої задачі»; у режимі симуляції дій немає. Єдині ключі кешу `queryKeys.editAssignments` / `queryKeys.document`.
- **Картка документа:** нові поля `ownerUserId` і `canManageEditAccess` (рішення сервера: автор або `Manage` проєкту).
- **Тести й сторожі:** доменні інваріанти, CHECK/UQ на реальній базі, детерміновані тести блокувань (через `dm_tran_locks`), e2e передачі місяця (EA-5g) — див. «Відомі обмеження».

### 2. ФВ-0.2: діапазон `[A:B]` за ключами публікації

- У рантаймі діапазон опублікованої формули читає **ключі, зафіксовані при Publish** (`PublishedRangeExpander`), а не поточний `RowDef.Ordinal`; розбіжність із поточним порядком попри граф дає попередження й лічильник у лозі (фолбек).
- Excel-експорт пише діапазон формули за порядком публікації, а не за рядками між кінцями за макетом.

### 3. Квота verify/validate

- `POST reports/snapshots/{id}/verify` і `POST documents/{id}/validate`: межа **100 запитів/хв на користувача** (`Security:RateLimit:VerifyPermitPerMinute` / `ValidatePermitPerMinute`), відмова `429` з `Retry-After`, код `ECR-REQ-0429` (D-386). Закриває знахідку P1-08 (друга половина), яка в RC19 була у відомих обмеженнях.

### 4. Перенос версії шаблону фоновою задачею

- `POST …/migrate-version`: опціональне поле `async` у запиті; при `async = true` — `202` + `MigrationAcceptedResponse` із `jobId`, прогрес стадій і причина відмови з задачі; один перенос на проєкт (замок), перевірка автора поверненого `jobId`; діалог переносу версії показує прогрес і переживає закриття. Синхронний режим без змін.

### 5. Читач архіву журналу змін комірок (НФ-8.9.6)

- Журнал змін комірок читає й архів аудиту (`arc.AuditCellChange`): позначка «Archive», вибір періоду перед межею гарячого журналу, `CellChangeView.fromArchive` у контракті.
- ⚠ Потрібне право `SELECT` на `arc.AuditCellChange` службовому акаунту (D-264, runbook п. 7.3). Без нього (або без архівної таблиці) читач **деградує до гарячого журналу**, а не падає.

### 6. FP: ReportViewer, одиниці/Rollup, права, UX

- **FP-1:** роль `ReportViewer` стартує зі зрізів; перелік проєктів віддається і за `Report.ViewRegulatory`.
- **FP-4/FP-5:** аргумент × коефіцієнт публікується з виходом у масі; приймач Rollup — джерело значення колонки Formula; проводка `boundColumnIds ∪ rollupTargets` у `PublishTemplateVersionHandler`.
- **FP-3/6/7:** порожній стан Documents без проєктів, підказка «порожня чернетка», CSV довідника без полів, дрібні UX-правки; вкладка «Schedule» шухляди з'єднання — лише з `Integration.EditSchedule`.
- **Права SystemAdministrator (D-388):** роль отримує **вісім адмін-прав** (Security, Mapping/Pipeline, Notifications, Campaign, публікація методик). Сід (`FP:sysadmin-rights`) **повертає їх, якщо адміністратор зняв**; додавання пишеться в журнал безпеки.
- **UI RC19 P3:** бургер і згортання на межі 900 px, скелети Health, назви типів Jobs, підписи Audit (en/ru/kz); обов'язковий Lookup без хрестика; у симуляції немає «New registry» / «Створити документ».

### 7. Категорійне правило: 422 при збереженні

- Правило категорії з невідомим аргументом (`@Nope`, `CST.X`, `!X`) повертає єдиний код **`ECR-CALC-0422`** з трьома messageKey (`categoryRuleUnknownArgument` та споріднені) замість `ECR-CALC-0438` (R16-4).
- **RowCount зрізу звіту = кількість рядків** (distinct `RowNo`), а не комірок (R16-5).
- R16-1: Lookup-колонка / поле шапки без довідника (`lookupRegistryDefId = null`) — `422 ECR-TMPL-0422`, а не 500 на `CK_*_Lookup`; зміна типу наявної колонки на Lookup — `422 columnDataTypeImmutable`.
- Повторний номер версії звіту, гонка двох створень версії (`UQ_ReportVersion`) — `409 ECR-RPT-4091`, а не 500.

### 8. Land-скрипти

- `tools/land`: повторна міграція на цільовій версії дає «0 змін»; `-MigrateDocumentId` приймає «3,10» і масив (R16-2/R16-3). Також виправлено ініціалізацію стану в Pester-тестах `Apply-ContractHeader`.

### 9. Тести й документація

- Рішення D-376…D-385 (розбіжності код ↔ ТЗ закрито оновленням ТЗ), D-386 (квота), D-387 (ФВ-5.14 «ТЗ під код»), D-388 (права SystemAdministrator); `CHECKSUMS` оновлено в тих самих комітах.
- Звіт про слабкі докази `docs/build/TESTS-WEAK-2026-10-11` (ФВ-5.15/0.2/5.13/5.14/4.3/1.15) і підсилення тестів: HTTP-потік відхилення → правка → повторне подання → затвердження, HTTP-негативи версій і публікації звіту, токен перегляду імпорту, сторож масового `ExecuteDelete`.
- Макет «Доступ до редагування» (`docs/design/hybrid`, EA-0), передача роботи 11.10, відповіді людини в `QUESTIONS-BUSINESS`.

## ⚠ Для адміністратора / застереження щодо оновлення

1. **Нова міграція EF `EA1EditAssignment`:** створює чотири таблиці; наявні дані не змінює. Передач у наявних документах немає, тому поведінка до першої передачі не змінюється.
2. **SystemAdministrator отримує 8 адмін-прав (D-388).** Оновлення мовчки розширює **наявних** носіїв ролі; якщо адміністратор свідомо зняв ці права, сід їх **поверне** (запис у журнал безпеки). Перевірте склад ролі після оновлення.
3. **`ECR-CALC-0438` → `ECR-CALC-0422`** для правила категорії: інтеграції, що розбирали код відповіді, треба оновити.
4. **RowCount старих зрізів** лишається старим числом (рахувалось за комірками); нові зрізи рахують рядки. Перерахунок старих зрізів не виконується.
5. **Прибрані ключі `editAssign.visibility*`** (клієнт передачі більше не використовує `visibility`); користувацькі переозначення цих ключів, якщо були, стають невикористаними.
6. **Квота 100/хв** на verify/validate: скрипти, що масово викликають ці маршрути, отримають `429`; поріг змінюється налаштуванням (runbook).
7. **Архів журналу змін:** видайте службовому акаунту `SELECT` на `arc.AuditCellChange` (D-264, runbook п. 7.3), інакше читач працює лише з гарячим журналом.

## Контракт API

- Нові маршрути EA: `/documents/{id}/edit-assignments…`, `/me/edit-assignments`, `/me/editor-sets`, кандидати, `apply-set`, `copy`; картка документа — `ownerUserId`, `canManageEditAccess`.
- `verify`/`validate`: додано відповідь `429`.
- `POST …/migrate-version`: поле `async` у запиті, відповідь `202 MigrationAcceptedResponse`.
- `CellChangeView.fromArchive`.
- `contracts/openapi.snapshot.json` і `src/Ecr.Web/src/api/schema.d.ts` оновлено; зміни адитивні, наявні клієнти не ламаються (окрім зміни коду помилки правила категорії, див. вище).

## Відомі обмеження RC20

- **e2e-спек передачі місяця (EA-5)** ще **не запускався на CI**: локатори можуть потребувати правок після першого прогону `e2e-stand`.
- **`apply-set` / `copy` у клієнті — N послідовних upsert** (не атомарно: при обриві частина зрізів уже має передачу); `applyEditorSet` / `updateEditorSet` / `deleteEditorSet` **не мають UI-споживача**.
- **Фрагмент імені у `candidates?q=`** потрапляє в access-логи сервера (query string).
- **`LockedByOwner` не закриває шапку** документа: блокування власником діє на таблиці, а не на полях шапки.
- **`recalculate` виконавцем прийнято** (D3): виконавець із передачею може запустити перерахунок.
- **`fp-sysadmin-rights` мовчки розширює** наявних носіїв ролі `SystemAdministrator` (див. застереження 2).
- **`HasEditAssignments`**: можливе застаріле `false` у вікні в мілісекунди після створення першої передачі.
- **`addRowDenied` без `reasonKey`**: відмова додавання рядка не називає причину.
- **`SourceEventSyncJob`**: `COUNT` рахує й видалені рядки (важливо для d3 «видалення рядка»).
- **Не ввійшло в RC20 (на огляді, піде в RC21):** `d14-unmatched-banner` (банер рядків без правила), `luf-dv-reason`, `luf-small-ux-2`, `d3-row-delete` (видалення рядка; P1 архітектурної деградації), `d1-cell-formulas`, `land-g8`, `land-g12`, `land-g13`, `land-g14`, `fix-health-facts-cold`, `fix-collect-deadlock`, `fix-patch-busy-503`.
- Успадковані з RC19 без змін: один великий PATCH може ескалувати блокування `doc.CellValue` (D-372); `useSession` без змін; стеля розміру тестової бази 192 МБ (D-375); перелік «не закрито» з `rc-2026-11-07.md` (окрім квоти verify/validate, яку закрито тут).
