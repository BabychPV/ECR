Призначення: операційні вимоги для проду (дії DBA/адміністратора до накату й зміни збірки, що впливають на експлуатацію).
Джерело: запит Аудиту 15.10.2026.
Застереження: публікувати разом з `lane/recalc-sql-timeout-followup` (6d055ee8d; мінімум `RecalcCommandTimeoutSeconds` 30).

Призначення: перелік дій DBA/адміністратора ДО вікна накату на прод і змін у збірці, що впливають на експлуатацію. Усі факти зі стенда `:5094` / `EcrLandUi` (локальний SQL Server, один диск `F:`). Значень прод-даних тут немає. Позначка «[не підтверджено джерелом — перевірити]» — значення, якого немає в першоджерелах; не вигадувалось.

## 1. Прегроу файлів `Ecr_hot` і журналу транзакцій

- **Що зробити.** До вікна збільшити розмір файлів `Ecr_hot` та журналу наперед (під тиждень роботи) і змінити крок приросту з 64 МБ на 512 МБ–1 ГБ:
  `ALTER DATABASE [<БД>] MODIFY FILE (NAME = N'Ecr_hot'..., SIZE = <ГБ>GB, FILEGROWTH = 512MB);` — те саме для файлу журналу (`MODIFY FILE` для логічного імені лог-файлу). Конкретні логічні імена й цільовий розмір узяти з `sys.database_files` прод-бази.
  Цільовий розмір «під тиждень» — [не підтверджено джерелом — перевірити]: джерела дають лише орієнтир «на кілька ГБ наперед» (RECALC-FAILED-RUNS-CAUSE, P1.1); на стенді `Ecr_hot` був 6 976 МБ при growth 64 МБ, журнал 20 679 МБ.
- **Чому (факт зі стенда).** 15.10 04:24:38Z в errorlog: «Autogrow of file 'Ecr_hot' in database 'EcrLandUi' was cancelled by user or timed out after 71344 milliseconds». Усі записи в hot-файл стояли 71 с; 60-секундний `CommandTimeout` (`SqlException -2`) спрацював одночасно в кількох прогонах recalc -> 3 Failed-прогони (8544, 8562, 8570), довгий «хвіст» повторів. Default trace за 50 хв: 18 приростів `Ecr_hot` (до 3 403 мс кожен) і 13 приростів журналу (460–806 мс).
- **Як перевірити.** `SELECT name, size*8/1024 AS size_mb, growth*8/1024 AS growth_mb, is_percent_growth FROM sys.database_files;` — growth >= 512 МБ, `is_percent_growth = 0`; після вікна в errorlog відсутні записи «Autogrow ... cancelled» (`xp_readerrorlog`).

## 2. Instant File Initialization (IFI) для облікового запису служби SQL Server

- **Що зробити.** Видати обліковому запису служби SQL Server право Windows «Perform volume maintenance tasks» (SeManageVolumePrivilege) і перезапустити службу SQL Server (право діє після перезапуску).
- **Чому.** На стенді `instant_file_initialization_enabled = N`: кожен приріст файлів даних — з обнуленням (zero-init), що разом із малим кроком дало 71-секундну зупинку. ⚠ IFI не діє на журнал транзакцій — журнал завжди обнуляється, тому для нього потрібен прегроу (п. 1) і регулярний BACKUP LOG (п. 3).
- **Як перевірити.** `SELECT servicename, instant_file_initialization_enabled FROM sys.dm_server_services;` -> `Y` для SQL Server (Database Engine).

## 3. Регулярний BACKUP LOG при recovery FULL

- **Що зробити.** При моделі відновлення FULL налаштувати регулярний `BACKUP LOG` (графік — на розсуд DBA, [не підтверджено джерелом — перевірити]: інтервал у джерелах не названо). На стендах без вимоги point-in-time допустимо `SIMPLE` — лише на стенді, не на проді без рішення власника даних.
  Бекап ДО вікна (COPY_ONLY) ланцюг журналу не рве і НЕ звільняє журнал — він не замінює BACKUP LOG.
- **Чому.** На стенді журнал `EcrLandUi` 20 679 МБ, використано 99,75 %, `log_reuse_wait_desc = LOG_BACKUP`; у `msdb` лише повні бекапи (21:17, 07:14, 08:05), бекапів ЖУРНАЛУ немає — журнал ніколи не звільняється й росте кроками по 64 МБ (MaxSize 2 ТБ).
- **Як перевірити.** `SELECT name, recovery_model_desc, log_reuse_wait_desc FROM sys.databases WHERE name = N'<БД>';` — `log_reuse_wait_desc` не `LOG_BACKUP` довгостроково; `DBCC SQLPERF(LOGSPACE)` — використання журналу далеко від 100 %; у `msdb.dbo.backupset` є записи `type = 'L'` за графіком.

## 4. Worker: `Jobs:Workers:MaxDuration` >= 04:00:00

- **Що зробити.** Виставити найдовшу тривалість однієї задачі воркера не менше `04:00:00` (вимога координатора). Ключ: `Jobs:Workers:MaxDuration` (формат `hh:mm:ss`, додатний інтервал).
  Де: `worker.settings.json` поруч з `Ecr.Worker.exe` (типові значення збірки, **оновлення MSI його перезаписує**) або змінна середовища служби `EcrWorker`: `ECR_Jobs__Workers__MaxDuration` (перекриває файл; ⚠ разом з рештою `Environment` служби НЕ переживає оновлення MSI — після оновлення виставити знову; `docs/admin/operations-runbook.md` §10.3). Після зміни — `Restart-Service EcrWorker`.
- **Чому.** Типове значення — `00:30:00` (`src/Ecr.Worker/Isolation/WorkerPoolOptions.cs`, `worker.settings.json`). Задача довша за межу закривається `Failed` («The job ran longer than the limit of ... (Jobs:Workers:MaxDuration)»), без ретраю. Для повного recalc великого проекту 30 хв може не вистачити — [не підтверджено джерелом — перевірити]: у джерелах немає виміру тривалості повного recalc на проді; на стенді вікно w5+w6 (2 документи × 7 періодів) = ≈5 хв.
  Вимога «>= 04:00:00» — рішення координатора; додаткового обґрунтування в першоджерелах не знайдено.
- **Як перевірити.** Після старту служби в лозі воркера немає помилки валідації конфігурації (недійсне значення зупиняє службу з кодом 3); значення видно в ефективній конфігурації (`worker.settings.json` / `Services\EcrWorker\Environment`). Після recalc — немає `Failed` з причиною `jobs.maxDurationExceeded`.

## 5. `rowKey` у форматі Table для прод-імпорту

- **Що зробити.** Прод-імпорт рядків (`Load-LandRows.ps1`, `Load-LandInputCells.ps1`) виконувати з форматом ключа з кодом таблиці: `p<doc>-<TableCode>-<seq:0000>`, напр. `p10-T3_00-0001` (`-RowKeyFormat Table`; у `Load-LandRows.ps1` це дефолт, у `Load-LandInputCells.ps1` дефолт — `Legacy`, тож задавати явно). Формат має збігатися з ключами рядків, що вже є в документі на стенді/проді (інакше `ROW_MISSING`).
- **Чому.** Старий ключ `p<doc>-<seq:0000>` повторювався в кожній таблиці документа, а `calc.CalculationResult` має лише `DocumentId` + `SourceRowKey` (без таблиці). Наслідок (звіт LAND-ROWKEY-PRODUCT-CHECK 14.10): дублікати груп результатів у 6 документах (doc 3, 4, 5, 6, 10, 14: 8 / 8 / 8 / 8 / 3102 / 840 груп), у doc 10 — до 4 рядків у групі; відображення таблиці змішує або сумує результати різних таблиць з однаковим `RowKey`. Прив'язка результату до таблиці — через `calc.CalculationResult.TableInstanceId` (harness читає його, README `tools/land`).
  Унікальність: ключ з кодом таблиці унікальний між таблицями документа; сам `RowKey` у БД унікальний лише в межах екземпляра таблиці (індекс `doc.TableRow (PeriodKey, TableInstanceId, RowKey)`).
  Чи має прод вже документи з Legacy-ключами і чи потрібне їх перезавантаження — [не підтверджено джерелом — перевірити]; README: «Міграція тестових документів: перезавантажити рядки новим ключем і зробити один recalc».
- **Як перевірити.** Після імпорту — `Compare-LandParityFull.ps1`: `summary.json` -> `rowKeyFormats {table, legacy, unknown}` (очікується legacy = 0, unknown = 0), `ambiguousEcrKeys` порожній; пакет `k1-postcheck`: DUP Current (проект × документ × період) = 0.

## 6. Інструменти `Load-LandRows` і `Invoke-LandRecalc` — лише hashtable-splat

- **Що зробити.** Параметри обох скриптів передавати лише splat-ом хеш-таблиці (`@params`), не масивом аргументів і не вручну зібраним рядком. Приклад:

  ```powershell
  $p = @{
      SourcePath   = 'F:\...\prod-sample'          # каталог LAND-PROD-<n>.json
      DocMap       = '{"LAND-PROD-7":12}'
      BaseUrl      = 'http://localhost:5094'
      ConfirmStand = 'localhost:5094/EcrLandUi'
      User         = 'land-owner'
      Password     = $pw
      SqlConnection= 'Server=localhost;Database=EcrLandUi;Integrated Security=true'
      RowKeyFormat = 'Table'
      Execute      = $true
  }
  .\Load-LandRows.ps1 @p

  $r = @{ DocMap = '{"LAND-PROD-7":12}'; PeriodKey = '202601','202602'; BaseUrl = 'http://localhost:5094'
          ConfirmStand = 'localhost:5094'; User = 'land-owner'; Password = $pw }
  .\Invoke-LandRecalc.ps1 @r
  ```
  Прапорці `-BaseUrl`, `-ConfirmStand` обов'язкові без дефолтів; мутація лише з явним `-ConfirmStand` і явним `-SqlConnection`.
- **Чому.** [не підтверджено джерелом — перевірити]: у README `tools/land`, звітах `.sync-local` і скриптах немає прямого пояснення, чому саме hashtable-splat (пошук «splat» знайшов лише `docs/build/decisions.md` D2-261 про інший випадок — розкладання масиву з позиційним аргументом у виклику зовнішньої програми дає не той рядок запуску). Загальний PowerShell-факт: splat масивом передає значення позиційно, а не за іменем параметра. Формулювання правила узгодити з координатором/Аналізом.
- **Як перевірити.** Передперегляд без `-Execute`/`-DryRun`: скрипт друкує лічильники й коди без запису; код виходу 0, `NO_DOC`/`NO_TABLE`/`MISSING_COLUMN` = 0.

## 7. Нове в збірці: стеля таймауту recalc і відкладення на SQL −2/1205

Лінії: `lane/recalc-sql-timeout-resilience` + `lane/recalc-sql-timeout-followup` (у `origin`; на момент приймання вікон 5+6 на `:5094` цієї логіки в збірці НЕ було: гілок `jobs.sqlStallDeferred` = 0). Наявність у RC перевірити перед вікном [не підтверджено джерелом — перевірити].

- `Database:RecalcCommandTimeoutSeconds` — типово **180** с, мінімум **30** (менше — старт зупиняється з назвою ключа; понад 3600 затискається до 3600). Застосовується до задачі recalc і гілок оркестратора; лише підвищує (глобальний `Database:CommandTimeoutSeconds` = 60 для решти не змінюється). Ціна: довше утримання applock документа при справжньому зависанні (до 180 с замість 60 с).
- `RecalculationJob`: `SqlException -2` (таймаут команди) і `1205` (жертва дедлока) -> `JobDeferredException` (відкладення без витрати ретраю: пауза 20 с + 0–9 с розсіювання за номером документа), а не 3 ретраї 30/60/120 с із `Failed`-прогонами. Стеля відкладень — `JobDeferral.MaxDeferral` = 30 хв від першого відкладення, далі `Failed`.
- Warning-лог, один рядок на відкладення: `RecalculationJob: документ {DocumentId}: зупинка бази (SqlException {SqlErrorNumber}: -2 таймаут команди, 1205 жертва дедлока); перерахунок відкладено на {Delay}...`. Допоміжний Warning: «не вдалося позначити {Runs} прогон(ів) Failed (зупинка бази)». Метрику/ключ каталогу `jobs.sqlStallDeferred` у приймальній шукати як ознаку гілки (звіт WINDOW56).
- `CalculationOutputWriter`: `SaveChanges` чанками по 5000 рядків в одній транзакції (атомарність збережена).
- `SafeErrorText`: збій БД усередині `AggregateException`/`TimeoutException`/`RetryLimitExceeded` читається як «database error», а не «unexpected».
- **Як перевірити.** Лог воркера/Api: рядки Warning зі `«відкладено на»` замість серії `fail: RecalculationJob`; `calc.CalculationRun` Failed = 0 за вікно; `Database:RecalcCommandTimeoutSeconds` < 30 -> служба не стартує (негативна перевірка на стенді).
- ⚠ Не заміна п. 1–3: відкладення маскує симптом; причина (autogrow/IFI/журнал) усувається лише інфраструктурою.

## 8. Паралельність recalc на проді 8–12: чого очікувати, що моніторити

- **Очікування.** Сам код паралельність витримує (звіт RECALC-FAILED-RUNS-CAUSE); обмеження — інфраструктура БД (п. 1–3) і один диск. Типові межі: `Calculations:MaxParallelism` = 4 (гілки методологій у документі), `Jobs:Recalculation:FanOutMaxConcurrency` = 4, `Jobs:Quartz:ThreadCount` = 16, `Database:MaxPoolSize` = 200 (пул не вузьке місце). Без п. 1–3 кожен stall = timeout усіх писачів + 3 job-ретраї 30/60/120 с -> каскад Failed і «хвіст» +35 с…+3,5 хв при 8–12 паралельних документах; дані не губляться (ретраї дають `Current`), ламається SLA. Скільки документів реально піде паралельно на проді — [не підтверджено джерелом — перевірити] (на стенді спостерігалося 15–20 одночасних прогонів; конфіг стенда відрізняється від appsettings).
- **Моніторинг (read-only, `NOLOCK`).**
  - `calc.CalculationRun` зі `Status = Failed` за вікно (очікується 0; старі Failed лишаються як історія, не «відкриваються»);
  - `itg.JobProgress`: немає `Running`/`Queued` після завершення, `Failed`/`Cancelled` = 0;
  - SQL errorlog (`xp_readerrorlog`): записи «Autogrow of file ... cancelled by user or timed out» — критичні;
  - дублі `Current` за (проєкт × документ × період) = 0;
  - лог Api/Worker: `ECR-SYS-0500`, `Unhandled`, 5xx = 0; «Execution Timeout Expired» (−2) — рахувати.
- **Як перевірити.** Пакет `k1-postcheck.sql` + `k1-api-smoke.ps1` (світлофор: QUEUE 0, FAILED/CANCELLED 0, DUP 0, A-14 лог).

## 9. Бекап перед вікном і порядок вікна

- **Бекап (до першої мутації).** `BACKUP DATABASE [<БД>] TO DISK = N'<шлях>.bak' WITH COPY_ONLY, INIT, COMPRESSION, CHECKSUM, STATS = 10;` -> `RESTORE VERIFYONLY FROM DISK = N'<шлях>.bak' WITH CHECKSUM;` (очікується «The backup set on file 1 is valid.», код 0) -> SHA256: `(Get-FileHash <файл> -Algorithm SHA256).Hash`; `RESTORE FILELISTONLY` -> 6 файлів: ROWS, LOG, Ecr_hot, Ecr_archive, Ecr_audit, Ecr_idx. Місце: F: >= 20 ГБ (відкат = RESTORE ~14 ГБ). Орієнтири: ~135 МБ стиснуто (бекап живого в чек-листі 13.10; пізніші `.bak` вікон 4 і 5+6 ≈ 717–759 МБ), ~100 с BACKUP, RESTORE на копії — 346 с. Бекап «після» вікна — так само.
- **Порядок вікна (послідовно, без паралельних важких кроків).** Substance (довідники/склад) -> `ParityBranch` -> `OptionalArguments` (лише чернетки; запускається ПІСЛЯ Methodologies/CompositionMass/ParityBranch) -> publish (від другої особи `land-reviewer`) -> повторно `-Stage Methodologies` (прив'язки колонок вимкнені до публікації) -> recalc. Точні назви кроків і команди — `window5094\CHECKLIST.md` (W-01…W-12); у ньому порядок: довідники (W-01…W-04) -> TypeFuel/GTU -> C12_03 -> публікація -> `OptionalArguments` -> `-Stage Methodologies` -> recalc. Відповідність порядку «Substance -> ParityBranch -> OptionalArguments» повному порядку в чек-листі підтвердити з виконавцем [не підтверджено джерелом — перевірити].
- **Відкат.** Єдиний повний відкат даних — `RESTORE ... WITH REPLACE` бекапу ДО вікна (порядок: stop сервісу за PID -> RESTORE -> start; `rollback.md` §4). Умови відкату — `rollback.md` §3.
- **Як перевірити.** `VERIFYONLY` valid, SHA256 записано в журнал; `pre-checks.out.txt` збережено поряд із бекапом; після вікна — `post-checks.sql`, світлофор без P0/P1.

## 10. Відомі обмеження

- **Холодний LP-45** (список документів `/documents?limit=50&periodKey=...`): після рестарту/бекапу/recalc перший запит до 28,8–34,6 с (вікна 4 і 5+6: 202601 — 28 806 мс і 34 649 мс); теплі — 66–134 мс. Після рестарту API виконати прогрів (по одному запиту на період) і лише тоді приймати LP-45; повторювати після прогріву. Критерій приймання — warm <= 5 с, cold <= 10 с (INFO). Окремий фікс холодного запиту — у черзі.
- **`error_cells` = 546** (усі в `T3_00`) — відома величина, не змінюється між вікнами (поріг A-13: <= 546); не дефект вікна.
- Інші прийняті обмеження вікон: Legacy-режим C11_01/C11_02 обнуляє ≈60 % спільних ключів проти Strict (питання методологу відкрите); 61 група дублів ключа в `LAND_SUBSTANCE_APPLICABILITY` (не C11_11_02) — давні чи залишок Ensure-Registry, не розслідувано; пороги шаблону `1.0.11.0` у `k1-postcheck.sql`/`k1-api-smoke.ps1` зашиті (A-16/S-03c дають очікуваний FAIL на 1.0.12.0).
