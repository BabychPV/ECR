# Реліз-нотатки: RC 2026-10-20 (кандидат №2) - розділ AN-37 L7-08

Файл охоплює лише зміну «одна опублікована версія методології на дату набуття чинності»
(AN-37 L7-08). Решту змін кандидата вносить той, хто складає нотатки RC; тут їх немає.

Коміти в `dev/integration`: `75d8d260` (міграція + тест), `0bbe61e7` (409 замість 500),
`cd01acb1` (runbook п. 8.6), `62b7dc38` (ключ каталогу), `387dddf2` (тест гонки), `cc878324` (контракт §7).

## BREAKING

| Зміна | Що робити |
|---|---|
| **Оновлення бази може зупинитись з `Msg 50708` на реальних даних.** Нова міграція `20261005110336_AN37MethodologyEffectiveUnique` додає унікальний фільтрований індекс `UQ_MV_Effective` на `calc.MethodologyVersion (MethodologyId, EffectiveFrom) WHERE Status = 1`. Якщо в базі вже є дві й більше **опубліковані** версії однієї методології з однаковою датою чинності, передперевірка перериває міграцію `THROW 50708` з переліком груп (методологія, дата, id і номери версій). Схема й дані **не змінюються**, автоматичного виправлення немає. | Перед оновленням знайти дублі запитом з `docs/admin/operations-runbook.md`, п. 8.6 (`... WHERE Status = 1 GROUP BY MethodologyId, EffectiveFrom HAVING COUNT(*) > 1`). Для кожної групи залишити чинною одну версію, зайву вивести з обігу (`Status = 2`) або виправити їй `EffectiveFrom`. Версії, якими вже рахували подані періоди, на іншу дату не переносити. Повторити оновлення. |
| Публікація версії методології на дату, вже зайняту іншою опублікованою версією: `409 ECR-CALC-0409`. У разі гонки двох паралельних публікацій другу відбиває індекс - також `409 ECR-CALC-0409`, із messageKey `err.ECR-CALC-0409.effectiveDateTakenNoVersion` (без `{version}`: SQL Server версію-суперника не називає), раніше таке могло дати 500. Код `ECR-CALC-0409` не новий. | Клієнт, що публікує, при 409 перезавантажує методологію й обирає іншу дату. |

## Міграції

- `20261005110336_AN37MethodologyEffectiveUnique` - індекс `UQ_MV_Effective` (унікальний, фільтр `[Status]=(1)`) і передперевірка `THROW 50708` першою командою `Up`. Обидва шляхи (`MigrateAsync` і ідемпотентний `migration.sql`) виконують передперевірку. Runbook п. 8.6.

## Перевірено (інтегратор, 05.10.2026)

- База розгорнута з `dev/integration` без міграції (`setup-dev-db.ps1`), `-Upgrade` двічі з вершини: обидва exit 0; відмінність лічильників рядків усіх таблиць користувача (однаковий запит до/після): `__EFMigrationsHistory` 80 -> 81, `sys_ecr.UiString` 11892 -> 11895, більше нічого.
- Копія з дублями (дві опубліковані версії на одну дату, плюс Deprecated, чернетка, інша методологія): `-Upgrade` падає `Msg 50708` з переліком, історія міграцій +0, індексу немає. Після розведення дубля (`Status = 2`): `-Upgrade` двічі exit 0, індекс є (`[Status]=(1)`, унікальний), історія +1.
- Ідемпотентний скрипт від `AN34CollectionCoverageDedupIndex` до вершини через `sqlcmd -I -b` двічі: exit 0, другий прогін без змін.
