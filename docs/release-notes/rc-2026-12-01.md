# Реліз-нотатки: RC38 (rc/2026-12-01): пачка «F1» — межа дітей розкладу перерахунку проєкту, відкладення при lockTimeout; детермінований тест пейсингу

Поверх RC37 (`rc/2026-11-29`, `rc-2026-11-29.md`). Серверна пачка: черга/виконавці перерахунку (ризикова зона) і тест. Зібрана на `lane/integ-x` лінійно (`cherry-pick -x`: `lane/integ-stale-timing`, `lane/integ-recalc-fanout`).

**Обсяг.** Міграцій EF — **немає**. Контракт API (`openapi.snapshot.json`, `schema.d.ts`) — без змін. Сід `Sql/**`, модель Land, `docs/tz/**` — без змін.

## Для адміністратора

- Новий необов'язковий ключ `Jobs:Recalculation:FanOutMaxConcurrency` (за замовчуванням 4; значення < 1 відхиляє валідація конфігурації). Описано в `docs/admin/operations-runbook.md`.
- Якщо після міграції версії проєкту частина документів лишилась неперерахованою, повторіть вручну `POST /projects/{id}/recalculate`.

## Що нового

### 1. F1: лавина recalc-job після міграції проєкту

- Було: fan-out ставив coalesced-задачу на кожен документ, і всі йшли паралельно (дефолт черги Quartz, пул 16 потоків). Запис обчислених комірок різних документів ескалював блокування `doc.CellValue` -> `ECR-DOC-4091` lockTimeout (до 15 с) -> 3 ретраї (30 + 60 + 120 с) -> `Failed` після 4 спроб; у стані «Running 70–85».
- Стало: друга межа в `QuartzJobTypeLimiter` (Gate: ліміт, лічильник, FIFO) — `FanOutMaxConcurrency = 4`. Діти fan-out (`IRecalculationJob` з `documentId > 0` і `fanOutParentJobId`) понад межу відкладаються тригером (як Excel).
- Ручний «Перерахувати» та інкрементний `FormulaRecalculationJob` після PATCH — поза межею.
- `RecalculationJob`/`FormulaRecalculationJob`: `ECR-DOC-4091` lockTimeout (або сирий `SqlException` 1222) -> `JobDeferredException`: пауза 20 с + 0–9 с розсіювання за номером документа БЕЗ витрати спроби ретраю; стеля `MaxDeferral` 30 хв, далі `Failed` «ресурс зайнятий». `JobRetryPolicy` не змінено.
- Оцінка повного перерахунку 91 документа: ceil(91/4) = 23 хвилі × найважчий документ, орієнтовно 2–6 хв; виміру на живих даних немає.

### 2. Тест пейсингу LandStaleValues (D-1)

- `Пейсинг_тримає_паузу…` став детермінованим: `Get-LandStaleUtcNow` у `tools/land/LandStaleValues.Lib.ps1` і керований годинник у `LandStaleValuesTests`; 20/20 під навантаженням.

## Відомі обмеження

- Межа діє лише в межах процесу (Quartz in-memory); режим Database і кілька процесів між собою не узгоджені.
- `FormulaRecalculationJob` отримав ту саму гілку відкладення без власного SQL-тесту.
- Клієнтський діалог `acceptGuardedOverwrite` (CL-8) — окремо; lazyTables/e2e без змін.
- Успадковані обмеження RC23–RC37 — у `rc-2026-11-14.md` … `rc-2026-11-29.md`.

## Зміна політики публікації: `strictBackdated` (lane `integ-c12-03-guard-2`, D-398; у найближчий RC після цієї пачки)

- Публікація версії методології в `Strict` з `effectiveFrom` ≤ сьогодні при попередній не-`Strict` версії **допускається**, якщо жодна з версій, чинних у вікні нової (`[effectiveFrom, наступна дата дії)`), не має жодного рядка результату (`calc.CalculationResult` + `arc.CalculationResult`, будь-який статус). Інакше — `422 ECR-CALC-0422` `strictBackdated`, як і раніше.
- Нових кодів, ключів і міграцій немає; `409 ECR-CALC-0409 effectiveDateTaken` (опублікована версія з тією самою датою) не змінено — для такої дати слід обрати іншу (наприклад, +1 день).
- Закриті періоди автоматично не перераховуються (ФВ-9.7).

## Зміна перевірки публікації: `ECR-CALC-0438` по «живій» версії шаблону (lane `integ-k-eng-lite`, D-399; у найближчий RC)

- Публікація версії методології і збереження правила категорії звіряють `@`-аргументи з колонками лише тих таблиць прив'язок, що належать **останній опублікованій версії** свого шаблону (чернетки й виведені з обігу не рахуються). Раніше перевірялися всі `TableDef` усіх версій: колонка, додана лише в нову версію шаблону, блокувала публікацію через старі версії, на які клон скопіював прив'язки.
- Якщо в методології немає жодної прив'язки на живій версії шаблону — перевірка як і раніше по всіх таблицях. Методології з прив'язками лише на одній версії — без змін.
- **Обмеження:** документи на старших версіях шаблону новий аргумент не отримають (`#ARG`, для необов'язкового `null`); їх варто перевести на живу версію міграцією версії проєкту.
- Без міграції EF, без зміни контракту, без нових кодів і ключів. Тести: `LiveTemplateVersionArgumentPublishTests` (5), `CalculationBindingStoreLiveTablesTests` (SQL).
