**Обсяг.** Міграцій EF — **немає**. Контракт API (`openapi.snapshot.json`, `schema.d.ts`) — без змін. Сід `Sql/**`, модель Land, `docs/tz/**` — без змін.

## Для адміністратора

- Новий необов'язковий ключ `Jobs:Recalculation:FanOutMaxConcurrency` (за замовчуванням 4; значення < 1 відхиляє валідація конфігурації). Описано в `docs/admin/operations-runbook.md`.
- Якщо після міграції версії проєкту частина документів лишилась неперерахованою, повторіть вручну `POST /projects/{id}/recalculate`.

## Що нового

### 1. F1: лавина recalc-job після міграції проєкту

- Було: fan-out ставив coalesced-задачу на кожен документ, і всі йшли паралельно (дефолт черги Quartz, пул 16 потоків). Запис обчислених комірок різних документів ескалював блокування `doc.CellValue` -> `ECR-DOC-4091` lockTimeout (до 15 с) -> 3 ретраї (30 + 60 + 120 с) -> `Failed` після 4 спроб; у стані «Running 70–85».
- Стало: друга межа в `QuartzJobTypeLimiter` (Gate: ліміт, лічильник, FIFO) — `FanOutMaxConcurrency = 4`. Діти fan-out (`IRecalculationJob` з `documentId > 0` і `fanOutParentJobId`) понад межу відкладаються тригером (як Excel).
- Ручний «Перерахувати» та інкрементний `FormulaRecalculationJob` після PATCH — поза межею.
- `RecalculationJob`/`FormulaRecalculationJob`: `ECR-DOC-4091` lockTimeout (або сирий `SqlException` 1222) -> `JobDeferredException`: пауза 20 с + 0–9 с розсіювання за номером документа БЕЗ витрати спроби ретраю; стеля `MaxDeferral` 30 хв, далі `Failed` «ресурс зайнятий». `JobRetryPolicy` не змінено.
- Оцінка повного перерахунку 91 документа: ceil(91/4) = 23 хвилі × найважчий документ, орієнтовно 2–6 хв; виміру на живих даних немає.
