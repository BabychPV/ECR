
## ✎ 2026-09-08: зональний бар'єр і обмін через `sync` — прибрано

**Пряме рішення людини.** До цього запису тут стояв дво-вузловий процес:
git-хуки, що фізично забороняли PK1 писати код і PK2 — торкатися `docs/`,
`contracts/`, `CLAUDE.md`, `.githooks/`, `.github/`, `.claude/`, `scripts/`;
гілка `sync` із журналами `PK1-LOG.md`/`PK2-LOG.md`, де кожна нова межа
каталогу означала `ASK` → чекати настанову → PR на розширення зони → мерж
— і так по колу щоразу, коли робота торкалася нового каталогу
(`docs/build/**`, потім `contracts/openapi.snapshot.json`, обидва того ж
дня). Людина попросила прибрати механізм цілком, а не латати його втретє.

**Що це означає практично:**
- Немає заборонених шляхів. Пиши код, тести, документацію, скрипти,
  конфігурацію CI — де потрібно для завдання.
- Гілка `sync` і файли `PK1-LOG.md`/`PK2-LOG.md` — необов'язкові. Історія
  рішень до 2026-09-08 лишається там як довідка; новий запис туди не
  вимагається жодним процесом.
- Немає ролі, що блокує роботу. `.sync-local/NODE` лишається лише для
  вибору моделі (`opus` для PK1, `sonnet` для PK2) і мітки в описі PR —
  якщо він тобі не потрібен, працюй без нього.

**Що НЕ прибрано, і чому це не той самий механізм:**
- **Шість гейтів CI** (`build`, `test`, `honesty-guard`, `server`,
  `client`, `a11y`) — критерій приймання коду в `main`, не зональний
  бар'єр. Це не адміністративна перепона між двома вузлами — це перевірка,
  що код працює. Прибрати й це означало б повернутися туди, звідки почався
  весь проєкт: тести, які нічого не доводять («тести мають бути
  повноцінними, а не просто для тестів» — вихідна вимога).
- **Заборона прямого пушу в `main` і force-push** (`.githooks/pre-push`) —
  базова гігієна git, не привід чекати дозволу: мерж уже автономний і
  миттєвий (нижче), тож PR — це не черга, а спосіб дати шести гейтам
  відпрацювати ДО того, як зміна потрапить у `main`.

## Мержиш власний PR сам — за двох умов разом

Людини в ланцюгу мержу немає: це цільовий стан процесу.

1. **Усі шість гейтів зелені** — `build`, `test`, `honesty-guard`, `server`,
   `client`, `a11y`. Не п'ять із шести і не «a11y ще йде».
2. Або є явне схвалення (рев'ю, якщо хтось його встиг лишити), або пройшло
   достатньо часу без заперечень — не чекай дозволу, якщо гейти зелені.

Форма: `gh pr merge <N> --squash --delete-branch`.

### ✎ 2026-09-17: мерж — пачкою раз на день

**Пряме рішення людини.** Умови мержу не змінюються — змінюється **момент**.
Не мержити PR одразу, щойно гейти позеленіли: довести роботу до зеленого,
лишити PR відкритим і перейти до наступної задачі. Мерж — раз на день,
однією пачкою по всіх готових PR.

**Причина:** повний прогін займає 10–12 хвилин (найдовший — `client`,
~11 хв). Очікування кожного PR окремо з'їдає непропорційно багато часу;
цикл «перевір → почекай → перевір знову» на кожен PR заборонений.

⛔ Пачка **не є** приводом мержити по червоному.

⚠ Гейтів **сім**, а не шість: `a11y` розділено на `a11y (dark)` і
`a11y (light)`.

⛔ Ніколи: `--admin`; мерж по червоному або по «ще йде»; `--no-verify`;
`git push --force`.

⚠ Якщо після мержу з'ясувалось, що щось не так — виправляєш **новим PR
уперед**, не ревертом чужої роботи. Виняток: змержене **не збирається** в
`main` — тоді це відновлення роботоздатності, не спір про якість.

⛔ Рецензент необов'язковий. Отже єдине, що стоїть між помилкою і `main`, —
гейти й твоя власна чесність у коміті/описі PR. **Зелений тест не є
доказом; доказ — тест, який падає, коли зламати те, що він перевіряє.**

## Судження замінює ескалацію — з одним винятком

Раніше неоднозначність зупиняла роботу («ASK, чекай PK1»). Тепер: приймай
рішення сам, документуй його одним рядком у коміті чи описі PR (що
вирішив і чому), і рухайся далі.

**Виняток — факти, які тобі просто невідомі**, а не питання судження:
фірмові кольори й логотип замовника, конкретні визначення колонок у
державних формах звітності, юридичні/договірні рішення. Такого не
вигадуй — назви прогалину прямо (в описі PR чи коміті) й запропонуй
нейтральний дефолт, який можна замінити пізніше без переробки. Різниця
проста: судження про ЯК зробити — твоє; факти про ЩО є правдою в світі
замовника — не твої, і вигадана відповідь коштує дорожче за назване
питання.

## Формат коміта

`[TYPE] опис`; TYPE: `CODE`, `CHORE`, `FIX`, `DOCS`, `TEST`.
Префікс `[PK1]`/`[PK2]` необов'язковий — лишай, якщо корисно для контексту,
не вимагається жодним хуком.

## Спільне

- `git add` тільки явними шляхами. Ніколи `git add -A` / `git add .`.
- `git push --force` заборонено.
- Git-хук відхилив push (main, force, non-fast-forward) — не обходь через
  `--no-verify`. Полагодь так, як хук і підказує (нова гілка, `git merge`).

## Особливості середовища

⚠ У Windows буває **два різні `git` одночасно** — один у `PATH` оболонки,
інший у складі Git for Windows, — і `git --version` відповідає різне з різних
оболонок. Тут це вже дало хибний замір. Дивна поведінка git → спершу
`(Get-Command git).Source`, а не логіка.

⚠ `gh` може не бути в `PATH` — тоді `& "C:\Program Files\GitHub CLI\gh.exe"`.

Рекомендовані форми — `git checkout -b <гілка>` і `git reset HEAD -- <файл>`:
працюють у будь-якій версії git.

### ✎ 2026-09-17: передумови першого запуску

Перевірено на живій машині. Кожен пункт **блокує** запуск, і жодного з них
не було в `04-environment.md` — на їх пошук пішли години.

1. **`nuget.config` у корені обов'язковий.** Без нього відновлення
   успадковує глобальний конфіг машини. За центрального керування пакетами
   (`Directory.Packages.props`) два джерела дають `NU1507`, а
   `TreatWarningsAsErrors` робить із нього помилку — і `dotnet ef` падає,
   тобто `setup-dev-db.ps1` і `smoke.ps1` не працюють у принципі.
   ⚠ Репозиторного конфігу **не досить**: `dotnet ef` оцінює проєкт у
   власному контексті поза деревом репозиторію і бачить лише глобальні
   джерела. Зайві джерела треба вимкнути: `dotnet nuget disable source <ім'я>`.
2. **`dotnet-ef` — окремий інструмент:**
   `dotnet tool install --global dotnet-ef --version "10.*" --ignore-failed-sources`.
3. **Тести без Docker.** 15 тестів **поза** категорією `Integration`
   мовчки потребують СУБД, тобто `--filter "Category!=Integration"` із
   `README.md` не рятує. Штатний обхід — локальний SQL Server:
   `$env:ECR_TEST_SQL = "Server=localhost;Integrated Security=true;TrustServerCertificate=True"`.
   Кожен git-worktree отримує власні бази (`SqlServerFixture.WorkspaceTag()`
   хешує каталог збірки), тож паралельні агенти не стикаються.
   Бази `EcrTest_*` лишаються після прогону навмисно.
4. **`npm test` вимагає Node ≥ 22.12** (`vitest@5`), хоча `engines` у
   `package.json` не оголошено — саме тому розбіжність версій непомітна.
5. `dotnet test` приймає **один** проєкт за виклик.

⚠ `tools/smoke.ps1` і `tools/e2e-stand.ps1` — єдині перевірки продукту «як
у користувача», і обидві позначені `ci-exempt`. Станом на 2026-09-17 обидві
**червоні**, і цього ніхто не помітив саме тому, що вони поза CI. Перед
тим, як довіряти зеленому CI, прожени їх руками.
