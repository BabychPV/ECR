  миттєвий (нижче), тож PR — це не черга, а спосіб дати шести гейтам
  відпрацювати ДО того, як зміна потрапить у `main`.

## Мержиш власний PR сам — за двох умов разом

Людини в ланцюгу мержу немає: це цільовий стан процесу.

1. **Усі шість гейтів зелені** — `build`, `test`, `honesty-guard`, `server`,
   `client`, `a11y`. Не п'ять із шести і не «a11y ще йде».
2. Або є явне схвалення (рев'ю, якщо хтось його встиг лишити), або пройшло
   достатньо часу без заперечень — не чекай дозволу, якщо гейти зелені.

Форма: `gh pr merge <N> --squash --delete-branch`.

### ✎ 2026-09-17: мерж — пачкою раз на день

**Пряме рішення людини.** Умови мержу не змінюються — змінюється **момент**.
Не мержити PR одразу, щойно гейти позеленіли: довести роботу до зеленого,
лишити PR відкритим і перейти до наступної задачі. Мерж — раз на день,
однією пачкою по всіх готових PR.

**Причина:** повний прогін займає 10–12 хвилин (найдовший — `client`,
~11 хв). Очікування кожного PR окремо з'їдає непропорційно багато часу;
цикл «перевір → почекай → перевір знову» на кожен PR заборонений.

⛔ Пачка **не є** приводом мержити по червоному.

⚠ 2026-09-18 пачок було дві за день, і це свідоме відхилення від букви
правила — називаю його, а не замовчую. Причина: наступна робота лежала
рівно у файлах, які змінювали відкриті PR (`src/test/setup.ts`,
`09-seed.sql`), тож чекати до завтра означало або конфлікт, або простій.
Мета правила — не рахувати мержі за календарем, а прибрати цикл
«перевір → почекай → перевір знову» на КОЖЕН PR; цієї мети друга пачка не
порушує. Усі гейти були зелені.

⚠ Гейтів **сім**, а не шість: `a11y` розділено на `a11y (dark)` і
`a11y (light)`.

### ✎ 2026-09-20: один PR на обидві сесії, мерж раз на тиждень

**Пряме рішення людини**, дослівно: «перестань робити багато пулреквестів,
зроби тільки один і докидуйте разом з іншою сесією туди зміни; треба швидше
розробляти; закривати пул реквест один раз на тиждень. Тобто створили один і
тільки туди комітимо».

Це **скасовує** каденцію «пачка раз на день» і правило «одна підзадача = один
PR» із розділу 4 нижче. Що діє натомість:

- Спільна гілка **`dev/integration`**, один PR у `main` (перший — #453).
  Обидві сесії комітять туди; окремих PR на підзадачу не відкриваємо.
- Порядок пушу: власна гілка від `origin/dev/integration` в **окремому**
  worktree → `git fetch` → `git rebase origin/dev/integration` (ребейз лише
  НЕзапушених комітів; `--force` лишається забороненим) →
  `git push origin HEAD:dev/integration`.
- Сім гейтів ганяються на кожен пуш. ⛔ Червоний гейт лагодиться наступним
  комітом **у ту саму гілку**, не окремим PR.
- Мерж у `main` — раз на тиждень і **лише по семи зелених**.
- Спільні файли (`09-seed.sql`, `openapi.snapshot.json`, `schema.d.ts`,
  `shared/ui/**`) — попереджати іншу сесію повідомленням; перегенерацію
  контракту робити останнім кроком після rebase.

⚠ Ризик називаю прямо: тиждень роботи живе поза `main`, і зелений гейт тут
означає «зелена гілка», а не «зелений `main`». Пом'якшення — щоденний rebase
і `git merge origin/main`, щойно в `main` щось доїжджає.

⛔ Ніколи: `--admin`; мерж по червоному або по «ще йде»; `--no-verify`;
`git push --force`.

⚠ Якщо після мержу з'ясувалось, що щось не так — виправляєш **новим PR
уперед**, не ревертом чужої роботи. Виняток: змержене **не збирається** в
`main` — тоді це відновлення роботоздатності, не спір про якість.

⛔ Рецензент необов'язковий. Отже єдине, що стоїть між помилкою і `main`, —
гейти й твоя власна чесність у коміті/описі PR. **Зелений тест не є
доказом; доказ — тест, який падає, коли зламати те, що він перевіряє.**

## ✎ 2026-09-18: Правила розробки — постійні, виконувати завжди

**Пряме рішення людини**, задане дослівно. Нижче — воно саме, з одним
зазначеним зняттям конфлікту.

### 0. Пріоритети при конфлікті правил

Коректність і тести → відсутність merge-конфліктів → швидкість. Ніколи
навпаки.

### 1. Старт будь-якої задачі — план до коду

Перш ніж змінити хоч один файл:

- `git fetch && git status` — переконатися, що працюємо від свіжого `main` і
  робоче дерево чисте;
- скласти план таблицею:

| # | Підзадача | Файли для запису | Залежить від | DoD (як перевіримо) | Режим |
|---|---|---|---|---|---|
| 0 | foundation: контракти/типи/міграції | … | — | компілюється, тести зелені | послідовно |
| 1 | … | … | 0 | … | паралельно |

- перевірити план на **перетин колонки «Файли для запису»** між паралельними
  рядками. Є перетин — об'єднати або серіалізувати. Це **єдина** умова, за
  якої дозволено паралелити;
- кожна підзадача — один PR ≤ 300–400 рядків diff, доведений до PR того ж
  дня. Не вміщається — ділити далі;
  - ✎ **2026-09-19, пряме рішення людини:** для PR виду «ендпоінт +
    споживач у клієнті + тести» межа — **до ~800 рядків** без згенерованих
    файлів (`openapi.snapshot.json`, `schema.d.ts`, файли міграції), **якщо
    тести становлять ≥ 40 %** diff. Причина: сім із восьми таких PR за день
    вийшли на 600–950 рядків, а поділити їх не дає сторож
    `EndpointCoverageTests` (ендпоінт без споживача червоний). Правило, яке
    порушують у кожному PR із поясненням, перестає бути правилом. Для чистого
    коду, рефакторингу й клієнтських екранів межа лишається 300–400. Частку
    тестів і розмір називати в описі PR;
- задача < ~50 рядків і один файл — **не декомпозувати**, робити напряму.

### 2. Порядок виконання (завжди однаковий)

Foundation (послідовно) → реалізації (паралельно, ≤ 3–4 гілки) → інтеграція
(послідовно).

- **Foundation** — єдине місце, де змінюються спільні ресурси: інтерфейси,
  глобальні типи, схема БД і міграції, конфіги, lock-файли, CI, спільні
  фікстури, shared-модулі. Мержиться ДО старту паралельних гілок.
- Під час паралельної фази спільні ресурси **read-only**. Виняток:
  append-only додавання константи/типу в кінець файлу, узгоджене в плані.
- Нова функціональність — у **нових** файлах/модулях, не в наявних великих.
- Міграції БД — по одній, послідовно, кожна окремим PR.

### 3. Контракт сабагента

Сабагентів використовувати для всіх незалежних підзадач із плану. Кожен
запуск містить:

- **дозволені файли** — явний список; усе інше заборонено, включно з тестами
  інших модулів;
- **заборонено**: ставити пакети, змінювати lock-файли/конфіги/міграції,
  створювати спільні тимчасові файли, займати порти, використовувати спільну
  тестову БД або env;
- **обов'язковий вихід**: список змінених файлів, команда та результат
  тестів, припущення, відкриті питання;
- **стоп-умова**: потрібен файл поза списком або спільний ресурс —
  зупинитися і повернути питання, не обходити обмеження.

**Інтегратор** (основна сесія) перед мержем перевіряє, що змінені файли
сабагентів не перетинаються, і запускає повний прогін тестів і lint. «Done»
від сабагента без прогону тестів **не приймається**.

### 4. Git та Pull Requests

- **Один PR на день — мінімум.** Наприкінці дня має бути щонайменше один
  відкритий або змержений PR. Немає — задачу нарізано неправильно.
- Одна підзадача = одна гілка = один PR. Гілка від свіжого `main`.
- Гілка живе ≤ 1 дня; > 2 днів — стоп і переділити задачу.
- Коміти атомарні.
- Лінійна історія (squash/rebase merge), гілка видаляється після мержу.
- Опис PR: What / Why / How tested / Risks / Depends on #N. CI зелений до
  запиту рев'ю.
- Великі зміни — stacked PRs, мержаться по черзі.
- **Рефакторинг, форматування, перейменування — окремий PR**, ніколи разом
  із функціональними змінами.

⚠ **Зняття конфлікту (судження, не відхилення).** Правило каже «перед PR
`git rebase main`», а розділ «Спільне» нижче забороняє `git push --force`.
Ребейз УЖЕ ЗАПУШЕНОЇ гілки без force неможливий. Тому: ребейз **до першого
пушу**; після пушу — `git merge origin/main`. Пріоритет 0 дотримано:
коректність і відсутність конфліктів вище за форму історії, а squash-мерж
однаково дає лінійну історію.

⚠ Про формат коміта: розділ «Формат коміта» нижче задає `[TYPE] опис`
українською, і саме його читають хуки й сторожі. Conventional commits
(`feat:`, `fix:`) з правила 4 у цьому репозиторії НЕ застосовуються — інакше
зламається те, що вже перевіряє формат.

### 5. Якість і межі

- Тести пишуться в тій самій підзадачі, що й код. Нова логіка без тестів не
  мержиться.
- Перед PR: lint, типізація, тести, ручна перевірка критичного шляху.
- **No scope creep**: усе поза DoD поточної підзадачі — у «Next steps».
- Бракує інформації — не блокуватися: зробити розумне припущення, явно
  зафіксувати його в PR і в звіті, продовжити.

### 6. Обов'язковий звіт після кожної задачі та підзадачі

```
Done      — що змінено, гілки/PR (посилання), змінені файли
Verified  — команди та результати тестів/lint; що перевірено вручну
Next steps — пріоритезовано:
  [parallel] можна запускати одночасно
  [blocks]   блокує інші кроки
  [debt]     техборг
  [question] відкриті питання / ризики / зроблені припущення
```

### 7. Стиль

Писати як розробник: коротко, конкретно, з іменами файлів і командами, без
води.

## ✎ 2026-09-18: працюй до стабільного рішення, а не до кінця задачі

**Пряме рішення людини.** Критерій зупинки — не «я зробив те, що просили», а
**стабільно працюючий продукт, який відповідає вимогам**. Доки цього немає,
робота триває: вибирай наступну задачу сам, сам стеж за саб-тасками (чи не
зависли, чи збалансоване навантаження), сам вирішуй, що робити далі. Не
зупиняйся, щоб доповісти й чекати.

**Але питай, якщо питання СПРАВДІ гальмує.** Це не скасування автономності й
не привід ескалювати неоднозначність — судження про ЯК лишається твоїм (див.
наступний розділ). Питай тоді, коли без відповіді робота або стає
неможливою, або піде намарно:

- **факти про світ замовника** — те, чого ти просто не можеш знати (фірмові
  кольори, визначення колонок у державних формах, автентифікація PI Web API,
  адресати сповіщень, юридичні рішення);
- **рішення, що змінює поведінку продукту** і має кілька чесних варіантів із
  різною ціною (так було з питанням «чи нормально відкривати всі 91 таблицю
  одразу» — відповіддю стало ліниве завантаження за прокруткою);
- **дані, без яких критерій приймання недосяжний** (побайтна звірка міграції
  без вивантаження з AF).

⛔ Що НЕ є приводом спинитися й запитати: вибір бібліотеки, форма API,
де поставити перевірку, як назвати ключ, чи варто розбити PR. Це судження —
прийми рішення, запиши одним рядком у коміті чи описі PR і рухайся далі.

⚠ Питання став **у правильний момент**: спершу зроби все, що від відповіді
не залежить, і лише тоді питай — разом із тим, що вже готове. Блокувальне
питання (зупинитися, нічого не віддавши) виправдане лише тоді, коли будь-яке
припущення зробило б роботу небезпечною або марною.

## Судження замінює ескалацію — з одним винятком

Раніше неоднозначність зупиняла роботу («ASK, чекай PK1»). Тепер: приймай
рішення сам, документуй його одним рядком у коміті чи описі PR (що
вирішив і чому), і рухайся далі.

**Виняток — факти, які тобі просто невідомі**, а не питання судження:
фірмові кольори й логотип замовника, конкретні визначення колонок у
державних формах звітності, юридичні/договірні рішення. Такого не
вигадуй — назви прогалину прямо (в описі PR чи коміті) й запропонуй
нейтральний дефолт, який можна замінити пізніше без переробки. Різниця
проста: судження про ЯК зробити — твоє; факти про ЩО є правдою в світі
замовника — не твої, і вигадана відповідь коштує дорожче за назване
питання.

## Формат коміта

`[TYPE] опис`; TYPE: `CODE`, `CHORE`, `FIX`, `DOCS`, `TEST`.
Префікс `[PK1]`/`[PK2]` необов'язковий — лишай, якщо корисно для контексту,
не вимагається жодним хуком.

## Спільне

- `git add` тільки явними шляхами. Ніколи `git add -A` / `git add .`.
- `git push --force` заборонено.
- Git-хук відхилив push (main, force, non-fast-forward) — не обходь через
  `--no-verify`. Полагодь так, як хук і підказує (нова гілка, `git merge`).

## Особливості середовища

⚠ У Windows буває **два різні `git` одночасно** — один у `PATH` оболонки,

оболонок. Тут це вже дало хибний замір. Дивна поведінка git → спершу
